## 3. 공연자(팀 리더) — 공연 생성부터 판매 시작까지

공연 생성·수정 5단계(합동 공연): **공연 정보·티켓 옵션 → 참여팀 → 정산 규칙 → 규칙 동의 → 보증금**(단독 공연은 참여팀 단계 생략, 4단계).

| 단계 | 화면 | 사용자 행동 | 기대 결과 | 뒤에서 일어나는 일 |
|---|---|---|---|---|
| 3-1 | **P-03 공연 생성·수정**(1단계) | 제목·설명·**공동 공연 체크**·일시·장소·예매 마감·티켓 옵션 입력 후 저장 | 공연 생성(상태 `DRAFT`), 합동 공연이면 P-04로 안내 | `POST /api/v1/performances` — 검표 페이지 링크(`/scan/:token`)도 이 시점에 함께 발급 |
| 3-2 | **P-04 참여팀 관리** | 팀 이름 검색 콤보박스로 참여팀 초대(팀당) | 초대 발송, 상태 배지 "초대 보냄(대기 중)" | `GET /api/v1/teams/search` → `POST /api/v1/performances/{id}/participants` |
| 3-3 | **P-04 참여팀 관리**(참여팀 리더 시점) | 초대받은 팀 리더가 로그인해 참여 수락 | 상태 배지 "수락함", 지갑 등록 배지 확인 | `POST /api/v1/performances/{id}/participants/{teamId}/accept` — 참여팀 리더의 지갑이 `LINKED`가 아니면 이후 규칙 설정·판매 시작이 막힌다 |
| 3-4 | **P-05 정산 규칙 설정** | 생성자가 참여팀 확정 후 진입, 고정/관객 선택 비율(1단계) + 팀별 고정 분배 비율(2단계) 드래그 막대로 설정 후 저장 | 규칙 저장 성공 모달 → "규칙 동의 받으러 가기"(P-06)로 안내 | `PUT /api/v1/performances/{id}/rules` — 공연 상태가 `PENDING_AGREEMENT`로 전이. 보증금 미납이어도 저장은 막히지 않는다 |
| 3-5 | **P-06 규칙 동의·판매 시작** | **각 참여팀 리더가 "우리 팀 동의하기"** — 지갑 서명 | 팀별 동의 상태가 `PENDING` → `AGREED`로 전이 | ① 서명 파라미터 요청(`POST .../rules/agreements/prepare`) → ② 지갑 서명 → ③ 발신자 서명 RLP 보고(`POST .../rules/agreements/signed-tx`) → ④ chain job 확정 대기(폴링) |
| 3-6 | **P-03 공연 생성·수정**(5단계 보증금) | 생성자가 보증금 서명(승인 → 납부, 수수료 대납) | 보증금 `PAID` | 보증금 prepare는 합동 공연이면 참여팀 ≥ 2를 요구한다. `createShow` 온체인 등록에는 규칙 해시(`rulesHash`)가 필요해 규칙 저장(3-4)이 선행돼야 한다. **시연 순서 주의: 3-3에서 초대한 참여팀이 전부 "수락함"(지갑 등록 포함)인지 확인한 뒤에 보증금으로 넘어간다** — 1팀만 수락했거나 수락이 덜 된 상태면 400 으로 막힌다 |
| 3-7 | **P-06 규칙 동의·판매 시작** | 전원 동의(`AGREED`) + 보증금 `PAID` 확인 후 생성자가 "판매 시작" 클릭 | 확인 모달("규칙과 참여팀이 잠깁니다") → 판매 시작 | `POST /api/v1/performances/{id}/sale/start` — **서명 없음**(운영자 실행). 온체인 `startSale`이 `DepositRequired`·`NotAllAgreed` 두 조건을 검사해, 조건 미충족이면 컨트랙트 단에서도 막힌다 |

| 4-5 | **A-06 예매 완료** | "내 티켓으로 이동" | 발권 완료 안내, 잔여 잔액 확인 | 결제 확정과 동시에 티켓 발급(ISSUED) |

## 6. 정산

| 단계 | 화면 | 사용자 행동 | 기대 결과 | 뒤에서 일어나는 일 |
|---|---|---|---|---|
| 6-1 | **P-08 정산 대시보드** | 공연 종료 후 운영자가 "집계 확정" | 정산 상태 `NONE` → `AGGREGATED` | `POST .../settlement/aggregate` — 서명 없음(운영자 실행), 202 |
| 6-2 | **P-08 정산 대시보드** | 운영자가 "잠금" | 팀별 분배액 확정, **48시간 이의제기 기간 시작** — 잠금 직후 조회 상태는 `DISPUTE_OPEN` | `POST .../settlement/lock`. 상태 순서 `NONE → AGGREGATED → LOCKED → DISPUTE_OPEN → RELEASED` / `HALTED`(API v7 §11) |
| 6-3 | **P-08 정산 대시보드**(선택, 조기 동의 경로) | 참여팀 전원(주최팀 포함) 리더가 "정산 동의" 클릭 | 전원 동의 시 **48시간 이의제기 기간을 건너뛰고 release가 열린다** | `POST .../settlement/approvals`(201, 서명 없음, 비가역 — 확인 모달 필수) |
| 6-4 | **P-08 정산 대시보드**(전원 조기 동의 안 한 경우) | 48시간 이의제기 기간 대기(이 기간에만 M-02에서 이의제기 접수·처리 가능) | 이의 없이 기간 만료, 또는 이의 승인 시 `HALTED`(→ P-10 취소 경로로 전액 환불) | 기간이 만료되면(열린 이의 0건) release 가 열린다 — 상태는 release 확정 뒤 `RELEASED`(6-5) |
| 6-5 | **P-08 정산 대시보드** | 운영자가 "release" 실행(또는 6-3 전원 동의로 자동) | 정산 상태 → `RELEASED`, "정산금 지급 완료" 모달, 각 팀 리더 지갑에 분배액 입금, **보증금 반환** | `POST .../settlement/release` → 온체인 `release` → `Released` 이벤트, 이어서 `DEPOSIT_RETURN` chain job |

## 시연 계정·데이터 준비물

- **관리자 코인 지급**: `/admin/coin`(M-03) — 잔액 부족 시연·리허설 중 유일한 지급 경로. 가입 기본 지급(100,000 YoYo, 자동 1회) 외에는 관리자가 여기서만 발행한다.
- **리허설 시드**: `exec/rehearsal/seed-genres.sql`(추천용 장르 시드), `exec/rehearsal/seed-times.sql`(시연 시간대·권한 시드).
- **리허설 대본·판별 절차**: `exec/rehearsal/RUNBOOK.md`(호출 도구 `exec/rehearsal/rehearse.sh`).
