## 2. 아키텍처 한 장

```
                              (443, TLS: Let's Encrypt)
사용자 ── 호스트 Nginx(j15b204.p.ssafy.io) ──┬─ /api/*         → 127.0.0.1:8080 (router 컨테이너)
                                             │                     │
                                             │                     ├─ 활성 색: backend-blue  (healthy면 트래픽)
                                             │                     └─ 대기 색: backend-green (healthy 확인 후 전환)
                                             │
                                             ├─ /jenkins/*     → 127.0.0.1:9090 (Jenkins 컨트롤러)
                                             ├─ /grafana/*     → 127.0.0.1:3001 (Grafana)
                                             ├─ /docs/*        → ~/app/docs (basic auth, API 문서 정적 파일)
                                             ├─ /uploads/*     → ~/app/uploads (포스터 등, backend와 바인드 공유)
                                             ├─ /hooks/gitlab  → b204-notify:9092 (Mattermost 알림)
                                             └─ 그 외 (/, 정적) → 127.0.0.1:3000 (frontend 컨테이너, nginx:alpine)

backend-blue/green ── MySQL(mysql:3306, 컨테이너 내부망) 
                  ├── Redis(redis:6379, 컨테이너 내부망, chain:owner/chain:active·세션·멱등키)
                  └── Kaia Kairos RPC(https://public-en-kairos.node.kaia.io, chainId 1001)
```

- 호스트 Nginx는 `127.0.0.1:8080`(router 컨테이너) 하나만 보므로, 백엔드 블루/그린 전환은 호스트 Nginx 설정을 건드리지 않는다.
- 지표는 Prometheus가 `app_default` 네트워크에서 컨테이너 이름으로 직접 스크랩한다(`exec/monitoring/prometheus.yml`) — 호스트 Nginx를 거치지 않는다.

## 6. 서버 배포 절차

### 6.1 최초 1회

1. 서버 준비(EC2, Docker/Compose 설치)
2. Jenkins 컨트롤러 기동 — `exec/jenkins/`(이미지 빌드: `docker-buildx-plugin` 포함)
3. Jenkins Credentials 등록(§3.5 표)
4. 호스트 Nginx 사이트 반영·인증서 — `exec/nginx/j15b204.p.ssafy.io.conf`를 `~/app/nginx/`로 복사한 뒤, 서버 상태에 따라 하나를 따른다. 이 conf 는 443 블록이 인증서 경로를 가리키므로 **인증서가 없으면 `nginx -t` 가 실패한다** — 새 서버는 반드시 발급을 심링크보다 먼저 한다.
   - **4-a. 인증서가 없는 새 서버** — nginx 설치 직후의 기본 사이트(`default`)가 켜진 상태에서 순서대로:
     1. `sudo apt-get install -y certbot python3-certbot-nginx` → `sudo certbot certonly --nginx -d j15b204.p.ssafy.io` — 운영 서버와 같은 nginx 플러그인 방식이다. 이 플러그인이 conf 443 블록이 `include` 하는 `/etc/letsencrypt/options-ssl-nginx.conf`·`ssl-dhparams.pem` 을 함께 만들고, 갱신 때마다 인증 뒤 nginx 를 다시 읽혀 새 인증서가 바로 적용된다(`--webroot`·`--standalone` 은 두 파일이 생기지 않고 갱신 뒤 reload 도 없어 쓰지 않는다)
     2. `sudo ln -sf /home/ubuntu/app/nginx/j15b204.p.ssafy.io.conf /etc/nginx/sites-enabled/` · `sudo rm -f /etc/nginx/sites-enabled/default`(conf 파일 머리 주석과 같다)
     3. `sudo nginx -t` → `sudo systemctl reload nginx`
   - **4-b. 인증서가 이미 있는 서버(현재 운영 서버)** — 심링크 두 줄(4-a의 2) → `sudo nginx -t` → `sudo systemctl reload nginx`. 운영 서버의 갱신 설정은 `authenticator = nginx`·`installer = nginx`(`/etc/letsencrypt/renewal/j15b204.p.ssafy.io.conf`, 2026-09-28 확인)이고 두 include 파일도 있어 다시 발급하지 않는다
5. 업로드 디렉토리 준비 — `sudo install -d -o 10001 -m 755 /home/ubuntu/app/uploads`(uid 10001 = backend 컨테이너 실행 유저)
6. 모니터링 스택 기동 — `exec/monitoring/`(`exec/monitoring/README.md`)
7. 최초 이관(단일 컨테이너 → 블루/그린) — 세부는 `exec/README.md` "최초 이관(1회)" 절

세부 명령은 `exec/README.md`(인프라 파일 위치·GitLab→Mattermost 알림·블루/그린 절)를 따른다.

### 6.2 이후(자동)

`develop` 머지 → GitLab 웹훅 → Jenkins(Multibranch Pipeline `b204`) → 테스트 → 이미지 빌드(태그 = 커밋 SHA 8자리) → 서버 `~/app/.env` 생성(Credentials `B204_ENV` + 자동 채움 4줄) → `exec/deploy/blue-green.sh` 실행. `master`는 같은 절차에 배포 승인(input) 단계가 추가된다.

**배포 방식은 블루/그린이다**:

1. 쉬는 색을 새 이미지 태그로 띄운다(`docker compose --profile <색> up -d`)
2. `/actuator/health`가 healthy가 될 때까지 대기(최대 `HEALTH_TIMEOUT`, 기본 180초) — healthy가 아니면 그 색을 내리고 배포를 중단한다(이전 색이 계속 받는다)
3. router의 `active_color.conf` 한 줄을 바꾸고 `nginx -s reload`로 전환
4. `/router/color`(내부 전용)로 실제 전환 확인(단발 판정 금지, 5회 재확인)
5. 체인 작업 소유권(`chain:owner`/`chain:active`, Redis)을 새 색으로 인계 — `SET chain:owner handover` → `HANDOVER_DRAIN_SECONDS`(기본 30초) 대기 → `SET chain:owner <새 색> EX 60`

세부(healthcheck 판정 근거·소유권 인계 경쟁 조건·주의사항)는 `exec/README.md` "블루/그린 배포(백엔드)" 절과 `exec/deploy/blue-green.sh` 머리말 주석을 따른다.

## 7. 배포 시 특이사항

- **컨트랙트 배포**는 자동 배포에 포함되지 않는다 — Jenkins Build with Parameters의 `DEPLOY_CONTRACT` 파라미터를 켠 수동 빌드로만 실행하고, `ADMIN_PRIVATE_KEY`(Secret text)를 그 스테이지에서만 읽는다.
- **MINTER 로테이션**은 `ROTATE_MINTER` 파라미터(+ `NEW_MINTER_ADDRESS`)로 실행한다. `DEPLOY_CONTRACT`와 동시에 켤 수 없다. 절차·주의사항(워커 정지·develop 브랜치 일시 중지 등)은 `exec/README.md` "MINTER 로테이션" 절.
- **마이그레이션은 additive만** — 두 색이 같은 스키마 위에서 겹쳐 도는 구간이 있으므로 컬럼 삭제·이름 변경·ENUM 값 제거·NOT NULL 추가는 금지. 지워야 하면 "안 쓰게 배포 → 다음 배포에서 삭제" 두 번에 나눈다.
- **Redis는 AOF 영속**이다(`redis_data` 볼륨). 무영속이면 재기동 시 `chain:owner`가 사라져 쉬는 옛 색이 소유권을 먼저 가져갈 수 있다. 블루/그린을 처음 적용하는 배포에서는 redis 컨테이너가 한 번 재생성돼 로그인 세션·멱등키가 전부 사라지므로, **예매 트래픽이 없는 시각에** 한다.
- **롤백**은 `~/app/deploy/rollback.sh` — 이전 색이 이미 떠 있어 트래픽 전환 1초 + 체인 소유권 인계 30초(합 30초+). 이미지 태그를 되감는 롤백(`IMAGE_TAG=<이전 sha> docker compose up -d`)은 컨테이너를 다시 만들어 1~2분 걸린다.
- **백업 대상**은 DB(`mysql_data` 볼륨)와 `~/app/uploads` 두 곳뿐이다. 컨테이너·이미지는 언제든 다시 만들지만 이 둘은 원본이 없다.
- **이미지 빌드 캐시**는 BuildKit(`DOCKER_BUILDKIT=1`)이 gradle 의존성(`/root/.gradle`)·pnpm 캐시(`/root/.cache/node/corepack`, `/root/.local/share/pnpm/store`)를 재사용한다. Jenkins 컨테이너에 `docker-buildx-plugin`이 있어야 한다(`exec/jenkins/Dockerfile`).

## 8. DB 접속 정보

- **로컬**(README §9.2, 비밀 아님 — 127.0.0.1에만 바인딩): MySQL `127.0.0.1:3307` DB `b204` 계정 `b204/b204`, root `root/root`. Redis `127.0.0.1:6379`.
- **운영**: 컨테이너 내부 네트워크 `mysql:3306`으로만 접속하고 호스트 포트를 열지 않는다. 계정은 Jenkins Credentials `B204_ENV`에만 있다.

## 9. DB 덤프

파일명 `exec/03_DB_덤프.sql` — MySQL 8.0.46, `mysqldump --single-transaction`, 테이블 25개, 2026-09-28 기준.

**이 커밋에는 덤프 파일 자체를 포함하지 않는다(팀 결정 대기).** 팀이 포함하기로 정하면 서버에서 다음으로 만든다.

```bash
# 비밀번호는 컨테이너 env 에서 읽는다(작은따옴표 — 호스트 셸이 펼치지 않는다)
docker exec b204-mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces --set-gtid-purged=OFF --default-character-set=utf8mb4 b204' > exec/03_DB_덤프.sql
```

복원:

```bash
# 비밀번호는 컨테이너 env 에서 읽는다 — 작은따옴표 안이라 호스트 셸이 펼치지 않는다
docker exec -i b204-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" b204' < exec/03_DB_덤프.sql
```

덤프는 `--databases` 없이 DB 이름 하나(`b204`)로 떴기 때문에 파일에 `CREATE DATABASE`·`USE` 문이 **없다**(확인함). 그래서 복원 명령이 지정한 `b204` 로 들어간다. `--databases`·`--all-databases` 로 다시 뜨면 파일 안의 `USE` 가 이 인자를 덮으니, 그때는 복원 명령에서 DB 이름을 빼거나 파일 상단을 확인한다.
