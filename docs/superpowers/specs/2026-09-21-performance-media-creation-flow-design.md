# 공연 미디어 생성 흐름·지갑 중복 안내 설계

- 작성일: 2026-09-21
- 대상: 공연 생성 D-22~D-27, 파일 업로드, 발급 티켓 표현, C-05 지갑 등록
- 기준 브랜치: `origin/develop` (`b45428f`)
- 관련 기존 범위: S15P21B204-99

## 1. 목적

피그마에 디자인됐지만 운영 코드에 없는 공연 포스터 편집, 티켓 이미지 업로드·제작,
등록 전 확인 화면을 실제 저장 가능한 기능으로 구현한다. 화면만 동작하는 것처럼 보이는
로컬 미리보기나 하드코딩 데이터는 만들지 않는다.

동시에 지갑 등록 화면에 이미 연결된 지갑이 있으면 새 지갑 생성 요청을 보내기 전에 이를
알리고 기존 지갑으로 계속하도록 한다. 오류는 모호한 공통 문구로 뭉개지 않고 원인과 다음
행동을 코드별로 안내한다.

## 3. 사용자 흐름

```text
D-22 기본 정보
  -> D-23 포스터 편집·업로드
  -> D-24 티켓 직접 제작 또는 D-24A 이미지 업로드
  -> D-25 티켓 옵션
  -> D-27 등록 전 확인
  -> 공연 생성 + 티켓 옵션 저장
  -> P-05 정산 규칙
```

공연은 D-27의 최종 제출 시 한 번만 생성한다. 중간 단계의 텍스트 값과 업로드 결과 ID·URL은
프론트 draft 상태에 유지한다. 이미지 파일은 선택 직후 편집하고 서버에 먼저 업로드한다.
업로드 직후 파일은 `TEMP` 상태이며, 공연에 연결되면 `ATTACHED`로 바뀐다. 24시간 동안
연결되지 않은 `TEMP` 파일은 배치가 메타데이터와 실제 파일을 함께 삭제한다.

새로고침하면 아직 생성하지 않은 텍스트 draft는 사라진다. 민감하지 않은 폼 전체를
`localStorage`에 장기 보관하지 않는다. 같은 화면 안의 API 실패·재시도에서는 모든 입력과
편집 상태를 유지한다.

## 4. 파일 업로드 계약

### 4.1 엔드포인트

```http
POST /api/v1/files
Authorization: Bearer <access token>
Content-Type: multipart/form-data

file=<binary>
purpose=PERFORMANCE_POSTER | TICKET_ARTWORK
```

공연 생성 권한이 있는 팀 리더만 호출할 수 있다. `purpose`에 따라 권장 비율과 최소 해상도를
검사하지만, 브라우저 편집 결과의 1~2px 반올림 오차는 허용한다.

성공 응답은 201이다.

```json
{
  "code": "SUCCESS",
  "data": {
    "uploadId": 1234,
    "url": "https://j15b204.p.ssafy.io/uploads/p/202609/uuid.jpg",
    "width": 1800,
    "height": 720,
    "bytes": 184320,
    "contentType": "image/jpeg"
  },
  "msg": "이미지를 업로드했습니다."
}
```

### 4.2 검증과 저장

- 서버 수신 허용 형식: JPEG, PNG
- 최대 전송 크기: 5MB
- 확장자가 아니라 파일 시그니처와 `ImageIO` 디코딩 결과로 판정
- 포스터 결과: 1080x1440, 3:4
- 티켓 결과: 1800x720, 5:2
- 파일명: 서버가 만든 UUID, 원본 파일명은 경로에 사용하지 않음
- 경로: `${UPLOAD_DIR}/p/yyyyMM/<uuid>.<ext>`
- 공개 URL: `${PUBLIC_BASE_URL}/uploads/p/yyyyMM/<uuid>.<ext>`
- UUID URL이므로 Nginx는 `public, immutable` 장기 캐시 사용
- 회원당 분당 20회로 업로드 요청 제한

브라우저 파일 선택은 JPEG, PNG, WebP를 지원한다. WebP를 포함한 모든 입력은 Canvas에서
JPEG 품질 0.82 또는 투명 배경이 필요한 경우 PNG로 재인코딩한 뒤 서버에 보낸다. 서버는
클라이언트 변환을 신뢰하지 않고 파일 시그니처, 디코딩 결과, 크기와 비율을 다시 검증한다.

## 5. 데이터 모델과 API 변경

### 5.1 데이터베이스

`performance`에 다음 nullable 컬럼을 추가한다.

```sql
ticket_image_path VARCHAR(500) NULL COMMENT '완성 티켓 이미지 URL 또는 경로'
```

기존 `poster_image_path`는 그대로 사용한다. 새 컬럼은 nullable이므로 기존 공연과 롤백 시
현재 자동 티켓 디자인이 계속 동작한다.

업로드 소유권과 고아 파일 정리를 위해 `uploaded_file`을 추가한다.

```sql
uploaded_file (
  id BIGINT PRIMARY KEY,
  owner_member_id BIGINT NOT NULL,
  purpose VARCHAR(32) NOT NULL,
  stored_path VARCHAR(500) NOT NULL UNIQUE,
  content_type VARCHAR(64) NOT NULL,
  byte_size BIGINT NOT NULL,
  width INT NOT NULL,
  height INT NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  attached_at DATETIME(6) NULL
)
```

`status`는 `TEMP`, `ATTACHED` 두 값만 사용한다. 공연 생성·수정은 현재 회원이 소유하고,
요청 필드와 `purpose`가 일치하며, 만료되지 않은 파일만 연결할 수 있다.

### 5.2 공연 API

생성·수정 요청은 공개 URL 문자열이 아니라 업로드 ID를 사용한다.

```json
{
  "posterUploadId": 1233,
  "ticketArtworkUploadId": 1234
}
```

서버는 ID에서 관리 경로를 조회해 `poster_image_path`, `ticket_image_path`를 저장한다. 성공한
트랜잭션에서 파일을 `ATTACHED`로 전환한다. 같은 파일 ID를 다른 공연에 다시 연결하지 않는다.
응답의 `ticketImageUrl`은 공연 공개 목록에는 넣지 않는다. 공연 상세에는 예매 흐름
미리보기용으로, 티켓 목록·상세와 주문 상세에는 발급 티켓 렌더링용으로 전달한다.

판매 시작 이후 포스터·티켓 업로드 ID 수정은 기존
`PERFORMANCE_ALREADY_ON_SALE`로 차단한다.

### 5.3 발급 티켓 표현

- `ticketImageUrl`이 있으면 저장 이미지를 티켓 앞면 아트로 사용한다.
- 없거나 이미지 로드가 실패하면 현재의 포스터 기반 자동 디자인을 사용한다.
- QR, 회전 시간, 상태, 티켓 번호와 실제 예매 정보는 이미지에 굽지 않는다.
- 동적 QR과 실제 정보는 기존 DOM 레이어로 이미지 위에 표시한다.
- 장식 이미지가 실패해도 입장 QR과 티켓 정보는 가려지지 않는다.

## 6. 프론트 화면 구조

### 6.1 Draft 상태

공연 생성 페이지가 다음 상태를 소유한다.

```ts
interface PerformanceCreationDraft {
  info: PerformanceInfoValues
  posterUploadId?: number
  posterImageUrl?: string
  ticketArtworkUploadId?: number
  ticketImageUrl?: string
  ticketTypes: TicketTypeDraft[]
}
```

각 단계는 draft를 직접 저장하지 않고 `value`와 `onChange` 계약으로 부모와 통신한다.
업로드 컴포넌트는 바이너리를 상위로 전달하지 않고 성공 URL과 메타데이터만 전달한다.

### 6.2 D-23 포스터 편집

- 파일 선택 후 3:4 고정 프레임에 표시
- 드래그 이동, 확대·축소, 가운데 맞춤, 90도 회전
- 축소 시 빈 영역이 생기지 않도록 최소 배율 제한
- `prefers-reduced-motion`에서는 전환 애니메이션 제거
- 완료 시 1080x1440 Canvas로 렌더링 후 업로드
- 업로드 실패 시 편집 값과 원본 Blob을 메모리에 유지

### 6.3 D-24 티켓 직접 제작

- 배경 이미지 선택 또는 포스터 재사용
- 읽기 가능한 범위의 강조색 선택
- 메인·서브 타이틀 편집
- 날짜·장소는 공연 draft 값을 기본값으로 사용
- 1800x720 미리보기와 모바일 축소 미리보기 제공
- QR·티켓 번호·상태는 제작 화면에 영구 이미지로 포함하지 않음
- 완료 시 평면 이미지로 렌더링해 업로드

### 6.4 D-24A 티켓 이미지 업로드

- 5:2 비율 이미지 선택
- 비율이 다르면 D-24 편집기로 이동해 자르기
- 올바른 비율이면 바로 미리보기 후 업로드
- 직접 만들기와 이미지 업로드 탭 간 이동 시 마지막 결과 유지

### 6.5 D-27 등록 전 확인

- 공연명, 일시, 장소, 포스터, 티켓 아트, 티켓 옵션을 한 화면에 표시
- 각 섹션에 해당 단계로 돌아가는 수정 링크 제공
- 최종 버튼은 한 번만 제출 가능
- 공연 생성 성공 후 티켓 옵션 저장에 실패하면 생성된 `performanceId`를 보존해 재시도
- 전부 성공한 뒤에만 정산 규칙 화면으로 이동

## 7. 지갑 중복 등록 UX

`/onboarding/wallet` 진입 즉시 `GET /api/v1/wallets/me`를 호출한다.

- 조회 중: `등록된 지갑을 확인하고 있어요`
- 404 `WALLET_NOT_FOUND`: 지갑 선택 화면
- 200: `linked` 화면으로 즉시 전환, 생성 액션 미노출
- 그 밖의 실패: 원인별 안내와 조회 재시도

기존 지갑 화면 문구:

```text
이미 등록된 지갑이 있어요
새 지갑을 만들지 않고 기존 지갑을 사용합니다.
Web3Auth · 0x12ab...89cd
```

조회와 생성 사이의 경쟁 상황은 `WALLET_ALREADY_LINKED`를 받으면 지갑을 재조회해 같은
화면으로 복구한다. `WALLET_ADDRESS_IN_USE`는 다른 계정의 주소나 회원 정보를 노출하지 않고
다른 지갑 선택 또는 기존 계정 로그인을 안내한다.

## 8. 오류 계약과 화면 문구

화면 분기는 항상 `code`로 한다. 서버 `msg`는 사용자가 이해할 추가 정보로만 표시하며
분기 조건으로 사용하지 않는다. 오류 패널은 원인, 영향, 다음 행동을 포함한다.

| 코드 | 상태 | 사용자 안내와 행동 |
| --- | --- | --- |
| `FILE_EMPTY` | 400 | 파일 내용이 없음. 다른 이미지 선택 |
| `FILE_TOO_LARGE` | 413 | 5MB 초과. 더 작은 이미지 선택 |
| `FILE_TYPE_NOT_ALLOWED` | 400 | JPG, PNG만 업로드 가능. WebP는 화면에서 JPG로 변환 후 재시도 |
| `FILE_IMAGE_INVALID` | 400 | 손상 또는 위장 파일. 다른 이미지 선택 |
| `FILE_DIMENSION_TOO_SMALL` | 400 | 목적별 최소 해상도 안내 후 재선택 |
| `FILE_UPLOAD_NOT_FOUND` | 404 | 업로드가 없거나 만료됨. 이미지 다시 업로드 |
| `FILE_UPLOAD_NOT_OWNED` | 403 | 현재 계정의 업로드가 아님. 현재 계정에서 다시 업로드 |
| `FILE_UPLOAD_PURPOSE_MISMATCH` | 400 | 포스터·티켓 용도가 다름. 올바른 영역에서 다시 업로드 |
| `FILE_STORAGE_FAILED` | 500 | 폼 유지, 잠시 후 업로드만 재시도 |
| `WALLET_ALREADY_LINKED` | 409 | 기존 지갑 조회 후 linked 화면 |
| `WALLET_ADDRESS_IN_USE` | 409 | 다른 지갑 또는 기존 계정 로그인 안내 |
| `PERFORMANCE_ALREADY_ON_SALE` | 409 | 이미지 포함 읽기 전용 전환 |
| `PERFORMANCE_NOT_OWNER` | 403 | 생성 팀 리더만 수정 가능 안내 |

브라우저 오프라인, 업로드 시간 초과, 이미지 디코딩 실패, Canvas 생성 실패와 메모리 부족은
서버 코드가 없는 클라이언트 오류로 구분한다. 각각 `CLIENT_OFFLINE`,
`CLIENT_UPLOAD_TIMEOUT`, `CLIENT_IMAGE_DECODE_FAILED`, `CLIENT_CANVAS_FAILED`,
`CLIENT_OUT_OF_MEMORY`로 매핑하고 원인과 재선택·재시도 행동을 표시한다.

알 수 없는 서버 오류는 모호한 문장만 표시하지 않는다.

```text
요청을 완료하지 못했습니다. 입력한 내용은 이 화면에 남아 있습니다.
다시 시도해도 계속되면 아래 오류 코드를 전달해 주세요.
코드: <server code 또는 HTTP status>
```

스택 트레이스, 서버 경로, 저장소 위치와 다른 회원 정보는 노출하지 않는다.

## 9. 보안

- 인증된 팀 리더만 업로드 가능
- 파일 시그니처와 이미지 디코딩 이중 검증
- UUID 파일명, 원본 파일명 경로 사용 금지
- 실행 파일·SVG·GIF 저장 금지
- 요청당 5MB 및 회원당 분당 20회 업로드 제한
- `UPLOAD_DIR`를 애플리케이션 정적 리소스와 분리
- Nginx는 `/uploads/`만 읽기 전용으로 제공
- 공연 쓰기 요청은 공개 URL이 아니라 소유권을 검증한 업로드 ID만 허용
- 24시간 지난 `TEMP` 파일은 경로가 `UPLOAD_DIR` 내부인지 재검증한 뒤 삭제
- 판매 시작 후 미디어 수정 차단
- 다른 계정에 연결된 지갑의 주소·회원 정보 비노출
- 로그에는 인증 토큰, 지갑 서명, 파일 본문을 남기지 않음

## 10. 테스트와 검증

### 10.1 백엔드

- 정상 JPEG·PNG 업로드와 브라우저 WebP→JPEG 변환
- 0바이트, 5MB 초과, 위장 확장자, 손상 이미지 거부
- purpose별 크기·비율 검증
- 파일명 경로 조작 무효화
- 팀 리더가 아닌 회원의 업로드 거부
- 다른 회원·다른 purpose·만료 업로드 ID 연결 거부
- `TEMP`→`ATTACHED` 전환과 24시간 고아 파일 정리
- 공연 생성·수정의 `ticket_image_path` 저장과 판매 시작 후 차단
- 티켓 목록·상세·주문 상세 응답의 이미지 URL
- 같은 계정 지갑과 다른 계정 주소의 전용 오류 코드 구분

### 10.2 프론트

- 편집 상태 유지와 실패 후 업로드 재시도
- D-22~D-27 단계 이동 시 draft 보존
- 최종 제출 중복 클릭 차단
- 공연 생성 성공·티켓 옵션 실패 후 같은 공연 재시도
- 저장 티켓 이미지 우선, 로드 실패 시 자동 디자인 폴백
- 각 오류 코드의 한국어·영어 문구와 올바른 행동 버튼
- 지갑 사전 조회 200·404·실패
- 생성 직전 `WALLET_ALREADY_LINKED` 경쟁 상황 복구
- `WALLET_ADDRESS_IN_USE`가 linked 화면으로 잘못 전환되지 않음

### 10.3 통합·수동 QA

- 로컬·테스트 프로필에서만 Spring `ResourceHandler`로 `/uploads/**` 정적 제공
- 운영 Nginx URL과 API 반환 URL 일치
- 8MB 휴대폰 사진 선택 후 브라우저 압축·업로드
- 공연 생성부터 공개 상세·예매 완료·내 티켓·티켓 상세까지 동일 아트 표시
- 모바일 360px와 데스크톱 1440px에서 편집·검토
- 페이지 새로고침·네트워크 단절·업로드 재시도
- 기존 지갑 회원의 온보딩 직링크 진입

## 11. 구현 분리

한 MR에 모든 층을 섞지 않고 다음 순서로 나눈다.

1. 계약·백엔드·인프라: 파일 API, 업로드 메타데이터·DB 컬럼, 고아 파일 배치,
   공연·티켓 응답, Nginx
2. 프론트 생성 흐름: 업로드 클라이언트, 편집기, 제작기, 검토 화면
3. 지갑 중복 UX: 사전 조회와 전용 코드 복구
4. 통합 검증: 실제 업로드 URL과 발급 티켓 E2E

각 구현은 테스트를 먼저 추가해 실패를 확인한 뒤 최소 코드로 통과시킨다. 커밋과 MR에는
확정된 Jira 키를 넣는다. 현재 문서의 추적 키는 기존 공연 연동 범위인 S15P21B204-99이며,
파일 업로드와 지갑 오류 코드가 별도 Jira로 발급되면 각 구현 커밋은 새 키를 사용한다.

## 12. 배포·롤백

- DB migration은 nullable 컬럼 추가라 기존 배포와 호환된다.
- 신규 프론트가 먼저 배포되지 않도록 백엔드·Nginx를 먼저 배포한다.
- 구버전 프론트는 신규 필드를 보내지 않으므로 계속 동작한다.
- 신규 이미지가 없는 공연은 현재 자동 티켓 디자인을 사용한다.
- 프론트 롤백 후에도 업로드 파일과 DB URL은 남지만 기존 화면 동작에는 영향이 없다.
- 서버 롤백 시 신규 컬럼을 즉시 삭제하지 않는다.
