# Stage Ledger 프론트엔드 고도화 설계

## 1. 목적

불러요 프론트엔드를 현재의 인터랙티브 목업에서 실제 API와 지갑 흐름이 연결된 제품 수준의 웹 애플리케이션으로 발전시킨다. 기존 다크 무대 정체성과 포스터 중심 탐색 경험은 유지하고, 정산·검증 화면은 계산 결과와 신뢰 근거가 빠르게 읽히도록 정리한다.

최신 기술은 효과 자체가 아니라 다음 사용자 경험을 강화할 때만 사용한다.

- 공연을 발견하고 선택하는 흐름의 연속성
- 결제·정산 과정의 집중도와 신뢰성
- 모바일 360~390px 환경의 안정성
- WebGPU 미지원·저사양·동작 줄이기 환경의 동일한 기능 보장

## 2. 확정된 제품 방향

디자인 방향은 **Stage Ledger**로 확정한다.

- 홈·공연 상세: 다크 객석, 포스터, 무대 조명을 중심으로 감성적 첫인상을 만든다.
- 예매·결제: 같은 색상 체계를 유지하되 배경 효과와 장식을 줄여 행동에 집중시킨다.
- 공연자·정산·검증·관리자: 고대비 중립 패널, 명확한 숫자 위계, 접힌 기술 근거를 사용한다.
- 기본 색상 값의 정본은 팀 토큰이며, 첫 진입 표시 테마는 의도적으로 `dark`를 사용한다.
- `Meta`·`Apple`은 개발 환경 비교용이며 프로덕션 UI에는 선택 진입점을 제공하지 않는다.
- 숫자·금액은 `Inter`, 예매번호·주소·시각 등 식별자는 `JetBrains Mono`를 사용한다. 디자인 토큰 문서 v2에 이 결정을 반영한다.

## 3. 범위 분해와 구현 순서

전체 작업은 독립적으로 검증 가능한 세 하위 프로젝트로 나눈다. 각 단계는 앞 단계가 통과한 뒤 시작한다.

### 단계 A. 제품 기반 안정화

1. 공연 상세→티켓 옵션→응원팀 선택 흐름의 목 데이터를 공연 ID 기준으로 단일화한다.
2. 모바일 페이지 전체 가로 넘침을 제거한다. 의도된 칩·필터 내부 스크롤은 유지한다.
3. 관객·공연자·검증·관리자 라우트를 지연 로드해 초기 청크를 줄인다.
4. 전역 무대 효과를 탐색 화면 중심으로 제한한다.
5. 디자인 토큰 폰트와 API 공통 응답 규격 링크를 현행 결정에 맞춘다.

단계 A의 완료 조건은 목 데이터만 사용해도 한 공연의 정보가 예매 완료 전까지 변하지 않고, 360px에서 페이지 전체 가로 스크롤이 없으며, 초기 번들에 관리자·스튜디오·지갑 SDK가 포함되지 않는 것이다.

### 단계 B. 실제 세로축 연결

1. OpenAPI 생성 타입과 기존 API 클라이언트를 사용해 공연 목록·상세 조회를 연결한다.
2. 티켓 옵션 조회, 주문 생성, 응원팀 선택, 결제 서명, 주문 완료 조회를 TanStack Query로 연결한다.
3. 로그인·지갑 등록·역할별 라우트 가드를 구현한다.
4. API 오류 코드를 사용자 행동으로 변환한다. 예: 품절은 옵션 재선택, 잔액 부족은 잔액 안내, 서명 거부는 재시도 가능한 원래 단계 유지.
5. 데모 모드에서는 동일 인터페이스의 fixture adapter를 사용하고, 프로덕션 코드에 화면별 임의 목 데이터를 남기지 않는다.

단계 B의 완료 조건은 사용자 한 명이 로그인→지갑 확인→공연 선택→응원팀 선택→서명 결제→티켓 확인의 세로축을 실제 API로 완료하는 것이다.

### 단계 C. 절제된 실험 기능

1. 공연 카드→상세 포스터에 View Transition API를 점진 적용한다.
2. View Transition 미지원 또는 `prefers-reduced-motion: reduce` 환경에서는 즉시 이동한다.
3. 홈 섹션 첫 진입에만 CSS `view()` 기반 짧은 reveal을 적용한다. 미지원 환경에는 정적 표시를 제공한다.
4. 언어·프로필·짧은 용어 설명에 네이티브 Popover API를 적용하되 기존 메뉴 동작을 fallback으로 보존한다.
5. vgpu는 홈·공연 상세 Hero에서만 지연 로드하고, 프레임 저하 시 품질을 낮추거나 CSS 배경으로 전환한다.
6. Paper Shaders, TypeGPU, Three.js, PixiJS, Rive, Spline, GSAP은 이번 범위에 추가하지 않는다.

단계 C의 완료 조건은 실험 기능을 모두 비활성화해도 정보·탐색·결제 기능에 차이가 없고, 동작 줄이기 환경에서 비필수 모션이 실행되지 않는 것이다.

## 4. 아키텍처

현재 의존 방향을 유지한다.

```text
app → pages → features → shared
```

- `app`: 라우터, 프로바이더, 가드, 라우트 단위 로딩 경계
- `pages`: 라우트 파라미터와 feature 조합, Query 결과 전달
- `features`: 공연·주문·결제·지갑·정산별 화면 로직과 상태 표현
- `shared/api`: OpenAPI 타입, HTTP 클라이언트, 공통 응답·오류 변환
- `shared/blockchain`: Web3Auth·Kaia Wallet·ethers-ext 격리
- `shared/fx`: vgpu·Canvas·CSS 향상 효과와 지원 여부 판정
- `shared/ui`: 접근성 있는 버튼·패널·Popover·전환 연결 요소

features끼리 직접 import하지 않는다. 예매 단계 간 공유 데이터는 별도 전역 상태 라이브러리를 추가하지 않고 URL의 `performanceId`·`orderId`와 Query 캐시를 기준으로 재구성한다.

## 5. 데이터 흐름

### 공연 탐색과 예매

```text
GET performances
  → performanceId 선택
  → GET performance detail
  → ticketTypeId·quantity 선택
  → 공동 공연이면 teamId 선택
  → POST order
  → senderSignedRlp 생성
  → POST signed transaction
  → chain job 폴링
  → order/ticket 조회
```

- Query Key는 도메인과 식별자가 드러나는 배열을 사용한다.
- 주문 전 선택 상태는 URL과 화면 로컬 상태로 유지한다.
- 주문 생성 뒤에는 `orderId`를 정본으로 삼는다.
- `PENDING`·`SUBMITTED` 상태에서만 체인 작업을 폴링한다.
- 성공 후 공연 잔여 수량, 주문, 티켓, 잔액 Query를 invalidate한다.

### 데모 모드

데모 데이터는 화면 컴포넌트 안의 상수로 두지 않는다. API와 같은 반환 타입을 갖는 fixture repository를 만들고 `import.meta.env.MODE === 'demo'`에서만 선택한다. 같은 `performanceId`는 모든 단계에서 같은 제목·포스터·팀·가격을 반환해야 한다.

## 6. 라우트와 접근 제어

가드는 다음 책임으로 분리한다.

- `GuestOnly`: 로그인 사용자의 로그인·회원가입 재진입 방지
- `Authenticated`: 토큰이 없으면 `/login?from=...`으로 이동
- `WalletRequired`: 로그인 응답의 `wallet == null`이면 `/onboarding/wallet`로 이동
- `PerformerOnly`: 팀 리더가 아니면 일반 홈 또는 권한 안내로 이동
- `AdminOnly`: 관리자만 `/admin/*` 접근
- `ParticipantLeaderOnly`: 해당 공연 참여팀 리더만 `/verify/:performanceId` 접근

가드가 사용자 정보를 조회 중일 때는 빈 화면 대신 공통 로딩 경계를 표시한다. 권한 API 실패와 실제 권한 없음은 다른 상태로 처리한다.

## 7. 시각·모션 규칙

### 탐색 화면

- vgpu StageFlare와 포스터 색 추출은 홈 Hero와 공연 상세 Hero에만 적용한다.
- 포스터가 시각적 주인공이며 텍스트 glow, 카드별 입체 회전, 상시 파티클을 추가하지 않는다.
- 카드 hover는 마우스가 정밀 포인터일 때만 2~4px 상승과 테두리 대비 변화로 제한한다.

### 거래 화면

- 예매·결제·지갑 화면에는 읽기 순서를 방해하는 전역 커서 조명을 사용하지 않는다.
- 주요 CTA는 화면당 하나를 우선하고, 진행 중에는 버튼 위치에서 상태를 이어서 보여준다.
- 잔액·금액·팀 선택은 색 외에 문구와 아이콘으로 상태를 구분한다.

### 정산·검증 화면

정보 순서는 다음으로 고정한다.

1. 일치·완료·중단 등 결론
2. 총액과 팀별 분배
3. 계산식과 사용자 재계산
4. 불변식·이벤트·기술 근거

체인 용어와 원시 값은 기본 접힘 영역에 둔다. 실패·불일치는 초록/빨강만으로 구분하지 않고 상태 문구와 차액을 함께 표시한다.

## 8. 반응형·접근성

- 기준 최소 폭은 360px이며 PC 브레이크포인트는 기존 768px을 유지한다.
- 페이지 루트는 `max-width: 100%`와 `min-width: 0`을 만족해야 한다.
- 가로 스크롤은 날짜 칩·필터처럼 명세가 허용한 내부 영역에만 존재한다.
- 모바일 하단 탭과 고정 CTA가 동시에 나타나는 화면은 safe-area를 포함한 하단 여백을 확보한다.
- 모든 클릭 대상은 44px 이상을 유지한다.
- 포커스 이동, dialog/popover 닫기, Escape, 포커스 복귀를 키보드로 검증한다.
- `prefers-reduced-motion`, `prefers-reduced-transparency`, `prefers-contrast` 기존 처리를 보존한다.

## 9. 성능 예산

- 모바일 4G LCP 목표: 3초 이하
- 초기 gzip 번들 목표: 500KB 이하
- 홈 초기 로드에 관리자·스튜디오·Web3Auth 구현 청크를 포함하지 않는다.
- Hero 포스터는 eager/fetch priority 후보, 접힌 영역과 목록 후반 포스터는 lazy 대상이다.
- vgpu·Motion GPU 연결 코드는 현재처럼 동적 import한다.
- viewport 밖의 반복 애니메이션은 정지한다.
- WebGPU 초기화 실패는 사용자 오류로 표시하지 않고 CSS fallback으로 전환한다.

## 10. 오류 처리

- 네트워크 실패: 현재 입력·선택을 보존하고 재시도 제공
- 인증 만료: Query 캐시와 토큰 정리 후 원래 경로를 저장해 로그인으로 이동
- 서명 거부: 실패 화면으로 보내지 않고 현재 단계에서 다시 시도 가능
- 품절·가격 변경: 최신 공연·티켓 데이터를 invalidate하고 선택을 다시 확인
- 체인 작업 지연: 중복 제출을 막고 상태 폴링과 종료 조건을 명시
- WebGPU·View Transition·Popover 미지원: 기능 손실 없는 정적/CSS/기존 React 경로 사용

## 11. 테스트 전략

모든 동작 변경은 실패하는 테스트를 먼저 작성한다.

- 단위 테스트: 공연 fixture 정합성, Query Key, 오류 코드 변환, 가드 판정, 모션 지원 판정
- 컴포넌트 테스트: 단계 이동 시 공연 정보 유지, 모바일 필터 접근성, Popover 키보드 동작
- 통합 테스트: 공연 상세→예매→팀 선택→결제 완료 세로축
- 회귀 테스트: 캐러셀 탭/드래그, HALTED 판정, 정산 계산, vgpu uniform 기존 테스트
- 빌드 검증: typecheck, lint, Vitest, production build, 청크 크기 비교
- 수동 QA: 360×800, 390×844, 768px, 1440px; 키보드 전용; reduced motion; WebGPU 비활성

## 12. 문서와 세션 인계 규칙

Claude·Codex 어느 환경에서 재개해도 같은 상태를 읽을 수 있도록 다음 파일을 유지한다.

- 이 문서: 제품 방향과 변경 불가 조건
- `docs/superpowers/plans/2026-09-10-stage-ledger-foundation-plan.md`: 테스트 우선 구현 순서
- `docs/frontend/STAGE_LEDGER_STATUS.md`: 현재 단계, 완료 항목, 다음 작업, 검증 명령과 마지막 결과
- `docs/frontend/STAGE_LEDGER_DECISIONS.md`: 구현 중 새로 확정한 결정과 근거
- `CLAUDE.md`: 위 세 문서로 가는 짧은 진입 링크

진행 문서는 매 작업 묶음이 끝날 때 갱신하며 다음 항목을 반드시 기록한다.

- 현재 브랜치와 기준 커밋
- 완료한 테스트의 이름
- 아직 구현되지 않은 항목
- 다른 팀 결정이나 실제 API가 필요한 차단 사항
- 되돌리는 방법과 영향 파일
- 다음 세션이 처음 실행할 검증 명령

제안, 구현, 검증을 구분한다. 실행하지 않은 검증을 통과로 기록하지 않고, 데모 fixture 동작을 실제 API 성공으로 표현하지 않는다.

## 13. 범위 제외

- 백엔드·컨트랙트 동작 변경
- Figma 원본의 임의 수정
- 새로운 3D·셰이더·애니메이션 라이브러리 추가
- 대규모 디자인 시스템 재작성
- 모든 대형 컴포넌트의 일괄 분해
- 명세 밖의 신규 기능 추가

대형 컴포넌트는 해당 단계에서 실제로 수정하는 영역만 분리한다.

## 14. 승인 기준

이 설계가 승인되면 단계 A부터 구현 계획을 작성한다. 단계 B의 실제 API 연결은 현재 OpenAPI와 백엔드 구현을 다시 대조한 뒤 진행하며, 계약이 충돌하는 항목은 추측하지 않고 `STAGE_LEDGER_STATUS.md`에 차단 사항으로 남긴다.
