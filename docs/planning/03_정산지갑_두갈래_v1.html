옵션 B + 자동 환급

가스 충전
팀 생성 시 운영지갑이 팀 지갑으로 소량 자동 전송, 잔액 임계 미달 시 자동 재충전. → §10 미결 안건 "충전 담당자·주기 협의"가 코드로 닫힙니다.
환급 방식
release 시 자동 push. 팀 출금 버튼 제거 — 시연에서 손이 하나 줄고, 취미 밴드가 이해할 이유가 없는 단계입니다.
팀 키 사용 범위
agreeToRules 서명 1회로 한정. 키 복호화 횟수 = 노출 횟수이므로 최소화하고, 나머지는 운영지갑 권한으로 처리합니다.

어느 쪽을 택해도 지금 잡을 것

  • 운영지갑 권한 2개로 분리 — minter/burner와 operator. 키 하나 유출로 무한 mint가 가능해지면 준비금 증명 자체가 무의미해집니다. 팀 수와 무관하게 2개 고정.
  • nonce 직렬 큐 — recordChoice가 한 지갑에서 나가므로 예매 100건이 몰리면 nonce 충돌·지연이 납니다. 단일 nonce 관리 큐 또는 recordChoiceBatch.
  • 예금주명 일치 검증 — 팀 정산계좌 등록 시 필수. 현재 설계에 빠져 있습니다.
  • 팀 대시보드에 지갑 주소 노출 — 키는 안 주더라도 주소와 익스플로러 링크를 보여주면 "각 팀이 독립 검증 경로를 갖는다"는 주장이 화면으로 성립합니다. 구현 비용 거의 0.
발표 방어

정직하게 인정하고 갈 부분

서버가 모든 팀 키를 보관하므로 암호학적으로는 플랫폼이 전원 동의를 위조할 수 있습니다. 문서 §8.3도 이미 "완전 커스터디얼 구조"라고 적어 두었습니다. 파고들어오면 이렇게 답하세요.

동의 주소가 서로 다르다는 사실은 온체인에 남지만, 키는 플랫폼이 보관합니다. 그래서 저희가 주장하는 건 탈중앙이 아니라 "잠근 뒤에는 플랫폼조차 못 바꾼다"와 "누구나 같은 값을 재계산할 수 있다" 입니다. 위조하면 팀이 즉시 반박할 수 있고, 그 흔적이 남는 구조입니다.

§8.3의 "보장하는 것 / 보장하지 않는 것" 표와 같은 논리라 발표 전체의 일관성이 유지됩니다. 덧붙일 한 줄 — 실서비스라면 팀 자산의 키를 플랫폼이 보관하는 것은 가상자산 보관관리업 영역입니다. 프로젝트는 테스트넷 모의라 해당 없지만, 물으면 "실서비스 전환 시 라이선스 과제"로 답하면 됩니다.
