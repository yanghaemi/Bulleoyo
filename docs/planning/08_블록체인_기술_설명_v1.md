## 1. 기본 개념 7개

### 1.1 블록체인 = 누구도 혼자 고칠 수 없는 공유 DB

여러 컴퓨터(노드)가 같은 장부를 복제해서 들고 있고, 새 기록(트랜잭션)은 다수가 검증한 뒤에만 추가된다. 추가된 기록은 지울 수 없다. **우리에게 중요한 성질은 두 가지다.**

- **불변**: 관객이 어느 팀을 골랐는지, 팀들이 어떤 규칙에 동의했는지가 한 번 기록되면 플랫폼 운영자도 못 바꾼다.
- **공개 검증**: 누구나 기록을 읽을 수 있다. 우리 서버가 보여주는 정산 결과를 관객·공연팀이 직접 대조할 수 있다.

MySQL과의 차이는 "누가 관리자냐"다. MySQL은 우리가 관리자라 우리가 고칠 수 있고, 그래서 남들이 우리를 믿어야 한다. 블록체인은 관리자가 없어서 믿을 대상이 필요 없다.

### 1.2 EVM = 블록체인 위에서 돌아가는 가상 컴퓨터

Ethereum Virtual Machine. 블록체인 위에 프로그램(스마트 컨트랙트)을 올려 실행하는 규격이다. Kaia는 EVM 호환 체인이라 이더리움용 언어(Solidity)·라이브러리(OpenZeppelin)·도구(Hardhat)를 그대로 쓴다.

### 1.3 지갑 = 키 한 쌍 + 주소

지갑은 앱이 아니라 **개인키 하나**다. 개인키에서 공개키가 나오고, 공개키에서 주소(`0x`로 시작하는 42자)가 나온다.

- **주소**: 계좌번호. 공개해도 된다. 코인이 여기로 온다.
- **개인키**: 도장. 이걸 가진 사람이 그 주소의 주인이다. 잃으면 복구 불가, 유출되면 코인 전부 탈취.
- **시드 문구(12~24 단어)**: 개인키를 사람이 적을 수 있게 바꾼 것. 우리는 관객에게 이걸 보여주지 않는다(§6).

"지갑 생성"은 난수 하나 뽑는 것이다. 서버 등록도, 승인도 필요 없다. 그래서 순식간에 생긴다.

### 1.4 트랜잭션 = 서명된 명령 한 건

"A 주소가 B 컨트랙트의 `purchase` 함수를 이 인자로 호출한다"를 A의 개인키로 **서명**한 데이터. 서명이 있어야 노드가 받아준다. 트랜잭션에는 이런 것이 들어 있다.

| 필드 | 뜻 | 우리 서비스에서 |
|---|---|---|
| from | 서명한 주소 | 관객 지갑 또는 서버 운영 지갑 |
| to | 받는 주소나 컨트랙트 | YoYo 또는 RevenueSplitter 컨트랙트 |
| data | 어떤 함수를 어떤 인자로 | `purchase(performanceId, teamId, amount)` 를 인코딩한 바이트 |
| nonce | from 주소가 보낸 tx의 순번 | 같은 지갑에서 동시에 두 개 보내면 충돌하는 원인(§7.3) |
| gas | 실행 수수료 상한 | 대납으로 플랫폼이 냄(§5) |

트랜잭션이 블록에 들어가면 **receipt(영수증)** 가 나온다. 성공/실패, 사용 가스, 발생한 이벤트가 들어 있다. 우리 서버는 이 receipt를 읽어 결제 성공을 판정한다(§7.4).

### 1.5 가스 = 실행 수수료

컨트랙트 실행에는 체인의 기본 코인(Kaia에서는 KAIA)이 수수료로 든다. 관객이 KAIA를 따로 가져야 하면 진입 장벽이 되므로 우리는 **플랫폼이 대신 낸다**(§5). 그래서 관객 지갑의 KAIA 잔액은 항상 0이어도 된다.

### 1.6 스마트 컨트랙트 = 체인 위에 배포된 프로그램 + 그 프로그램의 저장소

Solidity로 짠 코드를 배포하면 주소가 하나 생기고, 그 주소로 tx를 보내면 함수가 실행된다. 컨트랙트도 자기 저장 변수(상태)를 가진다. 예: YoYo 컨트랙트는 "주소별 잔액" 맵을 저장하고 있다.

- **함수 호출 두 종류**: 상태를 바꾸는 호출(tx 필요, 가스 듦, 서명 필요)과 읽기만 하는 호출(call, 무료, 서명 불필요). 잔액 조회는 call, 결제는 tx.
- **이벤트(event)**: 컨트랙트가 실행 중 남기는 로그. receipt에 담긴다. 우리는 `Purchased(performanceId, teamId, buyer, amount)` 같은 이벤트를 읽어 DB를 갱신하고, 검증 페이지는 이 이벤트의 합으로 집계를 재계산한다.
- **ABI**: 컨트랙트 함수·이벤트의 시그니처 목록(JSON). 프론트·백엔드가 컨트랙트를 호출하려면 주소 + ABI가 필요하다. Hardhat이 컴파일하면 나온다(§8).

### 1.7 테스트넷·파우셋·익스플로러

- **테스트넷**: 진짜 돈이 아닌 연습용 체인. 우리는 Kaia **Kairos**를 쓴다. 메인넷과 동작이 같고 코인 가치만 0이다.
- **파우셋(faucet)**: 테스트넷 코인을 무료로 주는 사이트. 우리 운영 지갑(fee payer)에 KAIA를 채울 때 쓴다. 일일 한도가 있다.
- **익스플로러**: 체인 기록을 웹에서 보는 사이트. Kairos는 **Kaiascan**. 검증 페이지의 "tx 보기" 링크가 여기로 간다.

## 2. 우리가 쓰는 체인: Kaia Kairos

| 항목 | 값 |
|---|---|
| 체인 | Kaia (구 Klaytn + Finschia 합병) |
| 네트워크 | Kairos 테스트넷, chainId **1001** |
| 기본 코인 | KAIA (가스비용. 관객은 안 가짐) |
| 블록 시간 | 약 1초 → 결제 후 1~2초면 확정 |
| 공개 RPC | `https://public-en-kairos.node.kaia.io` |
| 익스플로러 | `https://kairos.kaiascan.io` |

**왜 Kaia인가.** ① 수수료 대납이 프로토콜 기능이다. 이더리움 계열은 대납을 하려면 페이마스터 컨트랙트(ERC-4337)를 따로 짜야 한다. ② EVM 호환이라 배울 게 이더리움과 같다. ③ 국내 문서·커뮤니티가 많다. 선정 리서치는 `05_테스트넷_선정_리서치_v1.md`.

**RPC(노드)란.** 체인에 tx를 보내거나 데이터를 읽으려면 노드에 HTTP로 요청해야 한다. 이 요청 규격이 JSON-RPC이고 그 접속 주소가 RPC URL이다. 우리는 Kaia가 공개로 운영하는 노드를 쓴다. 우리가 노드를 직접 돌리지 않는다.

**KAIA와 YoYo는 다르다.** KAIA는 체인 자체의 코인(가스비). YoYo는 우리가 컨트랙트로 만든 토큰(결제 화폐). 관객은 YoYo만 보고, KAIA는 서버 운영 지갑만 가진다.

## 3. 코인 YoYo

### 3.1 ERC-20 = "토큰" 표준 인터페이스

ERC-20은 "잔액 조회·전송·승인" 함수 이름과 동작을 정한 표준이다. 이 표준을 따르는 컨트랙트가 곧 토큰이다. **토큰은 별도 코인이 아니라 컨트랙트 안의 `잔액[주소]` 맵**이다. "A가 YoYo 100을 가진다" = YoYo 컨트랙트 저장소에 `balances[A] = 100`이 적혀 있다.

우리가 쓰는 함수:

| 함수 | 뜻 | 누가 호출 |
|---|---|---|
| `balanceOf(addr)` | 잔액 조회(무료 call) | 서버(잔액 캐시 갱신), 프론트 |
| `transfer(to, amount)` | 내 잔액을 to로 | 관객 지갑 간 P2P 송금 |
| `approve(spender, amount)` | spender가 내 잔액에서 amount까지 빼가도록 허용 | 관객이 결제 전 RevenueSplitter에 허용 |
| `transferFrom(from, to, amount)` | 허용 받은 만큼 빼감 | RevenueSplitter가 `purchase` 안에서 실행 |
| `mint(to, amount)` | 새로 발행 | 서버 MINTER 키(시연용 지급) |
| `totalSupply()` | 총 발행량 | 검증 페이지 공시 |

**approve → transferFrom 2단계인 이유.** 컨트랙트가 남의 잔액을 함부로 못 빼가게 하는 ERC-20의 안전장치다. 결제는 "관객이 YoYo에 승인(approve) → RevenueSplitter의 purchase가 transferFrom으로 가져감"이다. 관객 입장에서는 서명이 2번 필요할 수 있어 UX가 나쁘다. Permit(서명 1번으로 approve 대체)은 P1이다.

### 3.2 우리 YoYo의 특징

- **`decimals = 0`**: 소수점 없음. 1 YoYo = 1원. 일반 토큰은 18자리 소수를 쓰는데 우리는 원 단위라 뺐다. 금액 계산에 소수점 오류가 없다.
- **소각(burn) 없음**: 법정화폐로 환급하는 출구가 없으니 소각할 일이 없다.
- **페그·준비금 없음**: 현실의 스테이블코인은 은행 예치금 1:1로 가치를 보증한다. 우리는 "화폐가 이미 코인인 세계"를 가정하므로 보증 대상이 없다. 심사에서 반드시 나오는 질문이다(§10).

### 3.3 역할(Role)과 서버 키 2개

OpenZeppelin `AccessControl`로 "이 함수는 이 역할만 호출 가능"을 건다.

| 역할 | 할 수 있는 것 | 키 보관 |
|---|---|---|
| MINTER | `YoYo.mint` | 서버 환경변수. 시연용 지급 전용. 탈취 시 무한 발행이라 가장 위험 |
| OPERATOR | RevenueSplitter의 집계·잠금·분배·halt·환불 | 서버 환경변수. 관객 코인을 임의로 못 옮김. 에스크로 안의 코인만, 규칙대로만 |

관객·팀 리더의 키는 서버가 **갖지 않는다**(§6). 그래서 이전 설계의 봉투 암호화(envelope encryption)는 필요 없어져 삭제됐다.

### 3.4 발행 어댑터(CoinIssuerPort)

"코인을 어디서 받아오나"를 인터페이스 하나로 감싼 것. 지금은 `MockIssuer` = 우리 YoYo의 `mint`. 나중에 실제 원화 스테이블코인 발행사가 생기면 `ExternalIssuer`로 교체하고 서비스 코드는 안 바꾼다. **AI나 외부 API가 아니라 Spring 인터페이스 + 구현체 하나**다. 발표에서 "확장 가능성"으로 쓰는 장치.

## 4. 정산 컨트랙트 RevenueSplitter

### 4.1 에스크로 = 컨트랙트가 돈을 맡아두는 것

관객이 결제하면 YoYo가 공연팀에게 바로 가지 않고 **RevenueSplitter 컨트랙트 주소**로 간다. 컨트랙트가 공연별로 "이 공연에 모인 코인 ○○"을 기록해 두고, 정산 시점에 규칙대로 리더 지갑들로 보낸다. 컨트랙트는 사람이 아니라 코드라서 규칙 밖으로 돈을 보낼 수 없다. 이게 "에스크로".

### 4.2 함수와 흐름

```
[공연 준비]
  createPerformance(performanceId, teamLeaders[], rulesHash)   OPERATOR
  agreeToRules(performanceId, rulesHash)                        각 팀 리더 지갑 서명 ← 신뢰 장치 ②
  lock(performanceId)                                           OPERATOR, 전원 동의 후. 이후 규칙 변경 불가
[판매]
  purchase(performanceId, teamId, amount)                       관객 지갑 서명 ← 신뢰 장치 ①
    → YoYo.transferFrom(관객 → 컨트랙트), 팀별 카운터 += 1, Purchased 이벤트
  refund(performanceId, ticketRef)                              OPERATOR, 공연 전 취소 시 관객에게 반환
[정산]
  aggregate(performanceId)                                      OPERATOR, 온체인 카운터 확정
  lockSettlement(performanceId)                                 OPERATOR
  release(performanceId)                                        OPERATOR, 규칙 × 집계 → 리더 지갑들로 transfer
  halt(performanceId)                                           OPERATOR, 치명 문제 시 전액 환불로 종료
```

정확한 시그니처는 컨트랙트 설계 명세(Jira -25)가 정본이고, 여기서는 역할 이해가 목적이다.

### 4.3 상태 기계

```
NONE → AGGREGATED → LOCKED → DISPUTE_OPEN(48h) → RELEASED
                                            ↘ HALTED (종착, 전액 환불)
```

- 분배(`release`) 전까지는 되돌릴 수 있다. 분배 후에는 못 되돌린다. 이게 의도다.
- **HALTED는 종착**이다. "문제를 고쳐서 다시 분배"는 없다. 고칠 수 있는 문제(DB·체인 집계 불일치, 이의제기)는 HALTED로 가기 전 단계에서 멈춘다(409 응답, DISPUTE_OPEN 보류).
- "왜 바로 분배 안 하나"에 대한 답: 온체인은 취소가 없으니 사람이 검토할 창을 앞에 둔다.

### 4.4 rulesHash

정산 규칙(균등·득표 비례·혼합, 비율)은 JSON으로 DB에 있다. 그 JSON의 해시(keccak256) 하나만 체인에 올린다. 팀들은 이 해시에 동의 서명한다. 나중에 누가 규칙을 바꾸면 해시가 달라져 바로 들킨다. **큰 데이터는 오프체인, 지문만 온체인**이 블록체인 설계의 기본 패턴이다.

## 5. 수수료 대납(Fee Delegation)

### 5.1 문제

`purchase`는 관객 지갑이 서명하는 tx다. 원래는 서명한 사람이 가스(KAIA)를 낸다. 관객에게 "KAIA를 먼저 구해 오세요"라고 할 수 없다.

### 5.2 Kaia의 해법: 서명 2개짜리 트랜잭션

Kaia에는 **발신자(sender)와 수수료 납부자(fee payer)가 다른 tx 타입**이 있다. `TxTypeFeeDelegatedSmartContractExecution`.

```
관객 브라우저                          우리 서버                        Kaia
1. tx 내용 작성(purchase 인자)
2. 관객 키로 발신자 서명
3. 서명된 RLP 바이트 → 서버로 전송  →  4. RLP 검증(내용이 서버가 발급한 것과 일치?)
                                       5. fee payer(OPERATOR 지갑) 서명 추가
                                       6. 전송                          →  7. 실행, 가스는 fee payer 차감
                                       8. receipt 수신, Purchased 이벤트 확인
                                       9. payment PAID, 티켓 발급
```

- **RLP**: tx를 바이트로 직렬화하는 인코딩 이름. "서명된 RLP"는 "서명 붙은 tx 바이트 덩어리"라고 읽으면 된다.
- 관객은 KAIA 0으로 결제할 수 있고, 관객 키는 브라우저를 떠나지 않는다.
- 4단계 검증이 중요하다. 서버가 아무 RLP나 대납하면 남이 우리 KAIA로 딴짓을 할 수 있다. 서버가 먼저 "이 공연·이 팀·이 금액"의 서명 파라미터를 발급하고(AWAITING_SIGNATURE), 돌아온 RLP가 그것과 같은지 확인한다.

### 5.3 왜 일반 라이브러리로 안 되나

ethers.js, web3.js, web3j는 **이더리움 표준 tx 타입만** 안다. Kaia의 대납 tx 타입은 모른다. 그래서 Kaia가 만든 확장을 쓴다.

| 위치 | 라이브러리 | 하는 일 |
|---|---|---|
| 프론트 | `@kaiachain/ethers-ext` (ethers v6 확장) | Web3Auth·Kaia Wallet 키로 대납 tx의 발신자 서명 RLP 생성 |
| 백엔드 | `web3j-ext` (kaia-sdk Java) | RLP 디코드, fee payer 서명 추가, 전송, receipt |

Hardhat 로컬 노드도 대납 tx를 못 돌린다. 대납 경로는 **Kairos에서 직접 검증**해야 하고, 이것이 Jira -14 스파이크의 핵심 항목이다. 이게 안 되면 스택을 다시 짜야 하므로 가장 먼저 확인한다.

### 5.4 OPERATOR 지갑 = fee payer

대납은 KAIA를 쓰므로 운영 지갑에 KAIA가 있어야 한다. 파우셋으로 채운다. 비기능 요구사항에 대납 지출 상한·잔액 알림이 있는 이유다.

## 6. 지갑과 로그인: Web3Auth

### 6.1 커스터디얼 vs 비수탁

- **커스터디얼(수탁)**: 서비스가 사용자 개인키를 보관. 거래소 방식. 사용자는 편하지만 서비스가 해킹되면 전원 피해. 이전 설계(v1)가 이거였다.
- **비수탁(non-custodial)**: 사용자가 키를 가짐. 서비스는 못 건드림. 대신 사용자가 키를 잃으면 끝. 우리 v2 설계.

### 6.2 Web3Auth가 하는 일

"구글로 로그인하면 지갑이 생긴다"를 구현한 서비스. 사용자는 시드 문구를 본 적도 없는데 개인키를 갖게 된다.

원리(간단히): 개인키를 여러 조각으로 나눠 ① Web3Auth 네트워크 ② 사용자 기기 ③ (선택) 백업 에 분산 보관한다. 소셜 로그인이 성공하면 조각을 모아 **브라우저 안에서** 키를 복원한다. Web3Auth도, 우리 서버도 완전한 키를 갖지 않는다.

- **SSS vs MPC**: 조각을 모아 키를 한 번 복원하는 방식이 SSS(Shamir Secret Sharing). 키를 끝까지 복원하지 않고 조각끼리 서명만 만드는 방식이 MPC. Web3Auth **Plug-and-Play Modal은 SSS**, MPC는 별도 SDK(MPC Core Kit)다. 우리는 Modal을 쓰므로 **발표·문서에서 "MPC"라고 쓰면 틀린다.** "비수탁 키 분산 지갑" 또는 "소셜 로그인 지갑"으로 표기한다.
- **idToken**: 로그인 성공 시 Web3Auth가 주는 JWT. 우리 서버는 이걸 받아 Web3Auth 공개키(JWKS)로 서명을 검증하고 회원을 식별한다. 일반 OAuth 백엔드 검증과 같다.
- **로그인과 지갑 등록 분리(§14-35)**: 로그인은 신원만 만든다. 지갑 등록은 로그인 후 첫 1회 별도 단계다. 이렇게 해야 "이미 지갑 있는 사람"도 같은 흐름에 들어온다.

### 6.3 외부 지갑(Kaia Wallet)과 서명 챌린지

Kaia Wallet 같은 브라우저 확장 지갑을 이미 쓰는 사람은 자기 주소를 등록한다. 문제는 "그 주소가 진짜 네 것이냐"다. 주소는 공개 정보라 남의 것을 적을 수 있다.

**서명 챌린지**: 서버가 무작위 문자열(nonce)을 주고, 사용자가 자기 개인키로 그 문자열에 서명해서 돌려보낸다. 서버는 서명에서 주소를 복원해 일치하면 등록한다. 개인키 없이는 서명을 못 만드니 소유 증명이 된다. Redis `wallet:challenge:{memberId}` TTL 300초가 이 nonce다. 웹사이트 로그인의 "Sign-In with Ethereum"과 같은 원리.

### 6.4 서명 = 승인 UX

관객이 결제할 때 Web3Auth나 Kaia Wallet이 "이 트랜잭션에 서명하시겠습니까" 창을 띄운다. 이게 은행 앱의 "이체 확인"에 해당한다. 화면설계에서 "서명 전 tx 요약 표시"가 있는 이유다.

## 7. 서버와 체인 연동

### 7.1 web3j

Java에서 EVM 체인을 호출하는 라이브러리. ABI를 주면 Java 클래스를 생성해 컨트랙트 함수를 메서드처럼 호출한다. 여기에 Kaia `web3j-ext`(`io.kaia:web3j-ext` v2.0.7)를 얹어 대납 tx를 처리한다. **버전 주의**: web3j-ext가 web3j **4.9.8**을 고정하므로 web3j를 따로 선언하지 않는다. web3j 5.x는 Java 21이 필수라 우리 Java 17과도 맞지 않는다. Kaia가 보증하는 Java 범위는 11~18이다.

### 7.2 왜 비동기 큐(chain_job)인가

tx는 보내는 즉시 끝나지 않는다. 노드에 접수 → 블록 포함 → receipt까지 1~3초, 혼잡하면 더 걸리고 실패할 수도 있다. HTTP 요청 안에서 기다리면 타임아웃과 중복 전송이 생긴다. 그래서 **"체인에 보낼 일"을 `chain_job` 테이블에 적고 워커가 처리**한다.

| 컬럼 | 뜻 |
|---|---|
| tx_type | MINT / PURCHASE / RELEASE / REFUND … |
| status | PENDING → SUBMITTED → CONFIRMED / FAILED |
| tx_hash | 전송 후 받은 해시. 익스플로러 링크에 씀 |
| idempotency_key | 같은 일을 두 번 보내지 않게 하는 키(예: 지급의 grantRef) |
| retry_count | 재시도 횟수 |

지급 이력 테이블을 따로 안 만들고 `chain_job(tx_type=MINT)`가 이력인 이유도 여기 있다.

### 7.3 nonce 직렬화

한 지갑이 보낸 tx는 순번(nonce)이 연속이어야 한다. 서버 OPERATOR 지갑이 동시에 여러 tx를 보내면 nonce가 겹쳐 실패한다. 그래서 운영 지갑 tx는 **한 줄로 세워서** 보낸다(단일 워커 또는 락). 관객 지갑은 각자 nonce가 따로라 문제없다.

### 7.4 receipt 검증

tx 해시만으로 성공을 믿지 않는다. receipt의 `status == 1`과 **우리 컨트랙트 주소에서 나온 `Purchased` 이벤트의 인자(공연·팀·금액·구매자)** 가 DB 결제 건과 일치하는지 확인한 뒤 PAID로 바꾼다. 이벤트를 파싱하려면 ABI가 필요하다.

### 7.5 대사(reconciliation)

정산 전 서버가 DB 집계(티켓 테이블 group by 팀)와 온체인 집계(컨트랙트 카운터)를 비교한다. 다르면 정산을 멈추고 관리자에게 넘긴다(409 `SETTLEMENT_AGGREGATE_MISMATCH`). 검증 페이지는 이걸 공개적으로 한다.

### 7.6 잔액 캐시

`balanceOf`는 무료 call이지만 RPC 왕복이 있어 화면마다 부르면 느리다. Redis `wallet:balance`에 캐시하고, 그 지갑이 관련된 chain_job이 CONFIRMED 될 때 갱신한다. 정본은 항상 체인이고 Redis는 표시용이다.

## 8. 개발 도구

| 도구 | 역할 | 비유 |
|---|---|---|
| **Solidity** | 컨트랙트 언어. 문법은 JavaScript + 정적 타입 | Java |
| **OpenZeppelin v5** | 검증된 컨트랙트 라이브러리. ERC-20, AccessControl, ReentrancyGuard를 가져다 상속 | Spring Security |
| **Hardhat 3** | 컴파일·테스트·배포 도구. 로컬 가짜 체인도 띄움 | Gradle + JUnit + 로컬 DB |
| **Kaia SDK 확장** | 서버 `web3j-ext`(Java), 프론트 `@kaiachain/ethers-ext/v6`(ethers 6). 대납 tx 타입을 다루는 유일한 방법 | 드라이버 |
| **Kaiascan** | 배포한 컨트랙트·tx 확인 | DB 관리 툴 |
| **파우셋** | 테스트넷 KAIA 지급 | — |

**배포 산출물**: Hardhat으로 Kairos에 배포하면 컨트랙트 **주소** 2개(YoYo, RevenueSplitter)와 **ABI** JSON이 나온다. 이 둘을 백엔드(web3j 래퍼 생성, 환경변수)와 프론트(호출용)에 넘긴다. 주소가 바뀌면(재배포) 양쪽 다 갱신해야 하므로 `deployments/kairos.json`에 커밋해 CI가 읽게 한다.

**로컬 개발의 한계**: Hardhat 로컬 노드는 일반 tx만 지원한다. 컨트랙트 로직 단위 테스트는 로컬에서, **대납 경로는 Kairos에서만** 테스트할 수 있다. OpenZeppelin v5는 v4와 API가 달라(`_beforeTokenTransfer` 삭제 등) v4 예제 코드를 그대로 옮기면 컴파일이 안 된다.

## 9. 용어 사전 (문서에서 마주치는 순서대로)

| 용어 | 한 줄 |
|---|---|
| 주소 (address) | 지갑·컨트랙트의 식별자. `0x` + 40자 hex, DB `CHAR(42)` |
| tx 해시 | 트랜잭션의 고유 ID. `0x` + 64자 hex, DB `CHAR(66)` |
| 서명 | 개인키로 만든 "내가 승인했다"는 증명. 공개키로 누구나 검증 |
| nonce | (tx) 지갑별 순번. (챌린지) 1회용 무작위 값. 같은 단어, 다른 뜻 |
| 가스 / fee payer | 실행 수수료 / 그 수수료를 대신 내는 주소 |
| RLP | tx 직렬화 인코딩. "서명된 RLP" = 서명 붙은 tx 바이트 |
| receipt | tx 실행 결과 영수증. 성공 여부·이벤트 포함 |
| 이벤트 / 로그 | 컨트랙트가 남긴 기록. receipt에 담김. 검증 페이지 집계 근거 |
| ABI | 컨트랙트 함수·이벤트 시그니처 JSON. 호출에 필수 |
| ERC-20 | 토큰 표준. YoYo가 따름 |
| decimals | 토큰 소수점 자리. YoYo = 0 |
| approve / allowance | "이 컨트랙트가 내 토큰을 이만큼 가져가도 됨" 허용 / 그 잔여 한도 |
| mint | 발행. MINTER 역할만 |
| 에스크로 | 컨트랙트가 정산 전까지 코인을 보관하는 상태 |
| rulesHash | 정산 규칙 JSON의 keccak256 지문 |
| release / halt | 분배 실행 / 전액 환불로 종료 |
| 테스트넷 / Kairos | 연습용 체인 / Kaia의 테스트넷 이름 |
| RPC | 노드에 요청하는 HTTP JSON 규격. 접속 주소를 RPC URL이라 함 |
| chainId | 체인 식별 번호. Kairos 1001. 서명에 포함돼 다른 체인에서 재사용 불가 |
| 비수탁 | 서비스가 사용자 키를 갖지 않음 |
| SSS / MPC | 키 조각 분산 후 복원 / 복원 없이 조각으로 서명. Web3Auth Modal은 SSS |
| idToken / JWKS | Web3Auth 로그인 JWT / 그 서명을 검증할 공개키 묶음 |
| 서명 챌린지 | nonce에 서명해 지갑 소유를 증명하는 절차 |
| 대사 (reconciliation) | DB 집계와 온체인 집계 비교 |
| CoinIssuerPort | 발행 소스를 감싼 Spring 인터페이스. MockIssuer / ExternalIssuer |

| 쓰지 말 것 | 대신 | 이유 |
