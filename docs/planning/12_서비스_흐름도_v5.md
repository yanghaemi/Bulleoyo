## 2. 결제·대납 시퀀스

```mermaid
sequenceDiagram
  participant U as 관객 브라우저
  participant S as 백엔드
  participant O as "OPERATOR (fee payer)"
  participant K as Kaia Kairos
  participant R as RevenueSplitter

  U->>S: 주문 생성 + POST .../payment/prepare
  S-->>U: "200 signRequests[APPROVE?, PURCHASE] + feePayer + expiresAt"
  Note over U: 지갑 팝업에 서명 요약 표시
  U->>U: "발신자 서명(RLP) 생성"
  U->>S: "POST .../signed-tx {kind, senderSignedRlp}"
  S->>S: RLP 디코드·발신자·to·data 대조
  S->>O: 대납 서명 요청
  O-->>S: feePayer 서명 추가
  S-->>U: 202 Accepted + jobId
  S->>K: 서명된 tx 전송
  K->>R: "purchase(showId, orderRef, teamIndex, amount)"
  R-->>K: transferFrom + escrow 적립 + votes+1 + Purchased 이벤트
  K-->>S: receipt
  S->>S: receipt 5항목 검증
  loop 프론트 폴링
    U->>S: "GET /chain/jobs/{jobId}"
  end
  S-->>U: CONFIRMED + txHash + explorerUrl
  S-->>U: "PAID + 티켓 ISSUED(QR)"
  Note over U: 관객 지갑 KAIA 잔액 0 유지 — 가스는 전액 대납
```

메시지 17개(참여자 5, 관객 지갑 KAIA 0 강조 Note 포함).

## 3. 정산 시퀀스

```mermaid
sequenceDiagram
  participant S as "백엔드 (OPERATOR)"
  participant D as MySQL
  participant R as RevenueSplitter
  participant T as 팀 리더 지갑
  participant V as 검증 페이지

  Note over S: 공연 종료 (판매 마감 이후)
  S->>D: "SELECT COUNT(ticket) group by team"
  S->>R: "aggregate(showId)"
  R-->>S: "votes(showId, teamIndex) 확정값"
  alt DB 집계 == 온체인 votes 합
    S->>R: "lockSettlement(showId)"
    Note over S: 이의제기 48h 창
    S->>R: "release(showId)"
    R->>T: "transfer(규칙 × 집계 분배액)"
    R-->>S: Released 이벤트
  else 불일치
    S-->>S: SETTLEMENT_AGGREGATE_MISMATCH 409
    Note over S: LOCKED_RULES 유지, release 보류
  end
  V->>R: "rulesHash·votes·Released 이벤트 조회 (무료 call)"
  V->>V: 규칙 × 집계 재계산 → 대조
```

메시지 12개(alt 분기 1개 — 대사 불일치 시 release 보류).

## 4. v2.1 대비 바뀐 것

| 구분 | v2.1 (폐기) | v5 (현행) |
|---|---|---|
| 화폐 입출구 | 금융망 결제·환급(계좌 이체) | 없음 — 화폐가 코인인 세계, YoYo는 원 단위 코인 자체 |
| 팀 지갑 | 커스터디얼(플랫폼이 팀별 지갑 자동 생성·보관) | 사용자 소유 지갑(Web3Auth MPC 또는 Kaia Wallet), 팀 지갑 = 리더 지갑 |
| 양도 | 취소·양도·교환 지원 | 삭제 — 티켓 상태 3값(`ISSUED`/`USED`/`CANCELLED`), `TRANSFER_*` 코드 철회 |
| 체인 | Polygon + Besu 이원화 | Kaia Kairos(chainId 1001) 단일 |
| 서명 주체 | 서버가 전 tx 서명 | 사용자 자산 이동 tx는 사용자 서명, 서버(OPERATOR)는 수수료 대납 서명만 |
| 운영 키 | 서버 커스터디(팀 지갑 포함) | **서버 런타임 키 2개(OPERATOR fee payer·MINTER)** — API v6 §0 그대로. 여기에 **배포·pause·rotate 전용 admin 콜드 키 1개**가 서버 밖(Jenkins 배포 스테이지 Secret text)에 추가됨 — 컨트랙트 인터페이스 v1(오민근 9/7, `RevenueSplitter` 생성자가 admin≠OPERATOR≠MINTER 강제). 서버 `.env`에는 들어가지 않는다 |

## 5. 발표용 메모

1. **1장(전체 흐름)** — 슬라이드 "서비스 개요"에 쓴다. 강조점은 "코인이 지갑·에스크로·지갑 사이에서만 움직인다"는 한 문장.
2. **2장(결제·대납)** — 슬라이드 "결제 UX"에 쓴다. 강조점은 관객 지갑 KAIA 잔액 0(가스 없이 결제)과 서명 2단계(발신자 서명 → 서버 대납).
3. **3장(정산)** — 슬라이드 "정산·검증"에 쓴다. 강조점은 대사(DB ↔ 온체인 votes 일치) 게이트와 48시간 이의제기 창, 그리고 release 이후 검증 페이지가 온체인 값만으로 재계산한다는 점.
4. SVG 내보내기는 [mermaid.live](https://mermaid.live)에 각 블록을 붙여넣거나, 로컬에서 `npx -y @mermaid-js/mermaid-cli -i 12_서비스_흐름도_v5.md -o service-flow_v5.svg`로 뽑는다.
5. 발표 담당이 SVG를 확정하면 `docs/planning/assets/service-flow_v5.svg`로 저장하고 이 문서 상단 링크를 갱신한다(이 문서는 아직 SVG를 갖지 않는다).
