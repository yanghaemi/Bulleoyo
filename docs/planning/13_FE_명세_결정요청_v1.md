# FE 명세 결정요청 v1 — 팀 결정 대기 목록

- 작성일 2026-09-08 · 작성 강병구(FE) · 상태: 팀 검토 대기 · D절 추가 2026-09-08

백엔드가 `develop`에 착지했다 — `backend/src` 133 파일, `refund`·`entry`·`payment`·`ticket` 도메인 패키지가 전부 들어와 있다. 이 문서는 프론트가 그 코드와 명세(요구사항 v6·기능 명세 v6·API v6·화면설계 v6·응답 규격 v3·컨트랙트 인터페이스 v1)를 대조·실측하다 발견한 것을 모은 **요청서**다. 판정문이 아니다 — 각 항목은 현상 → 근거 → 영향 → 제안 순으로 쓰고, 제안은 어디까지나 제안이다. 결정이 늦어질수록 이미 쓰인 코드(백엔드 133 파일, 프론트 골격)를 되돌리는 비용이 붙는다. 프론트는 MR !37(골격)이 `develop`에 머지됐고, 관객 예매 흐름 A-02~A-08 7개 화면이 수정 와이어프레임 기준으로 이식돼 MR !42로 올라가 있다(API 미연결, 예시 데이터 렌더링) — 화면 로직 착수 전이라는 전제는 더 이상 유효하지 않다. A~C절은 여전히 지금이 정정·결정 비용이 가장 싼 시점이지만, D절 항목들은 이미 화면 7개가 붙어 되돌림 비용이 붙기 시작했다.

## A. 구현으로 이미 판정된 것 — 문서 정정만 필요 (2건)

### A-1. 동적 QR은 서버 발급이다

- **현상**: 세 문서가 서로 다르게 적었다.
  - API 명세 v6 `API-ticket-06`: 서버가 `ticket.qr_secret`으로 HMAC을 계산해 **`qrToken`을 반환**하고, 클라이언트는 `rotateAfterMs`(30초)마다 **재호출**한다.
  - 기능 명세 v6 `F-ticket-06`(§A 표): "`qr_secret`을 내려주면 **클라이언트가 HMAC으로** 30초마다 회전하는 QR을 표시한다"
  - 화면설계 v6 `A-08` 컴포넌트 표: "서버에서 `qr_secret` 수신 → 클라이언트가 30초마다 자동 회전. **네트워크 불필요**"
- **근거**: 백엔드 구현이 API v6를 따랐다. `backend/src/main/java/com/ssafy/b204/ticket/dto/TicketDtos.java`의 `QrTokenResponse(ticketId, qrToken, issuedAt, expiresAt, rotateAfterMs)` — 서버가 서명한 짧은 수명 토큰을 내려준다.
- **영향**: 프론트는 클라이언트 HMAC을 구현하지 않는다(작업량 감소). 대신 **A-08의 "네트워크 불필요"는 사실이 아니게 된다** — 공연장 입구에서 30초마다 재호출이 필요하다. 신호가 약한 현장이면 입장 직전 실패로 이어질 수 있어 운영 대응(줄 서기 전 미리 화면 띄우기 등)이 필요하다.
- **제안**: 기능 명세 v6 F-ticket-06 설명과 화면설계 v6 A-08 동작 열을 API v6 기준으로 정정. A-08 상태 절에 재호출 실패 시 안내를 추가.
- **미해결로 남는 것**: **QR 페이로드 포맷과 `POST /api/v1/entries/verify` 요청 shape가 명세에 없다.** 관객 화면(A-08)이 만드는 QR과 검표 화면(S-02)이 읽는 값이 같은 규약이어야 하는데 그 규약을 적은 문서가 없다. 둘 다 프론트가 만든다. 백엔드 `EntryService`가 기대하는 형식을 명세에 올려 달라.

### A-2. 서명 거부는 결제만 서버에 보고한다

- **현상**: API v6 §0.4 ②는 "사용자가 팝업을 닫으면(거부) **서버에 아무것도 보고하지 않는다**"인데, 화면설계 v6 §5.14와 §8.2, A-05 상태 절은 `PAYMENT_SIGNATURE_REJECTED`(409)가 "**온다**"고 적었다. 거부는 지갑에서 끝나는 클라이언트 로컬 이벤트라 서버가 그 코드를 줄 경로가 없어 보였다.
- **근거**: 백엔드에 보고 경로가 있다. `backend/src/main/java/com/ssafy/b204/payment/dto/PaymentDtos.java`의 `PaymentSignedTxRequest(kind, senderSignedRlp, abandoned)` — `abandoned: true`면 `senderSignedRlp` 없이 보고한다. 같은 파일 주석이 **`ChainDtos.SignedTxRequest`에는 이 필드가 없다**고 명시한다.
- **영향**: 서명 거부 처리가 액션별로 갈린다. **결제(A-05)**는 `abandoned: true`로 서버에 보고하고, **보증금(P-03)·규칙 동의(P-06)**는 보고 경로가 없어 화면이 로컬에서 직전 상태로 되돌린다.
- **제안**: §5.14 ④'와 §8.2에서 `PAYMENT_SIGNATURE_REJECTED`를 "서버가 주는 에러 코드"가 아니라 "결제에 한해 클라이언트가 `abandoned`로 보고하는 상태"로 다시 쓴다. 보증금·동의용 거부 문구도 §5.14에 추가한다(현재 결제용 한 문장뿐이다).

## B. 팀 결정이 필요한 것 (5건)

### B-1. 에러 코드가 뭉개져 화면 분기가 불가능하다  ← 가장 큼

- **현상**: 화면설계 v6 §8.2의 신설 제안 12개 중 **5개의 잠정 대체 코드가 전부 `COMMON_CONFLICT`(409)**다. 그런데 화면 명세는 각각 다른 UI를 요구한다.

  | 화면 | 한 코드에 겹친 상황 | 화면이 요구하는 동작 |
  |---|---|---|
  | A-05 결제 | 잔액 부족 / 주문 만료(15분) / 이미 서명 대기 중 / 멱등키 본문 불일치 | 각각 §5.16 인라인 안내 / A-03 복귀 / 진행 중 안내 / 재시도 |
  | C-05 지갑 등록 | 이미 지갑 있음 / 그 주소가 다른 회원에 등록됨 / 챌린지 만료·재사용·발급 이력 없음 | 연결 정보 패널 전환 / 오류 안내 / 1단계 복귀 |

- **근거**: API v6 `API-payment-01` 4xx 표의 409 행이 네 상황을 한 코드로 묶었고, `API-wallet-04` 409 행이 다섯 상황을 묶었다. 응답 규격 v3 §1은 **`code`가 분기의 유일한 키**이고 `msg`로 분기 금지이며, 실패 시 `data`는 **예외 없이 `null`**이다.
- **영향**: 구분할 정보가 응답 어디에도 없다. 지금 명세대로면 A-05와 C-05의 화면 명세를 **구현할 수 없다**. `msg` 문자열을 보는 것은 규격 위반이고, 실패 응답에 필드를 더하는 것은 규격 §2가 금지한다.
- **제안**: 응답 규격 v4에 최소 5개를 정식 코드로 추가한다 — `PAYMENT_INSUFFICIENT_BALANCE`(재정의) · `PAYMENT_SIGNATURE_REJECTED` · `PAYMENT_TX_MISMATCH` · `WALLET_ALREADY_LINKED` · `WALLET_CHALLENGE_EXPIRED`. 전부 §8.2·§16.1에 이미 제안돼 있던 것이라 새로 설계할 것은 없다.

### B-2. 서명 tx에 넘길 값이 반쯤 비어 있다

- **현상 4가지**
  1. **`nonce`** — `signRequests` 필드 표에 없다. 그런데 §0.4 ①은 서버가 RLP를 디코드해 "`…value`·**`nonce`**·`chainId`와 **①에서 발급한 값**"을 대조한다고 적었고, `API-payment-02`는 "`signRequests`의 **`nonce`**·allowance 조건이 바뀌었으면 재생성"이라 적었다. **세 곳이 서로 어긋난다.** 서버가 주는지 프론트가 RPC로 조회하는지 정해져 있지 않다.
  2. **`gasPrice`** — 응답에 없고 언급도 없다. Kaia `0x31` 타입 RLP를 만들려면 필요하다.
  3. **APPROVE → PURCHASE 순서** — "배열 순서대로 서명·보고한다"만 있다. APPROVE 작업이 `CONFIRMED`될 때까지 기다렸다 PURCHASE를 서명하는지, nonce `n`·`n+1`로 연속 서명하는지 없다. 연속 서명이면 프론트가 nonce를 직접 증가시켜야 한다.
  4. **요청 본문이 API마다 다르다** — `API-payment-03`·`API-performance-14`는 `{kind, senderSignedRlp}`인데 **`API-rule-05`만 `{teamId, senderSignedRlp}`로 `kind`가 없다.** §0.4는 3단계 고정 패턴이라 선언했지만 공통 요청 타입을 만들 수 없다.
- **실측 추가**: 프론트가 만든 발신자 서명 RLP를 디코드해 보면 **`chainId`가 독립 필드로 존재하지 않는다.** 서명 `V`에 접혀 있다. 서버가 `chainId`를 대조하려면 필드 조회가 아니라 `V`에서 복원해야 한다. (2026-09-08 `@kaiachain/ethers-ext` v2.1.0 실측)
- **영향**: PoC 2에서 바로 부딪히는 지점이고, 서버(이강륜)의 RLP 검증 구현과 짝이 맞아야 한다. 어긋나면 결제가 4xx로 막힌다.
- **제안**: §0.4에 `nonce`·`gasPrice`의 출처와 두 서명의 순서 규칙을 한 표로 명시하고, `rule-05` 요청 본문에 `kind`를 추가해 세 API를 같은 모양으로 맞춘다. 오민근·이강륜·강병구가 같이 정해야 한다.

### B-3. 체인 설정을 환경변수로 갈지 API로 갈지 문서가 갈린다

- **현상**
  - **환경변수 쪽(3곳)**: 화면설계 v6 §1.2 원칙 11과 §5.3이 "체인·컨트랙트 설정은 프론트 **환경변수로 고정한다** `[팀 9/2]` — 설정 조회 API는 P1이며 MVP 화면은 호출하지 않는다", 기능 명세 v6 `F-coin-09`가 "`[P1]` — v1 §14-17 `[팀 9/2]`에서 프론트 환경변수 하드코딩으로 확정됐다"
  - **API 쪽(2곳)**: 요구사항 v6 §11이 "값은 서버 설정에서 읽어 내려보낸다. **프론트에 하드코딩하지 않는다**", 같은 문서 비기능 **AVAIL-01**이 "체인 설정은 `GET /coin/config`로 내려보내 프론트 하드코딩을 없애고"
- **영향**: 프론트 부팅 아키텍처가 갈린다. 현재 골격(MR !37)은 **환경변수**로 구현했다 — 팀 결정 표기 `[팀 9/2]`가 붙어 있고 3:2로 우세하기 때문이다.
- **제안**: 환경변수로 확정하고 **요구사항 v6의 두 줄(§11·AVAIL-01)을 정정**한다. 되돌리려면 프론트 `shared/config`와 부팅 순서를 바꿔야 하므로 지금 정하는 편이 싸다.

### B-4. 카카오 로그인은 커스텀 인증이 필요하다

- **현상**: 요구사항 v6 §9 MVP #1이 "Web3Auth 소셜 로그인(**구글·페이스북·카카오**)", 화면 C-01이 소셜 3버튼, API v6 `API-member-01`의 `provider` enum이 `GOOGLE`/`FACEBOOK`/`KAKAO`다. 개발 환경 안내 §3.2는 "카카오는 Web3Auth 기본 제공자에 없다 — 커스텀 인증이 필요한지 PoC 1에서 확인"으로 남겨 뒀다.
- **근거 (2026-09-08 SDK 실측, `@web3auth/modal` 10.16.0)**
  - `@toruslabs/customauth`의 `utils/enums.d.ts`에 `AUTH_CONNECTION.KAKAO = "kakao"`가 **1급 상수로 존재한다.**
  - 그러나 `handlers/HandlerFactory.js`가 제공자를 두 부류로 가른다.
    - **전용 핸들러(추가 설정 없이 동작)** — `GOOGLE` · `FACEBOOK` · `TWITCH` · `DISCORD` · `TELEGRAM` · `EMAIL_PASSWORDLESS` · `SMS_PASSWORDLESS` · `PASSKEYS`
    - **`JwtHandler` 경로** — `APPLE` · `GITHUB` · `LINKEDIN` · `TWITTER` · `LINE` · `REDDIT` · `WECHAT` · **`KAKAO`** · `FARCASTER` · `CUSTOM` · `AUTHENTICATOR`
  - JwtHandler 경로는 `if (!domain) throw new Error("Invalid params for jwt login. Missing domain")` — **OIDC 발급자(domain)를 갖춘 커스텀 auth connection을 대시보드에 만들어야 한다.**
- **영향**: 카카오를 쓰려면 Kakao Developers 앱 등록 + OIDC 설정 + Web3Auth 커스텀 connection 구성이 붙는다. 구글·페이스북은 추가 작업이 없다. 0층 시연은 관객 한 명이 로그인하면 되므로 카카오가 없어도 세로축이 성립한다.
- **제안**: 0층은 **구글 하나**로 간다. 카카오는 W4(1층)로 미루거나, W3 판정 결과에 따라 컷 후보로 올린다. 정하면 요구사항 v6 §9 · 화면 C-01 · API v6 `member-01` 세 곳을 함께 고친다.

### B-5. verify-01 응답에 팀별 결제·환불 건수가 없다 — 감사 지적을 화면으로 막을 수 없다

- **현상**: 컨트랙트 감사가 검증 화면 V-01에 **팀별 `결제 건수` · `환불 건수` · `환불 금액 합`**을 나란히 표시하도록 요구한다(컨트랙트 인터페이스 v1 §4.1, "리더 확정 2026-09-07, 방안 B", 담당 강병구). 그런데 **API v6 `API-verify-01` 응답에 그 데이터가 없다.**
- **근거 — 무엇을 막는 표시인가**
  - `refund`의 카운터 차감은 **금액과 무관하다.** 첫 환불에서 그 주문의 `quantity`가 전량 빠진다(A-2 확정). 1원만 환불해도 빠진다.
  - OPERATOR 키를 가진 쪽이 특정 팀 주문에만 1원씩 환불하면 이렇게 된다. `R = 1,000,000` · `selectionRatioBp = 5000` 기준.

    | | 카운터 | 선택 풀 |
    |---|---|---|
    | 정상 | `[10, 30, 10]` | `[100,000 / 300,000 / 100,000]` |
    | 공격 | `[10, 0, 10]` | `[250,000 / 0 / 250,000]` |

    B팀 주문 30건에 1원씩, **30원으로 300,000원이 옮겨간다.**
  - **집계 확정(`aggregate`)이 이것을 못 잡는다.** 서버 대사도 "환불 이력 있는 주문 제외"로 온체인과 같은 규칙을 쓰므로, 서버 값과 온체인 카운터가 **일치한 채로** 통과한다.
  - 막는 것은 관측뿐이다. `Refunded(showId, orderRef, buyer, teamIndex, refundAmount, quantity)`가 매 건 체인에 남는다. **환불 건수는 많은데 환불 금액이 작으면 그 자체가 신호다.**
- **현재 응답에 있는 것 / 없는 것** (API v6 `API-verify-01` 200 응답 실측)
  - `onchainCounters[]` = `{teamId, teamIndex, choiceCount}` — **이미 차감된 뒤의 순 카운터**다. 공격이 성공한 뒤의 모습만 보인다
  - `recalculationInput.refundedAmount` · `escrowReconciliation.refundedTotal` — **공연 전체 합계 하나**. 팀별로 쪼개지지 않는다
  - `shares[]` — 금액만(`fixedAmount`·`choiceAmount`·`dustAmount`·`totalAmount`)
  - **팀별 결제 건수·환불 건수·환불 금액은 어디에도 없다**
- **영향**: 데이터가 없으면 화면에 그릴 수 없다. 컨트랙트 인터페이스 v1 §4.1이 "**이 표시가 없으면 이 발견의 심각도는 중간이 아니라 높음이다 — 관측이 유일한 방어인데 화면에 없으면 관측이 아니다**"라고 적었으므로, API가 바뀌지 않으면 감사 지적이 '높음'으로 남는다. V-01은 아직 착수 전이라 지금 정하면 프론트 재작업은 없다.
- **제안**: `API-verify-01` 응답의 팀별 블록에 `purchaseCount` · `refundCount` · `refundedAmount` 세 필드를 추가한다. 이 API는 명세상 이미 "인덱싱된 온체인 이벤트"를 서버에서 집계하므로(§시스템 처리 3), `Purchased`·`Refunded`를 `teamIndex`별로 세면 된다. 프론트가 RPC로 직접 `getLogs` 하는 대안은 Kairos 공개 RPC의 블록 범위 제한과 "서버 집계" 구조에 어긋나 권하지 않는다.

## C. 부록 — 이미 보고했으나 아직 반영되지 않은 것

9/7 정합성 정정(MR !19)에 들어가지 않은 항목이다. 프론트 작업에는 직접 걸리지 않지만 시연 경로에 영향이 있다.

1. **`API-refund-02`의 "선택 카운터가 −1"** — 컨트랙트 인터페이스 v1 §4.1은 **첫 환불에서 그 주문의 `quantity` 전량**을 뺀다. 취소 API는 티켓 1장 단위인데 온체인 `refund`는 `orderRef` 단위라, 2매 주문에서 1매만 취소해도 온체인 표는 2가 빠진다. API v6 문장대로 서버를 짜면 집계 확정이 `SETTLEMENT_AGGREGATE_MISMATCH`(409)로 막힌다.
2. **`Purchased` 이벤트 시그니처** — API v6 §0.4 ④와 `API-payment-03`이 `Purchased(showId, orderRef, buyer, teamIndex, amount)`로 적었는데, 9/7 확정 시그니처는 끝에 **`uint16 quantity`**가 붙는다. `Refunded` 이벤트는 API v6에 언급이 없다.
3. **정산 상태 배지** — 요구사항 v6 §5-1은 `LOCKED` 직후 **자동으로 `DISPUTE_OPEN`으로 전이**한다고 적었고, 기능 명세 v6 `F-settlement-03`은 `LOCKED`에서 끝나고 `F-settlement-04`(이의 제출)가 `DISPUTE_OPEN`으로 전이시킨다. P-08 배지와 이의제기 버튼 노출 조건이 갈린다.
4. **`Released` 이벤트는 팀 수만큼 오지 않는다** — `RevenueSplitter.release()`에 `if (amount == 0) continue;`가 있어 **`payout`이 0인 팀에는 `Released` 이벤트가 나가지 않는다**(구현 확인). 8팀에 8건일 수도, 3팀에 0건일 수도 있다. 검증 화면이 이벤트로 정산 결과를 그릴 때 팀 배열과 1:1 매칭을 가정하면 안 되고, 이벤트가 없는 팀은 **0원 수령**으로 그린다. 결정 사항이 아니라 구현 주의사항이라 부록에 둔다.

## D. 와이어프레임 이식 중 발견 (2026-09-08, A-02~A-08)

수정 와이어프레임("Main Page Wireframe Design", TICKR 수정본 A-02R~A-08R)을 이식하며 명세와 대조하다 나온 것들이다. 이식 원칙은 "수정 요청서가 명시적으로 짚은 항목은 와이어프레임을 따르고, 짚지 않은 항목은 명세를 따른다"였고, 그 원칙으로도 판정이 안 되는 것만 여기 모았다.

### D-1. QR 페이로드 포맷과 검표 요청 shape가 어느 문서에도 없다 ← D절에서 가장 큼

- **현상**: A-1에서 "QR은 서버가 발급한다"까지는 판정됐지만, **그 QR 안에 무엇을 담느냐**는 규약이 없다. 관객 화면(A-08)이 만드는 QR과 검표 화면(S-02)이 읽는 값이 같은 규약이어야 하는데 그 규약을 적은 문서가 없다.
- **근거**: API v6 `API-ticket-06`은 응답으로 `qrToken`을 준다고만 하고 인코딩 규약은 없다. 백엔드 구현은 `TicketDtos.QrTokenResponse(ticketId, qrToken, issuedAt, expiresAt, rotateAfterMs)`. `POST /entries/verify`의 요청 body 형태도 명세에 없다.
- **영향**: A-08의 QR 인코딩 라이브러리를 고를 수 없다(디코딩 쪽과 짝이 맞아야 하므로). S-02 검표 화면도 착수할 수 없다. 현재 A-08은 QR 자리와 30초 회전 카운트다운만 만들어 두고 실제 인코딩은 비워 둔 상태다.
- **제안**: `qrToken` 문자열을 그대로 QR 페이로드로 쓰고(별도 JSON 래핑 없이), `POST /entries/verify` 요청 body를 `{ qrToken }`으로 명시한다. 라이브러리는 관객·검표가 같은 것을 쓴다.

### D-2. 예매 진행 단계 표시(Stepper)가 화면설계 v6 §5에 없다

- **현상**: 수정 와이어프레임 A-03~A-06에 진행 단계 표시가 공통으로 들어와 있는데, 화면설계 v6 §5 공통 컴포넌트 목록에 이 컴포넌트가 없다.
- **영향**: 단계 라벨·개수·현재 단계 판정 기준이 명세에 없어 화면마다 달라질 수 있다. 지금은 프론트가 `BOOKING_STEPS`로 임의 정의했다.
- **제안**: §5.17~§5.21 반응형 공통 규칙 근처에 절을 신설하고, 단계 배열과 각 화면의 현재 단계를 표로 고정한다.

### D-3. A-08 관람 안내 영역이 명세에 없고, 담을 필드도 API에 없다

- **현상**: 와이어프레임 A-08R에 "관람 안내 / Notice" 영역(입장 방법·운영 시간·반입 금지·촬영 안내·현장 유의사항·기타)이 새로 들어왔다.
- **근거**: 화면설계 v6 §4 A-08의 영역 구성은 "공연 정보, 회전 QR 영역, 상태 배지, 하단 고정 Cancel"까지다. 그리고 API v6 공연 응답에 공연별 안내 문구를 담을 필드가 없다.
- **영향**: 지금은 와이어프레임의 예시 문구를 고정 텍스트로 넣었다. 실제로는 공연마다 게이트 번호·운영 시간이 다르므로 고정 문구는 시연에서 틀린 정보를 보여준다.
- **제안**: 0층은 고정 문구로 두고, 화면설계 v6 A-08에 영역만 추가한다. 공연별 안내 필드는 1층에서 ERD·API에 함께 넣는다.

### D-4. "클라이언트는 환율을 재계산하지 않는다"와 A-03 실시간 합계가 부딪힌다

- **현상**: A-03에서 수량을 바꾸면 합계가 즉시 바뀌어야 하는데, 화면설계 v6 §5.4는 클라이언트가 환산을 재계산하지 않는다고 못박고 있다.
- **정리**: ₩ 합계는 단가 × 수량이라 클라이언트 계산이 맞고, ≈USD 환산만 서버 값이어야 한다. 둘이 섞여 있어 규칙 문장만으로는 판정이 안 된다.
- **제안**: §5.4에 "원화 합계는 클라이언트가 계산한다. 재계산 금지는 환산 통화(≈USD)에만 적용한다"는 예외 문장을 넣는다.

### D-5. 공연자(P) 화면의 모바일 접근 정책이 갈린다

- **현상**: 신현경(UI/UX)이 2026-09-08 MM에서 "P-01~P-10을 Desktop Web 전용으로 유지하고, 모바일에서 공연자 URL 직접 접근 시 PC 이용 안내 화면을 띄우자"고 제안했다.
- **근거(충돌)**: ① 화면설계 v6 §1.2-1은 "공연자(P)·관리자(M) 화면은 PC 우선이되 **양쪽 모두에서 동작해야 한다**(웹 전용, 컨벤션 §1)"고 적었다. ② §5.21(v6 신설)은 통째로 P 화면의 모바일 대응 규칙이고, 적용 화면에 P-01·P-02·P-04·P-06·P-07·P-08이 이름으로 열거돼 있다. 데스크톱 전용화하면 이 절이 사실상 무효가 된다. ③ 컷 라인 ⑥은 "PC 전용 2열 레이아웃 → 전 폭 1열"로, 급할 때 **모바일 쪽으로 무너뜨리는 것**이 원래 안전판이다. 데스크톱 전용화는 반대 방향이다.
- **추가 위험**: P-06 동의 서명은 컷 불가 항목이다. 리더가 폰만 가진 상황이면 그 공연은 판매 시작을 할 수 없다.
- **판정 기준 문제**: 무엇을 "모바일"로 볼지가 정해지지 않았다. 화면설계 v6 §1.5상 분기가 768px 하나뿐이라 뷰포트 폭으로 막으면 PC에서 창을 좁힌 리더가 작업 중에 잠긴다. User-Agent 판정은 신뢰할 수 없다.
- **제안**: 전면 차단 대신 ① §5.21대로 패널 접기를 유지하고 ② 모바일에서는 상단 권유 배너("표가 많은 화면입니다. PC에서 보시면 편합니다")만 띄우되 진입은 막지 않는다 ③ 최소한 P-01(목록)과 P-06(동의 서명)은 모바일에서 살린다. 그래도 전면 차단으로 간다면 화면설계 v6 §1.2-1과 §5.21을 **먼저** 개정해야 한다.

### D-6. 이식 중 이미 정리된 것 (결정 불필요, 기록용)

1. **디자인 토큰 팔레트** — 2026-09-08 신현경 확정으로 blue 기반(`--color-primary: #3129DD`, 선택색 `--color-sel: #D9468D`, 선택 배경 `--color-sel-soft: #FCE8F2`)으로 통일. 기술 스택 v3 §3.1의 amber `@theme`는 **UI/UX 확정값이 아니라 이강륜이 9/3에 `docs/design/mockup/` 시안에서 옮겨 둔 임시값**이었음이 본인 확인으로 밝혀졌다(정본끼리의 충돌이 아니었다). 토큰 정본은 `docs/design/14_디자인_토큰_v1.md`로 이관 예정(이강륜 작성, 스택 §3.1이 그 문서를 가리키게 한다). amber 목업 32개는 시안으로 보존하며 고치지 않는다. 한글 폰트 `Noto Sans KR`을 추가했다 — DM Sans에 한글 글리프가 없어 그때까지 한글이 OS별 `system-ui` 폴백으로 렌더되고 있었다. **미정 2건**: `warning` 색값, 키보드 focus-visible 링 색값(현재는 브랜드 보라 `#3129DD`를 임시 사용).
2. **하단 탭바 4개 vs 5개** — 와이어프레임은 5탭(Orders 포함)이나 화면설계 v6 §5.18과 §1.2 원칙 7이 4탭으로 못박았고 컷 불가 항목이므로 **명세대로 4탭**(홈·내 티켓·잔액·마이)으로 구현했다. 주문 내역은 C-03 안의 진입 항목이다.
3. **C-03 My Teams 노출 조건** — 신현경이 "일반 관객에게는 숨기자"고 제안했는데, 화면설계 v6 C-03 컴포넌트 표가 이미 "P-01 이동(**리더인 팀이 있을 때만 노출**)"으로 정해 두었다. 명세 변경 없이 그대로 구현하면 되고 결과는 제안과 같다. 와이어프레임이 명세를 따르지 않은 경우다.
