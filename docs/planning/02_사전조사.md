## 0. 핵심 결론 (조사가 기획에 미치는 영향)

1. **"시장은 역대 최대, 인디 무대는 반토막"** — 2025년 공연시장 1조 7,326억 원(+18.8%, KOPIS)인데 라이브클럽 관람 비율은 27.5%→15.4%(2022→2024, 콘진원). 발표 서사의 핵심 대비 구도.
2. **최강 차별점은 ④ 스마트 컨트랙트 공동 정산** — 국내 상용 사례 없음 + 정산 분쟁 실사례("카운팅 정산" 보이콧, Door Split 구두계약 분쟁) 확보. 옴니버스 공연이 실제 표준(서울 인디 공연 주간 35개에 165팀 출연, 공연당 평균 4~5팀).
3. **QR 입장은 단독 차별점이 못 됨** — 대형·중소 플랫폼 모두 이미 제공. "수기 명단 확인으로 입장하던 초소형 공연 구간의 자동화"로 좁혀야 유효.
4. **인디 특화 예매는 이미 후발** — 인디스트릿이 2026년 자체 예매 시스템 오픈. 차별화 무게중심은 ① 대관→공연 연결과 ④ 정산 자동화로.
5. **법적 타이밍이 완벽** — 암표 전면금지 개정 공연법이 **2026-08-28 시행** (매크로 요건 삭제, 구입가 초과 판매 전면 금지, 50배 과징금). "최초가 이하 재판매 제한"은 이 법의 코드화. 티켓 NFT는 금융위 가이드라인(2024-06)상 가상자산 제외 예시에 해당하도록 설계 가능.
6. **기술 스택 확정 가능** — Polygon Amoy(주) + EC2 Besu 프라이빗(시연 백업) 이중 배포, 완전 커스터디얼 서버 서명(web3j 단독), OZ v5 ERC-721 `_update` 오버라이드 양도 제한, 커스텀 정산 Splitter(pull 방식), Hardhat 3.
7. **NFT는 인프라로 숨겨라** — 살아남은 해외 모델(GET Protocol)은 NFT를 숨기고 "정산·양도 통제 기능"을 판다. 수집품 투기 모델(콘크릿, Coachella Keys)은 전부 실패·청산. 국내 최신 성공 사례는 네이버페이 Npay 월렛 × NC 다이노스(2026-08, 프로야구 최초 NFT 티켓).

### 1.2 문제 정의(P1~P7) 근거 판정

| # | 문제 | 판정 | 근거 요약 |
|---|------|------|-----------|
| P1 | 대형 플랫폼 진입장벽 | **근거 있음 (간접)** | 3사 모두 메일 문의→심사→판매대행 계약 구조, 멜론은 사업자등록증 요구. 단 "입점 거절" 직접 보도는 없음 — 절차적 장벽만 인용할 것 |
| P2 | 과정 파편화 | **근거 있음** | 정보 애그리게이터(인디스트릿·쇼디락스)가 별도 존재한다는 것 자체가 방증. 대관은 공연장별 개별 문의. SNS+계좌이체 거래 관행은 사기 기사에서 실증 |
| P3 | 판매·입장 관리 부담 | **근거 약함 (정황)** | 수기 명단 확인 관행의 직접 통계 없음 → **자체 인터뷰·설문으로 보강 권장**, 통계 인용 금지 |
| P4 | 공동 공연 기여도 산정 | **근거 강함** | 옴니버스가 주류(평균 4~5팀). "카운팅 정산"(관객 지목 팀에만 지급, 사전고지 없음) 보이콧 사태(2023). 모객 수 기반 배분·"팀별 매표 코드 분리" 수작업 관행 |
| P5 | 수기 정산 불투명 | **근거 있음 (정황)** | 구두 합의 Door Split·정산 시점 분쟁 사례 다수, "반년 만에 공연료 7만 원" 사례. 정량 통계는 없음 — 사례 기반 서술 |
| P6 | 선물·재판매 리스크 | **근거 있음 (재프레임 필요)** | 암표·사기 통계는 풍부하나 **대형 공연 중심**. 인디 공연은 오히려 '못 팔아서' 문제 → "안전한 양도·선물"(사기 방지) 프레임으로 쓸 것. "인디 공연 암표 성행" 주장 금지 |
| P7 | 공연 기록 부재 | **근거 있음 (간접)** | 라이브클럽 다수 미등록 → 공식 기록 공백. 인디 아카이브 채널 소멸(온스테이지 2023 종료, 헬로루키 중단). 관람 기록 앱 수요 존재(콘서트일기·너겟), 인디 특화는 없음 |

**팀 공유 주의**: P3·P5는 자체 인터뷰/설문으로 보강하면 기획서 설득력이 크게 오름. 헤럴드경제 폐업 기사(브이홀 등)는 2021 코로나기 자료 — 현재형으로 인용 금지. 인터파크 수수료 구체 %는 비공개 — 수치 인용 금지.

### 2.3 인디밴드 예매·정산 관행 (실증 자료)

- 합동공연 표준: 대관료+엔지니어+포스터+잡비를 참가팀 수로 균등 분담(홍대 기준 팀당 15~30만 원), **팀별 매표 코드 분리 → 자기가 판 만큼 가져가는 정산**, 구두 합의 → 정산 시점·매표 추적 불가로 분쟁 빈발 (HAPZOO 블로그)
- 소규모 클럽: 대관료 5~30만 원 또는 Door Split 계약, 명문화 부재로 공연 후 분쟁 다수. 예매 채널로 **카카오 오픈채팅** 언급 (스튜디오놀 가이드)
- 클럽 빵: 현장 입장료 + 병뚜껑 음료 교환권, 라인업은 다음 카페 공지 — 예매 시스템 부재의 전형
- 커뮤니티 분쟁 사례: "인디밴드 공연 정산방식 논란"(루리웹), "카운팅 정산" 보이콧(클리앙 2023)

### 3.2 입장 검증·양도 제한 구현 방식

- **동적 QR이 실전 표준**: GET Protocol — 시간·소유권 변경에 따라 QR 갱신, 스크린샷은 타임아웃 무효, 재판매 시 기존 QR 무효화·재발급. 콘크릿 장범준 — 다이내믹 QR + 기기 변경 시 추가 본인인증. Google Wallet Rotating Barcode(약 1분 주기 TOTP)가 기술 레퍼런스.
- **온체인 실시간 조회를 게이트에서 하는 서비스는 없음** — NFT는 소유권 원장, 입장은 짧은 TTL 서명 QR로 처리.
- **컨트랙트 레벨 재판매 통제**: GET — 판매 전 재판매 규칙(가격 상한·승인 채널·전송 횟수)을 컨트랙트에 인코딩. 참고 표준: ERC-721C(로열티 강제), ERC-7634(전송 횟수 상한).
- **한계 (장범준 사례의 교훈)**: 컨트랙트는 "컨트랙트를 경유하는 거래"만 강제 가능 — 계정/기기 통째 양도라는 오프체인 우회는 본인인증·1인 구매 제한·동적 QR로 보완해야 함. 기획서에 '한계와 보완'으로 명시하면 설득력 상승.

### 3.3 적용할 교훈

1. **지갑은 무조건 추상화** — 규모를 낸 곳(GET, SI, Npay) 전부 "유저는 블록체인 몰라도 됨". 시드문구 요구 = 관객 이탈.
2. **'수집품 NFT'와 '기능 NFT'를 분리** — 투기 모델은 전멸(콘크릿·Coachella), 생존 모델은 NFT를 인프라로 숨긴 기능·정산 판매(GET). 포지셔닝: "NFT라서 좋다" ❌ → "정산 자동화·양도 통제가 돼서 좋다" ✅
3. **외부 인프라 종속 금지** — 특정 거래소·외부 커스터디 종속 회피, 메타데이터 자체 관리.
4. **발표 최신 레퍼런스**: 네이버×NC(2026-08) — "국내 대기업이 지금 하고 있는 방향"으로 인용.
5. 체인 선택: 실서비스들은 저가스 L2/앱체인(Polygon 등) — 학생 프로젝트의 Polygon + ERC-721 + 커스텀 transfer 제한과 정렬됨.

## 5. 블록체인 기술 선정 (확정 권고안)

### 5.1 항목별 결론

| 항목 | 결론 | 핵심 근거 |
|------|------|-----------|
| 네트워크 | **개발: 로컬(Hardhat node/Anvil) → 시연: Polygon Amoy(주) + EC2 Besu 프라이빗 단일노드(백업) 이중 배포** | 커스터디얼이라 가스는 서버 지갑 몇 개만 부담 → faucet 제약이 사용자 수와 무관. Amoy 2초 블록 + 퍼블릭 익스플로러가 발표 어필. 시연 당일 퍼블릭넷 장애는 통제 불가 → 프라이빗 백업 필수 |
| 가스 대납 | **완전 커스터디얼 서버 서명** — 컨트랙트에 operator 권한, 서버 운영지갑이 모든 tx 전송 (사용자 지갑은 소유권 기록용 주소) | ERC-2771/4337은 "사용자 보유 키" 전제라 커스터디얼에선 무의미한 복잡도. 4337·EIP-7702는 "왜 안 썼나" 방어용 지식으로만 |
| 키 관리 | **envelope encryption** — 개인키를 AES-256-GCM(사용자별 DEK)으로 암호화, DEK는 KEK(KMS 또는 외부 주입 마스터키)로 재암호화해 DB 저장. 복호화는 서명 순간만, 감사 로그 | DB 평문·하드코딩 마스터키는 즉시 감점. 프로덕션 확장안으로 "KMS secp256k1 서명/HSM" 언급 |
| 토큰 표준 | **ERC-721 (OZ v5)** — tokenId별 상태 enum(ISSUED/USED/CANCELLED) | 티켓 1장 = 고유 토큰 + 개별 상태·이력 관리에 정합 |
| 양도 제한·가격 상한 | OZ v5는 `_beforeTokenTransfer` 삭제됨 → **`_update(to, tokenId, auth)` 오버라이드**로 민팅·소각·승인된 operator 외 전송 revert. 재판매는 컨트랙트 내 `resale()` 함수로만 허용 + `price <= facePrice` 강제 | v4 블로그 코드 복붙 시 컴파일 실패 주의. 실업계(GET, WICKET)와 동일한 "승인 채널 강제 + 가격 상한" 패턴 |
| 정산 컨트랙트 | **커스텀 Splitter** — OZ PaymentSplitter는 **v5에서 삭제**됨(4.x 소스 참조·개작). 가중치는 `startSale()` 시 one-way `locked=true`로 잠금, 관객 선택 카운트 온체인 누적, **pull 방식 `release()`** | push 루프는 수신자 revert 하나로 전체 정산 DoS. "판매 시작 후 변경 불가"를 코드로 증명 |
| 테스트 토큰 | 단순 ERC-20, `mint` 권한 = 서버 운영지갑 | |
| Spring 연동 | **web3j 단독** — LF Decentralized Trust 이관 후 활발 (v5.0.2, 2026-03 릴리스). 키 생성·서명·컨트랙트 래퍼·이벤트 구독 전부 커버 | "web3j 유지보수 중단"은 구정보. Node 사이드카는 4337 도입 시에만 재검토 |
| 개발 도구 | **Hardhat 3** (2025-08 릴리스) — 자료량·JS 연계 우위. Foundry는 테스트 품질 어필 시 혼용 | v2 튜토리얼과 설정 형식이 다름 — 문서 버전 확인 습관화 |

### 5.2 확정 아키텍처

```
[React 모바일웹] ──REST──> [Spring Boot]
                              ├─ Auth/회원 ─ 가입 시 EOA 키쌍 생성
                              ├─ KeyVault 서비스 ─ AES-GCM DEK + KEK(KMS/외부주입) 암복호
                              ├─ Web3j 서비스 ─ 운영지갑 서명·nonce 큐 직렬화·이벤트 구독
                              └─ DB (회원, encryptedKey, encryptedDek, iv, address, tx이력)
                                    │ JSON-RPC
                    ┌───────────────┴────────────────┐
            [Polygon Amoy (주)]            [EC2 Besu 프라이빗 (시연 백업)]
             ├─ TicketNFT     (ERC-721, _update 양도 제한, resale 가격 상한, 상태 enum)
             ├─ TestToken     (ERC-20, mint = 운영지갑)
             └─ RevenueSplitter (startSale 잠금, 관객선택 누적, pull release)
```

### 5.3 기술 리스크 체크리스트

- [ ] **Faucet 사전 확보**: Amoy faucet 일일 총량 제한 — 시연 최소 1주 전 팀원 계정 여러 개로 가스 확보. Google Cloud faucet은 메인넷 잔고 요구 없음
- [ ] **OZ v5 함정**: `_beforeTokenTransfer`·`PaymentSplitter` 제거됨 — v4 예제 코드 이식 금지
- [ ] **nonce 경합**: 운영지갑 하나로 동시 tx 시 충돌 — 서버 tx 큐 직렬화 또는 nonce 매니저 직접 구현 필요
- [ ] **push 정산 금지**: pull(`release()`) 모델 채택
- [ ] **시연 리허설**: 프라이빗 백업 노드로 전체 시나리오 1회 이상
- [ ] **Hardhat 3 문서 버전** 확인 습관화

## 7. 블록체인 필요성·스마트컨트랙트 적용방안 검증 (적대적 검증)

> 방법: 전체 조사 맥락을 물려받은 검증 에이전트가 악마의 변호인 관점에서 "완전 커스터디얼인데 블록체인이 뭘 보장하나"를 공격. **최종 권고: 유지 — 단, 주장 범위를 축소하고 신뢰 고리 3개를 보강할 것.**

### 7.1 적용 영역별 판정

| 적용 영역 | 판정 | 핵심 이유 |
|-----------|------|-----------|
| 정산 규칙 사전 고정 + 분배 산출 (Splitter) | ✅ **정당화 가능** | 시장조사가 실증한 분쟁 유형(사전고지 없는 "카운팅 정산", 구두합의 Door Split)이 정확히 "사후 규칙 변조·불투명 계산" 문제. 퍼블릭 체인 선(先)커밋은 서버가 전권을 쥐어도 **"기록의 소급 수정 불가"**만은 실제로 보장. 수식을 컨트랙트 내부에서 계산하면 제3자 재현 검증 가능 |
| NFT 티켓 소유권·이전 이력 | ⚠️ 약함 → **재프레임 시 상향** | 이중 판매 방지는 DB unique constraint로도 달성됨. **"정산의 근거 원장(팀별 유효 티켓 수)"으로 재프레임**하면 정산 스토리에 편입되어 정당화 |
| 관객 선택 집계 (오라클 입력) | ⚠️ 약함 → **개선안 1 적용 시 정당화** | 서버 집계 → 해시 커밋은 서버가 애초에 거짓 집계를 커밋하면 무력 (오라클 문제). 선택을 민팅 이벤트로 체인에 직접 기록하면 비판 소멸 |
| 재판매 가격 상한 강제 | ⚠️ 약함 | 폐쇄 마켓에선 서버 검증과 등가. 실질 가치는 "운영자가 몰래 상한을 풀 수 없음의 증명"뿐 — 보조 논거로만 |
| QR 입장·위조 방지 | ❌ **연출에 가까움** | 게이트 검증은 100% 서버 서명 QR (실서비스 어디도 게이트에서 온체인 조회 안 함). **블록체인 성과로 주장 금지 — 심사위원 한 방에 무너지는 지점** |
| 테스트 토큰 분배 시연 | ❌ 연출 → **프레임 전환 필요** | 실제 돈은 금융망이 움직이므로 토큰은 거울. **"온체인 정산액 = 이체 지시서, 금융망 = 집행, 대사로 불일치 검출"**로 명시하면 설계 포인트로 전환 |

### 7.2 "왜 블록체인인가" 정직한 방어 논리 (발표용)

**선(先)인정**: "기능만 보면 전부 DB로 됩니다. 블록체인은 기능 추가가 아니라 **신뢰 구조 변경**입니다."

1. **문제는 다자간 불신, DB는 단독 소유 장부** — 이해관계자는 참여팀들·기획팀·플랫폼 3자이고 분쟁 실사례가 있다. 플랫폼 DB는 "저희 화면을 믿으세요"지만, 퍼블릭 테스트넷 커밋은 참여팀에게 **플랫폼 화면을 거치지 않는 독립 검증 경로**(컨트랙트 주소 + 익스플로러)를 준다.
2. **보장하는 것**: ① 판매 시작 전 잠긴 정산 규칙의 사후 변조 불가 ② 기록의 소급 수정 불가 ③ 분배 계산의 결정론적 재현 가능 ④ 플랫폼이 사라져도 기록은 남음.
3. **보장하지 않는 것도 말한다**: 입력 데이터의 진실성은 오라클 문제 — "위조 원천 차단"이 아니라 **"위조하면 반드시 발각되는 구조"**로 대응.
4. **업계 정합성**: GET Protocol도 완전 커스터디얼 + 체인은 감사 가능한 원장. trustless를 주장하지 않는 것이 정직한 정답.

### 7.3 신뢰 보강 3종 (필수 — 없으면 "그냥 DB" 공격 방어 불가)

| # | 개선안 | 효과 | 난이도 |
|---|--------|------|:------:|
| 1 | **관객 선택을 민팅 트랜잭션 이벤트로 기록** — `mint()` 시 `ChoiceRecorded(ticketId, teamBitmap)` + 컨트랙트 내 카운터. 집계가 서버 입력이 아니라 체인 이벤트의 합이 됨 | 오라클 비판의 핵심 제거. 취소 시 카운터 감소도 자연스러움 | 하~중 |
| 2 | **팀별 동의 트랜잭션** — 각 팀 지갑 주소에서 `agreeToRules(showId, rulesHash)` 호출 후에만 `startSale()` 가능 | 아킬레스건(전 팀 동의 증명) 완화 + 강력한 시연 장면 | 중 |
| 3 | **공개 정산 검증 페이지** — 컨트랙트 주소·잠긴 규칙·온체인 집계·팀별 산출액·release tx 링크 + 브라우저 재계산 위젯 | 심사위원이 직접 검증하는 데모 동선. 구현 대비 효과 최대 | 하 |

보조: ④ 분배 수식 전부 Solidity 내 계산 (설계 원칙) ⑤ 온체인-금융망 대사 리포트(불일치 0건 화면) ⑥ MINTER/SETTLER 롤 분리 + Pausable.

### 7.4 컨트랙트 결함과 해결책 (설계 반영 필수)

| 결함 | 해결책 |
|------|--------|
| 정산 확정 후 환불 (release 후 회수 불가) | **시점 규칙**: 취소·환불 마감 → 집계 확정 → 정산 잠금 → 이의제기 기간(48h) → release 활성화. 마감 후 환불은 오프체인 준비금 정책으로 분리 |
| 판매 중 공연 취소 | show 레벨 상태 플래그 (전 티켓 루프 금지 — 가스). 티켓 유효성 = 티켓 상태 AND 공연 상태. finalize 영구 차단 |
| 반올림·잔액(dust) | 티켓당 가중치 10000bp 고정 배분, 최종 잔액은 마지막 팀 또는 공통 몫 귀속 — 컨트랙트에 명문화 |
| 취소 티켓의 선택 카운트 | `cancelTicket()`이 저장된 팀 비트맵으로 카운터 감소. **취소 마감 ≤ 정산 잠금** 순서를 컨트랙트가 강제 |
| 온체인 분배액 vs 금융망 이체 불일치 | **테스트 토큰 decimals=0, 1토큰=1원** (단위 불일치 원천 제거). 멱등키 + 팀별 이체 상태 머신 + 대사 배치 |
| 재판매 상한 기준가 | 티켓 타입 정가가 아니라 **해당 티켓의 실제 최초 구매가** 저장·강제 (얼리버드 구매자가 정가 재판매하면 개정 공연법 위반 상황 재현됨). 선물받은 티켓도 원 구매가 승계 |
| 재판매 대금 정산 편입 | 정책 공백 → §10 안건 추가 (권고: 재판매 대금은 판매자 개인 귀속, 공동 정산은 1차 판매만) |
| MD(굿즈) 수익 온체인 편입 | 정책 공백 → 티켓과 동일 시점 규칙에 태우거나 1차 버전은 오프체인 정산으로 분리 명시 |
| 테스트 토큰 무한 민팅 의심 | 민팅을 판매 발생분과 1:1로 제한 + totalSupply vs 판매 총액 대조를 검증 페이지에 노출 |
