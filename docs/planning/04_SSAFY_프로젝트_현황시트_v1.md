## 1. 서비스 설명 / 주요기능

> 여러 밴드가 함께 여는 소규모 공연의 **티켓 예매·양도·QR 입장부터 수익 정산까지** 하나로 잇는 티켓팅·공동 정산 플랫폼. 관객이 예매할 때 "누구를 보러 왔는지"를 선택하고(온체인 기록), 참여팀이 판매 시작 전에 합의·서명해 잠근 정산 규칙에 따라 **스마트 컨트랙트가 원화 스테이블코인(KRWS)으로 팀별 수익을 자동 분배**한다. 금융망 API가 입출금을 맡고, 예치금 1:1 준비금 증명을 공개한다. 타겟은 티켓 100매 이내·3~4팀 공동 공연의 취미·인디 밴드.
>
> **주요 기능**
> 1. 공연자 팀 지갑 자동 생성(커스터디얼)
> 2. 공동 공연 생성 → 정산 규칙 합의 → 팀별 동의 트랜잭션 → 컨트랙트 잠금(판매 후 변경 불가)
> 3. 티켓 예매 + 관람 목적 팀 선택(온체인 `recordChoice` 기록) → 금융망 결제 → KRWS 민팅·에스크로 예치
> 4. 서명된 동적 QR 티켓 발급 · 관계자용 QR 검표(재사용 차단)
> 5. 취소·환불(KRWS 소각 + 금융망 환불 + 선택 카운터 롤백)
> 6. 카카오톡 링크 양도(수락 즉시 소유권 이전 + 기존 QR 폐기·재발급)
> 7. 집계 → 컨트랙트 KRWS 분배(`release`) → 팀 환급(소각 → 금융망 원화 이체)
> 8. 공개 정산 검증 페이지(컨트랙트 주소·잠긴 규칙·온체인 집계·팀별 산출액·tx 링크·브라우저 재계산·준비금 증명)

출처: README §1~3, 기획 §1·§9.

## 2. 프로젝트의 특장점 (기능 관점)

> 1. **관객 선택 기반 공동 공연 수익 자동 정산** — 예매 시 선택한 "관람 목적 팀"이 정산 가중치가 된다. 국내 상용 사례가 확인되지 않은 유일 차별점(사전조사 §2.2).
> 2. **판매 전 규칙 잠금** — 참여팀 전원이 각자 지갑으로 동의한 뒤에만 판매가 시작되고, 이후에는 플랫폼도 규칙을 바꿀 수 없다. "사후 규칙 변경·불투명 계산" 분쟁을 원천 차단.
> 3. **누구나 검증하는 공개 정산 페이지** — 잠긴 규칙 × 온체인 집계를 브라우저에서 재계산해 서버 표시값과 대조. 심사위원이 직접 체험하는 동선.
> 4. **안전한 티켓 선물·양도** — 링크 수락 즉시 소유권 이전, 기존 QR은 폐기·재발급.
> 5. **관객에게 블록체인 노출 0** — 지갑·가스·주소 개념 없이 일반 예매와 같은 UX. 지갑은 공연자 팀 전용.
> 6. **수기 명단 입장의 자동화** — 구글폼·계좌이체·명단 대조로 운영되던 초소형 공연 구간을 서명 QR 검표로 대체.

출처: 기획 §1·§4·§8.3, README §1. QR 입장은 단독 차별점으로 쓰지 않는다(사전조사 §0-3).

## 3. 프로젝트의 차별점 / 독창성 (기술 관점)

> 1. **온체인 분배가 곧 실제 정산** — 원화 1:1 스테이블코인 KRWS(ERC-20, `decimals=0`, 1 KRWS = 1원)를 테스트넷에 자체 발행. 금융망 입금 확인 시 mint → 공연별 에스크로, 환불·환급 시 burn. 온체인 분배액과 금융망 이체액의 단위 불일치를 원천 제거.
> 2. **신뢰 보강 3종** — ① 관객 선택을 `recordChoice` 이벤트로 기록해 집계가 서버 입력값이 아닌 체인 이벤트의 합, ② 각 팀 지갑의 `agreeToRules(showId, rulesHash)` 동의 tx가 익스플로러에 남음, ③ 공개 검증 페이지. "그냥 DB로 되잖아요"에 대한 실체.
> 3. **정산 시점 규칙을 컨트랙트가 강제** — 취소 마감 → 집계 확정 → 정산 잠금 → 이의제기 48h → `release`. pull 방식 분배로 push 루프 DoS 회피, dust 귀속 규칙 명문화.
> 4. **준비금 증명** — 금융망 에스크로 계좌 잔액 ≥ KRWS 유통량을 검증 페이지에 상시 공개. 입법 추진 중인 디지털자산기본법의 핵심 요건(준비자산 1:1·상환청구권·공시)을 설계에 선반영.
> 5. **완전 커스터디얼 지갑의 키 관리** — 팀 지갑 개인키를 envelope encryption(AES-256-GCM DEK + KEK 외부 주입)으로 보관, 복호화는 서명 순간만 + 감사 로그. 운영지갑 권한을 minter/burner와 operator로 분리, nonce 직렬 큐로 동시 tx 충돌 방지.
> 6. **시연 가용성 이중화** — Polygon Amoy(주, 퍼블릭 익스플로러) + EC2 Hyperledger Besu 프라이빗(백업) 이중 배포.
> 7. **서명 동적 QR** — 30~60초 만료 토큰 + Redis `SETNX` 원타임 처리. (QR 보안은 서버 서명의 몫이며 블록체인 성과로 주장하지 않는다.)

출처: 기획 §6.1·§8, 사전조사 §5·§7, 정산 지갑 두 갈래.

## 4. 프로젝트에 활용된 AI 기술 (활용팀 작성 필수)

**현재 상태: 미결.** 8/26 컨설턴트·코치 권고("API 호출 수준의 AI는 특장점이 아니다")에 따라 AI 기능은 기획에서 전부 제외했고, 도입 여부·범위는 팀 협의(협의 안건 §12)로 정한다. 사전조사 §8이 "정산 투명성 서사와 직결"로 판정한 유일 후보는 **A3 정산 리포트 자연어 설명**이다. 결정에 따라 아래 둘 중 하나를 붙인다.

**기입안 A — 미도입 시**

> 해당 없음 (AI 미활용). 블록체인 정산·신뢰 구조에 집중.

**기입안 B — A3 도입 시**

> **정산 결과 자연어 리포트** — 공연 정산이 완료되면 온체인 선택 집계·잠긴 규칙·팀별 분배액·release tx를 구조화(JSON)해 LLM API에 전달하고, 공연자용 한국어 정산 설명서(왜 이 금액인지, 어느 항목에서 얼마가 왔는지, 검증 방법)를 생성한다. 수치는 컨트랙트 산출값을 그대로 인용하고 모델은 설명만 담당한다(수치 생성 금지). 생성 실패 시 표 형태 기본 리포트로 폴백.

## 9. 주요 기술 스택

> **블록체인**: Solidity · OpenZeppelin v5 · Hardhat 3 · Polygon Amoy 테스트넷(주) + Hyperledger Besu 프라이빗(EC2, 시연 백업) · 컨트랙트 2종 RevenueSplitter(동의·잠금·선택 카운터·pull release) + KRWS 스테이블코인(ERC-20 mint/burn, decimals=0) · TicketNFT(ERC-721)는 P2 확장
> **체인 연동**: web3j 5.0.2 — 운영지갑·팀 지갑 서버 커스터디, nonce 큐 직렬화, 이벤트 인덱싱
> **키 관리**: envelope encryption (AES-256-GCM DEK + KEK)
> **결제**: SSAFY 교육용 금융망 API (입출금 on/off-ramp)
> **프론트**: React · TypeScript · Vite · PWA · Kakao JavaScript SDK(공유)
> **백엔드**: Spring Boot 3 · Java 17 · JPA · MySQL · Redis · Flyway
> **인프라**: Docker · Jenkins/GitLab CI · AWS EC2 · Nginx
> **부가(P1)**: Google Wallet API (RotatingBarcode)

출처: README §4, 기획 §12.

## 15. 배포자동화

> GitLab CI(또는 Jenkins) → Docker 이미지 빌드·테스트 → AWS EC2 배포, Nginx 리버스 프록시 + HTTPS. `develop` 머지 시 dev 환경 자동 배포, `master`는 발표 환경. 스마트 컨트랙트는 Hardhat 스크립트로 Amoy·Besu에 배포하고 주소·ABI는 환경변수·버전 관리. MR 1인 승인 필수, 빌드·테스트 실패 시 머지 차단. 시크릿(`.env`, `application-*.yml`)은 저장소 미포함.

출처: README §4·§6, 컨벤션 §3.2, 비기능 계획 MAINT-03/06.
