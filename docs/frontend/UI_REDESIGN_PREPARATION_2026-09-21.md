# BULLEOYO 전 페이지 UI 리디자인 준비안

작성일: 2026-09-21
상태: 구현 전 준비 문서. 이 문서 작성으로 제품 코드·API·권한·거래 동작을 변경하지 않았다.

## 1. 목표와 결정된 방향

공연을 찾고, 예매하고, 티켓을 확인하고, 공연을 운영하는 데 필요한 정보가 먼저 보이도록 전 페이지의 정보 구조와 시각적 위계를 정리한다. 현재 홈의 추상적인 소개 문구를 더 큰 슬로건으로 교체하는 작업이 아니다. 불필요한 소개 블록을 걷어내고 실제 공연명·일시·장소·가격·상태·다음 행동에 공간을 배분한다.

원래 BULLEOYO/‘요’ 로고는 유지한다. 현재 다크 테마를 출발점으로 삼되, 모든 영역을 카드·테두리·배지로 감싸는 반복은 줄인다. 여기서 편집적 구성은 콘텐츠의 순서와 비중을 뜻한다. 잡지 표지, 거대한 영문, 호수·장식 라벨 같은 스타일 소품을 추가한다는 뜻이 아니다.

앞서 제시한 A안(타이포그래피 중심)과 B안(포스터 중심) 프리뷰는 사용자가 선호하지 않은 안이다. 두 안을 승인된 디자인으로 취급하거나 이전 스크린샷을 구현 기준으로 재사용하지 않는다. 이번 기준은 현재 서비스 화면, 원래 로고, 실제 데이터와 사용자의 비평이다.

### 유지할 계약

- 실제 API 필드, 인증·권한 판정, 결제·잔액·티켓·QR·정산 상태 전이를 유지한다.
- 인쇄는 기존 사용자 행동과 준비 완료 시점을 유지한다. 마운트 시 자동 인쇄나 자동 거래를 추가하지 않는다.
- Web3Auth SDK 준비 상태와 실제 지갑 생성 상태를 구분한다. 로딩 표현을 단순화하며 두 상태를 합치지 않는다.
- 메뉴의 시각적 정리는 새 클라이언트 권한 판정의 근거가 아니다. Studio 진입과 역할별 작업은 기존 라우트·권한 계약을 따른다.
- 장르·인기·좋아요·지역 순위 등 지원이 확인되지 않은 필터와 지표를 새로 만들지 않는다. 현재 확인한 검색어·날짜·상태와 실제 응답 필드 안에서 구성한다.
- 테스트넷·금액 단위·거래 결과·검증 판정 등 사실 전달에 필요한 문구는 감성 카피 정리 대상과 구분한다.

## 2. 근거와 확인 범위

| 구분 | 이번 준비안의 근거 | 해석 범위와 한계 |
| --- | --- | --- |
| 저장소 | 구현 저장소 `S15P21B204`의 `.worktrees/performance-media`, 기준 커밋 `5ce09c1`, 제품 기준 `b45428f` | 현재 준비안의 코드 기준이다. 문서용 `S15P11B204`와 혼동하지 않는다. |
| 원격 정보 | 로컬에 캐시된 `origin/develop` | 이번 확인에서 새 fetch를 하지 않았다. 최신 원격과 같다고 주장하지 않는다. |
| 별도 체크아웃 | 주 체크아웃 `feat/fe/errors`, `be821bd`, 미커밋 변경 존재 | 별도 작업 상태다. 이 문서의 근거 브랜치와 섞거나 변경을 되돌리지 않는다. |
| 사용자 화면 | 사용자가 제공한 홈 화면과 비평 | 홈의 소개 문구·정보 위계 문제를 판단하는 직접 근거다. |
| 추가 사용자 화면 5개 | 언어 선택 배경 이동, 둥근 폼의 안쪽 여백, 토스트 정렬, 포스터 카드 본문 여백, 헤더·푸터 구분선 | 공통 CSS QA 요구로 반영했다. 아래 코드 근거와 수정 제안을 분리하며, 이미 수정했다고 주장하지 않는다. |
| 실제 브라우저 | 현재 배포 홈 데스크톱 약 1265px, 모바일 요청 뷰포트 390×844; 모바일 `/performances`, `/performances/27`; `/login` DOM | 비로그인 게스트로 확인했다. 로그인 화면은 DOM 확인 범위이며 시각 검증을 완료한 것으로 취급하지 않는다. |
| 미확인 동작 | 인증 후 계정·구매·잔액·QR·Studio·운영 화면 | 코드 검토와 아래 구현 제안을 구분한다. 실제 로그인·결제·송금·QR 처리·정산 거래는 실행하지 않았다. |
| 제안 | 아래 카피·구성·공통 컴포넌트·단계별 구현안 | 현재 제품 상태가 아니라 다음 구현을 위한 기준이다. API 추가 승인을 뜻하지 않는다. |

근거 표기: **코드**는 저장소에서 확인한 구조·문구, **브라우저**는 위 범위에서 실제 확인한 화면·DOM, **제안**은 앞으로 구현할 내용이다. 코드에 있는 분기만으로 실제 서버 응답이나 로그인 후 화면 검증까지 완료됐다고 쓰지 않는다.

### 외부 참고의 사용 범위

- [Impeccable: Slop](https://impeccable.style/slop/): 반복되는 상투적 히어로, 추상 카피, 일률적 장식이 실제 콘텐츠를 가리는지 점검하는 참고 자료다. 이 서비스에서는 소개 문구 제거, 정보 우선순위, 불필요한 박스 축소에 한정해 적용한다. 브랜드와 상태 의미까지 일괄 제거하는 규칙으로 사용하지 않는다. [improve-design](https://impeccable.style/docs/improve-design/), [critique](https://impeccable.style/docs/critique/), [layout](https://impeccable.style/docs/layout/), [typeset](https://impeccable.style/docs/typeset/), [clarify](https://impeccable.style/docs/clarify/), [distill](https://impeccable.style/docs/distill/), [polish](https://impeccable.style/docs/polish/) 상세도 읽었지만 명령을 실행하거나 설치하지 않았다.
- [Anthropic frontend-design 참고 문서](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md): 서비스 맥락에 맞는 구체적인 시각적 결정을 하라는 관점을 참고한다. 외부 문서를 설치된 스킬로 실행한 것이 아니며, 과장된 타이포그래피나 새 브랜드 스타일의 도입 근거로 삼지 않는다.
- [Vercel 스킬 원문](https://raw.githubusercontent.com/vercel-labs/agent-skills/main/skills/web-design-guidelines/SKILL.md)과 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md): 키보드 조작, 포커스, 폼 피드백, 로딩, 화면 크기 변화에서의 사용성을 검토하는 기준으로 참고한다. 현재 코드가 모든 지침을 충족한다고 판정한 것은 아니다. 언어 감지·기본 locale·제출 버튼 활성화 지침을 일괄 적용해 기존 언어·동의·제출 정책을 바꾸지 않는다.
- [Resident Advisor 공연 목록](https://ra.co/events): Seoul 목록을 실제 브라우저 스크린샷으로 확인했다. 검정 헤더, 흰색 도시 선택 영역, 필터와 목록의 경계, 날짜별 묶음이 명확하다. 날짜·종류·장르 등 탐색 정보가 보이지만 우리 서비스는 현재 지원되는 검색어·날짜·상태만 사용한다.
- [DICE Berlin 공연 목록](https://dice.fm/browse/berlin-5e426dbb749e68e3e923d1e4): 초기 조회 실패 후 실제 브라우저에서 카드를 확인했다. 포스터 아래 제목·노란 날짜·장소·가격이 밀집되어 있다. 이미지와 텍스트가 왼쪽에 직접 정렬되는 구성 자체는 의도적인 디자인일 수 있다. 우리 카드의 안쪽 여백은 사용자 요구와 실제 카드 외곽 구조에 맞춰 정리하며, 다른 서비스의 여백 없는 카드를 보편적 오류로 분류하지 않는다. DICE 마케팅 홈의 거대한 문구를 가져오지 않는다.
- [DICE 공연 상세](https://dice.fm/event/7d5a9p-lambrini-girls-14th-may-astra-kulturhaus-berlin-tickets): 모바일 스크린샷과 DOM에서 실제 공연 제목·일시·장소·금액, 하단 고정 BUY NOW, 아래쪽 소개·환불 조건을 확인했다. 핵심 판단 정보와 행동의 근접성만 참고한다. 거래는 실행하지 않았으며 외부 환불 정책을 복제하지 않는다.
- [Mobbin segmented control 공개 탐색](https://mobbin.com/explore/mobile/ui-elements/segmented-control)과 [Ubank 화면](https://mobbin.com/explore/screens/8859286f-85f4-478f-8c0a-c08b2a7812a7): 실제 공개 스크린샷에서 inset pill 선택, Categories/Merchants 전환, 중첩 그룹과 금액 오른쪽 정렬을 확인했다. 정지 이미지이므로 전환 애니메이션을 검증한 근거는 아니다. 저장·복사·전체 flow는 가입이 필요하며 실행하지 않았다.
- [Mobbin toast 공개 탐색](https://mobbin.com/explore/mobile/ui-elements/toast): Turo Car Detail Saved의 VIEW 행동, Fanatics Live Watchlist Confirmation의 아이콘·한 줄 메시지·닫기, KakaoBank Transaction Confirmation의 두 줄 금액 안내, Turo Scanning Error Message를 공개 스크린샷으로 확인했다. 한 줄·두 줄·action을 각각 검증하는 기준에 연결한다. 전체 flow, 모션, 실시간 동작을 확인한 것은 아니다.
- [Nielsen Norman Group: Visual Hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/) 본문: 색·크기·묶음으로 위계를 만들고 실제 콘텐츠에서 확인하는 기준을 참고한다. 큰 제목만으로 위계가 해결된다고 해석하지 않는다.
- [Refactoring UI](https://refactoringui.com/): 공개 홈페이지와 목차만 확인했다. 책 전문과 유료 영상은 열람하지 않았으며 구체적인 내부 기법을 이번 조사 결과로 인용하지 않는다.
- [Toss 제품 브랜딩 팀](https://toss.tech/article/product-branding-team) 본문: 제품 안에서 경험하는 브랜드와 실제 사용자 피드백에 대한 내용을 확인했다. 이를 원래 로고·티켓 정체성 보존과 마케팅 화면 복제 자제로 연결한 것은 이 프로젝트에 대한 해석이다.
- [Frontend Fundamentals 코드 품질](https://frontend-fundamentals.com/code-quality/code/) 본문: 가독성·예측 가능성·응집도·결합도 네 기준을 확인했다. 스타일의 책임 위치를 명확히 하고 서로 다른 상태 계약을 무리하게 공통 컴포넌트로 합치지 않는 방향에 참고한다.

참고 문서는 읽기 자료다. `npx`, 패키지 설치, 외부 스킬 설치·실행은 이 준비 작업에 포함하지 않는다.

설치된 `emil-design-eng` 스킬의 정렬·상태 피드백·모션 판단 기준은 공통 UI 정리에 사용했다. 선택 배경의 이동처럼 상태 변화를 이해시키는 모션과 목적 없는 장식을 구분한다. 이는 위 외부 문서를 스킬로 설치·실행했다는 뜻이 아니다.

## 3. 보존할 강점

| 요소 | 보존 이유 | 정리 방식 |
| --- | --- | --- |
| 원래 BULLEOYO/‘요’ 로고 | 사용자가 유지하기를 원하는 식별 요소 | 홈 링크로 연결하고 공간에 맞는 크기만 조정한다. |
| 다크 기반과 실제 공연 이미지 | 기존 서비스의 인상과 공연 콘텐츠를 연결한다. | 실제 포스터를 정보와 함께 사용하고 대형 이미지의 반복을 줄인다. |
| 공연 상태 구분 | 사용자가 예매 가능 여부와 진행 상태를 판단하는 핵심 정보 | 상태별 의미와 노출 조건을 유지하며 배지의 시각적 강약을 정리한다. |
| 내 티켓·잔액·계정으로의 직접 접근 | 구매 후 다시 방문하는 사용자의 주요 경로 | 데스크톱과 모바일에서 각 기기의 탐색 구조를 보존한다. |
| 결제·지갑·QR·검증의 상태 안내 | 다음 행동과 거래 결과를 오해하지 않게 한다. | 실제 상태를 중심으로 짧게 쓰고 실패 시 재시도·수정 위치를 명확히 한다. |

## 7. 핵심 화면의 구체적인 정보 구조

### 공통 탐색

- 데스크톱: 원래 로고(홈) → `공연` / `내 티켓` / `잔액`의 기존 목적지 → 오른쪽 계정 진입 한 곳. Studio는 기존 계정·역할에 맞는 탐색 경로에 둔다.
- 모바일: 계정/My로 바로 가는 경로와 기존 하단 탭을 유지한다. 데스크톱 메뉴와 겹친다는 이유로 모바일의 직접 접근을 제거하지 않는다.

스타일 책임은 기본 컴포넌트 → 명시적인 variant → 페이지 배치 순서로 나눈다. 페이지의 descendant selector로 공통 컴포넌트 내부 padding을 다시 덮어쓰지 않는다. 광학적 정렬은 line-height·아이콘 박스·padding을 먼저 맞추고, 요소마다 `translateY`를 하드코딩하는 방식으로 해결하지 않는다.

## 11. 구현 시 필수 검증

### 상태·거래 회귀 방지

- [ ] 동일 생성·수정·결제 제출이 중복 실행되지 않는다. 이중 클릭·빠른 연속 입력·느린 응답에서도 이를 확인한다. 인증 refresh·상태 조회·폴링·명세상 후속 요청은 허용하며 요청 상한과 종료 조건을 검증한다.
- [ ] 마운트·화면 재진입·단순 상태 변경으로 생성·수정·결제·환불·발행·정산 요청이 자동 실행되지 않는다.
- [ ] 인증·역할·예매 가능 여부·결제·잔액·티켓·QR의 가드와 상태 전이를 기존 테스트·명세와 대조한다.
- [ ] 진행 중 버튼 잠금과 재시도 가능 시점을 실제 요청 상태에 맞춘다. 네트워크 실패를 거래 실패로 단정하지 않는다.
- [ ] 선택한 공연·티켓·팀·수량·금액 등 화면별 선택과 폼 입력이 실패·재렌더링·재시도에서 보존된다.
- [ ] SDK 준비 중, 실제 지갑 생성 중, 생성 실패와 재시도를 구분한다.
- [ ] 금액 단위·서버 계산값·잔액 부족·환불 가능 여부·정산 판정·미확인 상태의 의미를 보존한다.
- [ ] QR·티켓 출력은 기존 권한·준비 완료·사용자 요청 시점을 따른다. 자동 인쇄를 도입하지 않는다.
- [ ] 기존 관련 테스트와 변경 영역의 검증 명령을 수행하고 실제 결과를 기록한다. 준비 문서 작성만으로 테스트 통과를 주장하지 않는다.

### 화면·콘텐츠·접근성

- [ ] 뷰포트 너비 320 / 360 / 390 / 768 / 1280 / 1440px에서 주요 화면과 작업 흐름을 확인한다. 추가 CSS 캡처의 필수 비교 너비는 320 / 390 / 768 / 1440px다.
- [ ] 200% 확대에서 제목·폼·금액·행동 버튼이 잘리거나 겹치지 않고 필요한 정보에 접근할 수 있다.
- [ ] 한국어·영어, 긴 공연명·팀명·계정명에서 줄바꿈·말줄임·접근 가능한 전체 이름을 확인한다.
- [ ] 토스트 한 줄·두 줄·action 포함 상태에서 아이콘·텍스트·닫기/action의 정렬과 터치 영역을 확인한다.
- [ ] 토스트 닫기 버튼의 접근 가능한 이름이 KO/EN 선택 언어와 일치한다.
- [ ] 언어 선택을 빠르게 재전환해도 선택 배경과 실제 언어가 일치한다. 키보드와 reduced-motion 설정에서 확인한다.
- [ ] fieldset의 legend·본문·입력 텍스트 정렬을 한국어·영어·긴 라벨로 확인한다.
- [ ] 카드 padding의 중복 덮어쓰기를 정리한 뒤 화면별 computed style을 확인한다. 다른 CSS 로드 순서에서 다시 좌우 0으로 바뀌지 않는다.
- [ ] 푸터 전체 폭 구분선과 내부 max-width를 확인하고, 헤더는 기존 외곽 border의 실제 적용 결과와 비교한다.
- [ ] 포스터 없음·손상, 빈 목록, 검색 결과 없음, 로딩·오류·부분 데이터 상태를 각각 확인한다.
- [ ] 키보드 순서·보이는 포커스·입력 이름·오류 연결·로딩 결과 알림·색 대비·모션 감소를 확인한다.
- [ ] 모바일 계정 직접 접근·하단 탭·상세 행동 버튼·안전 영역이 겹치지 않는다.
- [ ] 각 링크의 이름이 실제 목적지와 맞는지 확인한다. 공시 링크는 공연별 정산과 구분한다.
- [ ] 변경한 화면의 실제 브라우저 결과를 기록하고 DOM 확인만 한 화면을 시각 검증 완료로 표시하지 않는다.

## 12. 다음 구현자에게 남기는 경계

구현자는 이 문서를 홈 카피 교체만의 요청으로 축소하지 않는다. 동시에 전 페이지를 한 번에 교체해 상태 회귀의 위치를 알 수 없게 만들지 않는다. Home/List·Detail에서 콘텐츠와 정보 구조를 구체화하고, 같은 기준을 계정·거래와 Studio·운영에 단계적으로 적용한다.

이번에 검증하지 않은 인증 후 실제 화면, 최신 원격 상태, 실제 거래 결과는 미확인으로 남긴다. 구현 시 해당 범위의 테스트 데이터와 안전한 검증 경로를 마련하고 수행 결과를 추가한다. 사실과 제안의 경계를 지키면서 다음 구현 단위로 바로 이어갈 수 있는 준비안이 이 문서의 완료 기준이다.
