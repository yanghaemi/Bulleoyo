## 1. 왜 별도 문서인가

- 노션 `기능 명세서`는 SSAFY 템플릿 DB(`functionalSpecification`)다. 컬럼이 **ID · 도메인 · 기능 · 기능 설명 · 시작 상태 · 종료 상태 · 우선순위 · 연관화면 · API**로, 상태 전이를 갖는 기능 단위 전용이다. 비기능("얼마나 빨리", "어떤 조건에서도")은 시작·종료 상태가 없어 이 표에 들어갈 자리가 없다.
- 비기능 항목은 **W5 검증 결과**(달성/미달/제외)를 기록해야 한다. 기능 명세서와 생명주기가 다르다.
- 발표 Q&A 방어 근거(사전조사 §4.2, 기획 §8.3 "보장하는 것/보장하지 않는 것")를 요구사항 형태로 고정해 두면 장표·답변이 문서와 어긋나지 않는다.

**[권]** 노션에는 문서 DB 안에 `[비기능 요구사항 명세서 v1]` 페이지를 새로 만들고 인라인 DB `nonFunctionalRequirement`를 둔다. 로컬 md가 원본, 노션은 열람·필터용 미러.

## 3. 작성 원칙

1. **측정 가능하게.** "빠르게", "안전하게" 금지. 수치가 어려우면 판정 가능한 기준(코드리뷰 체크 항목, 테스트 케이스 존재 여부)으로 쓴다.
2. **근거를 적는다.** 어느 문서 어느 절에서 왔는지(기획 §, 사전조사 §, 컨벤션 §, 지갑 문서). 근거 없는 수치는 산출 논리 한 줄을 붙인다(예: "Amoy 블록 ~2초 × 여유" → 60초).
3. **규모를 현실화한다.** 타겟은 티켓 100매·3~4팀·시연 환경이다. 목표값은 "시연 규모 + 여유 5~10배"를 상한으로 한다. TPS 만 단위 같은 수치는 쓰지 않는다.
4. **기능과 구분한다.** 무엇을 하는가 → 기능 명세서. 얼마나·어떤 조건에서도 → 비기능. "준비금 증명 페이지"는 기능이고, "에스크로 잔액 ≥ 유통량이 항상 성립하고 조회 주기 ≤ N분"이 비기능이다.
5. **보장하지 않는 것을 약속하지 않는다.** 기획 §8.3과 일치시킨다 — 입력 데이터의 진실성은 보장 항목이 아니고, QR 입장 보안은 서버 서명의 몫이며 블록체인 성과가 아니다.
6. **[팀]/[권] 표기.** 수치는 대부분 [권]으로 시작하고 팀 검토 후 [팀]으로 승격한다. 기획 §10 미결 안건에 걸린 항목은 `의존: §10 ○○`을 붙이되, 빈칸으로 두지 않고 [권] 수치를 채운다 — 미결이 작성을 막지 않는다.
7. **검증 방법을 W5와 연결한다.** 각 항목의 검증 방법은 노션 `테스트 시나리오` DB 또는 리허설 체크리스트로 이어져야 한다. 검증 방법 없는 항목은 넣지 않는다.

| 리스크 | 대응 |
|--------|------|

| 기획 변경으로 명세서 어긋남 | 버전 분리 원칙(v1 보존, v2 신규). 개정 이력 표 유지 |
