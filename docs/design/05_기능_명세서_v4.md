## 개요

이 문서는 [방향 전환 결정 문서 v1](../planning/06_방향전환_코인전환_v1.md)을 유일한 입력으로 기능 목록을 다시 세운 것이다. 서비스의 모든 가치 이동은 **가상 원화 스테이블코인 KRWS 1종**(ERC-20, decimals=0, 1 KRWS = 1원)으로 일어나며, 금융망은 충전(on-ramp)과 팀 원화 출금(off-ramp) 창구로만 남는다.

- **플랫폼이 시연용 가상 원화 스테이블코인을 발행·소각·준비금 공시한다.** 금융망 입금이 확인된 금액만 발행하고(F-coin-01), 팀에게 원화를 이체한 뒤에만 소각하며(F-coin-05), 금융망 예치 잔액 ≥ 유통량을 공개한다(F-coin-02·F-verify-02).
- **지갑은 사용자 소유(Web3Auth/외부 지갑)이고, 서버는 사용자 키를 보관하지 않는다.** 서버가 보관하는 키는 운영자(OPERATOR)·발행(MINTER)·소각(BURNER) 3개뿐이며, 결제·보증금·규칙 동의·팀 출금 예치는 사용자가 직접 서명한다.
- **서명이 필요한 기능의 공통 4단계** — ① 서버가 `…/prepare`로 서명 파라미터(`to`·`data`·`chainId`·표시용 요약)를 발급 → ② 프론트가 tx를 구성하고 사용자가 Web3Auth 내장 프로바이더 또는 외부 지갑 팝업으로 서명 → ③ 프론트가 `…/signed-tx {txHash}`로 보고 → ④ 서버가 receipt·이벤트를 검증해 상태를 전이한다. 이 4단계를 쓰는 기능은 F-rule-03, F-payment-05, F-performance-10, F-withdraw-01·02이며 공통 처리는 F-wallet-06이다.
- **금액 표기** — 모든 금액은 KRWS(=원) 정수이고, 화면·응답에는 표시 통화 환산(`display` 객체, USD 기본)을 "≈"로 병기한다. 환율은 표시에만 쓰고 정산·분배·컨트랙트·충전 금액에는 쓰지 않는다(P-17·P-22).
- **우선순위(상/중/하)** — 결정 문서 §11 말미 기준. **상** = Web3Auth 로그인·지갑, 카드 충전, 서명 결제(approve+purchase 2단계), release, 팀 출금, 준비금 공시, en UI / **중** = 외부 지갑 등록, 가상계좌 충전, 보증금, 표시 환율 등록 / **하** = `[P1]` 행(MVP 제외). `[P2]`(USDC 교환·온체인 출금·외국인 팀·ExternalIssuer·NFT)는 기능 행을 만들지 않고 §D 예약 목록에만 적는다.
- 오류 코드는 [API 공통 응답 규격 v3](./01_API_공통_응답_규격.md)에 있는 코드만 사용하고, 규격에 없는 코드가 필요한 자리는 **대체 코드로 응답하되 괄호에 신설 제안 코드**를 적었다. 제안 목록은 §D-1에 모았다.

## B. 기능별 상세

### B-1. 회원·인증 (`member`)

> **v4 원칙 — 로그인 하나로 가입·지갑까지 끝난다.** Web3Auth 소셜 로그인 3종(구글·페이스북·카카오)이 서비스 로그인이며, 최초 로그인이 곧 가입이고 그 자리에서 지갑이 등록된다(F-wallet-01). 국내 본인인증·휴대폰·국내 계좌는 요구하지 않는다(P-23). 자체 이메일 가입·로그인은 지갑이 없는 보조 경로로만 남는다.

### F-member-01 Web3Auth 로그인·가입
**선행조건**
- 프론트가 F-coin-09(체인·컨트랙트 설정 조회)로 chainId·RPC를 받아 Web3Auth를 초기화한 상태다.
**트리거**
- 방문자가 C-01에서 소셜 버튼(구글·페이스북·카카오) 하나를 눌러 로그인하고, 프론트가 idToken과 지갑 주소를 서버에 제출한다.
**동작**
1. Web3Auth idToken을 JWKS로 검증한다(서명·`aud`·`exp`·`nonce`, 요청의 지갑 주소가 토큰의 지갑 공개키와 일치하는지 포함).
2. `web3auth_verifier_id`로 회원을 조회하고, 없으면 회원을 생성한다(`auth_provider` = GOOGLE/FACEBOOK/KAKAO). 최초 로그인 시 C-02 폼으로 국가(`country_code`)를 1회 받고 `locale`·`display_currency`·`timezone` 기본값(en·USD·요청 시간대)을 저장한다.
3. 지갑 주소를 회원에 1:1로 등록한다(F-wallet-01, `provider=WEB3AUTH`, `status=LINKED`). 이미 등록된 주소가 다른 회원의 것이면 거부한다.
4. 세션 토큰(access 30분·refresh 14일)을 발급한다.
5. 신규 등록이면 가스 자동 충전(F-wallet-04)을 job으로 트리거하고, 응답은 이를 기다리지 않는다.
**예외 / 제한사항**
- idToken 검증 실패·만료(`AUTH_TOKEN_INVALID`, 401 / 신설 제안 `AUTH_WEB3AUTH_TOKEN_INVALID`)
- 지갑 주소가 다른 회원에 이미 등록됨(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_ALREADY_LINKED`)
- 국가 코드 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- Web3Auth 장애(`COMMON_EXTERNAL_SERVICE_ERROR`, 502 — 외부 지갑 등록 경로 F-wallet-05로 우회 안내)
**비고**
- 요구사항 흐름: Web3Auth 로그인·가입
- [권] P-1 인증 방식(소셜 3종 동결), P-23 외국인 가입. **v4 대체** — v3의 회원 가입(자체)·로그인·소셜 OAuth 직접 연동 3행을 이 행 하나로 합쳤다. 핵심 시연 경로 1단계(외국인 관객 구글 로그인).
- 서버는 사용자 개인키·니모닉·MPC 샤드를 어떤 형태로도 저장하지 않는다.

### F-member-02 자체 이메일 로그인(보조) **[P1 — 9/2 최소화]**
**선행조건**
- `auth_provider = LOCAL` 회원으로 가입돼 있다.
**트리거**
- 방문자가 C-01에서 "이메일로 계속"을 골라 이메일·비밀번호를 제출한다.
**동작**
1. 자격 증명을 검증하고 세션 토큰을 발급한다.
2. 지갑이 없으면 응답에 `walletLinked=false`를 담아 C-05(지갑 연결) 유도 배너를 띄운다.
**예외 / 제한사항**
- 자격 증명 불일치(`AUTH_INVALID_CREDENTIALS`, 401)
- 형식 오류(`COMMON_VALIDATION_FAILED`, 400)

### B-3. 지갑 (`wallet`)

> **v4 원칙 — 지갑은 사용자 소유(Web3Auth/외부 지갑)이고, 서버는 사용자 키를 보관하지 않는다.** 회원당 지갑 1개(주소 UNIQUE)이며 관객·팀 리더가 같은 구조를 쓴다. 서버가 보관하는 키는 OPERATOR·MINTER·BURNER 3개뿐이고, 사용자 자산을 움직이는 tx는 전부 사용자가 서명한다. 지갑 교체는 MVP에서 관리자 처리이며 화면은 P1이다(§14-14).

### F-wallet-01 지갑 등록(Web3Auth)
**선행조건**
- F-member-01의 idToken 검증이 통과했다.
**트리거**
- Web3Auth 로그인·가입(F-member-01)이 내부적으로 호출한다.
**동작**
1. 회원에게 이미 지갑이 있으면 주소 일치 여부만 확인하고 끝낸다(중복 등록 금지).
2. 없으면 `wallet` 레코드를 생성한다 — `provider=WEB3AUTH`, `address`, `verified_at`(idToken 검증 시각), `status=LINKED`.

4. 개인키·니모닉·MPC 샤드는 **저장하지 않는다.** 저장 대상은 주소와 검증 시각뿐이다.

**비고**
- 요구사항 흐름: 지갑 등록(Web3Auth)
- **v4 대체** — v3 "팀 지갑 자동 생성"(서버 키 생성·암호화 보관)을 폐지하고 비수탁 등록으로 바꿨다(P-2). `WALLET_CREATION_FAILED`·`WALLET_KEY_DECRYPT_FAILED` 코드는 v4에서 쓰이지 않는다(§D-1).
- 핵심 시연 경로 1단계. 팀 리더도 같은 기능으로 지갑을 얻고, 그 지갑이 곧 팀 지갑이다.

3. 전송 결과를 `chain_job(tx_type=GAS_CHARGE, signer_type=OPERATOR)`으로 기록하고 `wallet.gas_funded_at`을 갱신한다.
**예외 / 제한사항**
- 사용자 지갑 가스 부족 지속(`WALLET_GAS_INSUFFICIENT`, 409, 화면은 "잠시 후 다시 시도" 안내)
- 운영지갑 가스 부족(`CHAIN_GAS_INSUFFICIENT`, 500, 시연 전 사전 확보 대상 + 관리자 알림)
**비고**
- 요구사항 흐름: 가스 자동 충전
- [권] P-3. 사용자에게 가스 개념을 노출하지 않는다. Kaia 수수료 대납(fee delegation)은 P1이며, 도입되면 이 기능은 대납 실패 시의 예비 경로가 된다.

### F-wallet-05 외부 지갑 등록 **[P1 — 9/2 최소화: Web3Auth 모달 어댑터로 대체]**
**선행조건**
- 로그인 상태이며 아직 지갑이 없다. 브라우저에 Kaia Wallet·MetaMask 등 외부 지갑이 있다.
**트리거**
- 회원이 C-05에서 "이미 지갑이 있나요?"를 눌러 지갑을 연결한다.
**동작**
1. 서버가 챌린지를 발급한다 — 난수 nonce + 도메인 바인딩 메시지, **TTL 5분·1회용**(Redis `wallet:challenge:{memberId}`, 테이블 없음).
2. 프론트가 지갑에 메시지 서명을 요청하고 서명값을 서버로 보낸다.
3. 서버가 서명에서 주소를 복원해 요청 주소와 일치하는지, nonce가 살아 있고 아직 쓰이지 않았는지 확인한다. 검증 성공 시 nonce를 즉시 폐기한다.
4. `wallet` 레코드를 생성한다 — `provider=EXTERNAL`, `verified_at`(챌린지 검증 시각), `status=LINKED`.
5. 가스 자동 충전(F-wallet-04)을 트리거한다.
**예외 / 제한사항**
- 챌린지 만료·재사용(`COMMON_UNAUTHORIZED`, 401 / 신설 제안 `WALLET_CHALLENGE_EXPIRED`)
- 서명 검증 실패·주소 불일치(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `WALLET_SIGNATURE_INVALID`)
- 이미 지갑 보유·주소 중복(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_ALREADY_LINKED`)
**비고**
- 요구사항 흐름: 외부 지갑 등록
- **v4 신설** — [권] P-2. 컷 라인 1순위(외부 지갑 등록 제외 → Web3Auth만)이므로 Web3Auth 경로와 독립적으로 켜고 끌 수 있게 만든다. 모바일 외부 지갑(WalletConnect·딥링크)은 리허설 후 결정한다(§14-19).
- 시연 시나리오 ②(외부 지갑 리더: Kaia Wallet 등록 → 보증금 서명 → 동의 서명 → 출금 서명)의 출발점이다.

### F-wallet-06 사용자 서명 tx 보고·검증 **[9/2 변경 — 대납 tx: 발신자 서명 RLP 보고 → 서버 fee payer 서명·전송]**
**선행조건**
- 사용자가 프론트에서 tx에 서명해 전송했고 tx 해시를 받았다.
**트리거**
- 프론트가 각 도메인의 `…/signed-tx {txHash}` 엔드포인트로 해시를 보고한다(결제·보증금·규칙 동의·팀 출금 예치).
**동작**
1. 보고된 해시로 `chain_job`을 생성한다 — `signer_type=USER`, `status=SUBMITTED`, `wallet_id`, `tx_type`(APPROVE/PURCHASE/DEPOSIT/AGREE/TREASURY_IN), `issuer_type=MOCK`.
2. receipt를 조회해 성공 여부를 확인하고, **기대한 컨트랙트 주소·함수·이벤트·인자**가 맞는지 검증한다(예: `Purchased(showId, orderRef, buyer, teamIndex, amount)`의 `orderRef`와 서버 주문의 `order_ref`, `buyer`와 회원 지갑 주소, `amount`와 서버 계산 금액).
3. 일치하면 `CONFIRMED`으로 전이하고 해당 도메인 상태를 넘긴다(결제 PAID·보증금 PAID·동의 AGREED·출금 TRANSFERRING).
4. 불일치·revert면 `FAILED`로 기록하고 도메인별 실패 처리로 넘긴다. 사용자 서명 tx는 **서버가 재전송하지 않고** receipt 재조회만 한다.
5. 같은 해시가 중복 보고되면 첫 job을 그대로 반환한다(멱등).
**예외 / 제한사항**
- 존재하지 않거나 아직 전파되지 않은 해시(`CHAIN_TX_TIMEOUT`, 504, 지수 백오프로 재조회)
- 기대와 다른 tx(다른 컨트랙트·함수·금액·주소)(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- 서명자 주소가 회원 지갑과 다름(`COMMON_FORBIDDEN`, 403)
- 컨트랙트 revert(`COMMON_CONFLICT`, 409, 사유를 도메인 코드로 변환해 안내)
**비고**
- 요구사항 흐름: 사용자 서명 tx 보고·검증
- **v4 신설** — [권] P-18. 결정 문서 §2.5의 공통 규약을 한 기능으로 모았다. 이 기능을 재사용하는 도메인 기능은 F-payment-05·F-performance-10·F-rule-03·F-withdraw-02이며, 각 기능은 이벤트 검증 규칙만 다르게 정의한다.
- 전용 클라이언트 API는 없고 도메인별 `signed-tx` 엔드포인트와 `GET /api/v1/chain/jobs/{jobId}` 폴링으로 노출된다.

**비고**
- 요구사항 흐름: 공연 취소 / 공연 취소 일괄 환불(04는 두 흐름으로 나누지만 05는 단일 API·단일 행으로 처리한다 — §D-2 참조)
- [권] P-12(수수료 없음, 잠금 후에도 release 전까지 가능) + 보증금 반환 연계.

### F-performance-10 보증금 서명 납부
**선행조건**
- 공연 생성자(리더)이며 공연이 `DRAFT`, `deposit_status = UNPAID`다. 리더 지갑이 `LINKED`다.
**트리거**
- 리더가 P-03의 보증금 단계에서 "보증금 납부"를 누른다.
**동작**
1. 서버가 잔액을 확인한다. 부족하면 부족분을 A-14(충전)로 안내하고 진행을 멈춘다.
2. 서버가 `createShow`(운영자)로 온체인 공연을 만든 뒤 서명 파라미터를 발급한다 — `KRWS.approve(splitter, depositAmount)`와 `Splitter.deposit(showId)`의 `to`·`data`·`chainId=1001`·사람이 읽을 수 있는 요약("Deposit ₩50,000").
3. **프론트가 tx를 구성하고 사용자(리더)가 Web3Auth 내장 프로바이더 또는 외부 지갑으로 서명한다.** allowance가 이미 충분하면 approve는 생략한다.
4. 프론트가 `…/deposit/signed-tx {txHash}`로 보고하면 서버가 202 + jobId를 돌려주고, receipt와 `DepositPaid` 이벤트(showId·금액·납부자)를 검증한다(F-wallet-06).
5. 확정 시 `deposit_status = PAID`, `deposit_job_id`·`deposit_tx_hash`를 기록하고 규칙 설정(F-rule-01) 단계를 연다.
**예외 / 제한사항**
- 보증금 미납 상태로 규칙 설정 진입(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
- 잔액 부족(`PAYMENT_INSUFFICIENT_BALANCE`, 409, 충전 유도)
- 사용자가 서명 팝업을 닫음(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`, 상태 유지·재시도 가능)
- 기대와 다른 tx 보고(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- 가스 부족(`WALLET_GAS_INSUFFICIENT`, 409, F-wallet-04 재충전 후 재시도)
**비고**
- 요구사항 흐름: 보증금 서명 납부
- **v4 신설** — [권] P-21(공연당 50,000 KRWS 고정). 컷 라인 3순위(보증금 → 안내만)이므로 규칙 설정 진입 가드를 설정으로 끌 수 있게 만든다.
- 몰수(`forfeitDeposit`)는 P1이며 MVP에서는 반환 경로만 구현한다.

### F-performance-11 보증금 반환
**선행조건**
- `deposit_status = PAID`이며, 정산이 `RELEASED`로 확정됐거나 공연 취소 일괄 환불이 완료됐다.
**트리거**

**동작**

3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 `deposit_status = RETURNED`, `deposit_return_tx_hash`를 기록하고 리더에게 알린다.
**예외 / 제한사항**

**비고**

### B-5. 정산 규칙 (`rule`)

### F-rule-01 정산 규칙 설정
**선행조건**
- 공연 생성자이며 공연이 `DRAFT` 또는 `PENDING_AGREEMENT`이고 **보증금이 `PAID`다.**
**트리거**
- 생성자가 P-05에서 고정·관객선택 전체 비율(bp)과 팀별 고정 분배 비율(`team_share_bp`)을 입력하고 예상 분배액 시뮬레이션을 확인한다.
**동작**
1. 보증금 납부 여부와 공연 상태를 확인한다.
2. **1단계**: `fixed_ratio_bp + selection_ratio_bp = 10000`인지 검증한다. **2단계**: 참여팀별 `team_share_bp` 합이 10000인지 검증한다. 각 항목은 0도 허용한다.
3. 규칙을 저장하고 규칙 해시(`rulesHash`)를 다시 계산한다. **규칙이 바뀌면 기존 동의는 전부 `PENDING`으로 초기화된다.**
4. 공연 상태를 `PENDING_AGREEMENT`로 전환한다.
**예외 / 제한사항**
- 비율 합 불일치(`RULE_RATIO_SUM_INVALID`, 400)
- 이미 잠긴 규칙 수정(`RULE_ALREADY_LOCKED`, 409)
- 보증금 미납(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
- 주최자 아님(`PERFORMANCE_NOT_OWNER`, 403)
**비고**
- 요구사항 흐름: 정산 규칙 설정
- [권] P-5(기본값 고정 5000·관객선택 5000, 팀별 균등 배분, 각 항목 0 허용). 핵심 시연 경로 4단계.
- 나눗셈 버림 잔액(dust)은 공연을 생성한 팀에 귀속한다. `RULE_COMMON_COST_EXCEEDS_REVENUE`는 v2 이후 쓰이지 않는다.

### F-rule-02 규칙·동의 현황 조회
**선행조건**
- 참여팀 리더다.
**트리거**
- 공연자가 P-05·P-06에서 규칙과 팀별 동의 현황을 확인한다.
**동작**
1. 현재 규칙(두 비율·팀별 비율·규칙 해시)과 각 팀의 동의 상태(`PENDING`/`SIGNING`/`AGREED`)를 조회한다.
2. `SIGNING` 상태의 팀은 보고된 tx 해시와 익스플로러 링크를 함께 보여 준다.
**예외 / 제한사항**
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 규칙·동의 현황 조회
- **v4 변경** — 동의 상태에 `SIGNING`(서명 tx 보고 후 확정 전)이 추가됐다(§7).

### F-rule-03 정산 규칙 동의
**선행조건**
- 참여팀 리더이며 공연이 `PENDING_AGREEMENT`이고, 리더 지갑이 온체인 `teamWallets`에 포함돼 있다.
**트리거**
- 리더가 P-06에서 규칙 내용을 확인하고 "동의" 버튼을 누른다.
**동작**
1. 요청의 `rulesHash`가 현재 서버 규칙 해시와 같은지 확인한다.
2. 서버가 서명 파라미터를 발급한다 — `Splitter.agreeToRules(showId, rulesHash)`의 `to`·`data`·`chainId`와 사람이 읽을 수 있는 요약(비율·규칙 해시 앞 8자리).
3. **프론트가 tx를 구성하고 리더가 Web3Auth 또는 외부 지갑으로 서명한다.** 서명 직전 가스 잔액이 임계 미만이면 F-wallet-04로 자동 충전한다.
4. 프론트가 `…/agreements/signed-tx {txHash}`로 보고하면 서버가 202 + jobId를 돌려주고 동의를 `SIGNING`으로 전이한다.
5. 서버가 receipt와 이벤트(서명자 주소가 해당 팀 지갑인지, `rulesHash`가 일치하는지)를 검증해 `AGREED`로 확정한다(F-wallet-06). `rule_agreement.agree_job_id`에 job을 연결한다.
**예외 / 제한사항**
- 규칙 변경됨(`RULE_HASH_MISMATCH`, 409, 화면 새로고침 후 재동의)
- 이미 잠긴 규칙(`RULE_ALREADY_LOCKED`, 409)
- 서명 거부(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`, 상태는 `PENDING` 유지)
- 서명자가 참여팀 지갑이 아님(`COMMON_FORBIDDEN`, 403)
- 가스 부족(`WALLET_GAS_INSUFFICIENT`, 409)
**비고**
- 요구사항 흐름: 정산 규칙 동의
- **v4 변경** — v3의 "서버가 팀 키로 대신 서명" 방식을 폐지하고 리더 본인 서명 + tx 보고로 바꿨다(P-18). 서버는 팀 키를 갖고 있지 않다.
- 핵심 시연 경로 5단계 — 서로 다른 주소가 같은 규칙 해시에 동의한 기록이 익스플로러에 남는 장면이다.

### F-rule-04 판매 시작
**선행조건**
- 생성자이며 참여팀 전원이 `AGREED`다.
**트리거**
- 생성자가 P-06에서 판매 시작을 누른다.
**동작**
1. 전 참여팀 동의 여부와 참여팀 수(공동 공연은 2팀 이상), 보증금 `PAID`를 확인한다.
2. 운영자가 `Splitter.startSale(showId)`를 실행해 규칙을 잠근다.
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 공연을 `ON_SALE`로 전환한다.
**예외 / 제한사항**
- 미동의 팀 존재(`RULE_NOT_AGREED_BY_ALL`, 409, 미동의 팀 목록 노출)
- 참여팀 2팀 미만(`TEAM_MIN_COUNT_NOT_MET`, 409)
- 보증금 미납(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
**비고**
- 요구사항 흐름: 판매 시작
- 핵심 시연 경로 6단계. 이후 규칙 setter는 전부 revert되고, `purchase`는 `ON_SALE`이 아니면 revert된다.

### B-6. 예매·티켓 (`ticket`)

### F-ticket-01 주문 생성
**선행조건**
- 관객이 로그인 상태이며 공연이 `ON_SALE`이다.
**트리거**
- 관객이 A-03에서 티켓 타입·수량을, A-04에서 관람 목적 팀을 선택해 예매를 신청한다.
**동작**
1. 티켓 타입 재고를 Redis에서 원자적으로 차감하고 1인 4매 이내인지 검증한다.
2. 관람 목적 팀 선택값(한 팀)을 검증하고 참여팀 순번(`teamIndex`)으로 변환한다.
3. 주문을 `PENDING_PAYMENT`(15분 만료)로 생성하고 **온체인 `orderRef = keccak(orderId)`** 를 `ticket_order.order_ref`에 저장한다.
4. 응답에 `orderRef`·주문 금액(KRWS)·**지갑 잔액**·**부족분(shortfall)** 과 표시 통화 환산을 담아 A-05로 넘긴다.
5. 지갑이 없는 회원(자체 이메일 가입)에게는 지갑 연결이 필요하다는 표시를 함께 내려준다.
**예외 / 제한사항**
- 판매 시작 전(`TICKET_SALE_NOT_STARTED`, 409)
- 판매 마감 이후(`TICKET_SALE_CLOSED`, 409, 취소 마감 D-3과는 별개 시점)
- 재고 소진(`TICKET_SOLD_OUT`, 409)
- 수량 초과(`TICKET_PURCHASE_LIMIT_EXCEEDED`, 409)
- 팀 미선택·참여팀 아님(`TICKET_TEAM_CHOICE_REQUIRED`, 400 / `TICKET_TEAM_CHOICE_INVALID`, 400)
- 지갑 미연결(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_NOT_LINKED`)
**비고**
- 요구사항 흐름: 주문 생성
- **v4 변경** — 응답에 `orderRef`·잔액·부족분이 추가돼 A-05가 "Pay with balance"와 "Pay with card (KRW)"를 즉시 구분한다. 온체인 선택 기록은 결제 tx(F-ticket-10)에 흡수됐다.
- 15분 안에 결제되지 않으면 주문은 `CANCELLED`가 되고 재고가 원복된다. 이미 충전된 코인은 잔액으로 남는다.

### F-ticket-10 관람 목적 팀 선택 기록
**선행조건**
- 주문이 생성됐고 관람 목적 팀 선택값(`teamIndex`)이 확정됐다.
**트리거**
- 관객이 결제 tx에 서명하는 순간 함께 기록된다(별도 트리거 없음).
**동작**
1. 선택값을 주문에 저장한다. 결제 전에는 온체인에 기록하지 않는다.
2. **`Splitter.purchase(showId, orderRef, teamIndex, amount)` 한 트랜잭션이 결제와 선택 기록을 함께 처리한다** — `escrow[showId] += amount`와 `choiceCount[showId][teamIndex]++`가 같은 tx에서 일어난다.
3. 서버는 `Purchased` 이벤트의 `teamIndex`를 검증해 `ticket.choice_tx_hash`에 결제 tx 해시를 기록한다.
4. **환불 시 감소** — 운영자 `Splitter.refund(...)`가 카운터를 −1 한다(별도 취소 tx 없음).
5. **양도 수락 시 재선택** — 받는 사람이 팀을 다시 고르더라도 **온체인 카운터는 갱신하지 않는다**. 서버는 재선택을 별도 필드로 기록해 화면에만 보여주고, 정산 집계는 `purchase` 시점 카운터를 기준으로 한다(요구사항 v4 양도 수락·API v4 §18.3 #4와 동일).
**예외 / 제한사항**
- 선택 팀이 참여팀 아님(`TICKET_TEAM_CHOICE_INVALID`, 400, 주문 단계에서 차단)
- 이벤트의 `teamIndex`가 주문 값과 다름(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`, 결제 실패 처리)
- 카운터가 서버 집계와 어긋나면 집계 확정이 차단된다(`SETTLEMENT_AGGREGATE_MISMATCH`, 409)
**비고**
- 요구사항 흐름: 관람 목적 팀 선택 기록
- **v4 변경** — [권] §14-12. v3의 `recordChoice`·`cancelChoice` 별도 tx 2종이 삭제되고 `purchase`·`refund`에 흡수됐다. 운영자 tx가 2건 줄어 결제 지연과 실패 지점이 함께 줄었다.
- 집계가 서버 DB 값이 아니라 체인 이벤트의 합이 되게 하는 장치다. 전용 클라이언트 API는 없다.

### B-7. 코인 결제 (`payment`)

> **v4 원칙 — 티켓 대금은 전부 `Splitter.purchase`로 에스크로에 들어온다(P-24).** 금융망 직접 결제는 없다. 결제 수단은 ① 지갑 KRWS 잔액 ② "원화로 결제"(부족분 자동 충전 후 서명) 둘뿐이며, 어느 쪽이든 마지막 단계는 사용자 서명 tx다. 기본안은 `approve` + `purchase` 2단계 서명이고 ERC20Permit 1-서명은 P1이다(§14-6).

### F-payment-01 결제 시작(잔액)
**선행조건**
- 본인 주문이 `PENDING_PAYMENT`이며 지갑이 `LINKED`이고 잔액이 주문 금액 이상이다.
**트리거**
- 관객이 A-05에서 "Pay with balance"를 누른다(`POST …/payment {mode: BALANCE}`).
**동작**
1. 클라이언트 금액과 서버 계산 금액을 대조하고 지갑 잔액을 조회한다.
2. `payment` 레코드를 `REQUESTED`(mode=BALANCE)로 만들고 멱등키를 부여한다.
3. 서명 파라미터를 발급한다 — `tokenAddress`·`splitterAddress`·`showId`·`orderRef`·`teamIndex`·`amount`와 **approve 필요 여부**(현재 allowance ≥ amount면 생략), 표시용 요약("Confirm ₩15,000 payment").
4. 가스 잔액이 임계 미만이면 F-wallet-04로 자동 충전한 뒤 파라미터를 내려준다.
5. 결제 상태를 `AWAITING_SIGNATURE`로 전이하고, 이후는 F-payment-05가 이어받는다.
**예외 / 제한사항**
- 중복 결제(`PAYMENT_ALREADY_PAID`, 409)
- 금액 불일치(`PAYMENT_AMOUNT_MISMATCH`, 409, 위조 시도로 간주)
- 잔액 부족(`PAYMENT_INSUFFICIENT_BALANCE`, 409 — 화면은 F-payment-04로 전환 유도)
- 지갑 미연결(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_NOT_LINKED`)
- 주문 만료(`COMMON_CONFLICT`, 409, 재고 원복 후 재예매 안내)
**비고**
- 요구사항 흐름: 결제 시작(잔액)
- **v4 대체** — v3의 "연결 계좌에서 금융망 이체" 결제를 폐지했다(P-7 대체). 핵심 시연 경로 8단계.
- 프론트는 서명 팝업 직전에 `to`·금액을 사람이 읽을 수 있게 보여 준다(§2.3).

### F-payment-02 결제 상태 조회
**선행조건**
- 본인 주문이다.
**트리거**
- 클라이언트가 A-05에서 `pollAfterMs` 간격으로 상태를 조회한다.
**동작**
1. 결제 상태(`REQUESTED`/`CHARGING`/`AWAITING_SIGNATURE`/`PAYING`/`PAID`/`FAILED`)를 반환한다.
2. `CHARGING`이면 연결된 충전 건(`chargeId`)의 진행 상태를 함께 담는다.
3. `AWAITING_SIGNATURE`면 **서명 파라미터를 다시 담아** 프론트가 새로고침 뒤에도 이어서 서명할 수 있게 한다.
4. `PAYING`이면 보고된 tx 해시와 익스플로러 링크를 담는다.
**예외 / 제한사항**
- 주문 없음(`COMMON_NOT_FOUND`, 404)
- 타인 주문 접근(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 결제 상태 조회
- **v4 변경** — 상태가 3개에서 7개로 늘고 서명 파라미터 재발급 책임이 추가됐다(§7 Payment).

### F-payment-03 결제 실패·서명 거부 처리
**선행조건**
- 결제가 `CHARGING`·`AWAITING_SIGNATURE`·`PAYING` 중 하나에서 실패했다.
**트리거**
- 충전 실패, 사용자의 서명 거부, tx revert, 주문 15분 만료 중 하나가 발생한다.
**동작**
1. **충전 실패** — 결제를 `FAILED`로 두고 재고를 원복한다. 발행이 일어나지 않았으므로 잔액 변화가 없다(F-charge-04).
2. **서명 거부·팝업 닫힘** — 결제 상태를 `AWAITING_SIGNATURE`로 유지하고 주문 만료(15분)까지 재시도를 허용한다. **자동 충전된 코인은 잔액으로 남는다**("Your top-up stays in your balance").
3. **tx revert**(재고 소진·`startSale` 잠금·allowance 부족) — 사유를 도메인 코드로 변환해 표시하고 재시도를 안내한다. 코인은 이동하지 않았다.
4. **주문 만료** — 주문을 `CANCELLED`, 결제를 `FAILED`로 전이하고 재고를 원복한다.
5. 어떤 경로에서도 **돈이 사라지지 않는다**는 것을 화면 문구로 보장한다.
**예외 / 제한사항**
- 서명 거부(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`)
- tx revert(`COMMON_CONFLICT`, 409, 사유별 코드 매핑)
- 충전 실패(`PAYMENT_REQUEST_FAILED`, 502 / 신설 제안 `CHARGE_FAILED`)
- 응답 지연(`PAYMENT_TIMEOUT`, 504, 중복 결제 유도 방지 문구)
**비고**
- 요구사항 흐름: 결제 실패·서명 거부 처리
- **v4 변경** — 결정 문서 §3.3 실패 보상 규칙을 그대로 옮겼다. 전용 클라이언트 API 없이 F-payment-01·04·05 경로 안에서 수행된다.

### F-payment-04 원화로 결제(자동 충전 연계)
**선행조건**
- 본인 주문이 `PENDING_PAYMENT`이며 지갑이 `LINKED`이고 **잔액 < 주문 금액**이다.
**트리거**
- 관객이 A-05에서 "Pay with card (KRW)"를 누른다(`POST …/payment {mode: AUTO_CHARGE, chargeMethod, card}`).
**동작**
1. 부족분(`shortfall = 금액 − 잔액`)을 계산하고 충전 한도(1회 1,000~1,000,000 KRWS)를 검증한다.
2. `coin_charge`를 `purpose=AUTO_PAYMENT`, `ticket_order_id`와 함께 생성하고 F-charge-01(또는 02)을 실행한다. 결제 상태를 `CHARGING`으로 둔다.
3. 금융망 승인 → `FIAT_CONFIRMED` → F-coin-01의 발행 확정(`COMPLETED`)까지 진행한다.
4. 발행이 끝나면 결제를 `AWAITING_SIGNATURE`로 전이하고 F-payment-01과 **같은 서명 파라미터**를 발급한다(폴링 응답으로 전달).
5. 이후 서명·보고·검증은 F-payment-05가 이어받는다.
**예외 / 제한사항**
- 카드 승인 실패(`PAYMENT_REQUEST_FAILED`, 502 / 신설 제안 `CHARGE_CARD_DECLINED`, 재고 원복)
- 충전 한도 위반(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `CHARGE_AMOUNT_OUT_OF_RANGE`)
- 금융망 성공·발행 실패(`COIN_MINT_FAILED`, 500, 멱등키 고정 재시도 — F-coin-04)
- 응답 지연(`PAYMENT_TIMEOUT`, 504, 결과 재조회 예약)
**비고**
- 요구사항 흐름: 원화로 결제(자동 충전)
- **v4 신설** — [권] P-7·P-24. 외국인 관객에게 "카드로 원화 결제" 한 번의 경험을 주면서 원장을 코인 하나로 유지하는 경로다. 화면은 "Your card issuer converts to your currency" 환전 고지를 함께 보여 준다.
- 비용은 결제 지연(카드 승인 + 발행 1초 + 서명 2회)과 보상 로직 하나이며, 금융망 직접 결제를 병행하지 않는 이유는 §12.4에 있다.

### F-payment-05 결제 서명 tx 보고
**선행조건**
- 결제가 `AWAITING_SIGNATURE`이며 사용자가 tx에 서명해 전송했다.
**트리거**
- 프론트가 `POST /orders/{orderId}/payment/signed-tx {kind: APPROVE|PURCHASE, txHash}`로 보고한다.
**동작**
1. **프론트 tx 구성 → 사용자 서명(Web3Auth/외부 지갑) → signed-tx 보고 → 서버 receipt 검증** 4단계 중 뒤 두 단계를 담당한다.
2. `kind=APPROVE`면 `KRWS.approve` receipt를 확인하고 allowance를 재조회한 뒤 `purchase` 서명을 이어서 요청하게 한다(`payment.approve_job_id` 기록).
3. `kind=PURCHASE`면 결제를 `PAYING`으로 전이하고 receipt와 **`Purchased(showId, orderRef, buyer, teamIndex, amount)` 이벤트**를 검증한다 — `orderRef`가 주문의 `order_ref`와 같은지, `buyer`가 회원 지갑인지, `amount`가 서버 계산 금액과 같은지, `teamIndex`가 주문 선택과 같은지.
4. 모두 일치하면 `payment.status = PAID`, `purchase_tx_hash`·`purchase_job_id`를 기록하고 주문을 `PAID`로 전이한 뒤 **티켓 발급(F-ticket-11)** 을 트리거한다.
5. 불일치·revert면 F-payment-03의 실패 처리로 넘긴다. 같은 해시의 중복 보고는 첫 job을 그대로 반환한다.
**예외 / 제한사항**
- 기대와 다른 tx(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- tx revert(`COMMON_CONFLICT`, 409, 재고·잠금·allowance 사유 표시)
- receipt 지연(`CHAIN_TX_TIMEOUT`, 504, 재조회 — 사용자 tx는 서버가 재전송하지 않는다)
- 이미 결제됨(`PAYMENT_ALREADY_PAID`, 409)
**비고**
- 요구사항 흐름: 결제 서명 tx 보고
- **v4 신설** — [권] P-18·§2.5. 공통 검증 로직은 F-wallet-06이고, 이 행은 결제 도메인의 이벤트 검증 규칙과 상태 전이를 정의한다.
- 핵심 시연 경로 8단계의 마지막 구간. 결제와 관객 선택이 한 tx에 담기는 것이 검증 페이지의 대사 근거가 된다(§3.8).

### B-8. 충전 (`charge`)

> **v4 신설 도메인.** 금융망은 이제 결제 레일이 아니라 **충전(on-ramp)** 창구다. 원화 입금이 확인된 금액만 발행하며(§2.2), 발행 실행 자체는 coin 도메인(F-coin-01)이 맡는다. 한도는 1회 최소 1,000·최대 1,000,000 KRWS, 가상계좌 입금 기한 30분이다(P-19).

### F-charge-01 카드 충전(해외·국내)
**선행조건**
- 로그인 상태이며 지갑이 `LINKED`다.
**트리거**
- 회원이 A-14에서 금액을 고르고 해외 카드(기본 탭) 또는 국내 카드로 충전을 요청한다. F-payment-04가 내부적으로 호출하기도 한다.
**동작**
1. 금액 한도(1,000~1,000,000)와 카드 정보를 검증하고 `coin_charge`를 `REQUESTED`로 만든다(`method=FOREIGN_CARD|DOMESTIC_CARD`, `idempotency_key` 부여, `purpose=MANUAL|AUTO_PAYMENT`).
2. 화면에 원화 금액과 표시 통화 환산, **환전 고지**("Your card issuer converts to your currency")를 보여 준다. `display_rate_id`에 사용한 표시 환율을 스냅샷한다.
3. 금융망 카드 API로 **원화 금액** 거래를 생성한다(멱등키 전달). 해외 카드는 카드사가 환전해 원화로 매입한다고 가정하므로 준비금은 항상 원화 한 종류다.
4. 승인 응답(`card_transaction_no`)을 받으면 `FIAT_CONFIRMED`로 전이하고 준비금 스냅샷을 갱신한다.
5. F-coin-01(발행)을 호출해 `MINTING` → `COMPLETED`로 이어가고, 완료 시 지갑 잔액을 갱신해 표시한다.
**예외 / 제한사항**
- 한도 위반(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `CHARGE_AMOUNT_OUT_OF_RANGE`)
- 카드 승인 거절(`PAYMENT_REQUEST_FAILED`, 502 / 신설 제안 `CHARGE_CARD_DECLINED`)
- 금융망 응답 지연(`PAYMENT_TIMEOUT`, 504, 결과 재조회 예약 — 어느 경우에도 발행 없음)
- 준비금 불일치로 발행 중단(`COIN_RESERVE_MISMATCH`, 409, 관리자 알림)
- 지갑 미연결(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_NOT_LINKED`)
**비고**
- 요구사항 흐름: 카드 충전(해외·국내)
- **v4 신설** — 국내 카드(`DOMESTIC_CARD`)는 같은 API 호출이며 `card_region` 표시와 환전 고지 유무만 다르다. 핵심 시연 경로(외국인 관객 자국 카드 충전)의 중심이다.
- 카드 취소(모의)를 통한 관객 원화 출금은 P1이다(P-20).

### F-charge-02 가상계좌 충전 **[P1 — 9/2 최소화]**
**선행조건**
- 로그인 상태이며 지갑이 `LINKED`다(내국인 관객 부가 경로).
**트리거**
- 회원이 A-14의 가상계좌 탭에서 금액을 입력해 충전을 요청한다.
**동작**
1. `coin_charge`를 `REQUESTED`(`method=VIRTUAL_ACCOUNT`)로 만들고 금융망에 가상계좌 발급을 요청한다.
2. `202`로 `chargeId`·계좌번호·입금 기한(30분)을 반환하고 화면에 표시한다.
3. 입금 확인 폴링(또는 웹훅)으로 입금이 확인되면 `FIAT_CONFIRMED`로 전이한다. **시연 환경에서는 `POST /charges/{chargeId}/simulate-deposit`으로 입금을 시뮬레이션한다**(운영 프로필에서는 비활성).
4. F-coin-01(발행)을 호출해 `COMPLETED`까지 진행한다.
5. 30분 안에 입금이 없으면 `EXPIRED`로 종료한다(F-charge-04).
**예외 / 제한사항**
- 한도 위반(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `CHARGE_AMOUNT_OUT_OF_RANGE`)
- 가상계좌 발급 실패(`COMMON_EXTERNAL_SERVICE_ERROR`, 502)
- 입금 기한 초과(`COMMON_CONFLICT`, 409 / 신설 제안 `CHARGE_EXPIRED`)
- 시연 API를 운영 프로필에서 호출(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 가상계좌 충전
- **v4 신설** — [권] P-19. 컷 라인 2순위(가상계좌 → 카드만)이므로 탭 단위로 끌 수 있게 만든다.

### F-charge-04 충전 실패·만료 처리
**선행조건**
- 충전이 `REQUESTED` 또는 `FIAT_CONFIRMED`에서 더 진행되지 못했다.
**트리거**
- 카드 승인 거절·금융망 오류·응답 지연, 또는 가상계좌 30분 미입금이 감지된다.
**동작**
1. **카드 오류** — `FAILED`로 종료하고 `failure_code`를 기록한다. **어떤 경우에도 발행하지 않는다.**
2. **타임아웃** — 결과 재조회를 예약하고, 재조회로 승인이 확인되면 `FIAT_CONFIRMED`로 이어 발행한다(중복 승인 방지는 멱등키가 보장한다).
3. **가상계좌 미입금** — 기한 경과 배치가 `EXPIRED`로 종료하고 계좌를 회수한다.
4. **금융망 성공·발행 실패** — 충전은 `FIAT_CONFIRMED`로 두고 발행 job만 원래 멱등키로 재시도한다(F-coin-04). 사용자에게는 "잔액 반영 중"으로 표시한다.
5. `purpose=AUTO_PAYMENT` 건이면 결제 실패 처리(F-payment-03)로 결과를 넘긴다.
**예외 / 제한사항**
- 카드 승인 거절(`PAYMENT_REQUEST_FAILED`, 502 / 신설 제안 `CHARGE_CARD_DECLINED`)
- 기한 만료(`COMMON_CONFLICT`, 409 / 신설 제안 `CHARGE_EXPIRED`)
- 발행 실패 지속(`COIN_MINT_FAILED`, 500, 재시도 횟수 + 관리자 알림)
**비고**
- 요구사항 흐름: 충전 실패·만료 처리
- **v4 신설** — 전용 클라이언트 API 없이 배치·이벤트로 동작하며 결과는 F-charge-03으로 노출된다. "원화 입금 확인 없이는 어떤 경로로도 발행하지 않는다"는 §2.1 페그 규칙의 집행 지점이다.

### B-9. 코인 (`coin`)

> **v4 원칙 — 플랫폼이 시연용 가상 원화 스테이블코인을 발행·소각·준비금 공시한다.** 발행은 금융망 원화 입금 확인에만 결합되고(F-coin-01), 소각은 팀 원화 이체 성공 뒤에만 일어나며(F-coin-05), 예치 잔액 ≥ 유통량을 공개한다(F-coin-02). mint·burn·유통량·준비금 조회는 서비스 코드가 컨트랙트를 직접 부르지 않고 `CoinIssuerPort` 하나를 통과한다(F-coin-08).

### F-coin-01 발행(mint) 실행
**선행조건**
- 대상 충전이 `FIAT_CONFIRMED`이며(금융망 성공 응답 확인) 준비금 상태가 정상이다.
**트리거**
- F-charge-01·02가 금융망 확인 직후 호출한다.
**동작**
1. 충전 상태가 `FIAT_CONFIRMED`인지, 같은 멱등키로 이미 발행되지 않았는지 확인한다.
2. 준비금(금융망 원화 예치 잔액)이 발행 후 유통량 이상인지 확인한다. 불일치면 **발행을 중단하고** 관리자에게 알린다.
3. `CoinIssuerPort.mint(회원 지갑 주소, amount, chargeRef)`를 호출한다 — `chargeRef`는 `coin_charge.idempotency_key` 해시이고 `MINTER` 키로 서명한다.
4. `chain_job(tx_type=MINT, signer_type=OPERATOR, issuer_type=MOCK)`을 만들고 충전을 `MINTING`으로 전이한다.
5. receipt와 `Minted` 이벤트가 확정되면 `COMPLETED`로 전이하고 `mint_tx_hash`를 기록한다. 잔액 표시(원 값 + 환산)를 갱신한다.
**예외 / 제한사항**
- 원화 입금 미확인 상태의 발행 요청(`COMMON_CONFLICT`, 409, 어떤 경로로도 금지)
- 준비금 불일치(`COIN_RESERVE_MISMATCH`, 409, 발행·release 중단 + 관리자 알림)
- 발행 tx 실패(`COIN_MINT_FAILED`, 500, 원래 멱등키로 자동 재시도 — F-coin-04)
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504)
- MINTER 지갑 가스 부족(`CHAIN_GAS_INSUFFICIENT`, 500)
**비고**
- 요구사항 흐름: 발행(mint) 실행
- **v4 개명·변경** — v3 "결제 확인"(결제 시 에스크로 직접 발행)을 대체한다. 발행 대상이 에스크로가 아니라 **회원 지갑**이고, 에스크로에는 관객이 서명한 `purchase`로만 들어온다(P-24).
- [권] P-11. 1 KRWS = 1원, decimals=0이라 온체인 금액과 원화 금액의 단위가 같다.

### F-coin-04 온체인 작업 자동 재시도
**선행조건**
- 대상 작업이 `FAILED`이며 아직 확정되지 않았다.
**트리거**
- 발행·소각·분배 등 **운영자 서명 작업**이 실패하면 시스템이 스스로 재시도한다.
**동작**
1. `signer_type`을 확인한다. **`USER` job은 재전송하지 않고 receipt 재조회만 한다**(서버에 사용자 키가 없다).
2. `OPERATOR` job은 원래 멱등키를 유지한 채 즉시 3회까지 재시도하고 이후 지수 백오프로 연장한다.
3. jobId 폴링으로 `CONFIRMED`/`FAILED`를 갱신하고 재시도 횟수·결과를 감사 로그에 남긴다.
**예외 / 제한사항**
- 결정적 실패(revert·준비금 불일치)는 재시도하지 않고 즉시 중단 + 알림(`COIN_RESERVE_MISMATCH`, 409)
- 운영지갑 가스 부족·nonce 충돌(`CHAIN_GAS_INSUFFICIENT` 500 / `CHAIN_NONCE_CONFLICT` 500) — 재시도 대상
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504) — 재시도 대상
**비고**
- 요구사항 흐름: 온체인 작업 자동 재시도
- **v4 변경** — `signer_type` 분기가 추가됐다. 공통 재시도 정책은 F-admin-09에 있다. 전용 클라이언트 API는 없다.

### F-coin-05 소각(burn) 실행
**선행조건**
- 팀 출금의 **금융망 원화 이체가 성공(`TRANSFERRED`)** 했고, 소각 대상 금액이 상환 금고 잔액에 있다.
**트리거**
- F-withdraw-02가 이체 성공을 확인한 직후 호출한다.
**동작**
1. 출금 상태가 `TRANSFERRED`인지, 같은 `withdrawalRef`로 이미 소각되지 않았는지 확인한다.
2. `CoinIssuerPort.burnFromTreasury(amount, withdrawalRef)`를 호출한다 — `BURNER`(= 상환 금고) 키로 금고 자신의 잔액만 소각한다.
3. `chain_job(tx_type=BURN, signer_type=OPERATOR)`을 만들고 출금을 `BURNING`으로 전이한다.
4. `Burned` 이벤트 확정 시 `COMPLETED`로 전이하고 유통량·준비금 스냅샷을 갱신한다.
**예외 / 제한사항**
- 이체 성공 전 소각 시도(`COMMON_CONFLICT`, 409, **순서 불변** — 이체 성공 확인 후에만 소각한다)
- 금고 잔액 부족(`COIN_ESCROW_INSUFFICIENT`, 409, 즉시 중단 + 관리자 알림)
- 소각 tx 실패(`COIN_BURN_FAILED`, 500, 멱등키 고정 자동 재시도)
**비고**
- 요구사항 흐름: 소각(burn) 실행
- **v4 개명·변경** — v3 "금융망 환불"(환불·환급 시 소각)을 대체한다. **환불은 더 이상 소각하지 않는다** — 에스크로에서 관객 지갑으로 KRWS가 이동할 뿐이고 유통량은 그대로다(F-refund-02). 소각은 원화가 서비스 밖으로 나가는 팀 출금 한 경로에서만 일어난다.

### F-coin-07 표시 환율 등록
**선행조건**
- ADMIN 권한이다.
**트리거**
- 관리자가 M-03에서 통화쌍·환율·적용 시각을 입력한다(하루 1회, 시연 중에는 고정).
**동작**
1. 통화쌍 형식과 양수 여부를 검증한다.
2. `exchange_rate`에 새 행을 추가한다(`published_by`·`source=MANUAL`·`effective_from`). 기존 행은 수정하지 않고 이력으로 남긴다.
3. 등록 결과를 감사 로그(`RATE_CHANGE`)에 남기고 캐시를 무효화한다.
**예외 / 제한사항**
- 권한 없음(`COMMON_FORBIDDEN`, 403)
- 형식 오류·음수·적용 시각 역행(`COMMON_VALIDATION_FAILED`, 400)
**비고**
- 요구사항 흐름: 표시 환율 등록
- **v4 신설** — [권] P-17·§14-2(`USD_KRW` 1,350). 외부 시세 API 자동 갱신은 P1이다.

### F-coin-08 발행 어댑터 바인딩
**선행조건**
- 설정 `coin.issuer.token-address`(KRWS 배포 주소)가 주입돼 있다.
**트리거**
- 애플리케이션 기동 시 스프링 컨텍스트가 `CoinIssuerPort` 구현체를 바인딩한다.
**동작**
1. `CoinIssuerPort`(`tokenAddress`·`mint`·`burnFromTreasury`·`totalSupply`·`reserve`) 뒤에 **`MockIssuer` 하나**를 바인딩한다. 분기 로직은 만들지 않는다.
2. 서비스 코드(충전·출금·준비금·검증)는 컨트랙트를 직접 부르지 않고 이 인터페이스만 호출한다.
3. `chain_job.issuer_type`에 `MOCK`을 기록한다(P2 대비 감사 컬럼).
4. Splitter·프론트 `approve`·검증 페이지는 `tokenAddress()` 하나에만 의존한다.
**예외 / 제한사항**
- 토큰 주소 미설정·잘못된 주소로 기동(`COMMON_INTERNAL_ERROR`, 500, 기동 실패로 조기 발견)
- MINTER·BURNER 키 미주입(`COMMON_INTERNAL_ERROR`, 500)
**비고**
- 요구사항 흐름: 발행 어댑터 바인딩
- **v4 신설** — [권] P-25. 개발 범위는 인터페이스 1개 + 구현 1개다. 인가 발행사 코인으로 교체 가능하다는 설명은 리스크·Q&A 절에서만 쓰고(`ExternalIssuer`는 P2), 기능 설명에는 넣지 않는다.
- 표준 ERC-20이면 정산 흐름은 코드 변경 없이 동작한다(비기능 MAINT).

### F-coin-09 체인·컨트랙트 설정 조회 **[P1 — 9/2 최소화: 프론트 환경변수]**
**선행조건**
- 없음(비로그인 가능).
**트리거**

**동작**
1. 체인 설정을 반환한다 — `chainNamespace=eip155`, `chainId=0x3e9`(1001), `rpcTarget`, `displayName=Kaia Kairos`, `ticker=KAIA`, 블록 익스플로러 주소.

3. 응답은 공개 정보만 담고 키·비밀값을 포함하지 않는다. 캐시 가능(설정 변경 시 무효화).

**비고**

### B-10. 취소·환불 (`refund`)

### F-refund-01 환불액 미리보기
**선행조건**
- 소유자이며 티켓이 `ISSUED`다.
**트리거**
- 관객이 A-11 취소 화면에 진입한다.
**동작**
1. 현재 시점이 D-7/D-3 중 어느 구간인지 계산한다.
2. 수수료 구간에 따른 환불 예정 금액(KRWS)을 계산해 반환하고 표시 통화 환산을 병기한다.
3. **환불금이 지갑 잔액으로 돌아온다는 것**을 문구로 함께 안내한다("Refunded to your balance").
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
**비고**
- 요구사항 흐름: 환불액 미리보기
- [권] P-8(D-7 이전 전액 / D-3 이전 50% / D-3 00:00 이후 취소 불가).

### F-refund-02 개별 취소·환불
**선행조건**
- 소유자이며 티켓이 `ISSUED`이고 취소 마감 전이며 정산이 잠기지 않았다.
**트리거**
- 관객이 A-11에서 환불액을 확인하고 취소를 확정한다.
**동작**
1. 수수료 구간별 환불액을 재계산한다.
2. 운영자가 `Splitter.refund(showId, orderRef, 관객 지갑, teamIndex, refundAmount)`를 실행한다 — 에스크로에서 관객 지갑으로 KRWS를 보내고 **선택 카운터를 −1** 한다(별도 취소 tx 없음).
3. 202 접수 → jobId 폴링 → `Refunded` 이벤트 확정 시 환불을 `COMPLETED`, 티켓을 `CANCELLED`로 전이하고 `refund_tx_hash`·`to_wallet_id`를 기록한다.
4. 수수료분은 에스크로에 남아 정산 재원에 포함된다.
5. **환불금은 관객 지갑 잔액으로 남아 다음 예매에 쓰인다.** 소각하지 않으며 유통량은 변하지 않는다.
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
- 이미 취소 요청됨(`REFUND_ALREADY_REQUESTED`, 409)
- 정산 잠금 이후 요청(`REFUND_AFTER_SETTLEMENT_LOCK`, 409, F-refund-03)
- `orderRef`당 누적 환불이 구매액 초과(`COMMON_CONFLICT`, 409, 컨트랙트가 revert)
- 환불 tx 실패(`REFUND_TRANSFER_FAILED`, 500, 자동 재시도)
**비고**
- 요구사항 흐름: 개별 취소·환불
- **v4 변경** — 금융망 환불 이체와 소각이 사라지고 온체인 에스크로 → 지갑 반환 하나로 정리됐다(P-8). 카드 취소(모의)는 P1이다.
- 핵심 시연 경로 11단계. 관객 잔액 유지 정책(P-20)의 근거는 §3.7에 있다.

### F-refund-03 정산 잠금 이후 취소 차단
**선행조건**
- 정산이 `LOCKED` 이상이다.
**트리거**
- 관객이 정산 잠금 이후 F-refund-02와 같은 취소를 시도한다.
**동작**
1. 대상 공연의 정산 상태를 확인한다.
2. `LOCKED` 이상이면 컨트랙트가 `refund`를 revert하므로 요청을 미리 차단하고 안내로 전환한다.
**예외 / 제한사항**
- 정산 잠금 이후 취소 시도(`REFUND_AFTER_SETTLEMENT_LOCK`, 409)
**비고**
- 요구사항 흐름: 정산 잠금 이후 취소 차단
- F-refund-02와 같은 엔드포인트의 가드 조건이다. release 후 환불은 회수 불가하다는 정책 경계를 명문화한 행이다.

### B-13. 정산 (`settlement`)

### F-settlement-01 정산 조회
**선행조건**
- 참여팀 리더다.
**트리거**
- 공연자가 P-08 대시보드에 진입한다.
**동작**
1. 정산 상태 머신(`NONE` → `AGGREGATED` → `LOCKED` → `DISPUTE_OPEN` → `RELEASED` / `HALTED`)과 팀별 분배액을 조회한다.
2. `release_tx_hash`, 팀별 `released`·`wallet_address`(수령 주소 스냅샷)·`withdrawn_amount`, **보증금 반환 상태**를 함께 반환한다.
3. 금액은 원 값 + 표시 통화 환산으로 표시한다.
**예외 / 제한사항**
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 정산 조회
- **v4 변경** — 종단 상태에서 `REDEEMED`가 삭제되고 `RELEASED`가 종단이다(§14-11). 원화 수령 여부는 정산 상태가 아니라 출금 이력(F-withdraw-03)이 보여 준다.

### F-settlement-02 집계 확정
**선행조건**
- 공연이 `ENDED`이며 취소 마감(D-3)이 지났다.
**트리거**
- 생성자 또는 ADMIN이 P-08에서 집계 확정을 누른다.
**동작**
1. 온체인 카운터(`choiceCountOf`)와 서버 집계를 대사한다.
2. 일치하면 운영자가 `Splitter.aggregate(showId, validTicketCount)`를 실행해 유효 티켓 수를 확정한다. 불일치면 자동 정산을 중단한다.
3. 잠긴 두 비율로 팀별 분배액을 산출해 `AGGREGATED`로 전이한다.
**예외 / 제한사항**
- 대사 실패(`SETTLEMENT_AGGREGATE_MISMATCH`, 409, 관리자 확인 후 진행)
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504)
**비고**
- 요구사항 흐름: 집계 확정
- **분배 공식(2단계 비율)** — `F = floor(R × bp_f / 10000)`, `S = floor(R × bp_s / 10000)`, `bp_f + bp_s = 10000`. 팀별로 `f_i = floor(F × w_i / 10000)`, `s_i = (T > 0) ? floor(S × n_i / T) : floor(S / N)`, `base_i = f_i + s_i`를 구하고 `dust = R − Σ base_i`를 공연 생성 팀에 귀속해 `Σ pay_i = R`(1원 오차 불허)을 만든다. `R`은 에스크로 잔액(구매 − 환불)이며 보증금은 별도 계정으로 제외한다.
- 산출은 컨트랙트가 수행하고 서버와 검증 페이지(F-verify-03)가 같은 공식을 재현해 세 값이 일치해야 진행한다. 핵심 시연 경로 13단계.

### F-settlement-05 release 실행
**선행조건**
- 정산이 `LOCKED`이며 48시간이 지났거나 열린 이의제기가 없다. 준비금 상태가 정상이다.
**트리거**
- 이의제기 기간 경과로 스케줄러가 자동 실행하거나, 생성자·ADMIN이 수동 실행한다.
**동작**
1. 미해결 이의제기와 준비금 상태를 확인한다(불일치면 중단).
2. 운영자가 `Splitter.release(showId)`를 실행해 **각 팀 리더 지갑으로 KRWS를 push 전송**한다(dust 포함, 이벤트 `Released(showId, teamWallet, amount)`).
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 정산을 `RELEASED`로 전이하고 `release_tx_hash`, 팀별 `released`·`released_at`을 기록한다.
4. **팀 리더에게 알림을 보내고 P-09에 "원화로 받기" 배지를 띄운다.** 자동 원화 이체는 하지 않는다(리더 서명이 필요하다).
5. 보증금 반환(F-performance-11)을 트리거한다.
**예외 / 제한사항**
- 이의제기 기간 중(`SETTLEMENT_DISPUTE_PERIOD`, 409)
- 아직 잠금 전(`SETTLEMENT_NOT_LOCKED`, 409)
- 이미 release됨(`SETTLEMENT_ALREADY_RELEASED`, 409)
- 준비금 불일치(`COIN_RESERVE_MISMATCH`, 409, release 중단 + 관리자 알림)
- 에스크로 잔액 부족(`COIN_ESCROW_INSUFFICIENT`, 409)
**비고**
- 요구사항 흐름: release 실행
- **v4 변경** — [권] P-10 대체. 종단이 `RELEASED`이며 자동 환급(F-redeem-03)은 삭제됐다. 팀이 원화를 받으려면 리더가 직접 서명해야 한다(F-withdraw-01·02).
- 핵심 시연 경로 15단계. 분배액 합은 잠긴 규칙 × 카운터 재계산값과 1원도 다르지 않아야 한다(§3.8-3).

### B-14. 출금 (`withdraw`)

> **v4 신설 도메인(구 `redeem` 대체).** 팀이 원화를 받는 경로는 **리더 서명 예치 → 금융망 원화 이체 → 소각** 하나뿐이다. 자동 push 이체는 리더 서명이 필요해 불가능하므로 폐지했다(P-10). 이체 성공 확인 후에만 소각하며 순서는 뒤집히지 않는다. 관객 원화 출금은 P1, 온체인 출금·USDC 역교환은 P2다.

### F-withdraw-01 팀 원화 출금 시작
**선행조건**
- 팀 리더이며 리더 지갑에 KRWS 잔액이 있고, **검증된 정산 계좌가 등록**돼 있다. 최소 출금액 1,000 KRWS.
**트리거**
- 리더가 P-09에서 "원화로 받기"를 누르고 금액(전액 또는 일부)과 계좌를 고른다.
**동작**
1. 잔액·최소 금액·계좌 검증 상태를 확인한다. 계좌가 없으면 F-team-07(정산 계좌 등록)로 유도한다.
2. `coin_withdrawal`을 `AWAITING_SIGNATURE`로 생성한다(`kind=BANK_TRANSFER`, 멱등키 부여, 대상 정산이 특정되면 `settlement_id` 연결).
3. 서명 파라미터를 발급한다 — `KRWS.transfer(상환 금고 주소, amount)`의 `to`·`data`·`chainId`와 표시 요약("Receive ₩320,000 to your bank account").
4. **프론트가 tx를 구성하고 리더가 Web3Auth 또는 외부 지갑으로 서명한다.** 서명 직전 가스 임계 미달이면 F-wallet-04로 자동 충전한다.
5. 이후 보고·이체·소각은 F-withdraw-02가 이어받는다.
**예외 / 제한사항**
- 정산 계좌 미등록·미검증(`COMMON_CONFLICT`, 409 / 신설 제안 `WITHDRAW_ACCOUNT_NOT_REGISTERED`)
- 잔액 부족·최소 금액 미만(`PAYMENT_INSUFFICIENT_BALANCE`, 409 / 신설 제안 `WITHDRAW_NOTHING_TO_WITHDRAW`)
- 처리 중 건 중복 요청(`COMMON_CONFLICT`, 409 / 신설 제안 `WITHDRAW_ALREADY_REQUESTED`)
- 리더 아님(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 팀 원화 출금 시작
- **v4 신설(구 F-redeem-03 대체)** — [권] P-10·P-20(수수료 0). 팀 잔액 전액 또는 일부를 선택할 수 있다.
- 시연 시나리오 ②의 마지막 서명 장면이다.

### F-withdraw-02 출금 예치 tx 보고·이체·소각
**선행조건**
- 출금이 `AWAITING_SIGNATURE`이며 리더가 예치 tx에 서명해 전송했다.
**트리거**
- 프론트가 `POST …/withdrawals/{withdrawalId}/signed-tx {txHash}`로 보고한다.
**동작**
1. **프론트 tx 구성 → 사용자 서명 → signed-tx 보고 → 서버 receipt 검증** 4단계의 뒤 두 단계를 수행한다. `chain_job(tx_type=TREASURY_IN, signer_type=USER)`을 만든다.
2. receipt를 검증한다 — 수신자가 상환 금고 주소인지, 금액이 출금 요청액과 같은지, 송신자가 리더 지갑인지. 확인되면 `TRANSFERRING`으로 전이하고 `treasury_in_tx_hash`를 기록한다.
3. 금융망 원화 이체를 요청한다(멱등키 고정, 대상 = 검증된 정산 계좌). 성공하면 `TRANSFERRED`로 전이하고 `bank_tx_id`를 기록한다.
4. **이체 성공을 확인한 뒤에만** F-coin-05(소각)를 호출한다 — `BURNING` → `Burned` 확정 시 `COMPLETED`. 순서는 뒤집히지 않는다.
5. **이체 실패 시** 운영자가 금고에서 리더 지갑으로 되돌리고(`TREASURY_RETURN`) `RETURNED`로 전이한다. 이 경우 소각하지 않는다.
6. 각 단계 전환을 P-09 화면에 단계 표시로 노출한다(예치 → 이체 → 완료).
**예외 / 제한사항**
- 기대와 다른 tx(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- 서명 거부(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`, `AWAITING_SIGNATURE` 유지)
- 금융망 이체 실패(`COMMON_EXTERNAL_SERVICE_ERROR`, 502 / 신설 제안 `WITHDRAW_BANK_TRANSFER_FAILED`, 자동 재시도 후 금고 반환)
- 소각 실패(`COIN_BURN_FAILED`, 500, 멱등키 고정 재시도 — 이체는 이미 성공했으므로 되돌리지 않는다)
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504)
**비고**
- 요구사항 흐름: 출금 예치·이체·소각
- **v4 신설** — [권] P-10·§2.2. "이체 성공 후 소각" 순서 불변은 준비금 공시(예치 ≥ 유통량)를 지키기 위한 규칙이다. 이체 전에 소각하면 예치금은 남았는데 유통량이 먼저 줄어 공시가 흔들린다.
- 핵심 시연 경로 16단계.

### F-withdraw-04 이체·소각 자동 재시도
**선행조건**
- 출금이 `TRANSFERRING`·`TRANSFERRED`·`BURNING` 단계에서 실패했다.
**트리거**
- 금융망 이체 또는 소각이 실패하면 시스템이 스스로 재시도한다(관리자 트리거는 P1 화면).
**동작**
1. 실패 단계를 판정한다 — 예치(사용자 tx)는 재전송하지 않고 receipt 재조회만 한다.
2. **금융망 이체 실패** — 원래 멱등키로 즉시 3회 재시도 후 지수 백오프. 중복 이체가 생기지 않게 멱등키를 고정한다.
3. 이체가 최종 실패하면 운영자가 금고 → 리더 지갑 반환 tx를 실행하고 `RETURNED`로 종료한다(리더에게 알림).
4. **소각 실패** — 이체는 이미 성공했으므로 되돌리지 않고 소각만 재시도한다. 소각 확정 전까지 준비금 공시에 "정산 중" 차액을 표시한다.
5. 재시도 횟수·결과를 감사 로그에 남긴다.
**예외 / 제한사항**
- 이체 실패 지속(`COMMON_EXTERNAL_SERVICE_ERROR`, 502 / 신설 제안 `WITHDRAW_BANK_TRANSFER_FAILED`)
- 소각 실패 지속(`COIN_BURN_FAILED`, 500, 관리자 알림)
- 결정적 실패(계좌 폐쇄 등)는 재시도하지 않고 금고 반환으로 종료
**비고**
- 요구사항 흐름: 출금 자동 재시도
- **v4 신설(구 F-redeem-02 개명·변경)** — 계좌 미등록 보류가 사라졌다(출금 시작 단계에서 계좌를 이미 요구한다). 관리자 수동 재시도(`POST /admin/withdrawals/{withdrawalId}/retry`)는 P1이다.

### B-15. 정산 검증 (`verify`)

> **v4 원칙 — 정산 검증(V-01)은 참여팀 전용, 준비금 공시(V-02)는 공개.** 이 도메인은 자체 엔티티 없이 `settlement`·`rule`·`coin`·`chain_job`을 읽기 전용으로 조합한다. 검증 화면은 블록체인 용어 노출이 허용되는 두 화면 중 하나다.

### F-verify-01 정산 검증 데이터 조회
**선행조건**
- 로그인 상태이며 해당 공연의 참여팀 리더다.
**트리거**
- 참여팀 리더가 V-01 화면에 들어간다.
**동작**
1. 참여팀 소속을 확인한다(로그인 필수). 개인정보는 포함하지 않는다.
2. **토큰 주소(`token()`)**·정산 컨트랙트 주소·잠긴 규칙(두 비율 bp·규칙 해시)·팀별 동의 tx·판매 시작 잠금 tx를 반환한다.
3. **에스크로 잔액(`escrowOf`)**·온체인 선택 카운터·유효 티켓 수·팀별 산출액·**`Released` 이벤트**·`release_tx_hash`·팀 지갑 주소·보증금 반환 tx를 반환한다.
4. §3.8 불변식 대사 결과를 함께 반환한다 — ① 유통량 = Σ발행 − Σ소각 ② `escrowOf` = Σ구매 − Σ환불 − Σ분배 ③ Σ`Released` = 재계산 분배액 합 ④ 예치 ≥ 유통량.
5. 각 tx 해시에 익스플로러 링크를 붙이고, 진행 중이면 현재 단계와 다음 단계 예정 시각을 표시한다.
**예외 / 제한사항**
- 비로그인 조회(`COMMON_UNAUTHORIZED`, 401)
- 참여팀 소속 아님(`COMMON_FORBIDDEN`, 403)
- 공연 없음(`PERFORMANCE_NOT_FOUND`, 404)
- 불변식 대사 실패(`SETTLEMENT_AGGREGATE_MISMATCH`, 409, 화면에 불일치 항목 표시)
**비고**
- 요구사항 흐름: 정산 검증 데이터 조회
- **v4 변경** — 토큰 주소·에스크로 잔액·팀 지갑 주소·`Released` 이벤트·불변식 대사가 추가됐다. 핵심 시연 경로 17단계.

### F-verify-02 준비금 공시 조회

### F-admin-09 온체인 실패 자동 재시도
**선행조건**
- 운영자 온체인 트랜잭션 또는 금융망 이체가 `FAILED`이며 확정되지 않았다.
**트리거**
- 작업이 실패하면 시스템이 스스로 재시도한다(관리자 트리거 없음).
**동작**
1. 실패 유형을 판정한다 — 일시적 실패(가스 부족·nonce 충돌·타임아웃·외부 API 오류)와 결정적 실패(revert·준비금 불일치)를 구분한다.
2. **`signer_type=OPERATOR` 작업만 재전송한다.** 대상은 `createShow`·`startSale`·`refund`·`aggregate`·`lock`·`release`·`returnDeposit`·`halt`·`mint`·`burn`·가스 전송과 금융망 이체다.
3. **`signer_type=USER` 작업(approve·purchase·deposit·agree·treasury-in)은 재전송하지 않고 receipt 재조회만 한다** — 서버에 사용자 키가 없기 때문이다. 최종 실패는 사용자에게 재시도를 안내한다.
4. 일시적 실패는 원래 멱등키를 유지한 채 즉시 3회, 이후 지수 백오프로 재시도한다.
5. 운영지갑 tx는 nonce 직렬 큐로 순서를 보장하고, 재시도 횟수·결과를 감사 로그에 append-only로 남긴다.
**예외 / 제한사항**
- 결정적 실패(`COIN_RESERVE_MISMATCH` 409 / `COIN_MINT_FAILED` 500 / `REFUND_TRANSFER_FAILED` 500) — 즉시 중단 + 알림
- 운영지갑 가스 부족·nonce 충돌(`CHAIN_GAS_INSUFFICIENT` 500 / `CHAIN_NONCE_CONFLICT` 500) — 재시도 대상
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504) — 재시도 대상
- 온체인 반영이 최종 실패하면 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다
**비고**
- 요구사항 흐름: 온체인 작업 자동 재시도
- **v4 변경** — `signer_type` 분기가 핵심이다. 도메인별 구현은 F-coin-04(발행·소각·운영자 tx)·F-withdraw-04(이체·소각)이며 전용 클라이언트 API는 없다.

### D-2. 판단이 필요한 지점

1. **화면 `S-01`** — 결정 문서 §10의 "유지" 목록은 `S-02·03`만 적고 `S-01`을 빠뜨렸다. 그러나 F-entry-01(검표 페이지 접근)이 살아 있으므로 연관화면을 `S-01 검표 — 공연 선택`으로 유지했다. 화면설계 v4가 S-01을 S-02에 합칠 계획이라면 이 행의 연관화면을 함께 고쳐야 한다(합계도 35 ↔ 36으로 달라진다).
2. **`API-verify-01`의 `/public` 접두** — 결정 문서 §9는 경로를 `GET /public/performances/{performanceId}/verification`으로 적으면서 actor를 "참여팀(로그인)"으로 뒀다. v3에서는 로그인 필수가 되며 `/public`을 뺐던 경로다. 교차 검증(9/2)에서 API 명세서 v4와 같이 **`/public` 없는 경로 + 참여팀 로그인**으로 통일했고, 결정 문서 §9도 같은 경로로 정정했다. "누구나 재계산"(공개 열람) 전환 여부는 결정 문서 §14-22 안건.
3. **양도 수락 시 카운터 갱신 방법** — `recordChoice`·`cancelChoice`가 삭제되어(§2.4) 양도 재선택 시 온체인 카운터를 조정할 함수가 컨트랙트 목록에 없다. F-transfer-03은 "운영자 조정 tx"로 적었으나, ① `refund` + 재구매로 표현할지 ② `adjustChoice(showId, from, to)` 같은 운영자 함수를 하나 추가할지 ③ 양도 시 재선택을 막고 원 선택을 유지할지 세 안 중 하나를 컨트랙트 담당자와 정해야 한다. **③을 채택했다**(요구사항 v4·API v4와 동일, 결정 문서 §14-21). 본문 F-ticket-10·F-transfer-03에 반영.
4. **04에 없는 05 행의 근접 매핑(4건)** — F-team-02(내 팀 목록 조회) → "팀 정보 조회·수정", F-performance-04(내 팀 참여 공연 목록 조회) → "공연 탐색·상세 조회", F-performance-06(참여팀 제외) → "참여팀 초대·수락", F-admin-09(온체인 실패 자동 재시도) → "온체인 작업 자동 재시도". 요구사항 명세서 v4 담당자 확인이 필요하다.
5. **`공연 취소` / `공연 취소 일괄 환불` 통합** — 04는 두 도메인의 별개 흐름으로 두지만 05는 API-performance-12 하나가 상태 전환·일괄 환불·보증금 반환 트리거를 함께 처리하므로 F-performance-09 한 행에 두 흐름명을 적었다.
6. **`F-member-09`와 `F-member-06`의 API 공유** — 둘 다 `PATCH /members/me`를 쓴다. 화면(C-03·C-04)과 요구사항 흐름이 달라 행을 나눴으니, API 명세서 v4는 한 엔드포인트의 부분 갱신으로 기술하면 된다.
7. **`F-coin-04`·`F-withdraw-04`·`F-admin-09` 세 재시도 행의 경계** — F-admin-09가 공통 정책(실패 유형 판정·멱등키·nonce 큐·`signer_type` 분기)을 정의하고, F-coin-04는 발행·소각·운영자 온체인 작업, F-withdraw-04는 금융망 이체·소각 재시도와 금고 반환을 담당한다. 구현은 한 모듈이어도 문서상 세 행을 유지했다.
8. **관객 잔액 출금 부재** — 관객 잔액은 유지 정책이며 출금 화면·기능이 없다(P-20). "지갑에서 직접 옮긴 코인의 원화 상환 경로는 없다"는 고지는 화면설계 v4가 A-13에 담는다. 관객 카드 취소·원화 출금은 P1, 온체인 출금은 P2다.
9. **`F-coin-08`의 기능 성격** — 런타임 사용자 흐름이 아니라 기동 시 바인딩이라 트리거가 사용자 행동이 아니다. 노션 DB에 넣을 때 "시스템 기능" 구분이 필요하면 별도 속성으로 표시해야 한다.

### D-3. P2 예약(기능 행 없음)

USDC 교환·역교환(`tUSDC`·`KRWSExchange`), 팀 온체인 출금, 외국인 팀, `ExternalIssuer`(인가 발행사 코인 어댑터), 외부 지갑 교체 화면, NFT 티켓. MVP에는 컨트랙트를 배포하지 않고 기능 행도 만들지 않는다. P1 예약은 `[P1]` 표기 12행과 ERC20Permit 1-서명 결제·Kaia 수수료 대납·관객 카드 취소 출금·보증금 몰수다.
