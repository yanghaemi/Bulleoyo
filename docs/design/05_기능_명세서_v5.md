## 개요

이 문서는 [방향 전환 결정 문서 v2](../planning/06_방향전환_코인전환_v2.md)를 유일한 입력으로 기능 목록을 다시 세운 것이다. **화폐가 코인인 미래를 가정한다. 플랫폼은 시연용 코인을 지급할 뿐 발행·상환·준비금의 주체가 아니며, 모든 가치 이동은 지갑 간 온체인 이체다.** KRWS(ERC-20, decimals=0, 1 KRWS = ₩1)는 이 세계의 원(₩) 그 자체이고, 법정화폐 입출구는 문서 어디에도 없다.

- **지갑은 사용자 소유(Web3Auth/Kaia Wallet), 서버는 사용자 키를 보관하지 않는다.** 서버가 보관하는 키는 운영자(OPERATOR = fee payer)와 발행(MINTER) **2개뿐**이며, 결제·보증금·규칙 동의는 사용자가 직접 서명한다.
- **코인을 얻는 유일한 경로는 시연용 지급(faucet)이다.** Web3Auth 최초 로그인 시 100,000 KRWS가 회원 지갑으로 지급되고(F-member-01 → F-coin-01), 부족하면 관리자가 M-03에서 추가 지급한다(F-coin-10). 지급 이력은 별도 테이블 없이 `chain_job(tx_type=MINT)`이 남긴다(§14-31).
- **서명이 필요한 기능의 공통 5단계 [팀 9/2 — Kaia 수수료 대납]** — ① 서버가 `…/prepare`(또는 결제 시작)로 서명 파라미터(`to`·`data`·`chainId`·표시용 요약)를 발급 → ② 프론트가 Kaia `FeeDelegatedSmartContractExecution` tx를 구성하고 사용자가 **발신자 서명만** 한다(Web3Auth 키 또는 Kaia Wallet, 사용자 지갑 KAIA 잔액 0) → ③ 프론트가 `…/signed-tx {kind, senderSignedRlp}`로 발신자 서명 RLP를 보고 → ④ 서버(운영지갑 = fee payer)가 대납 서명 후 전송하고 202 + jobId를 돌려준다 → ⑤ 서버가 receipt·이벤트를 검증해 도메인 상태를 전이한다. 이 5단계를 쓰는 기능은 F-rule-03, F-payment-05, F-performance-10이며 공통 처리는 F-wallet-06이다.
- **금액 표기** — 모든 금액은 KRWS(=₩) 정수이고, 화면·응답에는 표시 통화 환산(`display` 객체, USD 기본)을 "≈"로 병기한다. 환율은 표시에만 쓰고 정산·분배·컨트랙트·지급 금액에는 쓰지 않는다(P-17·P-22).
- **우선순위(상/중/하)** — 결정 문서 v2 §11 말미 기준. **상** = Web3Auth 로그인·지갑·기본 지급, 서명 결제(approve + purchase), QR 입장, release, 검증 페이지·발행량 공시, en UI, 관리자 지급 / **중** = 보증금, 표시 환율, 이의제기 / **하** = `[P1]` 행(MVP 제외). `[P2]`는 양도 4행과 §D-3 예약 목록이다.
- 오류 코드는 [API 공통 응답 규격 v3](./01_API_공통_응답_규격.md)에 있는 코드만 사용하고, 규격에 없는 코드가 필요한 자리는 **대체 코드로 응답하되 괄호에 신설 제안 코드**를 적었다. 제안 목록은 §D-1에 모았다.
- 이 문서에는 법정화폐·은행·금융 결제망 경로가 등장하지 않는다(P-26). 현실 매핑(인가 발행사 코인·CBDC를 `tokenAddress()`에 꽂는 것)은 결정 문서 v2 §12.2-4의 Q&A 영역이며 기능 행으로 만들지 않는다.

## B. 기능별 상세

### B-1. 회원·인증 (`member`)

> **v5 원칙 — 로그인 하나로 가입·지갑·기본 잔액까지 끝난다.** Web3Auth 소셜 로그인 3종(구글·페이스북·카카오)이 서비스 로그인이며, 최초 로그인이 곧 가입이고 그 자리에서 지갑이 등록되고(F-wallet-01) 기본 잔액 100,000 KRWS가 지급된다(F-coin-01, P-27). 국내 본인인증·휴대폰은 요구하지 않는다(P-23). 자체 이메일 가입·로그인은 `[P1]`이다(v1 §14-18).

### F-member-01 Web3Auth 로그인·가입
**선행조건**
- 프론트가 chainId(`0x3e9`)·RPC·컨트랙트 주소를 환경변수로 갖고 Web3Auth를 초기화한 상태다(설정 조회 API는 P1 — F-coin-09).
**트리거**
- 방문자가 C-01에서 소셜 버튼(구글·페이스북·카카오) 하나를 눌러 로그인하고, 프론트가 idToken과 지갑 주소를 서버에 제출한다.
**동작**
1. Web3Auth idToken을 JWKS로 검증한다(서명·`aud`·`exp`·`nonce`, 요청의 지갑 주소가 토큰의 지갑 공개키와 일치하는지 포함).
2. `web3auth_verifier_id`로 회원을 조회하고, 없으면 회원을 생성한다(`auth_provider` = GOOGLE/FACEBOOK/KAKAO). 최초 로그인 시 C-02 폼으로 국가(`country_code`)를 1회 받고 `locale`·`display_currency`·`timezone` 기본값(en·USD·요청 시간대)을 저장한다.
3. 지갑 주소를 회원에 1:1로 등록한다(F-wallet-01, `provider=WEB3AUTH`, `status=LINKED`). 이미 등록된 주소가 다른 회원의 것이면 거부한다.
4. 세션 토큰(access 30분·refresh 14일)을 발급한다.
5. **신규 회원이면 기본 잔액 지급 job을 트리거한다** — `chain_job(tx_type=MINT, wallet_id, amount=100000, requester_id=NULL, idempotency_key='grant:signup:{memberId}')`을 만들고 F-coin-01이 `mint`를 실행한다. 응답은 확정을 기다리지 않고 `grantJobId`만 담는다.
6. 화면은 "Welcome — your balance is ₩100,000 (≈ $74)"로 안내한다(§3.0). 재로그인·지갑 교체(P1)에서는 재지급하지 않는다(멱등키가 보장).
**예외 / 제한사항**
- idToken 검증 실패·만료(`AUTH_TOKEN_INVALID`, 401 / 신설 제안 `AUTH_WEB3AUTH_TOKEN_INVALID`)
- 지갑 주소가 다른 회원에 이미 등록됨(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_ALREADY_LINKED`)
- 국가 코드 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- Web3Auth 장애(`COMMON_EXTERNAL_SERVICE_ERROR`, 502 — Kaia Wallet 연결 경로는 P1이므로 재시도를 안내한다)
- 기본 지급 job 실패(`COIN_MINT_FAILED`, 500) — 로그인·가입은 성공으로 유지하고 지급만 재시도한다(F-coin-04). 화면은 "잔액 반영 중"으로 표시한다
**비고**
- 요구사항 흐름: Web3Auth 로그인·가입
- [권] P-1 인증 방식(소셜 3종 동결·v1 §14 [팀 9/2]), P-23 외국인 가입, **P-27 시연용 지급**. 핵심 시연 경로 1단계(외국인 관객 구글 로그인 → 이미 지갑에 있던 ₩).
- **v5 변경** — 5·6번(기본 잔액 지급·환영 문구)이 추가됐다. v4의 가스 자동 충전 트리거는 삭제됐다(수수료 대납).
- 서버는 사용자 개인키·니모닉·MPC 샤드를 어떤 형태로도 저장하지 않는다.

### F-member-02 자체 이메일 로그인(보조) **[P1]**
**선행조건**
- `auth_provider = LOCAL` 회원으로 가입돼 있다(`LOCAL`은 §7에서 예약값이다).
**트리거**
- 방문자가 C-01에서 "이메일로 계속"을 골라 이메일·비밀번호를 제출한다.
**동작**
1. 자격 증명을 검증하고 세션 토큰을 발급한다.
2. 지갑이 없으면 응답에 `walletLinked=false`를 담아 C-05(지갑 연결) 유도 배너를 띄운다.
**예외 / 제한사항**
- 자격 증명 불일치(`AUTH_INVALID_CREDENTIALS`, 401)
- 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
**비고**
- 요구사항 흐름: 자체 이메일 로그인(보조)
- **[P1]** — v1 §14-18 [팀 9/2]에서 MVP 밖으로 확정됐다. 지갑이 없는 회원은 주문까지는 가능하지만 결제 시작(F-payment-01)에서 지갑 연결을 요구받고, 기본 잔액 지급도 지갑 등록 시점에 일어난다.

### F-member-03 액세스 토큰 재발급
**선행조건**
- 유효한 리프레시 토큰을 보유한다(서버 보관소는 **Redis** `auth:refresh:{jti}`, TTL 14일 — 테이블 없음).
**트리거**
- 클라이언트가 액세스 토큰 만료를 감지한다.
**동작**
1. 리프레시 토큰을 검증한다 — 서명 확인 후 **Redis** `auth:refresh:{jti}` 키 존재를 조회한다. 키가 없으면 만료·폐기·재사용이므로 거부한다.
2. 새 액세스 토큰(30분)·새 리프레시 토큰(14일)을 발급하고 **기존 키를 삭제**한다(회전). 삭제된 키로 재시도가 들어오면 탈취 의심으로 그 회원의 토큰 집합 전체를 폐기한다 [권].
**예외 / 제한사항**
- 토큰 만료·위조(`AUTH_TOKEN_EXPIRED`, 401 / `AUTH_TOKEN_INVALID`, 401)
**비고**
- 요구사항 흐름: 액세스 토큰 재발급
- 인증 방식(Web3Auth·LOCAL)과 무관하게 동일하다.

### F-member-04 로그아웃

**트리거**

### B-3. 지갑 (`wallet`)

> **v5 원칙 — 지갑은 사용자 소유(Web3Auth/Kaia Wallet), 서버는 사용자 키를 보관하지 않는다.** 회원당 지갑 1개(주소 UNIQUE)이며 관객·팀 리더가 같은 구조를 쓴다. 서버가 보관하는 키는 **OPERATOR(= fee payer)·MINTER 2개뿐**이고, 사용자 자산을 움직이는 tx는 전부 사용자가 발신자 서명한다. 사용자 지갑에는 KAIA를 넣지 않는다 — 수수료는 운영지갑이 대납한다(v1 §14-4 [팀 9/2]). 지갑 교체는 MVP에서 관리자 처리이며 화면은 P1이다(§14-14).

### F-wallet-01 지갑 등록(Web3Auth)
**선행조건**
- F-member-01의 idToken 검증이 통과했다.
**트리거**
- Web3Auth 로그인·가입(F-member-01)이 내부적으로 호출한다.
**동작**
1. 회원에게 이미 지갑이 있으면 주소 일치 여부만 확인하고 끝낸다(중복 등록 금지).
2. 없으면 `wallet` 레코드를 생성한다 — `provider=WEB3AUTH`, `address`, `verified_at`(idToken 검증 시각), `status=LINKED`.
3. **신규 등록이면 기본 잔액 지급(F-coin-01)을 멱등키 `grant:signup:{memberId}`로 트리거한다.** 가스 전송은 하지 않는다(수수료 대납).
4. 개인키·니모닉·MPC 샤드는 **저장하지 않는다.** 저장 대상은 주소와 검증 시각뿐이다.
**예외 / 제한사항**

- 주소 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- 지갑 정지 상태에서 재로그인(`COMMON_FORBIDDEN`, 403, `status=SUSPENDED`)
**비고**
- 요구사항 흐름: 지갑 등록(Web3Auth)
- **v5 변경** — 3번의 가스 자동 충전이 기본 잔액 지급으로 교체됐다. `wallet` 테이블에 키 컬럼도, 가스 관련 컬럼도 없다(§8).
- 핵심 시연 경로 1단계. 팀 리더도 같은 기능으로 지갑을 얻고, 그 지갑이 곧 팀 지갑이다.

### F-wallet-05 외부 지갑 등록 **[P1]**
**선행조건**
- 로그인 상태이며 아직 지갑이 없다. 브라우저에 **Kaia Wallet**이 있다(수수료 대납 서명을 지원하는 지갑만 대상 — v1 §14-23·26 [팀 9/2]).
**트리거**
- 회원이 C-05에서 "이미 지갑이 있나요?"를 눌러 지갑을 연결한다.
**동작**
1. 서버가 챌린지를 발급한다 — 난수 nonce + 도메인 바인딩 메시지, **TTL 5분·1회용**(Redis `wallet:challenge:{memberId}`, 테이블 없음).
2. 프론트가 지갑에 메시지 서명을 요청하고 서명값을 서버로 보낸다.
3. 서버가 서명에서 주소를 복원해 요청 주소와 일치하는지, nonce가 살아 있고 아직 쓰이지 않았는지 확인한다. 검증 성공 시 nonce를 즉시 폐기한다.
4. `wallet` 레코드를 생성한다 — `provider=EXTERNAL`, `verified_at`(챌린지 검증 시각), `status=LINKED`.
5. 기본 잔액 지급(F-coin-01)을 트리거한다.
**예외 / 제한사항**
- 챌린지 만료·재사용(`COMMON_UNAUTHORIZED`, 401 / 신설 제안 `WALLET_CHALLENGE_EXPIRED`)
- 서명 검증 실패·주소 불일치(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `WALLET_SIGNATURE_INVALID`)
- 이미 지갑 보유·주소 중복(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_ALREADY_LINKED`)
**비고**
- 요구사항 흐름: 외부 지갑 등록

### F-wallet-06 사용자 서명 tx 보고·검증
**선행조건**
- 서버가 서명 파라미터를 발급한 상태이고, 사용자가 Kaia `FeeDelegatedSmartContractExecution` tx에 **발신자 서명**을 완료했다. 사용자 지갑의 KAIA 잔액은 0이어도 된다.
**트리거**
- 프론트가 각 도메인의 `…/signed-tx {kind, senderSignedRlp}` 엔드포인트로 발신자 서명 RLP를 보고한다(결제·보증금·규칙 동의).
**동작**
1. **prepare → 사용자 발신자 서명(대납 tx) → signed-tx(`senderSignedRlp`) 보고 → 서버 fee payer 서명·전송 → receipt 검증** 5단계 중 3~5단계를 담당한다.
2. 보고된 RLP를 디코딩해 **서명 전 검증**을 수행한다 — tx 타입이 수수료 대납 타입인지, `to`가 기대 컨트랙트(KRWS 또는 RevenueSplitter)인지, `data`의 함수 셀렉터·인자가 발급한 파라미터와 같은지, 복원한 발신자 주소가 회원 지갑 주소인지. 하나라도 다르면 **전송하지 않고** 거부한다.
3. `chain_job`을 생성한다 — `signer_type=USER`, `fee_delegated=true`, `status=SUBMITTED`, `wallet_id`, `tx_type`(APPROVE/PURCHASE/DEPOSIT/AGREE), `issuer_type=MOCK`, `sender_signed_rlp`·`fee_payer`·`fee_paid` 컬럼 기록.
4. 운영지갑(fee payer) 키로 대납 서명해 전송하고 202 + jobId를 반환한다. 전송된 tx 해시를 job에 기록한다.
5. receipt를 조회해 성공 여부와 **기대한 이벤트·인자**를 검증한다(예: `Purchased(showId, orderRef, buyer, teamIndex, amount)`의 `orderRef`와 서버 주문의 `order_ref`, `buyer`와 회원 지갑 주소, `amount`와 서버 계산 금액).
6. 일치하면 `CONFIRMED`으로 전이하고 해당 도메인 상태를 넘긴다(결제 PAID·보증금 PAID·동의 AGREED).
7. 불일치·revert면 `FAILED`로 기록하고 도메인별 실패 처리로 넘긴다. **사용자 서명 tx는 서버가 새로 만들어 재전송하지 않고** receipt 재조회만 한다(같은 RLP 재전송은 nonce 충돌 시 1회 허용).
8. 같은 RLP·같은 멱등키가 중복 보고되면 첫 job을 그대로 반환한다(멱등).
**예외 / 제한사항**
- RLP 디코딩 실패·기대와 다른 tx(다른 컨트랙트·함수·금액·주소)(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- 서명자 주소가 회원 지갑과 다름(`COMMON_FORBIDDEN`, 403)
- 대납 전송 실패·운영지갑 KAIA 부족(`CHAIN_GAS_INSUFFICIENT`, 500, 시연 전 사전 확보 대상 + 관리자 알림 · 재시도 — F-admin-09)
- nonce 충돌(`CHAIN_NONCE_CONFLICT`, 500, 직렬 큐로 재전송)
- receipt 확정 지연(`CHAIN_TX_TIMEOUT`, 504, 지수 백오프로 재조회)
- 컨트랙트 revert(`COMMON_CONFLICT`, 409, 사유를 도메인 코드로 변환해 안내)
**비고**
- 요구사항 흐름: 사용자 서명 tx 보고·검증
- **v5 변경** — v4의 "tx 해시 보고" 4단계를 **발신자 서명 RLP 보고 + 서버 대납 전송** 5단계로 바꿨다(v1 §14-4 [팀 9/2], 결정 문서 v2 §2.5). 이 기능을 재사용하는 도메인 기능은 F-payment-05·F-performance-10·F-rule-03 **3개**다(v4의 F-withdraw-02는 삭제).
- 2번의 서명 전 검증이 새 방어선이다 — 서버가 전송 주체이므로 임의 tx를 대납해 주지 않도록 `to`·`data`·발신자를 모두 대조한다.
- 전용 클라이언트 API는 없고 도메인별 `signed-tx` 엔드포인트와 `GET /api/v1/chain/jobs/{jobId}` 폴링으로 노출된다.

### F-performance-10 보증금 서명 납부
**선행조건**
- 공연 생성자(리더)이며 공연이 `DRAFT`, `deposit_status = UNPAID`다. 리더 지갑이 `LINKED`다.
**트리거**
- 리더가 P-03의 보증금 단계에서 "보증금 납부"를 누른다.
**동작**
1. 서버가 리더 지갑 잔액을 확인한다. 부족하면 **"Insufficient balance · ₩n short" 안내만** 하고 진행을 멈춘다(시연에서는 관리자 지급 F-coin-10으로 해소, §3.5).
2. 서버가 `createShow`(운영자)로 온체인 공연을 만든 뒤 **서명 파라미터를 발급(prepare)** 한다 — `KRWS.approve(splitter, depositAmount)`와 `Splitter.deposit(showId)`의 `to`·`data`·`chainId=1001`·사람이 읽을 수 있는 요약("Deposit ₩50,000").
3. 프론트가 수수료 대납 tx를 구성하고 **리더가 발신자 서명만 한다**(Web3Auth 키 또는 Kaia Wallet). allowance가 이미 충분하면 approve는 생략한다.
4. 프론트가 `…/deposit/signed-tx {kind, senderSignedRlp}`로 **발신자 서명 RLP를 보고**하면, 서버가 서명 전 검증 후 **fee payer 서명·전송**하고 202 + jobId를 돌려준다.
5. 서버가 **receipt와 `DepositPaid` 이벤트**(showId·금액·납부자)를 검증한다(F-wallet-06). 확정 시 `deposit_status = PAID`, `deposit_job_id`·`deposit_tx_hash`를 기록하고 규칙 설정(F-rule-01) 단계를 연다.
**예외 / 제한사항**
- 보증금 미납 상태로 규칙 설정 진입(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
- 잔액 부족(`PAYMENT_INSUFFICIENT_BALANCE`, 409 — 안내만, 유도 화면 없음)
- 사용자가 서명 팝업을 닫음(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`, 상태 유지·재시도 가능)
- 기대와 다른 RLP 보고(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- 운영지갑 KAIA 부족으로 대납 실패(`CHAIN_GAS_INSUFFICIENT`, 500, 재시도 + 관리자 알림)
**비고**
- 요구사항 흐름: 보증금 서명 납부
- [권] P-21(공연당 50,000 KRWS 고정). 컷 라인 1순위(보증금 → 안내만)이므로 규칙 설정 진입 가드를 설정으로 끌 수 있게 만든다.
- **v5 변경** — 1번의 잔액 부족 처리가 "안내만"으로 바뀌고, 3~5번이 수수료 대납 5단계로 재작성됐다. 몰수(`forfeitDeposit`)는 P1이며 MVP에서는 반환 경로만 구현한다.

### F-performance-11 보증금 반환
**선행조건**
- `deposit_status = PAID`이며, 정산이 `RELEASED`로 확정됐거나 공연 취소 일괄 환불이 완료됐다.
**트리거**
- F-settlement-05(release 확정) 또는 F-performance-09(일괄 환불 완료) 이벤트가 발생한다.
**동작**
1. 대상 공연의 보증금 상태를 확인한다(중복 반환 금지).
2. 운영자가 `Splitter.returnDeposit(showId)`를 실행해 생성팀 리더 지갑으로 보증금을 되돌린다.
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 `deposit_status = RETURNED`, `deposit_return_tx_hash`를 기록하고 리더에게 알린다.
**예외 / 제한사항**
- 이미 반환됨(`COMMON_CONFLICT`, 409)
- 반환 tx 실패(`CHAIN_TX_TIMEOUT`, 504, 자동 재시도 — F-admin-09)
- 에스크로 잔액 부족(`COIN_ESCROW_INSUFFICIENT`, 409, 즉시 중단 + 관리자 알림)
**비고**
- 요구사항 흐름: 보증금 반환
- [권] P-21. 전용 클라이언트 API 없이 정산 조회(F-settlement-01)와 P-03·P-08 화면에 상태로 노출된다. 몰수(P1)는 같은 컨트랙트 함수 짝(`forfeitDeposit`)으로 확장한다.

### B-5. 정산 규칙 (`rule`)

### F-rule-01 정산 규칙 설정
**선행조건**
- 공연 생성자이며 공연이 `DRAFT` 또는 `PENDING_AGREEMENT`이고 **보증금이 `PAID`다.**
**트리거**
- 생성자가 P-05에서 고정·관객선택 전체 비율(bp)과 팀별 고정 분배 비율(`team_share_bp`)을 입력하고 예상 분배액 시뮬레이션을 확인한다.
**동작**
1. 보증금 납부 여부와 공연 상태를 확인한다.
2. **1단계**: `fixed_ratio_bp + selection_ratio_bp = 10000`인지 검증한다. **2단계**: 참여팀별 `team_share_bp` 합이 10000인지 검증한다. 각 항목은 0도 허용한다.
3. 규칙을 저장하고 규칙 해시(`rulesHash`)를 다시 계산한다. **규칙이 바뀌면 기존 동의는 전부 `PENDING`으로 초기화된다.**
4. 공연 상태를 `PENDING_AGREEMENT`로 전환한다.
**예외 / 제한사항**
- 비율 합 불일치(`RULE_RATIO_SUM_INVALID`, 400)
- 이미 잠긴 규칙 수정(`RULE_ALREADY_LOCKED`, 409)
- 보증금 미납(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
- 주최자 아님(`PERFORMANCE_NOT_OWNER`, 403)
**비고**
- 요구사항 흐름: 정산 규칙 설정
- [권] P-5(기본값 고정 5000·관객선택 5000, 팀별 균등 배분, 각 항목 0 허용). 핵심 시연 경로 4단계.
- 나눗셈 버림 잔액(dust)은 공연을 생성한 팀에 귀속한다. `RULE_COMMON_COST_EXCEEDS_REVENUE`는 v2 이후 쓰이지 않는다.

### F-rule-02 규칙·동의 현황 조회
**선행조건**
- 참여팀 리더다.
**트리거**
- 공연자가 P-05·P-06에서 규칙과 팀별 동의 현황을 확인한다.
**동작**
1. 현재 규칙(두 비율·팀별 비율·규칙 해시)과 각 팀의 동의 상태(`PENDING`/`SIGNING`/`AGREED`)를 조회한다.
2. `SIGNING` 상태의 팀은 대납 전송된 tx 해시와 익스플로러 링크를 함께 보여 준다.
**예외 / 제한사항**
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 규칙·동의 현황 조회
- 동의 상태 `SIGNING`은 RLP 보고 후 receipt 확정 전 구간이다(§7 RuleAgreement).

### F-rule-03 정산 규칙 동의
**선행조건**
- 참여팀 리더이며 공연이 `PENDING_AGREEMENT`이고, 리더 지갑이 온체인 `teamWallets`에 포함돼 있다.
**트리거**
- 리더가 P-06에서 규칙 내용을 확인하고 "동의" 버튼을 누른다.
**동작**
1. 요청의 `rulesHash`가 현재 서버 규칙 해시와 같은지 확인한다.
2. 서버가 **서명 파라미터를 발급(prepare)** 한다 — `Splitter.agreeToRules(showId, rulesHash)`의 `to`·`data`·`chainId`와 사람이 읽을 수 있는 요약(비율·규칙 해시 앞 8자리).
3. 프론트가 수수료 대납 tx를 구성하고 **리더가 발신자 서명만 한다.** 사용자 지갑에 KAIA는 필요하지 않다.
4. 프론트가 `…/agreements/signed-tx {kind, senderSignedRlp}`로 **발신자 서명 RLP를 보고**하면, 서버가 서명 전 검증 후 **fee payer 서명·전송**하고 202 + jobId를 돌려주며 동의를 `SIGNING`으로 전이한다.
5. 서버가 **receipt와 이벤트**(서명자 주소가 해당 팀 지갑인지, `rulesHash`가 일치하는지)를 검증해 `AGREED`로 확정한다(F-wallet-06). `rule_agreement.agree_job_id`에 job을 연결한다.
**예외 / 제한사항**
- 규칙 변경됨(`RULE_HASH_MISMATCH`, 409, 화면 새로고침 후 재동의)
- 이미 잠긴 규칙(`RULE_ALREADY_LOCKED`, 409)
- 서명 거부(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`, 상태는 `PENDING` 유지)
- 서명자가 참여팀 지갑이 아님(`COMMON_FORBIDDEN`, 403)
- 대납 전송 실패(`CHAIN_GAS_INSUFFICIENT`, 500, 재시도 + 관리자 알림)
**비고**
- 요구사항 흐름: 정산 규칙 동의
- 서버는 팀 키를 갖고 있지 않다. 리더 본인 발신자 서명 + RLP 보고만이 동의를 만든다(P-18).
- **v5 변경** — 3·4번을 수수료 대납 흐름으로 재작성하고 가스 자동 충전 문구를 삭제했다.
- 핵심 시연 경로 5단계 — 서로 다른 주소가 같은 규칙 해시에 동의한 기록이 익스플로러에 남는 장면이다.

### F-rule-04 판매 시작
**선행조건**
- 생성자이며 참여팀 전원이 `AGREED`다.
**트리거**
- 생성자가 P-06에서 판매 시작을 누른다.
**동작**
1. 전 참여팀 동의 여부와 참여팀 수(공동 공연은 2팀 이상), 보증금 `PAID`를 확인한다.
2. 운영자가 `Splitter.startSale(showId)`를 실행해 규칙을 잠근다.
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 공연을 `ON_SALE`로 전환한다.
**예외 / 제한사항**
- 미동의 팀 존재(`RULE_NOT_AGREED_BY_ALL`, 409, 미동의 팀 목록 노출)
- 참여팀 2팀 미만(`TEAM_MIN_COUNT_NOT_MET`, 409)
- 보증금 미납(`COMMON_CONFLICT`, 409 / 신설 제안 `PERFORMANCE_DEPOSIT_REQUIRED`)
**비고**
- 요구사항 흐름: 판매 시작
- 핵심 시연 경로 6단계. 이후 규칙 setter는 전부 revert되고, `purchase`는 `ON_SALE`이 아니면 revert된다.

**비고**

2. **`Splitter.purchase(showId, orderRef, teamIndex, amount)` 한 트랜잭션이 결제와 선택 기록을 함께 처리한다** — `escrow[showId] += amount`와 `choiceCount[showId][teamIndex]++`가 같은 tx에서 일어난다.
3. 서버는 `Purchased` 이벤트의 `teamIndex`를 검증해 `ticket.choice_tx_hash`에 결제 tx 해시를 기록한다.
4. **환불 시 감소** — 운영자 `Splitter.refund(...)`가 카운터를 −1 한다(별도 취소 tx 없음).
5. **양도 수락 시 재선택(P2)** — 받는 사람이 팀을 다시 고르더라도 **온체인 카운터는 갱신하지 않는다**. 서버는 재선택을 별도 필드로 기록해 화면에만 보여주고, 정산 집계는 `purchase` 시점 카운터를 기준으로 한다.
**예외 / 제한사항**
- 선택 팀이 참여팀 아님(`TICKET_TEAM_CHOICE_INVALID`, 400, 주문 단계에서 차단)
- 이벤트의 `teamIndex`가 주문 값과 다름(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`, 결제 실패 처리)
- 카운터가 서버 집계와 어긋나면 집계 확정이 차단된다(`SETTLEMENT_AGGREGATE_MISMATCH`, 409)
**비고**
- 요구사항 흐름: 관람 목적 팀 선택 기록
- [권] §14-12·§14-21. 집계가 서버 DB 값이 아니라 체인 이벤트의 합이 되게 하는 장치다. 전용 클라이언트 API는 없다.

### F-ticket-11 티켓 발급
**선행조건**
- 결제 tx receipt가 확정되고 `Purchased` 이벤트 검증이 끝났다(F-payment-05).
**트리거**
- 결제 확정 이벤트가 발생한다.
**동작**
1. 주문 수량만큼 티켓 레코드를 생성한다.
2. 각 티켓을 `ISSUED`로 초기화하고 `ticket.qr_secret`(TOTP 비밀키)을 생성한다.
3. 발급 완료를 A-06에 표시한다(Kairos 블록 1초라 "Confirming…"은 수 초다).
**예외 / 제한사항**
- 결제 미확정 상태에서 발급 시도(`COIN_MINT_PENDING`, 409 / 신설 제안 `PAYMENT_PENDING`)
**비고**
- 요구사항 흐름: 티켓 발급
- 발급 시점은 "결제 tx receipt 확정" 하나다. 전용 클라이언트 API는 없다.

### B-7. 코인 결제 (`payment`)

> **v5 원칙 — 결제 수단은 지갑 KRWS 잔액 하나다(P-7·P-24).** 모든 티켓 대금은 `Splitter.purchase`로 에스크로에 들어오고, 마지막 단계는 언제나 사용자 발신자 서명 tx다. 기본안은 `approve` + `purchase` 2단계 서명이며 ERC20Permit 1-서명은 P1이다(§14-6). **잔액이 부족하면 안내로 끝난다** — 결제 화면에 다른 수단이나 잔액 확보 버튼은 없다(§3.3·§10 §5.16).

### F-payment-01 결제 시작(잔액)
**선행조건**
- 본인 주문이 `PENDING_PAYMENT`이며 지갑이 `LINKED`다.
**트리거**
- 관객이 A-05에서 "Pay ₩15,000 from balance"를 누른다(`POST …/payment`, **본문 없음** — `mode` 파라미터가 삭제됐다).
**동작**
1. 클라이언트 금액과 서버 계산 금액을 대조하고 지갑 KRWS 잔액을 조회한다.
2. **잔액 < 주문 금액이면 409로 끝낸다** — 주문은 `PENDING_PAYMENT`로 유지되고 재고도 잡아 둔 채, 화면은 "Insufficient balance · ₩n short"만 표시한다. 관객이 잔액을 확보하면(시연: 관리자 지급 F-coin-10) 같은 주문으로 재시도한다.
3. 잔액이 충분하면 `payment` 레코드를 `REQUESTED`로 만들고 멱등키를 부여한다(`mode`·자동 지급 연계 컬럼 없음 — §8).
4. **서명 파라미터를 발급한다** — `tokenAddress`·`splitterAddress`·`showId`·`orderRef`·`teamIndex`·`amount`와 **approve 필요 여부**(현재 allowance ≥ amount면 생략), 표시용 요약("Confirm ₩15,000 payment"), 수수료 대납 tx 타입 정보.
5. 결제 상태를 `AWAITING_SIGNATURE`로 전이하고, 이후는 F-payment-05가 이어받는다. 가스 관련 사전 처리는 없다.
**예외 / 제한사항**
- 잔액 부족(**409 `PAYMENT_INSUFFICIENT_BALANCE`**, 규격 v5 신설 제안 / 대체 `COMMON_CONFLICT` — 안내 전용, 다른 결제 경로로 전환하지 않는다)
- 중복 결제(`PAYMENT_ALREADY_PAID`, 409)
- 금액 불일치(`PAYMENT_AMOUNT_MISMATCH`, 409, 위조 시도로 간주)
- 지갑 미연결(`COMMON_CONFLICT`, 409 / 신설 제안 `WALLET_NOT_LINKED`)
- 주문 만료(`COMMON_CONFLICT`, 409, 재고 원복 후 재예매 안내)
**비고**
- 요구사항 흐름: 결제 시작(잔액)
- **v5 변경** — 요청 본문의 `mode`가 삭제되고 잔액 부족이 "전환 유도"에서 "안내"로 바뀌었다(P-7 대체). 핵심 시연 경로 8단계.
- 프론트는 서명 팝업 직전에 `to`·금액을 사람이 읽을 수 있게 보여 준다(§2.3).

### F-payment-02 결제 상태 조회
**선행조건**
- 본인 주문이다.
**트리거**
- 클라이언트가 A-05에서 `pollAfterMs` 간격으로 상태를 조회한다.
**동작**
1. 결제 상태(`REQUESTED`/`AWAITING_SIGNATURE`/`PAYING`/`PAID`/`FAILED`/`REFUNDED`)를 반환한다. **`CHARGING`은 없다**(§7 Payment).
2. `AWAITING_SIGNATURE`면 **서명 파라미터를 다시 담아** 프론트가 새로고침 뒤에도 이어서 서명할 수 있게 한다.
3. `PAYING`이면 서버가 대납 전송한 tx 해시와 익스플로러 링크를 담는다.
4. 잔액 부족으로 아직 시작하지 못한 주문이면 현재 잔액과 부족액을 함께 담아 안내 문구를 갱신한다.
**예외 / 제한사항**
- 주문 없음(`COMMON_NOT_FOUND`, 404)
- 타인 주문 접근(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 결제 상태 조회
- **v5 변경** — 상태가 7개에서 6개로 줄고(`CHARGING` 삭제) 4번 안내 갱신이 추가됐다.

### F-payment-03 결제 실패·서명 거부 처리
**선행조건**
- 결제가 `AWAITING_SIGNATURE`·`PAYING` 중 하나에서 실패했거나, 잔액 부족으로 시작되지 못했다.
**트리거**
- 잔액 부족, 사용자의 서명 거부, `purchase` revert, 대납 전송 실패, 주문 15분 만료 중 하나가 발생한다.
**동작**
1. **잔액 부족** — 결제 레코드를 만들지 않고 409로 끝낸다. 주문은 `PENDING_PAYMENT`로 유지되고 잔액 변화는 없다. **잔액 확보 유도 화면은 없다.**
2. **서명 거부·팝업 닫힘** — 결제 상태를 `AWAITING_SIGNATURE`로 유지하고 주문 만료(15분)까지 재시도를 허용한다. **잔액은 그대로 남는다**("Your balance is unchanged").
3. **`purchase` revert**(재고 소진·`startSale` 잠금·allowance 부족) — 사유를 도메인 코드로 변환해 표시하고 재시도를 안내한다. 코인은 이동하지 않았다.
4. **대납 전송 실패**(운영지갑 KAIA 부족·nonce 충돌) — 같은 RLP로 재전송을 시도하고, 실패가 지속되면 관리자에게 알린 뒤 사용자에게 "잠시 후 다시 시도"를 안내한다. 사용자 자산은 움직이지 않았다.
5. **주문 만료** — 주문을 `CANCELLED`, 결제를 `FAILED`로 전이하고 재고를 원복한다.
6. 어떤 경로에서도 **돈이 사라지지 않는다**는 것을 화면 문구로 보장한다.
**예외 / 제한사항**
- 잔액 부족(`PAYMENT_INSUFFICIENT_BALANCE`, 409, 규격 v5 신설 제안)
- 서명 거부(`COMMON_CONFLICT`, 409 / 신설 제안 `PAYMENT_SIGNATURE_REJECTED`)
- tx revert(`COMMON_CONFLICT`, 409, 사유별 코드 매핑)
- 대납 전송 실패(`CHAIN_GAS_INSUFFICIENT` 500 / `CHAIN_NONCE_CONFLICT` 500)
- 응답 지연(`PAYMENT_TIMEOUT`, 504, 중복 결제 유도 방지 문구)
**비고**
- 요구사항 흐름: 결제 실패·서명 거부 처리
- **v5 변경** — 결정 문서 v2 §3.3의 실패 보상 규칙을 그대로 옮겼다. **잔액 확보 실패 분기가 사라지고** 대납 전송 실패 분기가 새로 들어왔다. 전용 클라이언트 API 없이 F-payment-01·05 경로 안에서 수행된다.

### F-payment-05 결제 서명 tx 보고
**선행조건**
- 결제가 `AWAITING_SIGNATURE`이며 사용자가 수수료 대납 tx에 발신자 서명을 완료했다.
**트리거**
- 프론트가 `POST /orders/{orderId}/payment/signed-tx {kind: APPROVE|PURCHASE, senderSignedRlp}`로 보고한다.
**동작**
1. **prepare → 사용자 발신자 서명(대납 tx) → signed-tx(`senderSignedRlp`) 보고 → 서버 fee payer 서명·전송 → receipt 검증** 5단계 중 3~5단계를 담당한다(공통 처리 F-wallet-06).
2. `kind=APPROVE`면 RLP를 검증·대납 전송해 `KRWS.approve` receipt를 확인하고 allowance를 재조회한 뒤 `purchase` 서명을 이어서 요청하게 한다(`payment.approve_job_id` 기록).
3. `kind=PURCHASE`면 대납 전송 후 결제를 `PAYING`으로 전이하고 receipt와 **`Purchased(showId, orderRef, buyer, teamIndex, amount)` 이벤트**를 검증한다 — `orderRef`가 주문의 `order_ref`와 같은지, `buyer`가 회원 지갑인지, `amount`가 서버 계산 금액과 같은지, `teamIndex`가 주문 선택과 같은지.
4. 모두 일치하면 `payment.status = PAID`, `purchase_tx_hash`·`purchase_job_id`를 기록하고 주문을 `PAID`로 전이한 뒤 **티켓 발급(F-ticket-11)** 을 트리거한다.
5. 불일치·revert면 F-payment-03의 실패 처리로 넘긴다. 같은 RLP의 중복 보고는 첫 job을 그대로 반환한다.
**예외 / 제한사항**
- 기대와 다른 RLP(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `PAYMENT_TX_MISMATCH`)
- tx revert(`COMMON_CONFLICT`, 409, 재고·잠금·allowance 사유 표시)
- 대납 전송 실패(`CHAIN_GAS_INSUFFICIENT`, 500 / `CHAIN_NONCE_CONFLICT`, 500)
- receipt 지연(`CHAIN_TX_TIMEOUT`, 504, 재조회 — 서버는 새 tx를 만들어 재전송하지 않는다)
- 이미 결제됨(`PAYMENT_ALREADY_PAID`, 409)
**비고**
- 요구사항 흐름: 결제 서명 tx 보고
- **v5 변경** — 본문이 `{kind, txHash}`에서 `{kind, senderSignedRlp}`로 바뀌었고 서버가 전송 주체가 됐다(v1 §14-4 [팀 9/2]).
- 핵심 시연 경로 8단계의 마지막 구간. 관객 문구는 "Pay ₩15,000 from balance" → "Confirm in your wallet" → "Confirming…" → "Paid"다(§3.3).

### B-8. 코인 (`coin`)

> **v5 원칙 — 코인을 얻는 유일한 경로는 시연용 지급이다.** `KRWS`에는 `mint`만 남았고(§2.2) 소각 규칙도 소각 권한 키도 없다. 지급은 ① 가입 시 자동 1회 100,000 KRWS ② 관리자 수동(1회 최대 1,000,000) 두 가지이며(P-19·P-27), 별도 지급 이력 테이블 없이 `chain_job(tx_type=MINT)`이 요청자·금액·멱등키를 남긴다(§14-31). 공시는 **총 발행량·에스크로 합계·지갑 보유 합계** 세 값이다(P-11). mint·발행량 조회는 서비스 코드가 컨트랙트를 직접 부르지 않고 `CoinIssuerPort` 하나를 통과한다(F-coin-08).

### F-coin-01 지급(mint) 실행
**선행조건**
- 지급 근거가 확정됐다 — ① `wallet` 등록 확정(F-wallet-01, API-member-01 성공) 또는 ② 관리자 지급 요청 접수(F-coin-10). 발행량 대사 상태가 정상이다.
**트리거**
- F-wallet-01이 신규 지갑 등록 직후 호출하거나, F-coin-10이 관리자 요청으로 호출한다.
**동작**
1. 같은 멱등키(`grant:signup:{memberId}` 또는 관리자 요청의 `grantRef`)로 이미 지급되지 않았는지 확인한다.
2. 지급 한도를 검증한다 — 가입 기본 **100,000**, 관리자 1회 최대 **1,000,000**, 회원당 누적 상한 없음(시연) [권] P-19.
3. **발행량 불변식을 확인한다** — `totalSupply` = Σ(전 지갑 잔액) + Σ(전 공연 `escrowOf` + 보증금). 불일치면 **지급을 중단하고** 관리자에게 알린다(§3.8-4).
4. `CoinIssuerPort.mint(회원 지갑 주소, amount, grantRef)`를 호출한다 — `MINTER` 키로 서명하며, MINTER는 OPERATOR와 별도 주소·별도 권한이다(§2.3).
5. `chain_job(tx_type=MINT, signer_type=OPERATOR, issuer_type=MOCK, wallet_id, amount, requester_id, idempotency_key=grantRef)`을 만들고 202 + jobId를 반환한다. `requester_id`는 관리자 지급이면 관리자, 가입 자동 지급이면 NULL이다.
6. receipt와 `Minted(to, amount, grantRef)` 이벤트가 확정되면 `CONFIRMED`으로 전이하고, 지갑 잔액 표시(원 값 + 환산)와 V-02 발행량을 갱신한다. 감사 로그에 `GRANT`를 남긴다(§7 AuditLog).
**예외 / 제한사항**
- 멱등키 중복(첫 job을 그대로 반환, 재지급 없음)
- 한도 초과(`COMMON_VALIDATION_FAILED`, 400 / 신설 제안 `COIN_GRANT_LIMIT_EXCEEDED`)
- 발행량 불변식 불일치(`COIN_RESERVE_MISMATCH`, 409 → 규격 v5에서 `COIN_SUPPLY_MISMATCH`로 개명 제안 · 지급·release 중단 + 관리자 알림)
- 지급 tx 실패(`COIN_MINT_FAILED`, 500, 원래 멱등키로 자동 재시도 — F-coin-04)
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504)
- MINTER 지갑 KAIA 부족(`CHAIN_GAS_INSUFFICIENT`, 500)
**비고**
- 요구사항 흐름: 지급(mint) 실행
- **v5 변경** — 발행 근거가 "법정화폐 입금 확인"에서 **"가입 확정 또는 관리자 지급 요청"** 으로 바뀌었다(P-25·P-27). 이것이 이 세계의 유일한 mint이며, 대응 소각 기능은 없다(F-coin-05 삭제).
- [권] P-11·P-19. 1 KRWS = ₩1, decimals=0이라 온체인 금액과 표기 금액의 단위가 같다.

### F-coin-02 발행량·에스크로 공시 조회
**선행조건**
- 없음(비로그인 가능).
**트리거**
- 누구나 V-02(발행량·에스크로 공시) 화면에 진입하거나, 관리자가 M-03에서 이상 경고를 확인한다.
**동작**
1. `CoinIssuerPort.totalSupply()`로 **총 발행량**을 조회한다.
2. 전 공연 `escrowOf(showId)` 합계(+ 보증금 계정)로 **에스크로 합계**를, 두 값의 차로 **지갑 보유 합계**를 계산한다.
3. `chain_job(tx_type='MINT')` 건수로 **지급 건수(`grantCount`)** 를, 조회 시각으로 `asOf`를 채운다(1분 캐시).
4. 불변식 4를 대사한다 — `totalSupply` = Σ(전 지갑 잔액) + Σ(에스크로 + 보증금). 결과(일치/불일치 항목)를 응답에 담는다.
5. 세계관 고지 문구("화폐가 코인인 미래를 가정한 테스트넷 시연 · 실가상자산·실화폐 없음")를 함께 반환한다.
**예외 / 제한사항**
- 불변식 불일치(`COIN_RESERVE_MISMATCH`, 409 / 개명 제안 `COIN_SUPPLY_MISMATCH` — 지급·release 중단 상태를 화면에 함께 표시)
- 조회 실패(`COMMON_EXTERNAL_SERVICE_ERROR`, 502, 캐시 값과 조회 시각 표시)
**비고**
- 요구사항 흐름: 발행량·에스크로 공시 조회
- **v5 개편** — 예치 잔액 대조가 사라지고 **발행량·에스크로·지갑 보유 3분할 대사**로 바뀌었다(P-11·§3.8-4, §14-30). 이 세계에는 코인 밖의 자산이 없으므로 대사 대상도 체인 안에서 닫힌다.
- API는 `GET /coin/supply`(API-coin-01) 하나이며 F-verify-02가 같은 응답으로 공개 화면 V-02를 구성한다. 이쪽은 수치 조회, 저쪽은 대사·고지 표시를 담당한다.

### B-9. 취소·환불 (`refund`)

### F-refund-01 환불액 미리보기

2. 수수료 구간에 따른 환불 예정 금액(KRWS)을 계산해 반환하고 표시 통화 환산을 병기한다.
3. **환불 코인이 관객 지갑으로 돌아온다는 것**을 문구로 함께 안내한다("Refunded to your wallet").
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
**비고**
- 요구사항 흐름: 환불액 미리보기
- [권] P-8(D-7 이전 전액 / D-3 이전 50% / D-3 00:00 이후 취소 불가).

### F-refund-02 개별 취소·환불
**선행조건**
- 소유자이며 티켓이 `ISSUED`이고 취소 마감 전이며 정산이 잠기지 않았다.
**트리거**
- 관객이 A-11에서 환불액을 확인하고 취소를 확정한다.
**동작**
1. 수수료 구간별 환불액을 재계산한다.
2. 운영자가 `Splitter.refund(showId, orderRef, 관객 지갑, teamIndex, refundAmount)`를 실행한다 — 에스크로에서 관객 지갑으로 KRWS를 보내고 **선택 카운터를 −1** 한다(별도 취소 tx 없음).
3. 202 접수 → jobId 폴링 → `Refunded` 이벤트 확정 시 환불을 `COMPLETED`, 티켓을 `CANCELLED`로 전이하고 `refund_tx_hash`·`to_wallet_id`를 기록한다.
4. 수수료분은 에스크로에 남아 정산 재원에 포함된다.
5. **환불 코인은 관객 지갑으로 돌아와 다음 예매에 쓰인다.** 총 발행량은 변하지 않는다.
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
- 이미 취소 요청됨(`REFUND_ALREADY_REQUESTED`, 409)
- 정산 잠금 이후 요청(`REFUND_AFTER_SETTLEMENT_LOCK`, 409, F-refund-03)
- `orderRef`당 누적 환불이 구매액 초과(`COMMON_CONFLICT`, 409, 컨트랙트가 revert)
- 환불 tx 실패(`REFUND_TRANSFER_FAILED`, 500, 자동 재시도)
**비고**
- 요구사항 흐름: 개별 취소·환불
- **v5 변경** — v4의 "환불 코인은 관객 잔액으로 남는다" 문장이 **"환불 코인은 관객 지갑으로 돌아온다"** 로 교체됐다(§3.4). 코인 밖으로 나가는 경로는 없다.
- 핵심 시연 경로 11단계. 잔액 정책의 근거는 §3.7(P-20)에 있다.

- F-refund-02와 같은 엔드포인트의 가드 조건이다. release 후 환불은 회수 불가하다는 정책 경계를 명문화한 행이다.

### B-12. 정산 (`settlement`)

> **v5 원칙 — `release`가 곧 수령 완료다(P-9·P-10).** 정산 종단 상태는 `RELEASED`이고, 그 뒤에 팀이 밟을 단계는 없다. 코인이 곧 돈이므로 리더 지갑에 KRWS가 들어온 시점이 끝이다(§3.6). 수령 확인은 `settlement_share.released`·`released_at`·`wallet_address` 세 컬럼이 담당한다.

### F-settlement-01 정산 조회
**선행조건**
- 참여팀 리더다.
**트리거**
- 공연자가 P-08 대시보드에 진입한다.
**동작**
1. 정산 상태 머신(`NONE` → `AGGREGATED` → `LOCKED` → `DISPUTE_OPEN` → `RELEASED` / `HALTED`)과 팀별 분배액을 조회한다.
2. `release_tx_hash`, 팀별 `released`(수령 여부)·`releasedAt`·`walletAddress`(수령 주소 스냅샷), **보증금 반환 상태**를 함께 반환한다.
3. 금액은 원 값 + 표시 통화 환산으로 표시하고, 확정된 팀에는 "Received" 배지를 붙인다.
**예외 / 제한사항**
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 정산 조회
- **v5 변경** — 응답에서 `withdrawnAmount`와 수령 후 단계 상태가 삭제됐다(§8 `settlement_share.withdrawn_amount` 컬럼 삭제). 종단은 `RELEASED` 하나다(P-10).

### F-settlement-02 집계 확정
**선행조건**
- 공연이 `ENDED`이며 취소 마감(D-3)이 지났다.
**트리거**
- 생성자 또는 ADMIN이 P-08에서 집계 확정을 누른다.
**동작**
1. 온체인 카운터(`choiceCountOf`)와 서버 집계를 대사한다.
2. 일치하면 운영자가 `Splitter.aggregate(showId, validTicketCount)`를 실행해 유효 티켓 수를 확정한다. 불일치면 자동 정산을 중단한다.
3. 잠긴 두 비율로 팀별 분배액을 산출해 `AGGREGATED`로 전이한다.
**예외 / 제한사항**
- 대사 실패(`SETTLEMENT_AGGREGATE_MISMATCH`, 409, 관리자 확인 후 진행)
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504)
**비고**
- 요구사항 흐름: 집계 확정
- **분배 공식(2단계 비율)** — `F = floor(R × bp_f / 10000)`, `S = floor(R × bp_s / 10000)`, `bp_f + bp_s = 10000`. 팀별로 `f_i = floor(F × w_i / 10000)`, `s_i = (T > 0) ? floor(S × n_i / T) : floor(S / N)`, `base_i = f_i + s_i`를 구하고 `dust = R − Σ base_i`를 공연 생성 팀에 귀속해 `Σ pay_i = R`(1원 오차 불허)을 만든다. `R`은 에스크로 잔액(구매 − 환불)이며 보증금은 별도 계정으로 제외한다.
- 산출은 컨트랙트가 수행하고 서버와 검증 페이지(F-verify-03)가 같은 공식을 재현해 세 값이 일치해야 진행한다. 핵심 시연 경로 13단계.

### F-settlement-03 정산 잠금

**비고**

### F-settlement-05 release 실행
**선행조건**
- 정산이 `LOCKED`이며 48시간이 지났거나 열린 이의제기가 없다. 발행량 대사 상태가 정상이다.
**트리거**
- 이의제기 기간 경과로 스케줄러가 자동 실행하거나, 생성자·ADMIN이 수동 실행한다.
**동작**
1. 미해결 이의제기와 발행량 불변식 상태를 확인한다(불일치면 중단).
2. 운영자가 `Splitter.release(showId)`를 실행해 **각 팀 리더 지갑으로 KRWS를 push 전송**한다(dust 포함, 이벤트 `Released(showId, teamWallet, amount)`).
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 정산을 `RELEASED`로 전이하고 `release_tx_hash`, 팀별 `released`·`released_at`을 기록한다.
4. **팀 리더에게 "₩412,300 received" 알림을 보내고 P-08에 "Received" 배지를 띄운다. 여기서 정산이 끝난다** — 이후 단계는 없다(§3.6).
5. 보증금 반환(F-performance-11)을 트리거한다.
**예외 / 제한사항**

- 아직 잠금 전(`SETTLEMENT_NOT_LOCKED`, 409)
- 이미 release됨(`SETTLEMENT_ALREADY_RELEASED`, 409)
- 발행량 불변식 불일치(`COIN_RESERVE_MISMATCH`, 409 / 개명 제안 `COIN_SUPPLY_MISMATCH`, release 중단 + 관리자 알림)
- 에스크로 잔액 부족(`COIN_ESCROW_INSUFFICIENT`, 409)
**비고**
- 요구사항 흐름: release 실행
- **v5 변경** — [권] P-10 대체. 4번의 "다음 단계 안내" 배지가 **수령 완료 배지**로 바뀌었다. 코인이 곧 돈이므로 팀이 추가로 서명할 것이 없다.
- 핵심 시연 경로 15단계이자 **마지막 자금 이동**. 분배액 합은 잠긴 규칙 × 카운터 재계산값과 1원도 다르지 않아야 한다(§3.8-3).

### B-13. 공개 검증 (`verify`)

> **v5 원칙 — 정산 검증(V-01)은 참여팀 전용, 발행량·에스크로 공시(V-02)는 공개.** 이 도메인은 자체 엔티티 없이 `settlement`·`rule`·`coin`·`chain_job`을 읽기 전용으로 조합한다. 검증 화면은 온체인 용어 노출이 허용되는 두 화면이다.

### F-verify-01 정산 검증 데이터 조회
**선행조건**
- 로그인 상태이며 해당 공연의 참여팀 리더다.
**트리거**
- 참여팀 리더가 V-01 화면에 들어간다.
**동작**
1. 참여팀 소속을 확인한다(로그인 필수). 개인정보는 포함하지 않는다.
2. **토큰 주소(`token()`)**·정산 컨트랙트 주소·잠긴 규칙(두 비율 bp·규칙 해시)·팀별 동의 tx·판매 시작 잠금 tx를 반환한다.
3. **에스크로 잔액(`escrowOf`)**·온체인 선택 카운터·유효 티켓 수·팀별 산출액·**`Released` 이벤트**·`release_tx_hash`·팀 지갑 주소·보증금 반환 tx를 반환한다.
4. §3.8 불변식 대사 결과를 함께 반환한다 — ① `totalSupply` = Σ(`Minted`)(지급의 합, 단조 증가) ② `escrowOf` = Σ구매 − Σ환불 − Σ분배 ③ Σ`Released` = 잠긴 규칙 × 카운터 재계산 합(1원 오차 0) ④ `totalSupply` = Σ지갑 잔액 + Σ(에스크로 + 보증금).
5. 각 tx 해시에 익스플로러 링크를 붙이고, 진행 중이면 현재 단계와 다음 단계 예정 시각을 표시한다.
**예외 / 제한사항**
- 비로그인 조회(`COMMON_UNAUTHORIZED`, 401)
- 참여팀 소속 아님(`COMMON_FORBIDDEN`, 403)
- 공연 없음(`PERFORMANCE_NOT_FOUND`, 404)
- 불변식 대사 실패(`SETTLEMENT_AGGREGATE_MISMATCH`, 409, 화면에 불일치 항목 표시)
**비고**
- 요구사항 흐름: 정산 검증 데이터 조회
- **v5 변경** — 4번 불변식 ①·④가 코인 안에서 닫히는 형태로 재정의됐다(예치 잔액 대조 삭제 — §3.8). 화면 문구에서도 코인 밖 자산 언급이 사라졌다. 핵심 시연 경로 17단계.

### F-verify-02 발행량·에스크로 공시
**선행조건**
- 없음(비로그인 가능 · `GUEST` actor 허용 경로 — §4).
**트리거**
- 누구나 V-02 화면에 진입한다.
**동작**
1. F-coin-02(`GET /coin/supply`)의 응답으로 **총 발행량 · 에스크로 합계 · 지갑 보유 합계 · 지급 건수 · 갱신 시각** 다섯 값을 표시한다(1분 캐시).
2. **불변식 4 대사 결과**를 항목별로 보여 준다 — `totalSupply` = Σ지갑 잔액 + Σ(에스크로 + 보증금)이 성립하는지, 불일치면 어느 항목이 얼마나 벌어졌는지.
3. **"화폐가 코인인 미래를 가정한 테스트넷 시연 · 실가상자산·실화폐 없음"** 고지를 함께 표시한다(§2.1).
4. 불일치 상태면 **지급·release가 중단됐다**는 사실을 함께 보여 준다(P-11).
5. 총 발행량은 소각이 없으므로 단조 증가한다는 설명을 한 줄로 덧붙인다.
**예외 / 제한사항**
- 불변식 불일치(`COIN_RESERVE_MISMATCH`, 409 / 개명 제안 `COIN_SUPPLY_MISMATCH`, 중단 상태 표시)
- 조회 실패(`COMMON_EXTERNAL_SERVICE_ERROR`, 502)
**비고**
- 요구사항 흐름: 발행량·에스크로 공시
- **v5 개편** — 공시 대상이 "코인 밖 예치 자산 ↔ 유통량" 대조에서 **"발행량 ↔ 지갑 + 에스크로"** 대사로 바뀌었다(P-11·§14-30). 이 세계에는 코인 밖 자산이 없으므로 공시도 체인 안에서 완결된다.
- API는 F-coin-02와 같은 `API-coin-01`이며 v4의 별도 공개 엔드포인트(API-verify-02)는 삭제됐다(§9). MINTER 키 유출 시 이 화면이 이상을 드러내는 감시 장치다(§2.3).

### F-verify-03 정산 재계산 검증
**선행조건**

**트리거**

**동작**

2. 브라우저가 잠긴 두 비율 × 온체인 카운터로 F-settlement-02의 공식을 그대로 실행해 팀별 분배액을 재계산한다(서버 계산값을 그대로 받아 쓰지 않는다).
3. 재계산 결과를 `Released` 이벤트 금액과 대조해 "불일치 0건"을 표시하고, 에스크로 잔액·발행량 불변식도 함께 대사한다. 계산은 2초 안에 끝낸다.
**예외 / 제한사항**

**비고**

### F-admin-09 온체인 실패 자동 재시도
**선행조건**
- 운영자 온체인 트랜잭션 또는 대납 전송이 `FAILED`이며 확정되지 않았다.
**트리거**
- 작업이 실패하면 시스템이 스스로 재시도한다(관리자 트리거 없음).
**동작**
1. 실패 유형을 판정한다 — 일시적 실패(운영지갑 KAIA 부족·nonce 충돌·타임아웃·RPC 오류)와 결정적 실패(revert·발행량 불일치)를 구분한다.
2. **`signer_type=OPERATOR` 작업만 새로 만들어 재전송한다.** 대상은 `createShow`·`startSale`·`refund`·`aggregate`·`lock`·`release`·`returnDeposit`·`halt`·`mint`다.
3. **`signer_type=USER` 작업(approve·purchase·deposit·agree)은 사용자 서명을 다시 만들 수 없으므로** 보고된 RLP 재전송(1회) 또는 receipt 재조회만 한다 — 서버에 사용자 키가 없기 때문이다. 최종 실패는 사용자에게 재시도를 안내한다.
4. 일시적 실패는 원래 멱등키를 유지한 채 즉시 3회, 이후 지수 백오프로 재시도한다.
5. 운영지갑 tx는 nonce 직렬 큐로 순서를 보장하고(대납 전송도 같은 큐를 쓴다), 재시도 횟수·결과를 감사 로그에 append-only로 남긴다.
**예외 / 제한사항**
- 결정적 실패(`COIN_RESERVE_MISMATCH` 409 / `COIN_MINT_FAILED` 500 / `REFUND_TRANSFER_FAILED` 500) — 즉시 중단 + 알림
- 운영지갑 KAIA 부족·nonce 충돌(`CHAIN_GAS_INSUFFICIENT` 500 / `CHAIN_NONCE_CONFLICT` 500) — 재시도 대상
- 확정 지연(`CHAIN_TX_TIMEOUT`, 504) — 재시도 대상
- 온체인 반영이 최종 실패하면 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다
**비고**
- 요구사항 흐름: 온체인 작업 자동 재시도
- **v5 변경** — 재시도 목록에서 소각·법정화폐 관련 작업이 빠지고 **대납 전송**이 들어왔다. 도메인별 구현은 F-coin-04이며(v4의 F-withdraw-04는 삭제) 전용 클라이언트 API는 없다.
- 운영지갑이 모든 사용자 tx의 fee payer이므로 nonce 직렬 큐와 KAIA 잔액 감시가 v5에서 더 중요해졌다(§14-27).

### D-2. 판단이 필요한 지점

1. **P0 API 합계 62 ↔ 57 → 교차 검증(9/2) 결론: API 명세서 v5 §17의 P0 59가 정본.** 결정 문서 v2 §9의 "약 62"는 v4를 70으로 잡은 개산이고, 이 표의 57은 기능이 참조하지 않는 P0 API 2개(관리자 전용 조회 등)가 빠진 수치다. 결정 문서 v2 §9는 P0를 "약 62"로 적었고 이 문서 §C-1의 P0(P1·P2 제외)는 57행이다. 차이 5행은 v4 §9가 P0로 세던 `[P1]` 행(API-member-02·08, API-wallet-03·04, API-coin-04)에서 온다. **API 명세서 v5 §19 검수표가 정본 수치를 확정해야 한다.**
2. **화면 `S-01`** — 결정 문서 v2 §10은 `S-01`을 개별 열거하지 않고 "나머지 유지"로 다룬다. F-entry-01(검표 페이지 접근)이 살아 있으므로 연관화면을 `S-01 검표 — 공연 선택`으로 유지했고, 그래서 §C-2가 34행·§10이 33개다. 화면설계 v5가 S-01을 S-02에 합치면 이 행과 합계를 함께 고쳐야 한다.
3. **금지 문자열과 삭제 이력의 충돌** — 결정 문서 v2 §15 ④는 `charge`·`withdraw`를 도메인·API·기능 ID로 쓰지 못하게 하지만, §15.3은 삭제 행을 `[v5 삭제]` 한 줄로 남기라고 지시한다. 두 지시를 함께 만족시키기 위해 **삭제 행을 §A-2 전용 표로 분리**하고 옛 ID를 참조용으로만 적었다. 본문 §B에는 해당 도메인 절이 존재하지 않는다. 노션 반영 시 §A-2 행을 "삭제" 상태로 남길지, 행 자체를 지울지는 오케스트레이터 판단이다.
4. **④ 금지 문자열과 ⑨ 필수 문장의 충돌** — §15 ⑨가 각 문서 개요에 1회 넣으라고 지시한 문장에는 ④가 금지한 낱말이 들어 있다. **⑨를 우선**해 §개요에 원문 그대로 1회 넣었고, 그 밖의 본문 서술에서는 해당 낱말을 쓰지 않았다.
5. **04에 없는 05 행의 근접 매핑(4건)** — F-team-02(내 팀 목록 조회) → "팀 정보 조회·수정", F-performance-04(내 팀 참여 공연 목록 조회) → "공연 탐색·상세 조회", F-performance-06(참여팀 제외) → "참여팀 초대·수락", F-admin-09(온체인 실패 자동 재시도) → "온체인 작업 자동 재시도". 요구사항 명세서 v5 담당자 확인이 필요하다.
6. **`공연 취소` / `공연 취소 일괄 환불` 통합** — 04는 두 도메인의 별개 흐름으로 두지만 05는 API-performance-12 하나가 상태 전환·일괄 환불·보증금 반환 트리거를 함께 처리하므로 F-performance-09 한 행에 두 흐름명을 적었다.
7. **`F-member-09`와 `F-member-06`의 API 공유** — 둘 다 `PATCH /members/me`를 쓴다. 화면(C-03·C-04)과 요구사항 흐름이 달라 행을 나눴으니, API 명세서 v5는 한 엔드포인트의 부분 갱신으로 기술하면 된다.
8. **`F-coin-01`과 `F-coin-10`의 경계** — F-coin-01은 mint 실행 엔진(멱등키·한도·불변식·`chain_job`)이고, F-coin-10은 관리자 화면·API·이력 조회다. 가입 자동 지급은 F-wallet-01 → F-coin-01 경로로만 흐르고 F-coin-10을 거치지 않는다. 구현이 한 서비스여도 문서상 두 행을 유지했다.
9. **`F-coin-02`와 `F-verify-02`가 같은 API를 공유** — 개편 후 두 행 모두 `API-coin-01`을 쓴다(v4에서는 각각 `/coin/supply`·`/public/reserve-proof`였다). 노션 DB에서 API 열이 중복되므로, 한 행으로 합칠지 조회(coin)·표시(verify)로 나눠 둘지는 요구사항 v5 §6 흐름 목록과 맞춰 정해야 한다. 이 문서는 §14-30을 근거로 **두 행 유지**를 택했다.
10. **`F-coin-08`의 기능 성격** — 런타임 사용자 흐름이 아니라 기동 시 바인딩이라 트리거가 사용자 행동이 아니다. 노션 DB에 넣을 때 "시스템 기능" 구분이 필요하면 별도 속성으로 표시해야 한다.
11. **잔액 부족 시 관리자 지급 의존** — MVP에서 잔액을 확보하는 유일한 경로가 F-coin-10(관리자 수동)이다. 리허설 중 관객이 스스로 해결할 수 없으므로, 시연 시나리오에 "관리자 화면을 띄워 둔다"는 운영 절차가 필요하다(§13 W5). 자동 재지급(잔액이 임계 미만이면 자동 mint)을 넣을지는 결정 문서 §14-29의 연장 안건이다.
12. **`F-wallet-06`의 서명 전 검증 범위** — 서버가 대납 서명·전송의 주체가 되면서 "임의 tx를 대납해 주지 않는" 검증이 새로 필요해졌다(`to`·함수 셀렉터·인자·발신자 대조). 검증을 얼마나 엄격하게 할지(예: `data` 전체 바이트 비교 vs 셀렉터 + 디코딩 인자 비교)는 백엔드·블록체인 담당자가 정해야 한다. 이 문서는 **셀렉터 + 디코딩 인자 비교**로 적었다.

### D-3. P2 예약(기능 행 없음)

외국인 자국 코인 ↔ KRWS 교환(`tUSDC`·`KRWSExchange` — 플랫폼 밖 가정, DEX 연동), `ExternalIssuer`(인가 발행사 코인·CBDC 어댑터 · 현실 매핑 설계만), 외부 지갑 교체 화면, NFT 티켓. MVP에는 컨트랙트를 배포하지 않고 기능 행도 만들지 않는다(§2.4·§14-32).

**P1 예약** — `[P1]` 표기 15행과 ERC20Permit 1-서명 결제(§14-6), 보증금 몰수(`forfeitDeposit`), 표시 환율 외부 시세 자동 갱신, 지갑 교체 화면(§14-14).
