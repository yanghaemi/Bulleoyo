## 1. 공통 전제 (SSOT)

### 1.1 범위

- **포함(P0)**: 기획 v2.1 §9 MVP 12개 — 공연자·팀 등록+팀 지갑 / 공연 생성 / 참여팀·정산 규칙·팀별 동의·잠금 / 예매+금융망 결제+KRWS 민팅 / 관람 목적 팀 선택(온체인) / 티켓 발급(동적 QR) / 취소·환불 / 양도(선물) / QR 입장 / 집계 / KRWS 분배(release)+환급 / 정산 조회+공개 검증 페이지(준비금 증명)
- **포함(P1, 문서에 "P1" 표기)**: 교환(옵션 변경) · 월렛 패스(구글) · 공연 기록(포토 티켓) · 카카오 로그인 · 관리자 신고/사용자 관리
- **제외(P2)**: NFT 티켓 · 유료 재판매 · NFC · 애플 월렛 · AI 기능 — 요구사항 명세서 "확장 범위"에만 나열, 기능·API·화면에는 넣지 않는다

### 1.2 사용자 유형 (actor)

| 코드 | 이름 | 설명 | 인증 |
|------|------|------|------|

### 1.4 정책 전제 [권] — 기획 §10 미결 안건의 문서 작성용 임시 확정

팀이 다르게 결정하면 §6 영향 매트릭스에 따라 해당 행만 고친다. 정책 번호는 화면 ID(`P-01`~`P-10`)와 접두가 같으므로 다른 문서에서 인용할 때는 **`정책 P-8`처럼 '정책'을 붙인다**.

| ID | 화면명 | 사용자 | 라우트 | 한 줄 |

### 1.9 문서 간 참조 규칙

- 화면은 항상 `ID 화면명`(§1.6). 기능 명세서 `연관화면`, API 명세서 "연관 화면", 화면설계 제목이 같은 문자열.
- API는 항상 `메서드 경로`(§1.7). 기능 명세서 `API`(2차에서 관계 연결), 화면설계 "연결 API".
- 기능은 기능 명세서 `기능`(제목) 문구를 요구사항 명세서의 기능 흐름 제목과 **같게** 쓴다(1:1 원칙). 요구사항 흐름 하나를 기능 여러 행으로 세분화한 경우 기능 명세서 표의 `요구사항 흐름` 열에 상위 흐름 제목을 적어 연결한다(노션 DB에는 `기능 설명` 앞에 `[요구사항: …]`로 붙인다). 요구사항에 없는 P1 기능은 `확장 범위(§10)`로 표기.
- 에러 사유는 규격 v3 코드명을 괄호로 병기한다 — 예: "재고 소진(`TICKET_SOLD_OUT`)".
- 상태값은 §1.5 문자열 그대로.

### 2.3 API 명세서 — opus

- **목적·독자**: FE·BE 계약. 규격 v3의 실제 인스턴스.
- **형식**: 엔드포인트마다 — 번호·이름 / 메서드·경로 / 권한(actor) / 설명 / Path·Query 파라미터 표 / Request Body(JSON 예시 + 필드 표: 이름·타입·필수·제약) / Response(성공 예시 — 래퍼 `{ code, data, msg }`, status 200/201/202) / 에러 코드 표(규격 v3 §3의 코드만, 발생 조건) / 비동기 여부(202 + jobId → `GET /api/v1/chain/jobs/{jobId}`) / 연관 화면·기능 / 비고(멱등키·rate limit·캐시).
- **공통 절**: 인증 헤더, 페이지네이션, 비동기 작업 폴링 규약, 멱등키 헤더(`Idempotency-Key`, 결제·취소·환급), 시간 표기(ISO 8601, KST), 금액(원 단위 정수), 주소·tx 해시 형식, 규격 v3 링크.
- **분량**: §1.7 P0 69개 전부 상세, P1 2개(API-member-08·API-admin-03)와 교환·월렛·기록 예약 경로는 경로만. 
- **신설 제안 절**: 규격 v3에 없는 코드가 필요하면 여기에 모아 두고 본문에는 쓰지 않는다(규격 §2 "문서에 없는 코드는 배포하지 않는다").
- **노션**: DB `APISpec` 행 생성 — `URI`(제목: `메서드 경로` 형식이 아니라 **경로만**, 메서드는 `메서드` 선택) · `API 이름` · `Query Params` · 본문은 **SSAFY 행 템플릿 순서**를 따른다: `## 요구사항` → `## Request`(`### Headers` Content-Type/Accept/Authorization · `### Cookies` · `### Body` json) → `### 시스템 처리` → `## Response`(`### 200 OK`·`201`·`202` 성공 json, 이어서 `400`·`401`·`403`·`404`·`409`·`410`·`429`·`502` 중 해당하는 status별 실패 json — 각 json은 규격 v3 래퍼). 로컬 md의 엔드포인트 절도 같은 순서로 써서 노션 반영 때 그대로 옮긴다. `기능명` 관계는 ② 행 생성 후 연결. 템플릿 뷰 "users | 유저 정보"는 무시하고 도메인별 뷰는 팀이 노션에서 추가.
- **검수**: 경로·메서드가 §1.7과 글자 단위로 일치, 에러 코드가 규격 v3에 존재, 상태값이 §1.5.

### 2.4 화면설계 (디자인 제외) — sonnet

- **목적·독자**: FE 2명이 Figma 와이어프레임을 그리기 전에 합의하는 **구조·흐름·컴포넌트 명세**. BE는 화면별 필요 API를 확인.
- **디자인 제외의 정의**: 색·타이포·아이콘·간격·이미지·모션·비주얼 톤은 다루지 않는다. 다루는 것은 화면 목록, 정보 구조, 흐름, 화면별 영역·컴포넌트·데이터 필드·액션·상태·검증 규칙·연결 API·연결 기능.
- **목차**: 개요·원칙(모바일 웹 360px 기준, 관객 화면 블록체인 용어 0, 검표 화면 1초 판정 피드백, 공개 검증 페이지 로그인 없음) / 사용자 유형별 정보 구조(IA)·네비게이션 / 화면 흐름도(mermaid — 관객 예매·양도·취소, 공연자 공연 생성→동의→정산, 검표, 공개 검증) / 화면 34개 명세(§1.6 순서; 각: 목적·진입 경로·영역 구성(헤더/본문/하단 액션)·컴포넌트 표(컴포넌트·유형·표시 데이터/입력 필드·동작·연결 API·연결 기능)·상태(로딩/빈/에러/권한 없음/처리 중 202)·입력 검증 규칙·모바일 고려) / 공통 컴포넌트(상태 배지, 202 진행 표시, tx 링크, 금액 표기, 토스트=`msg`) / 디자인 단계 인수인계 노트(Figma에서 정할 것 목록).
- **로컬 md**: 표와 mermaid만, ASCII 와이어프레임은 넣지 않는다(디자인 제외 원칙 유지).
- **노션**: 새 페이지 `[화면설계 v1] 구조·흐름·컴포넌트 (디자인 제외, 2026-08-28)` 문서 DB에 생성. mermaid는 코드 블록으로 그대로.
- **검수**: 화면 34개 전부 존재, 화면마다 연결 API가 §1.7에 있음, 관객 화면에 지갑·가스·tx 용어 없음(V-01·V-02 제외).

## 7. 규격 v3 개정 후보 — 문서 작성 중 수집 (v4에서 일괄 반영)

문서 본문에서는 쓰지 않고 각 문서의 "신설 제안" 절에만 적힌 것들을 여기에 **통일된 이름으로** 모은다. 04(요구사항)·06(API)이 각자 제안한 이름이 달랐던 항목은 규격 §1의 `도메인_사유` 규칙에 맞춰 코디네이터가 확정했고, 두 문서의 신설 제안 절도 이 이름으로 정렬한다. 규격 §2 "문서에 없는 코드는 배포하지 않는다" 원칙대로 **v4로 개정한 뒤에** 코드에 넣는다.
