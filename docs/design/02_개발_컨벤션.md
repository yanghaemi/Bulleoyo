## 3. Git

### 3.1 브랜치

- `master` — 배포 기준
- `develop` — 통합 기준
- **[팀]** 작업 브랜치는 **도메인 단위**로 만든다. 기능 하나당 브랜치를 만들지 않는다.
- **[팀]** 브랜치 이름에 Jira 키를 넣지 않는다 (협의 안건의 `feat/be/B204-12-ticket-transfer` 추천안은 폐기).

```
feat/{파트}/{도메인}   기능 개발   feat/be/settlement, feat/fe/ticket, feat/bc/splitter, feat/ml/recommendation
fix/{파트}/{내용}      버그 수정   fix/be/entry-qr
docs/{내용}            문서
```

저장소 README의 `feat/{파트}/{기능}` 구조를 유지하고, **리프를 기능 단위에서 도메인 단위로 바꾼다.** 파트 구분(be/fe/bc/ml)을 없애면 같은 도메인을 FE·BE가 함께 작업할 때 한 브랜치를 공유하게 되어 MR이 뒤엉킨다. **[ML, 2026-09-22]** ML 서버(노트북)·학습 스크립트·`ml/` 디렉터리 작업의 파트는 `ml`이다 — 예 `feat/ml/recommendation`.

도메인 목록: `member`, `wallet`, `team`, `performance`, `rule`, `ticket`, `payment`, `coin`, `refund`, `entry`, `settlement`, `verify`, `admin`, `contract`, `infra` **[Infra, 2026-09-07]** 도메인 목록을 API v6 13개 기준으로 정정. **[ML, 2026-09-22]** `recommendation` 추가(API v7 §14).

#### Jira 브랜치 생성 기능

- **[권]** Jira 이슈 화면의 **"Create branch" 버튼은 사용하지 않는다.** 브랜치는 로컬에서 직접 만든다.
- Jira의 branch name template은 `이슈 1개 = 브랜치 1개`를 전제로 `{이슈키}-{요약}` 형태를 생성한다. 템플릿 변수에 도메인 개념이 없어 `feature/settlement` 같은 이름을 만들 수 없고, 버튼을 누르면 Jira 키가 박힌 브랜치가 생겨 컨벤션을 위반한다. 그래서 템플릿을 수정하는 대신 기능 자체를 쓰지 않는다.

#### 연동 트레이드오프 (인지하고 갈 것)

브랜치·커밋에서 프로젝트 키(`S15P21B204-24` 형식)를 빼면 **Jira 개발 패널에 브랜치·커밋·MR이 자동으로 연결되지 않는다.** Jira는 정식 이슈 키 문자열만 스캔하므로 `#24` 표기로는 인식하지 못한다.

- **[팀, 2026-08-31 변경]** 자동 연동을 살리기로 결정했다. **커밋 메시지 본문 마지막 줄에 정식 키(`S15P21B204-24`)를 쓴다.** 브랜치 이름 규칙(`feat/{파트}/{도메인}` 등, 프로젝트 키 미포함)은 그대로 유지 — 브랜치는 도메인 단위라 이슈 1:1 매핑이 안 되므로 브랜치명에는 키를 넣지 않는다.
- 커밋 메시지에 정식 키를 쓰면 GitLab이 이를 Jira 이슈로 인식해 브랜치·커밋·MR을 개발 패널에 자동으로 연결한다. 클로징 키워드(`Closes` 등)를 함께 쓰지 않는 한 이슈가 자동으로 닫히지는 않는다(아래 "Auto-close" 항목 참고).

#### GitLab의 "Auto-close referenced issues on default branch"

**기본값 그대로 두면 된다.** 이 옵션은 **GitLab 이슈**에만 작동하며, Jira 이슈는 이것으로 닫히지 않는다. 우리는 Jira로 이슈를 관리하므로 켜져 있어도 사실상 동작할 대상이 없다.

대신 실제로 지켜야 할 규칙이 하나 생긴다.

- **[권]** 커밋·MR 본문에 **클로징 키워드(`Closes`, `Fixes`, `Resolves`)를 쓰지 않는다.** 참조는 `S15P21B204-24`처럼 정식 키만 적는다.
  - 정식 키(`S15P21B204-24`)는 GitLab 자체 이슈 번호 형식(`#24`)과 겹치지 않으므로 GitLab 이슈가 엉뚱하게 닫힐 위험은 없다. 다만 Jira 쪽 스마트 커밋(smart commit) 연동이 켜져 있다면 클로징 키워드로 Jira 이슈가 전이될 수 있으므로, 상태 전이는 여전히 담당자가 Jira에서 직접 한다.
  - 키워드를 쓰지 않으면 GitLab의 "Auto-close" 설정이 켜져 있어도 아무 일도 일어나지 않는다.
- **[권]** 이슈 종료는 Jira에서 담당자가 직접 한다. 자동 종료에 의존하지 않는다 — 번다운 잔여량이 실제 진행과 어긋나는 것을 막기 위해서다.
- GitLab 이슈를 아예 쓰지 않기로 확정한다면 이 옵션을 꺼 두는 것이 사고 방지에는 더 확실하다. 필수는 아니다.

### 3.2 머지 전략 **[권]**

- 머지는 **GitLab MR로만** 한다. `develop`·`master`에 직접 push 금지.
- `feat/{파트}/{도메인}` → `develop`: **Merge commit(`--no-ff`)**. 도메인 브랜치는 여러 작업 커밋을 담는 긴 수명 브랜치라 squash하면 "커밋 단위 = 작업 단위" 규칙이 무의미해진다.
- `develop` → `master`: 릴리스 시점에 merge commit.
- 작업 브랜치가 develop을 따라갈 때는 `git pull --rebase origin develop`. develop 히스토리에 역방향 머지 커밋을 남기지 않는다.
- MR은 **1명 이상 승인** 후 머지. 리뷰어는 해당 도메인을 직접 작성하지 않은 사람으로 지정한다.
- MR 본문은 저장소의 `.gitlab/merge_request_templates/default.md`를 사용한다.
- 도메인 브랜치가 오래 살면 충돌이 커진다. 한 도메인 작업이 끝나면 즉시 MR을 올리고, 다음 작업은 새 브랜치에서 시작한다.

### 3.3 커밋

- **[팀]** **커밋 단위 = 작업 단위.** 하나의 커밋에 하나의 완결된 작업만 담는다. 여러 작업을 한 커밋에 섞지 않는다.
- **[권]** 메시지 형식: `type: 요약` — 요약은 한국어, 50자 이내, 마침표 없음.
- **[권]** 타입: `feat` `fix` `refactor` `style` `docs` `test` `chore` `build` `ci`
- **[팀]** 이슈가 있는 작업만 본문 마지막 줄에 **정식 Jira 키**(`S15P21B204-19` 형식)로 참조한다. 이슈 없이 처리한 간단한 작업은 참조 없이 본문에 내용을 적는다. 정식 키를 쓰는 이유는 Jira 개발 패널 자동 연동 때문이다(§3.1 연동 트레이드오프).

```
feat: 예매 시 관람 목적 팀 선택 저장

정산 집계의 입력값이므로 공동 공연에서는 필수로 검증한다.
S15P21B204-19
```

```
chore: 응답 래퍼 필드명 오타 수정
```

## 4. DB

- **[권]** 테이블·컬럼 이름은 snake_case, 테이블은 단수형.
- **[팀]** **PK 이름은 테이블별로 다르게 둔다.** `테이블명_id` 형식 — `member_id`, `performance_id`, `ticket_id`.
  - 이 규칙의 이점: FK 컬럼명이 참조 대상 PK와 그대로 일치해 조인 조건과 ERD가 읽기 쉬워진다.
  - 대가: PK 이름이 제각각이라 `id` 하나로 통일하는 제네릭 `BaseEntity`를 쓸 수 없다. 엔티티마다 `@Id` 필드를 따로 선언한다.
- **[권]** PK 타입은 `BIGINT AUTO_INCREMENT`.
- **[권]** MySQL 예약어를 테이블명으로 쓰지 않는다. `show`, `order`는 예약어라 백틱 없이 쓸 수 없으므로 **`performance`(공연)**, **`ticket_order`(주문)** 로 명명한다. 코드·API·문서에서도 같은 용어를 쓴다.
- **[권]** 금액 컬럼은 `BIGINT`(원 단위 정수). 테스트 토큰이 `decimals=0`, 1토큰=1원이라 소수가 발생하지 않는다. `DOUBLE`은 쓰지 않는다.
- **[권]** 공통 컬럼 `created_at`, `updated_at`은 `DATETIME(6)`. 소프트 삭제가 필요한 테이블만 `deleted_at`을 둔다.
- **[권]** 체인 관련 컬럼: 주소 `CHAR(42)`, 트랜잭션 해시 `CHAR(66)`, `token_id BIGINT UNSIGNED`.
- **[권]** 문자셋 `utf8mb4`, 정렬 `utf8mb4_0900_ai_ci`.
- **[권]** 인덱스 이름: `idx_테이블_컬럼`, 유니크 `uk_테이블_컬럼`, 외래키 `fk_자식_부모`.
- **[권, 2026-09-04]** 스키마 정본은 Flyway 마이그레이션(`V{n}__*.sql`)이다. JPA `ddl-auto=none`. 상태 컬럼은 MySQL `ENUM`이며 엔티티는 `@Enumerated(EnumType.STRING)`으로 매핑한다(Hibernate 6.3+의 enum 매핑 변경으로 `validate`와 충돌하므로 `validate`도 쓰지 않는다). ENUM 값 변경은 `ALTER TABLE … MODIFY … ENUM(...)` 마이그레이션과 코드 배포를 함께 계획한다.
- **[팀]** **ERD 도구는 ERD 클라우드**를 사용한다. 공유 링크를 팀 노션에 고정하고, 내보낸 이미지와 DDL을 `docs/design/`에 함께 커밋한다.

## 6. 아직 정하지 않은 것

- 스토리 포인트 정밀 산정 기준(도메인별 난이도 가중치 등) — 우선 피보나치 스케일(1/2/3/5/8/13)로 시작하고, 첫 스프린트 계획 회의에서 팀 기준으로 보정한다. **필드 자체는 이슈 등록 시 필수(§2 참고)이므로 기준 미확정을 이유로 비워두지 않는다.**
- **[팀]** 블록체인 관련 세부 컨벤션(컨트랙트 파일 구조, 테스트 네이밍, 배포 스크립트 규칙)은 학습을 진행하면서 조정한다. 현재는 권고안을 그대로 둔다.
