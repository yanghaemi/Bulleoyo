## B. 기능별 상세

### B-1. 회원·인증 (`member`)

### F-member-01 회원 가입(자체)
**선행조건**
- 이메일이 기존 회원과 중복되지 않는다.
**트리거**
- 방문자가 C-02 화면에서 이메일·비밀번호·이름·연락처·약관 동의를 제출한다.
**동작**
1. 요청 값을 검증하고 이메일 중복을 확인한다.
2. 비밀번호를 해시해 회원 레코드를 생성하고 인증 방식을 `LOCAL`로 기록한다.
3. 자동 로그인 없이 가입 완료 응답을 반환한다.
**예외 / 제한사항**
- 필수 값 누락·형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- 이메일 중복(`AUTH_EMAIL_DUPLICATED`, 409)
**비고**
- 요구사항 흐름: 회원 가입 (자체)
- [권] P-1 인증 방식 — v2에서 **자체 가입과 OAuth(카카오·네이버)가 모두 P0**다. OAuth 경로의 가입·로그인은 F-member-08에서 다룬다.

### F-member-02 로그인
**선행조건**
- 가입된 계정이 존재한다.
**트리거**
- 회원이 C-01 화면에서 이메일·비밀번호를 입력하거나, 카카오·네이버 로그인 버튼을 누른다(OAuth 경로는 F-member-08).
**동작**
1. 자격 증명을 검증한다. OAuth 전용 회원(`LOCAL`이 아닌 회원)이 비밀번호 로그인을 시도하면 거부하고 해당 OAuth 로그인을 안내한다.
2. 정지·탈퇴 상태 여부를 확인한다.
3. 액세스 토큰(30분)과 리프레시 토큰(14일, 서버 저장·회전)을 발급한다.
**예외 / 제한사항**
- 자격 증명 불일치(`AUTH_INVALID_CREDENTIALS`, 401, 아이디 없음과 비밀번호 불일치를 구분해 알리지 않는다)
- OAuth 전용 회원의 비밀번호 로그인 시도(`AUTH_INVALID_CREDENTIALS`, 401 + 해당 OAuth 로그인 안내)
- 로그인 요청 횟수 초과(`COMMON_TOO_MANY_REQUESTS`, 429)
**비고**
- 요구사항 흐름: 로그인·로그아웃(04는 로그인·로그아웃을 한 흐름으로 다루나, 05는 API 단위로 분리했다)
- [권] P-1 JWT access 30분 / refresh 14일(서버 저장·회전). OAuth 로그인도 같은 토큰 규격을 쓴다.

### F-member-03 액세스 토큰 재발급
**선행조건**
- 서버에 회전 가능한 리프레시 토큰이 저장돼 있다.
**트리거**
- 클라이언트가 액세스 토큰 만료(`AUTH_TOKEN_EXPIRED`) 응답을 받고 자동으로 재발급을 요청한다.

### B-4. 공연 (`performance`)

### F-performance-01 공연 생성
**선행조건**
- 로그인 상태이며 팀 리더다. 수정의 경우 공연 생성자이며 공연이 `DRAFT` 상태다.
**트리거**
- 리더가 P-03에서 제목·일시·장소를 입력해 생성을 요청하거나, 생성자가 판매 시작 전 정보를 수정한다.
**동작**
1. 공연 일시가 미래이고 입장 시각이 공연 일시와 정합한지 검증한다.
2. 공연 일시에서 **취소 마감(D-3 00:00)과 판매 마감(공연 시작 1시간 전)을 자동 계산해 저장한다.** 두 마감은 별개 시점이며, 취소 마감 이후에도 판매 마감까지 예매는 계속 가능하다.
3. 공연을 `DRAFT` 상태로 생성하고 생성자를 참여팀 리더로 등록한다.
4. 공연별 **검표 페이지 링크(서명 토큰)를 함께 자동 생성한다**(F-performance-07).
5. 판매 시작 전이면 제목·일시·장소 등 정보를 수정할 수 있고, 일시를 바꾸면 두 마감을 다시 계산한다.
**예외 / 제한사항**
- 일시 오류(`PERFORMANCE_DATE_INVALID`, 400)
- 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- 판매 시작 후 수정 시도(`PERFORMANCE_ALREADY_ON_SALE`, 409)
- 주최자 아님(`PERFORMANCE_NOT_OWNER`, 403)
**비고**
- 요구사항 흐름: 공연 생성(수정 포함 — 04는 별도 "공연 정보 수정" 흐름을 두지 않고 생성에 포함한다)
- 핵심 시연 경로 2단계("공동 공연 생성"). 티켓 타입·가격·수량은 F-performance-02(티켓 옵션 설정)로 분리했다.
- [권] P-9 시점 규칙(04 v2 §7.4) — 취소 마감 D-3 00:00 → 판매 마감 공연 시작 1시간 전(`ON_SALE` → `SALE_CLOSED`) → 공연 종료(`ENDED`).

### B-5. 정산 규칙 (`rule`)

### F-rule-01 정산 규칙 설정
**선행조건**
- 공연 생성자이며 공연이 `DRAFT` 상태다.
**트리거**
- 생성자가 P-05에서 균등·관객선택 두 비율(bp)을 입력하고 예상 분배액 시뮬레이션을 확인한다.
**동작**
1. 공연 상태가 `DRAFT` 또는 `PENDING_AGREEMENT`인지 확인한다.
2. **두 비율의 합이 10000bp(100%)인지 검증한다.** 각 항목은 0도 허용한다.
3. 규칙을 저장하고 규칙 해시(`rulesHash`)를 새로 계산한다. **규칙이 바뀌면 기존 팀별 동의는 전부 `PENDING`으로 초기화된다.**
4. 공연 상태를 `PENDING_AGREEMENT`로 전환한다.
**예외 / 제한사항**
- 비율 합 불일치(`RULE_RATIO_SUM_INVALID`, 400)
- 이미 잠긴 규칙 수정(`RULE_ALREADY_LOCKED`, 409)
- 주최자 아님(`PERFORMANCE_NOT_OWNER`, 403)
**비고**
- 요구사항 흐름: 정산 규칙 설정
- [권] P-5 정산 공식(기본값 **균등 5000·관객선택 5000**, 각 항목 0 허용). 핵심 시연 경로 4단계.
- **v2 변경** — v1의 **공통 비용 항목과 기획 기여 비율을 제거**해 2단계 공식으로 단순화했다. 이에 따라 `RULE_COMMON_COST_EXCEEDS_REVENUE`(409)는 이 문서에서 더 이상 사용하지 않는다. 나눗셈 버림 잔액(dust)은 **공연을 생성한 팀**에 귀속한다(04 v2 §7.2).

**비고**

### F-rule-03 정산 규칙 동의
**선행조건**
- 참여팀 리더이며 공연이 `PENDING_AGREEMENT` 상태다.
**트리거**
- 리더가 P-06에서 규칙 내용을 확인하고 동의 버튼을 누른다.
**동작**

2. 팀 지갑 서명으로 `agreeToRules(showId, rulesHash)` 트랜잭션을 전송한다.
3. 202 접수 → jobId 폴링(`GET /api/v1/chain/jobs/{jobId}`) → `CONFIRMED` 확정 시 해당 팀 동의 상태를 `AGREED`로 갱신한다.
**예외 / 제한사항**

- 이미 잠긴 규칙(`RULE_ALREADY_LOCKED`, 409)

**비고**

- [권] P-2(팀 키는 이 서명 1회에만 사용). 핵심 시연 경로 5단계, 서로 다른 주소가 같은 규칙 해시에 동의한 기록이 익스플로러에 남는 핵심 시연 장면.

### F-rule-04 판매 시작

2. `startSale()` 트랜잭션을 전송해 `locked=true`로 전환한다.
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정 시 공연 상태를 `ON_SALE`로 전환한다.
**예외 / 제한사항**

**비고**
- 요구사항 흐름: 판매 시작
- 핵심 시연 경로 6단계. 이후 규칙 setter는 전부 revert된다.

### F-coin-04 발행·소각 작업 자동 재시도

**동작**
1. 대상 공연의 정산 상태를 확인한다.
2. `LOCKED` 이상이면 온체인 회수가 불가하므로 요청을 차단하고 고객센터 문의 안내로 전환한다.
**예외 / 제한사항**
- 정산 잠금 이후 취소 시도(`REFUND_AFTER_SETTLEMENT_LOCK`, 409, 오프체인 준비금 정책으로 분리)
**비고**
- 요구사항 흐름: 정산 잠금 이후 취소 차단
- release 후 환불은 회수 불가하다는 정책 경계를 명문화한 행이다(기획 §8.3). F-refund-02와 같은 엔드포인트의 가드 조건이다.

### B-10. 양도 (`transfer`)

### F-transfer-01 양도 링크 생성
**선행조건**
- 소유자이며 티켓이 `ISSUED` 상태다.
**트리거**
- 관객이 A-09에서 양도 링크 생성을 요청한다.
**동작**
1. 티켓 상태가 양도 가능한지 확인한다(입장·취소·양도중 아님).
2. 24시간 만료 서명 토큰을 생성하고 티켓을 `TRANSFER_PENDING`으로 전환한다.
3. 카카오 공유용 링크를 반환한다.
**예외 / 제한사항**
- 양도 불가 상태(`TRANSFER_NOT_ALLOWED`, 409)
- 본인 소유 아님(`TICKET_NOT_OWNED`, 403)
**비고**
- 요구사항 흐름: 양도 링크 생성
- [권] P-13 양도(카카오 공유 링크, 24h 만료). 핵심 시연 경로 10단계.

### F-transfer-02 양도 정보 조회
**선행조건**
- 링크(토큰)가 유효하다.
**트리거**
- 링크를 받은 사람이 A-10에 접속한다.
**동작**
1. 토큰의 서명·만료·사용 여부를 확인한다. 만료된 토큰은 양도를 `EXPIRED`로 전이하고 티켓을 `ISSUED`로 되돌린다.
2. 토큰으로 티켓 요약 정보(공연 제목·일시·장소·티켓 종류·보낸 사람 표시 이름)를 조회한다. 개인정보와 QR은 포함하지 않는다.
3. 공동 공연이면 "양도 수락 시 관람 목적 팀을 선택합니다"를 안내한다.
4. **비회원이면 "회원 가입 후 양도를 받을 수 있습니다"를 안내하고 회원 가입·로그인 화면으로 유도한다.** 가입(자체 또는 카카오·네이버 OAuth) 후 양도 수락 화면으로 자동 복귀한다.
**예외 / 제한사항**
- 링크 없음(`TRANSFER_LINK_NOT_FOUND`, 404)
- 링크 만료(`TRANSFER_LINK_EXPIRED`, 410)
- 이미 사용된 링크(`TRANSFER_LINK_ALREADY_USED`, 409)
**비고**
- 요구사항 흐름: 양도 정보 조회
- 비로그인 상태에서도 조회 가능(수락은 로그인 필요, §1.2 GUEST 정의).
- **v2 추가** — 비회원 가입 유도 동선이 F-member-08(OAuth 로그인) P0 승격의 주요 근거다. 복귀 지점은 A-10 양도 수락 화면이다.

### F-transfer-03 양도 수락
**선행조건**
- 로그인한 관객이며 자기 자신에게 양도하는 것이 아니다. 공동 공연이면 관람 목적 팀을 선택했다.
**트리거**
- 관객이 A-10에서 로그인(또는 OAuth 가입) 후 관람 목적 팀을 고르고 수락을 누른다.
**동작**
1. 토큰의 서명·만료·사용 여부를 다시 확인하고, 동시 수락을 막기 위해 원자적으로 처리한다.
2. 자기 자신 양도 여부와 수락 후 보유 수량(1인 4매 이내)을 확인한다.
3. 소유자를 DB 트랜잭션으로 변경하고 티켓을 `ISSUED`(새 소유자)로 되돌린다.
4. 기존 QR 시드를 즉시 폐기하고 새 시드를 발급한다. 보낸 사람 화면의 QR은 그 즉시 무효가 된다.
5. **관람 목적 팀 재선택을 온체인에 반영한다** — 운영지갑이 `cancelChoice(ticketId)` → `recordChoice(ticketId, newTeamId)` 2건을 순서대로 전송한다. 요청은 `202`로 접수하고 jobId 폴링으로 확정을 확인하며, 양도 응답은 확정을 기다리지 않는다.
6. 양도를 `COMPLETED`로 전환하고 토큰을 무효화한다.
**예외 / 제한사항**
- 자신에게 양도 시도(`TRANSFER_SELF_NOT_ALLOWED`, 400)
- 링크 만료(`TRANSFER_LINK_EXPIRED`, 410)
- 이미 사용됨(`TRANSFER_LINK_ALREADY_USED`, 409)
- 수락 후 보유 수량 초과(`TICKET_PURCHASE_LIMIT_EXCEEDED`, 409)
- 동시 수락 충돌(`COMMON_CONFLICT`, 409)
- 2건의 온체인 트랜잭션 중 하나라도 실패하면 즉시 3회 재시도 후 시스템 자동 연장 재시도(F-admin-09). **온체인 반영이 실패해도 소유권 이전은 롤백하지 않으며**, 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다
**비고**
- 요구사항 흐름: 양도 수락
- [권] P-13(수락 즉시 소유자 변경 + QR 시드 재발급). 핵심 시연 경로 10단계.
- **v2 변경** — 종료 상태를 `ACCEPTED` → **`COMPLETED`**(04 v2 §5-1 `transfer.status`)로 맞추고, 관람 목적 팀 재선택(`cancelChoice`→`recordChoice` 2tx)을 동작에 추가했다. 온체인 반영은 F-ticket-10과 같은 경로를 쓴다.

### F-transfer-04 양도 취소·만료
**선행조건**
- 양도가 `PENDING` 상태다.
**트리거**
- 보낸 소유자가 A-09에서 양도 취소를 누르거나, 생성 후 24시간이 경과한다.
**동작**
1. 소유자가 취소를 요청하면 즉시 `CANCELLED`로 전환하고 티켓을 `ISSUED`로 되돌린다.
2. 24시간 경과 시 스케줄러가 자동으로 `EXPIRED`로 전환하고 티켓을 `ISSUED`로 되돌린다.
**예외 / 제한사항**
- 이미 수락됨(`TRANSFER_LINK_ALREADY_USED`, 409)
- 링크 없음(`TRANSFER_LINK_NOT_FOUND`, 404)
**비고**
- 요구사항 흐름: 양도 취소·만료
- [권] P-13(24h 만료). 만료 처리는 전용 클라이언트 API 없이 배치로 수행된다.

### B-11. 입장 (`entry`)

### F-entry-01 검표 페이지 접근
**선행조건**
- 유효한 검표 페이지 링크(서명 토큰)를 보유한다. **계정·로그인은 필요하지 않다.**
**트리거**
- 검표 담당자가 공유받은 링크로 S-01에 진입한다.
**동작**
1. 링크의 서명 토큰이 유효한지, 해당 공연의 것인지 검증한다.
2. 유효하면 해당 공연의 QR 스캔 화면(S-02)으로 이어지는 검표 화면을 표시하고, 입장 가능 시간대와 입장 요약(총 티켓 수·입장 완료 수)을 함께 보여준다.
3. 검표 담당자의 계정 정보는 서비스에 저장하지 않는다.
**예외 / 제한사항**
- 토큰 서명 불일치·만료·다른 공연의 토큰(`ENTRY_SCANNER_NOT_AUTHORIZED`, 403)
- 공연 없음(`PERFORMANCE_NOT_FOUND`, 404)
**비고**
- 요구사항 흐름: 검표 페이지 접근 (v2)
- **v2 변경** — v1의 "검표 공연 목록 조회"(`GET /api/v1/performances/staff/me`, STAFF 회원 지정 전제)를 폐지하고 링크 토큰 인증으로 대체했다. 링크 생성·공유는 F-performance-07.
- 화면 ID `S-01`(§1.6 명칭 "검표 — 공연 선택")은 유지하되 역할이 "배정 공연 목록"에서 "링크 진입·공연 확인"으로 바뀐다 — 명칭 변경 필요 여부는 "신설 제안" 참조.

### F-entry-02 QR 검증·입장 처리
**선행조건**
- 스캐너가 해당 공연의 검표 페이지 링크 토큰으로 접근한 상태다(F-entry-01).
**트리거**
- 검표 담당자가 S-02에서 관객 QR을 스캔한다.
**동작**
1. QR 서명과 만료 시각(발급 후 60초 이내)을 검증한다.
2. 검표 권한(공연별 검표 페이지 링크 토큰의 유효성·공연 일치)을 확인한다.
3. Redis `SETNX`로 원타임 처리해 중복 입장을 차단한다.
4. 입장 이력을 기록하고 티켓을 `USED`로 전환한다.
**예외 / 제한사항**
- QR 만료(`ENTRY_QR_EXPIRED`, 401, 화면에서 자동 재발급 유도)
- 서명 위조·복제(`ENTRY_QR_SIGNATURE_INVALID`, 401, 검표 이력에 기록)
- 중복 입장(`ENTRY_ALREADY_ENTERED`, 409, 최초 입장 시각 표시)
- 입장 허용 시간대 아님(`ENTRY_NOT_IN_TIME_WINDOW`, 409)
- 검표 권한 없음(`ENTRY_SCANNER_NOT_AUTHORIZED`, 403)
**비고**
- 요구사항 흐름: QR 검증·입장 처리
- [권] P-14. QR 보안은 서버 서명의 몫이며 블록체인 성과가 아니다(기획 §8.3). 핵심 시연 경로 12단계.
- **v2 변경** — 검표 권한 판정이 "회원의 STAFF 지정"에서 "검표 페이지 링크 토큰 검증"으로 바뀌었다(SEC-03). `ENTRY_SCANNER_NOT_AUTHORIZED`(403)는 유효하지 않은 링크로 검표를 시도한 경우에 쓴다.

### F-entry-03 입장 현황 조회
**선행조건**
- 유효한 검표 페이지 링크 토큰을 보유하거나, 참여팀 소속 회원이다.
**트리거**
- 검표 담당자·공연자가 S-03에서 입장 수·이력을 확인한다.
**동작**
1. 검표 페이지 링크 토큰이 해당 공연의 것으로 유효한지, 또는 요청자가 참여팀 소속인지 확인한다.
2. 공연별 입장 수/총 발급 수, 최근 이력, 중복·실패 시도 로그를 조회한다. 관객 개인정보는 표시하지 않고 티켓 식별 정보와 시각만 보여준다.
**예외 / 제한사항**
- 유효하지 않은 검표 페이지 링크(`ENTRY_SCANNER_NOT_AUTHORIZED`, 403)
- 검표 링크 없이 참여팀도 아닌 회원의 조회(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 입장 현황 조회
- **v2 변경** — 접근 주체를 "STAFF 회원"에서 "검표 페이지 링크 토큰 보유자 또는 참여팀 소속"으로 바꿨다.

### B-12. 정산 (`settlement`)

### F-settlement-01 정산 조회
**선행조건**
- 참여팀 소속 회원이다(정산 검증 페이지는 별도 화면, F-verify-01 — v2에서 이 역시 참여팀 전용이다).
**트리거**
- 공연자가 P-08 대시보드에 진입한다.
**동작**
1. 정산 상태 머신(`NONE`~`REDEEMED`)과 팀별 분배액·관련 tx를 조회한다.
**예외 / 제한사항**
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 정산 조회
- 없음.

### F-settlement-02 집계 확정
**선행조건**
- 공연이 `ENDED` 상태이며 취소 마감(D-3)이 지났다.
**트리거**
- 생성자 또는 ADMIN이 P-08에서 집계 확정을 누른다.
**동작**
1. 온체인 선택 카운터 합과 서버 집계를 대사한다.
2. 일치 시 잠긴 두 비율로 팀별 분배액을 산출해 정산 결과를 `AGGREGATED`로 확정한다. 불일치 시 자동 정산을 중단한다.
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정.
**예외 / 제한사항**
- 대사 실패(`SETTLEMENT_AGGREGATE_MISMATCH`, 409, 관리자 확인 후 진행)
**비고**
- 요구사항 흐름: 집계 확정
- [권] P-9 정산 시점(취소 마감 D-3 → 판매 마감 공연 시작 1시간 전 → 공연 종료 → 집계 확정). 핵심 시연 경로 13단계.
- **분배 공식(04 v2 §7.2, v2에서 2단계로 단순화)** — `E = floor(R × bp_e / 10000)`, `S = floor(R × bp_s / 10000)`이고 `bp_e + bp_s = 10000`이다. 팀별로 `e_i = floor(E / N)`, `s_i = (T > 0) ? floor(S × n_i / T) : floor(S / N)`, `base_i = e_i + s_i`를 구한 뒤 잔액 `dust = R - Σ base_i`를 **공연을 생성한 팀**에 귀속시켜 `Σ pay_i = R`(1원 오차 불허)을 만든다. **공통 비용·기획 기여 항목은 v2에서 제거됐다.**
- 분배 산출은 컨트랙트 안에서 수행하고 서버와 검증 페이지(F-verify-03)가 같은 공식을 재현하며, 세 값이 모두 일치해야 정산을 진행한다.

### F-settlement-03 정산 잠금
**선행조건**
- 정산이 `AGGREGATED` 상태다.
**트리거**
- 생성자 또는 ADMIN이 P-08에서 잠금을 실행한다.
**동작**
1. 집계 결과를 `LOCKED`로 전환한다.
2. 48시간 이의제기 기간을 시작한다(`DISPUTE_OPEN`으로 진입 가능).
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정.
**예외 / 제한사항**
- 집계 미확정 상태에서 시도(`SETTLEMENT_NOT_LOCKED`, 409)
**비고**
- 요구사항 흐름: 정산 잠금
- [권] P-9. 핵심 시연 경로 14단계.

### F-settlement-04 이의제기 제출
**선행조건**
- 참여팀 리더이며 정산이 `LOCKED` 상태이고 잠금 후 48시간 이내다.
**트리거**
- 리더가 P-08에서 이의 사유를 제출한다.
**동작**
1. 이의제기를 `OPEN` 상태로 접수한다.
2. 정산 상태를 `DISPUTE_OPEN`으로 전환하고 release 자동 실행을 보류한다.
**예외 / 제한사항**
- 이의제기 기간 아님(`SETTLEMENT_DISPUTE_PERIOD`, 409, 남은 시간 표시)
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 이의제기 제출
- [권] P-16 이의제기(48h, 접수 시 release 자동 실행 보류·수동 재개). 핵심 시연 경로 14단계.

### F-settlement-05 release 실행
**선행조건**
- 정산이 `LOCKED` 상태이며 48시간 경과했거나(자동), 열린 이의제기가 없다.
**트리거**
- 이의제기 기간 경과로 스케줄러가 자동 실행하거나, 생성자·ADMIN이 수동 실행한다.
**동작**
1. 이의제기 미해결 여부를 확인한다.
2. 컨트랙트 `release()`를 실행해 팀 지갑으로 KRWS를 분배한다.
3. 202 접수 → jobId 폴링(`GET /api/v1/chain/jobs/{jobId}`) → `CONFIRMED` 확정 시 정산 상태를 `RELEASED`로 전환한다.
4. F-redeem-03(자동 환급 실행)을 트리거한다.
**예외 / 제한사항**
- 이의제기 기간 중(`SETTLEMENT_DISPUTE_PERIOD`, 409)
- 아직 잠금 전(`SETTLEMENT_NOT_LOCKED`, 409)
- 이미 release됨(`SETTLEMENT_ALREADY_RELEASED`, 409)
**비고**
- 요구사항 흐름: release 실행
- [권] P-9(48h 경과 후 자동, 수동 트리거 병행). 핵심 시연 경로 15단계.

### B-13. 환급 (`redeem`)

**트리거**

**동작**

**비고**

- [권] P-10(팀 출금 버튼 없음, 이력 조회만).

### F-redeem-02 환급 자동 재시도
**선행조건**
- 대상 환급이 `FAILED` 상태다.
**트리거**
- 환급이 실패하면 **시스템이 스스로 재시도한다**(관리자가 트리거하지 않는다). **계좌 미등록으로 보류된 건은 팀이 P-02에서 정산 계좌를 등록하는 시점에 자동으로 재개한다.**
**동작**
1. 환급 상태가 `FAILED`인지 확인한다.
2. 팀 정산 계좌 등록 여부를 다시 확인한다. 미등록이면 등록 이벤트(F-team-07)를 기다렸다가 자동 재개한다.
3. **원래 멱등키를 그대로 사용해** 이체를 재요청하고, 성공 확인 후 소각(F-coin-05)을 진행한다. 중복 이체가 발생하지 않게 한다.
4. 환급을 `PENDING`으로 되돌려 즉시 3회까지 재시도한 뒤 지수 백오프로 연장 재시도한다.
5. 재시도 횟수와 결과를 감사 로그에 남긴다.
**예외 / 제한사항**
- 이미 접수된 건에 중복 요청(`REDEEM_ALREADY_REQUESTED`, 409)
- 정산 계좌 미등록(`REDEEM_ACCOUNT_NOT_REGISTERED`, 409, 계좌 등록 시 자동 재개)
- 금융망 이체 실패 지속(`REDEEM_BANK_TRANSFER_FAILED`, 502, 재시도 횟수 증가 + 알림)
- 결정적 실패는 즉시 중단하고 알림을 보낸다
**비고**
- 요구사항 흐름: 환급 자동 재시도
- **v2 변경** — v1의 관리자 수동 재시도(`POST /api/v1/admin/redemptions/{redemptionId}/retry`, M-02)를 폐지하고 시스템 자동 재시도로 대체했다. 전용 클라이언트 API는 없으며 결과는 F-redeem-01(환급 이력 조회)로 노출된다. 04 v2 §12는 `REDEEM_ALREADY_REQUESTED`의 설명을 "자동 환급 작업이 이미 접수된 건에 재시도가 중복 요청된 경우"로 고칠 것을 제안한다.

### F-redeem-03 자동 환급 실행
**선행조건**
- 정산이 `RELEASED` 상태이며 팀 정산 계좌가 등록돼 있다.
**트리거**
- F-settlement-05(release 실행) 확정 이벤트가 발생한다.
**동작**
1. 팀별 KRWS 잔액을 확인한다.
2. KRWS 소각(F-coin-05)을 호출하고 금융망으로 팀 정산 계좌에 원화를 자동 이체(push)한다.
3. 환급 상태를 `TRANSFERRED`로, 실패 시 `FAILED`로 기록한다.
**예외 / 제한사항**
- 환급할 잔액 없음(`REDEEM_NOTHING_TO_REDEEM`, 409)
- 정산 계좌 미등록(`REDEEM_ACCOUNT_NOT_REGISTERED`, 409)
- 소각 실패(`COIN_BURN_FAILED`, 500, 금융망 이체 보류)
- 금융망 이체 실패(`REDEEM_BANK_TRANSFER_FAILED`, 502)
**비고**
- 요구사항 흐름: 자동 환급 실행
- [권] P-10 환급 방식(자동 push, 팀 출금 버튼 없음). 핵심 시연 경로 16단계.

### B-14. 정산 검증 (`verify`)

> **v2 원칙 — 정산 검증(V-01)은 참여팀 전용, 준비금 증명(V-02)만 공개.** F-verify-01·03은 로그인한 참여팀 소속 회원만 조회할 수 있고, F-verify-02(준비금 증명)와 F-coin-02(유통량·준비금)는 비로그인 공개를 유지한다. 이 도메인은 자체 엔티티 없이 `settlement`·`rule`·`coin`·`chain_job`을 읽기 전용으로 조합한다.

### F-verify-01 정산 검증 데이터 조회
**선행조건**
- **로그인 상태이며 해당 공연의 참여팀 소속 회원이다.**
**트리거**
- 참여팀 소속 회원이 로그인한 뒤 공연 상세의 링크나 직접 주소로 V-01 화면에 들어간다.
**동작**
1. 요청자가 해당 공연의 참여팀 소속인지 확인한다(로그인 필수). 개인정보는 어떤 항목도 포함하지 않는다.
2. 컨트랙트 주소·잠긴 규칙(두 비율 bp·규칙 해시)·팀별 동의 tx·판매 시작 잠금 tx를 조회한다.
3. 온체인 선택 카운터·유효 티켓 수·총 매출·팀별 산출액·release tx·환급 완료 여부를 함께 반환하고, 각 tx 해시에 익스플로러 링크를 붙인다.
4. 정산이 진행 중이면 현재 단계와 다음 단계 예정 시각을 표시한다.
**예외 / 제한사항**
- 비로그인 조회(`COMMON_UNAUTHORIZED`, 401)
- 참여팀 소속 아님(`COMMON_FORBIDDEN`, 403)
- 공연 없음(`PERFORMANCE_NOT_FOUND`, 404)
**비고**
- 요구사항 흐름: 정산 검증 데이터 조회
- 기획 §8.3 "보장하는 것"(결정론적 재현, 독립 검증 경로)의 실체. 핵심 시연 경로 17단계. 브라우저 재계산은 F-verify-03으로 분리했다.
- **v2 변경** — v1의 비로그인 공개 조회를 폐지하고 **참여팀 전용(로그인 필수)** 으로 전환했다. 공개로 남는 것은 준비금 증명(F-verify-02·F-coin-02)뿐이다. 이에 따라 경로에서 `/public`을 뺐다(`GET /api/v1/performances/{performanceId}/verification`) — "신설 제안" 참조.

### F-verify-02 준비금 증명 조회
**선행조건**
- 없음(비로그인 가능).
**트리거**
- 누구나 V-02 화면에 진입한다.
**동작**
1. 금융망 에스크로 계좌 잔액(API 조회)과 KRWS 총 유통량을 비교해 1:1 여부를 표시한다.
2. 결과는 1분 캐시로 제공하고 갱신 시각을 함께 표시한다.
**예외 / 제한사항**
- 준비금 불일치(`COIN_RESERVE_MISMATCH`, 409, mint·release 중단 상태 표시)
**비고**
- 요구사항 흐름: 준비금 증명 조회
- [권] P-11. 핵심 시연 경로 18단계. F-coin-02와 함께 같은 화면(V-02)을 구성한다.
- **v2 유지** — 정산 검증(V-01)이 참여팀 전용으로 바뀐 뒤에도 **준비금 증명(V-02)만 비로그인 공개를 유지한다.** 참여팀 확인 없이 조회할 수 있는 별도 엔드포인트로 제공한다(04 v2 `verify` 장).

### F-verify-03 정산 재계산 검증
**선행조건**
- **로그인한 참여팀 소속 회원**이며, F-verify-01의 검증 데이터(잠긴 두 비율·온체인 카운터·팀별 산출액)가 조회됐다.
**트리거**
- 참여팀 소속 회원이 V-01의 "재계산" 위젯을 실행한다.
**동작**
1. 요청자가 해당 공연의 참여팀 소속인지 확인한다(로그인 필수).
2. 브라우저(클라이언트)가 잠긴 두 비율 × 온체인 카운터로 04 v2 §7.2 공식을 그대로 실행해 팀별 분배액을 재계산한다. 서버 계산값을 그대로 받아 쓰지 않는다.
3. 재계산 결과를 서버가 표시한 값과 대조해 "불일치 0건" 여부를 표시하고, 온체인 분배액 합과 금융망 환급액 합의 대사 결과도 함께 보여준다. 계산은 2초 안에 끝낸다.
**예외 / 제한사항**
- 비로그인 조회(`COMMON_UNAUTHORIZED`, 401)
- 참여팀 소속 아님(`COMMON_FORBIDDEN`, 403)
- 검증 데이터 없음(`PERFORMANCE_NOT_FOUND`, 404)
**비고**
- 요구사항 흐름: 정산 재계산 검증
- 기획 §8.3 "참여팀의 독립 검증 경로"의 실체 — 심사위원이 **참여팀 계정으로 로그인해** 직접 재계산하는 핵심 시연 장면이다. 별도 API 없이 F-verify-01의 응답 데이터로 브라우저에서 계산한다.
- **v2 변경** — 비로그인 공개에서 참여팀 전용으로 전환됐다(F-verify-01과 동일 사유). 재계산 대상은 균등·관객선택 2비율이며 dust는 공연 생성 팀 귀속으로 검산한다.

- nonce 충돌(`CHAIN_NONCE_CONFLICT`, 500, 서버 내부 재시도 후 노출)
**비고**
- 요구사항 흐름: 확장 범위(§10) — 04 v2에서 "운영지갑·감사 로그 조회 화면"으로 P1 이관됐다.
- **v2 변경** — MVP 제외. 운영지갑 가스 부족·nonce 충돌은 화면 대신 알림으로 처리한다.

### F-admin-08 감사 로그 조회 [P1]
**선행조건**
- ADMIN 권한이다.
**트리거**
- 관리자가 M-04에서 감사 로그를 검색한다.
**동작**
1. 관리자 권한 행사·키 복호화 등 주요 이벤트의 감사 로그를 검색한다.
**예외 / 제한사항**
- 권한 없음(`COMMON_FORBIDDEN`, 403)
**비고**
- 요구사항 흐름: 확장 범위(§10) — 04 v2에서 "운영지갑·감사 로그 조회 화면"으로 P1 이관됐다. **로그 적재 자체는 MVP이고 검색 UI만 P1이다.**
- 팀 지갑 키 복호화(`WALLET_KEY_DECRYPT_FAILED`) 발생 시 감사 로그에 함께 남는다(기획 §6.1).

### F-admin-09 온체인 실패 자동 재시도
**선행조건**
- 온체인 트랜잭션 또는 금융망 이체 작업이 `FAILED` 상태이며 확정되지 않았다.
**트리거**
- 온체인 작업(`chain_job`·`coin_job`) 또는 환급 이체가 실패하면 **시스템이 스스로 재시도한다**(관리자가 트리거하지 않는다).
**동작**
1. 대상 작업의 실패 유형을 판정한다 — 일시적 실패(가스 부족·nonce 충돌·타임아웃·외부 API 오류)와 결정적 실패(컨트랙트 revert·준비금 불일치)를 구분한다.
2. 일시적 실패는 **원래 멱등키를 유지한 채** 즉시 3회까지 재시도하고, 그 뒤에는 지수 백오프로 연장 재시도한다. 대상은 `agreeToRules`·`startSale`·`recordChoice`·`cancelChoice`·mint·burn·`release`와 금융망 이체다.
3. 결정적 실패는 재시도하지 않고 즉시 중단한 뒤 알림을 보낸다.
4. 운영지갑 트랜잭션은 nonce 직렬 큐로 순서를 보장해 재시도가 순서를 깨지 않게 한다.
5. 재시도 횟수와 결과를 감사 로그에 append-only로 남긴다.
**예외 / 제한사항**
- 결정적 실패(`COIN_RESERVE_MISMATCH` 409 / `COIN_MINT_FAILED` 500 / `COIN_BURN_FAILED` 500) — 즉시 중단 + 알림
- 운영지갑 가스 부족·nonce 충돌(`CHAIN_GAS_INSUFFICIENT` 500 / `CHAIN_NONCE_CONFLICT` 500) — 재시도 대상
- 트랜잭션 확정 지연(`CHAIN_TX_TIMEOUT`, 504) — 재시도 대상
- 온체인 반영이 최종 실패하면 사용자 자산 상태는 서버가 책임지고, 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다
**비고**
- 요구사항 흐름: 발행·소각 작업 자동 재시도 / 환급 자동 재시도(공통 재시도 정책 — 04 v2 `admin` 장 서두와 §5 공통 운영 원칙 10번. 도메인별 흐름 2개를 아우르는 행이므로 "신설 제안" 참조)
- **v2 신설** — 04 v2가 관리자 수동 재처리(v1의 F-coin-04·F-redeem-02·F-admin-05)를 폐지하면서 생긴 시스템 기능이다. 도메인별 구현은 F-coin-04(mint/burn)·F-redeem-02(환급)이고, 그 밖의 온체인 트랜잭션(F-rule-03·04, F-ticket-10, F-transfer-03, F-refund-02, F-performance-09, F-settlement-02·03·05)도 같은 정책을 따른다.
- 전용 클라이언트 API는 없다. 비기능 REL-04·REL-09 대응.

## 신설 제안

본문에는 새 식별자를 쓰지 않았다. §1·04와 어긋나거나 판단이 필요했던 지점만 여기에 기록한다.

1. **교환·월렛 패스·관람 기록 전용 화면 없음** — §1.6에 옵션 교환(F-ticket-07)·구글 월렛 패스(F-ticket-08)·관람 기록(F-ticket-09) 전용 화면이 없어 기존 화면(A-08, A-08, C-03)에 연관지었다. 새 화면 ID(A-08·C-03 외의 것)는 만들지 않았다. 화면설계 문서에서 P1 확장 시점에 전용 화면 신설 여부를 검토해야 한다.
2. **교환·월렛 패스·관람 기록 전용 API 없음** — §1.7 P0/P1 인벤토리에 이 세 기능의 엔드포인트가 없다(§1.7 안내대로 "API 명세서 P1 예약 경로 절"에서 경로만 별도 정의 예정). F-ticket-07·08·09의 API 컬럼은 `-`로 비워 두었다.
3. **전용 클라이언트 API 없는 시스템 기능 9건** — F-wallet-04(가스 자동 충전), F-ticket-10(관람 목적 팀 선택 기록), F-ticket-11(티켓 발급), F-payment-03(결제 실패·타임아웃 처리), F-coin-05(KRWS 소각), F-verify-03(정산 재계산 검증)에 더해 **v2에서 F-coin-04(발행·소각 자동 재시도)·F-redeem-02(환급 자동 재시도)·F-admin-09(온체인 실패 자동 재시도)** 3건이 추가됐다. 04 요구사항 흐름에는 있으나 §1.7 인벤토리에 전용 엔드포인트가 없는 시스템 자동 처리·클라이언트 계산 기능이다. API 컬럼은 `-`이거나 트리거가 되는 기존 API를 재사용 표기했다. 운영·감사 관점에서 전용 조회 API가 필요하면 API 명세서 작성 시 신설을 제안한다.
4. **04에 없는 05 행의 근접 매핑(4건, 판단 필요)** — 다음 05 행은 04 v2의 61개 흐름에 정확히 대응하는 항목이 없어 가장 가까운 흐름에 연결했다. 04 담당자 확인이 필요하다. (v1의 7건 중 관리자 관련 3건은 해당 05 행이 `[P1]`·요구사항 흐름 "확장 범위(§10)"로 바뀌어 목록에서 빠졌다.)
   - F-team-02(내 팀 목록 조회) → "팀 정보 조회·수정"
   - F-performance-04(내 팀 참여 공연 목록 조회) → "공연 탐색·상세 조회"
   - F-performance-06(참여팀 제외) → "참여팀 초대·수락"
   - F-admin-09(온체인 실패 자동 재시도) → "발행·소각 작업 자동 재시도 / 환급 자동 재시도" — **04 v2는 도메인별 재시도 흐름 2개(coin·redeem)만 §6에 두고, 이를 아우르는 공통 재시도 정책은 `admin` 장 서두 문단과 §5 공통 운영 원칙 10번에 서술한다.** 05는 `agreeToRules`·`recordChoice`·`release` 등 mint/burn·환급 외 온체인 작업의 재시도 주체를 명시해야 해서 별도 행으로 세웠다. 04에 "온체인 실패 자동 재시도" 흐름을 신설할지 확인이 필요하다.
5. **`공연 취소`/`공연 취소 일괄 환불` 통합** — 04는 이 둘을 performance·refund 두 도메인의 별개 흐름으로 나누지만, 05는 API-performance-12 하나가 상태 전환과 일괄 환불을 함께 처리하므로 F-performance-09 한 행에 두 흐름명을 모두 적었다(신규 refund 행을 추가하지 않았다).
6. **v2에서 바뀐 API 경로 4건(§1.7 인벤토리 갱신 필요)** — 04 v2 반영으로 §1.7의 P0 인벤토리와 어긋나게 된 경로다. API 명세서 작성 전에 계획 문서 §1.7을 갱신해야 한다.
   - `API-member-08` — `POST /api/v1/auth/kakao`(P1) → **`POST /api/v1/auth/oauth/{provider}`(P0)**. 카카오·네이버를 한 경로로 받는다. 00 계획 §1.9의 "P-1 인증(카카오 P0 승격)" 항목이 실제로 확정된 것이다.
   - `API-performance-10` — `PUT /api/v1/performances/{performanceId}/staff`(검표 관계자 지정) → **`GET /api/v1/performances/{performanceId}/staff-link`**(검표 페이지 링크 조회). 쓰기에서 읽기로 성격이 바뀐다. `performance_staff` 엔티티도 폐지 대상이다(04 v2에서 v1 토글로 보존).
   - `API-entry-03` — `GET /api/v1/performances/staff/me`(STAFF 회원 기준) → **`GET /api/v1/entries/staff-page/{token}`**(링크 토큰 기준, 비인증 경로). 인증 방식이 JWT에서 서명 토큰으로 바뀌므로 규격 v3의 인증 헤더 규칙 적용 대상에서 제외해야 한다.
   - `API-verify-01` — `GET /api/v1/public/performances/{performanceId}/verification` → **`GET /api/v1/performances/{performanceId}/verification`**. 참여팀 전용(로그인 필수)이 되어 `/public` 접두가 맞지 않는다. 공개로 남는 것은 `API-verify-02`(`GET /api/v1/public/reserve-proof`)뿐이다.
7. **화면 ID `S-01`의 명칭** — §1.6은 `S-01`을 "검표 — 공연 선택"으로 부르지만, v2에서는 공연을 고르는 화면이 아니라 **검표 페이지 링크로 진입해 해당 공연 하나를 확인하는 화면**이다. 화면설계 문서에서 "검표 — 페이지 진입" 같은 명칭으로 바꿀지 확인이 필요하다. 문자열은 §1.6 값을 그대로 두었다.
8. **P1 화면 3개의 MVP 제외** — `M-01`(관리자 대시보드)·`M-03`(회원·공연 관리)·`M-04`(운영지갑·감사 로그)는 v2에서 P1 기능만 남아 MVP 화면설계 대상이 아니다. `M-02`(정산·작업 관리)도 P0로는 이의제기 처리 하나뿐이라 화면 범위를 대폭 줄여야 한다. §1.6 화면 인벤토리를 34개로 유지할지, MVP 30개로 줄이고 나머지를 P1 표기할지 결정이 필요하다.
9. **`RULE_COMMON_COST_EXCEEDS_REVENUE` 미사용** — v2에서 공통 비용 항목이 사라져 이 코드를 쓰는 지점이 없다. 규격 v3에서 제거할지, 예약 코드로 남길지 확인이 필요하다(04 v2 §12 신설 제안 표에는 포함돼 있지 않다).
10. **`API-chain-01`의 도메인 소속** — §1.3 도메인 코드에 "chain"이 없어(§1.3 코드 접두 표에서 `CHAIN_*`은 verify 도메인에 함께 묶여 있음) 온체인 작업 상태 폴링(`GET /api/v1/chain/jobs/{jobId}`) 공통 엔드포인트를 coin 도메인의 F-coin-01에 대표로 배치했다. rule·ticket·refund·performance·settlement 도메인의 비동기 함수들도 같은 엔드포인트를 폴링용으로 재사용한다고 명시했다. 별도 "공통" 도메인 신설 여부는 API 명세서 작성자와 협의가 필요하다.
