## B. 기능별 상세

### B-1. 회원·인증 (`member`)

### F-member-01 회원 가입
**선행조건**
- 이메일이 기존 회원과 중복되지 않는다.
**트리거**
- 방문자가 C-02 화면에서 이메일·비밀번호·이름·연락처·약관 동의를 제출한다.
**동작**
1. 요청 값을 검증하고 이메일 중복을 확인한다.
2. 비밀번호를 해시해 회원 레코드를 생성한다.
3. 자동 로그인 없이 가입 완료 응답을 반환한다.
**예외 / 제한사항**
- 필수 값 누락·형식 오류(`COMMON_VALIDATION_FAILED`, 400)
- 이메일 중복(`AUTH_EMAIL_DUPLICATED`, 409)
**비고**
- 요구사항 흐름: 회원 가입
- [권] P-1 인증 방식(이메일+비밀번호 자체 로그인 P0, 카카오 P1).

### F-member-02 로그인
**선행조건**
- 가입된 계정이 존재한다.
**트리거**
- 회원이 C-01 화면에서 이메일·비밀번호를 입력한다.
**동작**
1. 자격 증명을 검증한다.
2. 액세스 토큰(30분)과 리프레시 토큰(14일, 서버 저장·회전)을 발급한다.
**예외 / 제한사항**
- 자격 증명 불일치(`AUTH_INVALID_CREDENTIALS`, 401)
**비고**
- 요구사항 흐름: 로그인·로그아웃(04는 로그인·로그아웃을 한 흐름으로 다루나, 05는 API 단위로 분리했다)
- [권] P-1 JWT access 30분 / refresh 14일(서버 저장·회전).

### F-member-03 액세스 토큰 재발급
**선행조건**
- 서버에 회전 가능한 리프레시 토큰이 저장돼 있다.
**트리거**
- 클라이언트가 액세스 토큰 만료(`AUTH_TOKEN_EXPIRED`) 응답을 받고 자동으로 재발급을 요청한다.
**동작**
1. 리프레시 토큰의 유효성과 폐기 여부를 확인한다.
2. 새 액세스 토큰을 발급하고 리프레시 토큰을 회전한다.
**예외 / 제한사항**
- 액세스 토큰 만료 시에만 자동 재시도(`AUTH_TOKEN_EXPIRED`, 401)
- 서명 불일치·위조 토큰은 재시도 없이 즉시 로그아웃(`AUTH_TOKEN_INVALID`, 401)
**비고**
- 요구사항 흐름: 액세스 토큰 재발급
- [권] P-1. `AUTH_TOKEN_EXPIRED`와 `AUTH_TOKEN_INVALID`는 같은 401이지만 클라이언트 분기가 반대다(규격 v3 §1 예시).

### B-2. 공연팀 (`team`)

### F-team-01 팀 생성
**선행조건**
- 로그인 상태다.
**트리거**
- 회원이 P-02에서 팀 이름 등 기본 정보를 입력해 팀 생성을 요청한다.
**동작**
1. 팀 레코드를 생성한다.
2. 팀 지갑 생성(F-wallet-01)을 동기 호출해 EOA를 발급한다.
3. 지갑 생성 실패 시 팀 생성 트랜잭션 전체를 롤백한다.
**예외 / 제한사항**
- 지갑 생성 실패 시 팀 생성 자체 롤백(`WALLET_CREATION_FAILED`, 500)
- 형식 오류(`COMMON_VALIDATION_FAILED`, 400)
**비고**

### B-5. 정산 규칙 (`rule`)

### F-rule-01 정산 규칙 설정
**선행조건**
- 공연 생성자이며 공연이 `DRAFT` 상태다.
**트리거**
- 생성자가 P-05에서 공통 비용과 균등·관객선택·기획기여 비율(bp)을 입력한다.
**동작**
1. 세 비율의 합이 10000bp(100%)인지 검증한다.
2. 공통 비용이 총 매출을 초과하지 않는지 검증한다(시뮬레이션 단계).
3. 규칙을 저장하고 공연 상태를 `PENDING_AGREEMENT`로 전환한다.
**예외 / 제한사항**
- 비율 합 불일치(`RULE_RATIO_SUM_INVALID`, 400)
- 공통 비용이 매출 초과(`RULE_COMMON_COST_EXCEEDS_REVENUE`, 409)
**비고**

**동작**

**예외 / 제한사항**
- 없음(공개 조회, 캐시 만료 시 재조회).
**비고**

- [권] P-11. 핵심 시연 경로 18단계("준비금 증명").

### F-coin-04 발행·소각 작업 재시도

**트리거**

### F-coin-05 KRWS 소각
**선행조건**
- 소각 대상 금액이 확정됐다(취소 환불액 또는 팀 환급액).
**트리거**
- F-refund-02(개별 취소·환불) 또는 F-redeem-03(자동 환급 실행)이 내부적으로 호출한다.
**동작**
1. 대상 금액만큼 KRWS를 burn한다.
2. burn 작업은 jobId로 생성되며 폴링으로 `CONFIRMED`/`FAILED`를 확인한다.
3. 확정 시 후속 금융망 이체(환불 또는 환급)를 진행한다.
**예외 / 제한사항**

**비고**
- 요구사항 흐름: KRWS 소각
- 전용 클라이언트 API는 없으며 환불·환급 API 안에서 함께 처리된다(신설 제안 참조).

### B-9. 취소·환불 (`refund`)

### F-refund-01 환불액 미리보기
**선행조건**
- 소유자이며 티켓이 `ISSUED` 상태다.
**트리거**
- 관객이 A-11에서 취소 화면에 진입한다.
**동작**
1. 현재 시점이 D-7/D-3 중 어느 구간인지 계산한다.
2. 수수료 구간에 따른 환불 예정 금액을 계산해 반환한다.
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
**비고**
- 요구사항 흐름: 환불액 미리보기
- [권] P-8 취소 수수료(D-7 이전 전액 / D-3 이전 50% / D-3 00:00 이후 취소 불가).

### F-refund-02 개별 취소·환불
**선행조건**
- 소유자이며 티켓이 `ISSUED` 상태이고 취소 마감 전이며 정산이 잠기지 않았다.
**트리거**
- 관객이 A-11에서 환불액을 확인하고 취소를 확정한다.
**동작**
1. 수수료 구간별 환불액을 재계산한다.
2. KRWS 소각(F-coin-05)을 호출하고 금융망으로 환불 이체를 요청한다.
3. 컨트랙트의 `cancelChoice()`로 온체인 선택 카운터를 롤백한다(F-ticket-10 반대 처리).
4. 202 접수 → jobId 폴링(`GET /api/v1/chain/jobs/{jobId}`) → 확정 시 티켓을 `CANCELLED`로 전환한다.
**예외 / 제한사항**
- 취소 마감 경과(`REFUND_DEADLINE_PASSED`, 409)
- 이미 취소 요청됨(`REFUND_ALREADY_REQUESTED`, 409)
- 정산 잠금 이후 요청(`REFUND_AFTER_SETTLEMENT_LOCK`, 409, F-refund-03 참조)
- 환불 이체 실패(`REFUND_TRANSFER_FAILED`, 502, 재시도 대기)
**비고**
- 요구사항 흐름: 개별 취소·환불
- [권] P-8·P-9. 핵심 시연 경로 11단계.

### F-refund-03 정산 잠금 이후 취소 차단
**선행조건**
- 정산이 `LOCKED` 이상 상태다.
**트리거**
- 관객이 정산 잠금 이후에 F-refund-02와 동일한 취소 요청을 시도한다.
**동작**
1. 대상 공연의 정산 상태를 확인한다.
2. `LOCKED` 이상이면 온체인 회수가 불가하므로 요청을 차단하고 고객센터 문의 안내로 전환한다.
**예외 / 제한사항**
- 정산 잠금 이후 취소 시도(`REFUND_AFTER_SETTLEMENT_LOCK`, 409, 오프체인 준비금 정책으로 분리)
**비고**
- 요구사항 흐름: 정산 잠금 이후 취소 차단
- release 후 환불은 회수 불가하다는 정책 경계를 명문화한 행이다(기획 §8.3). F-refund-02와 같은 엔드포인트의 가드 조건이다.

### B-10. 양도 (`transfer`)

### F-transfer-01 양도 링크 생성
**선행조건**
- 소유자이며 티켓이 `ISSUED` 상태다.
**트리거**
- 관객이 A-09에서 양도 링크 생성을 요청한다.
**동작**
1. 티켓 상태가 양도 가능한지 확인한다(입장·취소·양도중 아님).
2. 24시간 만료 서명 토큰을 생성하고 티켓을 `TRANSFER_PENDING`으로 전환한다.
3. 카카오 공유용 링크를 반환한다.
**예외 / 제한사항**
- 양도 불가 상태(`TRANSFER_NOT_ALLOWED`, 409)
- 본인 소유 아님(`TICKET_NOT_OWNED`, 403)
**비고**
- 요구사항 흐름: 양도 링크 생성
- [권] P-13 양도(카카오 공유 링크, 24h 만료). 핵심 시연 경로 10단계.

### F-transfer-02 양도 정보 조회
**선행조건**
- 링크(토큰)가 유효하다.
**트리거**
- 링크를 받은 사람이 A-10에 접속한다.
**동작**
1. 토큰으로 티켓 요약 정보(공연·좌석 없음·상태)를 조회한다.
**예외 / 제한사항**
- 링크 없음(`TRANSFER_LINK_NOT_FOUND`, 404)
- 링크 만료(`TRANSFER_LINK_EXPIRED`, 410)
- 이미 사용된 링크(`TRANSFER_LINK_ALREADY_USED`, 409)
**비고**
- 요구사항 흐름: 양도 정보 조회
- 비로그인 상태에서도 조회 가능(수락은 로그인 필요, §1.2 GUEST 정의).

### F-transfer-03 양도 링크 수락
**선행조건**
- 로그인한 관객이며 자기 자신에게 양도하는 것이 아니다.
**트리거**
- 관객이 A-10에서 로그인 후 수락을 누른다.
**동작**
1. 자기 자신 양도 여부를 확인한다.
2. 소유자를 DB 트랜잭션으로 변경한다.
3. 기존 QR 시드를 폐기하고 새 시드를 발급한다.
4. 티켓을 `ISSUED`(새 소유자)로, 양도는 `ACCEPTED`로 전환한다.
**예외 / 제한사항**
- 자신에게 양도 시도(`TRANSFER_SELF_NOT_ALLOWED`, 400)
- 링크 만료(`TRANSFER_LINK_EXPIRED`, 410)
- 이미 사용됨(`TRANSFER_LINK_ALREADY_USED`, 409)
**비고**
- 요구사항 흐름: 양도 링크 수락
- [권] P-13(수락 즉시 소유자 변경 + QR 시드 재발급). 핵심 시연 경로 10단계.

### F-transfer-04 양도 취소·만료
**선행조건**
- 양도가 `PENDING` 상태다.
**트리거**
- 보낸 소유자가 A-09에서 양도 취소를 누르거나, 생성 후 24시간이 경과한다.
**동작**
1. 소유자가 취소를 요청하면 즉시 `CANCELLED`로 전환하고 티켓을 `ISSUED`로 되돌린다.
2. 24시간 경과 시 스케줄러가 자동으로 `EXPIRED`로 전환하고 티켓을 `ISSUED`로 되돌린다.
**예외 / 제한사항**
- 이미 수락됨(`TRANSFER_LINK_ALREADY_USED`, 409)
- 링크 없음(`TRANSFER_LINK_NOT_FOUND`, 404)
**비고**
- 요구사항 흐름: 양도 취소·만료
- [권] P-13(24h 만료). 만료 처리는 전용 클라이언트 API 없이 배치로 수행된다.

### F-entry-02 QR 검증·입장 처리
**선행조건**

**트리거**

**동작**

- 중복 입장(`ENTRY_ALREADY_ENTERED`, 409, 최초 입장 시각 표시)
- 입장 허용 시간대 아님(`ENTRY_NOT_IN_TIME_WINDOW`, 409)
- 검표 권한 없음(`ENTRY_SCANNER_NOT_AUTHORIZED`, 403)
**비고**
- 요구사항 흐름: QR 검증·입장 처리
- [권] P-14. QR 보안은 서버 서명의 몫이며 블록체인 성과가 아니다(기획 §8.3). 핵심 시연 경로 12단계.

### F-settlement-02 집계 확정
**선행조건**

**트리거**

**예외 / 제한사항**

### F-settlement-03 정산 잠금
**선행조건**
- 정산이 `AGGREGATED` 상태다.
**트리거**
- 생성자 또는 ADMIN이 P-08에서 잠금을 실행한다.
**동작**
1. 집계 결과를 `LOCKED`로 전환한다.
2. 48시간 이의제기 기간을 시작한다(`DISPUTE_OPEN`으로 진입 가능).
3. 202 접수 → jobId 폴링 → `CONFIRMED` 확정.
**예외 / 제한사항**
- 집계 미확정 상태에서 시도(`SETTLEMENT_NOT_LOCKED`, 409)
**비고**
- 요구사항 흐름: 정산 잠금
- [권] P-9. 핵심 시연 경로 14단계.

### F-settlement-04 이의제기 제출
**선행조건**
- 참여팀 리더이며 정산이 `LOCKED` 상태이고 잠금 후 48시간 이내다.
**트리거**
- 리더가 P-08에서 이의 사유를 제출한다.
**동작**
1. 이의제기를 `OPEN` 상태로 접수한다.
2. 정산 상태를 `DISPUTE_OPEN`으로 전환하고 release 자동 실행을 보류한다.
**예외 / 제한사항**
- 이의제기 기간 아님(`SETTLEMENT_DISPUTE_PERIOD`, 409, 남은 시간 표시)
- 참여팀 아님(`SETTLEMENT_NOT_PARTICIPANT`, 403)
**비고**
- 요구사항 흐름: 이의제기 제출
- [권] P-16 이의제기(48h, 접수 시 release 자동 실행 보류·수동 재개). 핵심 시연 경로 14단계.

### F-settlement-05 release 실행
**선행조건**
- 정산이 `LOCKED` 상태이며 48시간 경과했거나(자동), 열린 이의제기가 없다.
**트리거**
- 이의제기 기간 경과로 스케줄러가 자동 실행하거나, 생성자·ADMIN이 수동 실행한다.
**동작**
1. 이의제기 미해결 여부를 확인한다.
2. 컨트랙트 `release()`를 실행해 팀 지갑으로 KRWS를 분배한다.
3. 202 접수 → jobId 폴링(`GET /api/v1/chain/jobs/{jobId}`) → `CONFIRMED` 확정 시 정산 상태를 `RELEASED`로 전환한다.
4. F-redeem-03(자동 환급 실행)을 트리거한다.
**예외 / 제한사항**
- 이의제기 기간 중(`SETTLEMENT_DISPUTE_PERIOD`, 409)
- 아직 잠금 전(`SETTLEMENT_NOT_LOCKED`, 409)
- 이미 release됨(`SETTLEMENT_ALREADY_RELEASED`, 409)
**비고**
- 요구사항 흐름: release 실행

## 신설 제안

본문에는 새 식별자를 쓰지 않았다. §1·04와 어긋나거나 판단이 필요했던 지점만 여기에 기록한다.

1. **교환·월렛 패스·관람 기록 전용 화면 없음** — §1.6에 옵션 교환(F-ticket-07)·구글 월렛 패스(F-ticket-08)·관람 기록(F-ticket-09) 전용 화면이 없어 기존 화면(A-08, A-08, C-03)에 연관지었다. 새 화면 ID(A-08·C-03 외의 것)는 만들지 않았다. 화면설계 문서에서 P1 확장 시점에 전용 화면 신설 여부를 검토해야 한다.
2. **교환·월렛 패스·관람 기록 전용 API 없음** — §1.7 P0/P1 인벤토리에 이 세 기능의 엔드포인트가 없다(§1.7 안내대로 "API 명세서 P1 예약 경로 절"에서 경로만 별도 정의 예정). F-ticket-07·08·09의 API 컬럼은 `-`로 비워 두었다.
3. **전용 클라이언트 API 없는 시스템 기능 6건** — F-wallet-04(가스 자동 충전), F-ticket-10(관람 목적 팀 선택 기록), F-ticket-11(티켓 발급), F-payment-03(결제 실패·타임아웃 처리), F-coin-05(KRWS 소각), F-verify-03(정산 재계산 검증)은 04 요구사항 흐름에는 있으나 §1.7 인벤토리에 전용 엔드포인트가 없는 시스템 자동 처리·클라이언트 계산 기능이다. API 컬럼은 `-`이거나 트리거가 되는 기존 API를 재사용 표기했다. 운영·감사 관점에서 전용 조회 API가 필요하면 API 명세서 작성 시 신설을 제안한다.
4. **04에 없는 05 행의 근접 매핑(7건, 판단 필요)** — 다음 05 행은 04의 64개 흐름에 정확히 대응하는 항목이 없어 가장 가까운 흐름에 연결했다. 04 담당자 확인이 필요하다.
   - F-team-02(내 팀 목록 조회) → "팀 정보 조회·수정"
   - F-performance-04(내 팀 참여 공연 목록 조회) → "공연 탐색·상세 조회"
   - F-performance-06(참여팀 제외) → "참여팀 초대·수락"
   - F-coin-03(mint/burn 작업 목록 조회) → "발행·소각 작업 재시도"
   - F-admin-05(정산 목록·실패 건 조회) → "실패 작업 재처리"
   - F-admin-02·F-admin-04(회원 목록/공연 목록 관리 조회) → "회원·공연 관리"(04가 원래 하나로 묶은 흐름)
   - F-admin-07·F-admin-08(운영지갑/감사 로그 조회) → "운영지갑·감사 로그 조회"(04가 원래 하나로 묶은 흐름)
5. **`공연 취소`/`공연 취소 일괄 환불` 통합** — 04는 이 둘을 performance·refund 두 도메인의 별개 흐름으로 나누지만, 05는 API-performance-12 하나가 상태 전환과 일괄 환불을 함께 처리하므로 F-performance-09 한 행에 두 흐름명을 모두 적었다(신규 refund 행을 추가하지 않았다).
6. **`API-chain-01`의 도메인 소속** — §1.3 도메인 코드에 "chain"이 없어(§1.3 코드 접두 표에서 `CHAIN_*`은 verify 도메인에 함께 묶여 있음) 온체인 작업 상태 폴링(`GET /api/v1/chain/jobs/{jobId}`) 공통 엔드포인트를 coin 도메인의 F-coin-01에 대표로 배치했다. rule·ticket·refund·performance·settlement 도메인의 비동기 함수들도 같은 엔드포인트를 폴링용으로 재사용한다고 명시했다. 별도 "공통" 도메인 신설 여부는 API 명세서 작성자와 협의가 필요하다.
