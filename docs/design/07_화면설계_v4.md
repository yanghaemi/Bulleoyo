## 1. 개요·원칙

### 1.1 이 서비스가 화면에서 지켜야 할 전제

- **플랫폼이 시연용 가상 원화 스테이블코인을 발행·소각·준비금 공시한다.** 관객이 원화를 충전하면 발행(mint)되고, 팀이 원화로 받아가면 소각(burn)된다. 그 대차는 V-02 준비금 공시 화면이 공개한다. 인가 발행사 코인으로의 교체 가능성은 발표 Q&A·리스크 문서에서만 다루고 화면에는 나타나지 않는다.
- **지갑은 사용자 소유(Web3Auth/외부 지갑), 서버는 사용자 키를 보관하지 않는다.** 그래서 값이 움직이는 순간(결제·보증금·규칙 동의·팀 원화 출금 예치)에는 반드시 **사용자 서명 단계**가 화면에 들어간다. 서버가 대신 눌러줄 수 있는 액션은 판매 시작·환불·집계·잠금·release·보증금 반환·발행·소각뿐이다.
- **탈중앙을 주장하지 않는다.** 정산 흐름은 운영자가 발의하고 사용자가 서명한다. 화면 문구도 그 사실에 맞춘다.

### 1.2 화면 원칙 11개

1. **기준 폭**: 모바일 웹 360px. 관객 화면(A·C 접두)은 모바일 우선, 공연자(P)·관리자(M) 화면은 데스크톱 우선이되 모바일에서도 동작해야 한다(웹 전용, 컨벤션 §1).
2. **블록체인 용어 0 (개정)**: 관객이 보는 화면(A·C 접두)에는 가스·주소·tx 해시·컨트랙트·토큰·체인·mint/burn이라는 단어를 노출하지 않는다. **예외 3가지만 허용한다** — ① **V-01 정산 검증**(참여팀 리더 전용) ② **V-02 준비금 공시**(공개) ③ **서명 단계의 한 줄** `Confirm in your wallet` / "지갑에서 확인해 주세요"(§5.14). P·M 접두 화면(공연자·관리자)은 종전대로 전문 용어를 허용한다.
   - A-13의 문서상 화면명은 "내 지갑"이지만 **화면에 실제로 찍히는 라벨은 `Balance` / "잔액"** 이다. C-05 지갑 연결은 "이미 지갑이 있는 사람"만 오는 화면이라 지갑이라는 단어를 쓴다(진입 문구가 `Already have a wallet?`).
3. **금액 표기 (P-22)**: 금액은 **원 값(₩ 정수, 천 단위 구분)을 항상 먼저 쓰고**, 회원의 `display_currency`가 KRW가 아니면 **환산값을 `≈`로 병기**한다(예: `₩15,000 ≈ $11.10`). 환산은 **표시 전용**이며, 결제·환불·정산·분배·충전 요청에 실리는 값은 언제나 원 정수다. 환산값에는 사용한 환율과 시각을 툴팁으로 붙인다(§5.4).
4. **언어 (P-22·P-23)**: 관객 화면 문구는 **en 기본 + ko 병기**로 설계한다(타깃 = 외국인 관객). 공연자(P)·관리자(M) 화면은 ko. 모든 화면 헤더에서 **언어 스위치(en/ko)**에 닿을 수 있어야 한다(§5.11). 로그인 전에는 브라우저 로케일로 제안하고, 로그인 후에는 `member.locale`을 따른다.
5. **시간 표기 (P-22)**: 공연 일시·마감 시각·입금 기한은 **회원 시간대 기준으로 표시하고 KST를 괄호로 병기**한다(예: `Sep 20, 7:00 PM (KST 19:00)`). 공연은 한국에서 열리므로 KST가 사실상의 기준 시각이다(§5.13).
6. **서명 UX 원칙 (P-18)**: 사용자 서명이 필요한 액션은 ① **지갑 팝업을 띄우기 전에 무엇에 서명하는지 사람이 읽을 수 있는 요약**(금액·대상·건수)을 화면에 먼저 보여주고 ② **사용자가 팝업을 닫거나 거부하면 직전 화면 상태로 그대로 되돌린다**(진행 중이던 주문·요청은 사라지지 않는다) ③ **가스는 플랫폼이 자동으로 처리하므로 사용자에게 노출하지 않는다**(잔액 부족은 자동 충전으로 조용히 해결하고, 지연될 때만 "Preparing…"으로 표시한다). 서명은 결제 시 최대 2회(승인 → 결제)이며, 이미 승인이 충분하면 1회로 줄어든다.
7. **하단 탭 5개**: 관객 하단 탭은 **홈(A-01) · 내 티켓(A-07) · 주문내역(A-12) · 내 지갑(A-13) · 마이페이지(C-03)**. v3의 4개에서 "내 지갑"이 5번째로 들어왔다.
8. **비동기 작업(202) 처리**: `POST`가 `202 + jobId`를 반환하면 화면은 즉시 "처리 중" 상태로 전환하고 `GET /api/v1/chain/jobs/{jobId}`를 폴링해 결과를 반영한다. **사용자 서명 tx도 같다** — 프론트가 서명·전송한 뒤 `POST …/signed-tx {txHash}`로 보고하면 `202 + jobId`가 오고, 서버가 receipt·이벤트를 검증할 때까지 같은 방식으로 폴링한다. 완료 전 이탈 시에도 재진입하면 원본 리소스 조회 API로 최신 상태를 다시 가져온다.
9. **에러 처리**: 모든 실패 응답은 `code`로 분기하고, `msg`는 그대로 토스트에 노출한다(클라이언트는 `msg` 문자열로 분기하지 않는다). 규격 v3에 없는 코드(`CHARGE_*`·`WITHDRAW_*`·`WALLET_*`·`PAYMENT_SIGNATURE_REJECTED` 등)는 §8.2 "규격 v4 신설 제안"에 모아 두었다.
10. **토큰 재발급(전 화면 공통)**: 인증이 필요한 화면 어디서든 `AUTH_TOKEN_EXPIRED`(401)를 받으면 화면 전환 없이 `POST /api/v1/auth/refresh`로 조용히 재발급받아 원요청을 재시도한다. 개별 화면 절에는 반복 기재하지 않는다.
11. **체인·익스플로러**: 모든 tx 링크는 **Kaia Kairos(chainId 1001 = `0x3e9`)** 익스플로러(Kaiascan)를 새 창으로 연다. 프론트는 체인·컨트랙트 설정을 `GET /api/v1/coin/config`로 받아 지갑 SDK를 초기화한다(하드코딩 금지). **tx 링크는 P·M·V 화면에만 노출한다.**

### 1.3 v3에서 그대로 유지되는 규칙

- **검표 화면은 링크 토큰으로 접근한다**: 검표 담당자에게 계정을 만들지 않는다. 공연 생성 시 자동 생성된 공연별 검표 페이지 링크로 `/scan/:token`에 접속하면 로그인 없이 검표 화면이 열린다(SEC-03).
- **검표 판정 피드백**: S-02 QR 스캔 판정은 1초 이내에 색상 표시 + 소리 + 진동으로 알린다(PERF-03·UX-04).
- **V-01 접근 권한**: 정산 검증은 해당 공연의 참여팀 리더만 로그인 후 접근한다(AUDIT-01). 무로그인 공개는 **V-02 준비금 공시**만이다.
- **판매 마감과 취소 마감은 다르다**: 취소 마감은 공연일 D-3 00:00, 판매 마감은 공연 시작 1시간 전. 두 시각 사이는 "예매 가능·환불 불가" 구간이므로 A-02·A-03·A-11 문구에서 구분해 표기한다.

## 2. 사용자 유형별 정보 구조(IA)·네비게이션

### GUEST

- **진입점**: 홈(A-01), 공유된 공연 상세 링크(A-02), 로그인(C-01), 회원가입 보조 폼(C-02), 양도 수락 링크(A-10, 조회는 가능·수락은 로그인 필요), **준비금 공시(V-02, 로그인 불필요)**, 검표 페이지 링크(S-02, 링크 토큰만으로 접근). **정산 검증(V-01)은 GUEST 진입점이 아니다.**
- **네비게이션**: 하단 탭 없음. 상단에 홈 / **언어 스위치(en·ko)** / 로그인만 노출한다.
- **로그인 = 소셜 3버튼**: C-01은 **구글·페이스북·카카오** 버튼 3개가 주 액션이고 "이메일로 계속"이 보조다. 최초 로그인이 곧 가입이며, 이때 지갑이 자동으로 만들어지고 국가·언어·통화를 한 번 확인받는다(C-02 보조 폼 1회 노출).
- **권한 없는 화면 접근**: 로그인이 필요한 화면(예매·결제·내 티켓·내 지갑·마이페이지) 접근 시 C-01로 이동시키고 원래 경로를 저장해 로그인 성공 후 복귀시킨다. 토스트는 `COMMON_UNAUTHORIZED`의 `msg`를 그대로 띄운다.

### AUDIENCE

- **진입점**: 로그인 후 기본 홈(A-01).
- **네비게이션**: **하단 탭 5개** — 홈(A-01) · 내 티켓(A-07) · 주문내역(A-12) · **내 지갑(A-13)** · 마이페이지(C-03). 예매·결제·충전·양도·취소 흐름은 탭 바 없이 단계형(뒤로가기)으로 진행한다.
- **잔액 접점**: 잔액은 A-13(탭)과 A-05(결제) 두 곳에서 항상 확인할 수 있고, 충전(A-14)은 A-13 "Top up" 버튼과 A-05의 "Pay with card (KRW)" 두 경로로 들어간다.
- **설정**: 마이페이지(C-03)에서 **언어·통화 설정(C-04)**과 **지갑 연결(C-05)**로 들어간다. Web3Auth로 가입한 회원에게 C-05는 정보 표시 화면이고, 이메일로 가입한 회원에게는 **첫 결제 전 반드시 거쳐야 하는 화면**이다.
- **공연자 전환**: C-03에서 리더인 팀이 있으면 "내 팀" 버튼으로 PERFORMER 영역(P-01)에 들어간다. 같은 계정이 관객·공연자 역할을 동시에 가진다.
- **권한 없는 화면**: 본인 소유가 아닌 티켓 상세 접근 시 `TICKET_NOT_OWNED`(403) → 목록 복귀 + 토스트.

### PERFORMER (한국인 팀 리더)

- **진입점**: C-03 "내 팀" 또는 로그인 시 리더인 팀이 있으면 P-01로 바로 진입.
- **네비게이션**: 데스크톱은 사이드 메뉴 — 대시보드(P-01) · 팀 관리(P-02) · (공연 선택 후) 참여팀·규칙·동의·판매현황·정산(P-03~P-08) · **팀 출금(P-09)** · 정산 검증(V-01, 참여팀 전용). 모바일은 상단 드로어 메뉴로 대체한다.
- **서명이 필요한 지점 3곳**: ① **P-03 보증금 납부**(공연 생성 직후, 규칙 설정 진입 전) ② **P-06 규칙 동의** ③ **P-09 "원화로 받기"**. 세 곳 모두 §5.14 서명 단계 컴포넌트를 같은 모양으로 쓴다.
- **지갑 = 리더 지갑 = 팀 지갑**: 팀에 별도 지갑을 만들지 않는다. P-02는 리더 지갑의 주소·잔액·익스플로러 링크와 정산 계좌를 함께 보여주고, 잔액이 모자라면 A-14 충전으로 보낸다.
- **권한**: 팀 리더만 공연자 화면에 진입한다(팀원 개념 없음). 공연 생성자 전용 기능(공연 수정·참여팀 관리·규칙 설정·판매 시작·집계 확정·잠금·release·공연 취소·보증금)은 다른 참여팀 리더에게 비활성 처리한다.
- **권한 없는 화면**: 자기 팀이 아닌 공연 관리 화면 접근 시 `PERFORMANCE_NOT_OWNER`/`COMMON_FORBIDDEN`(403) → 안내 후 P-01 복귀.

### STAFF (검표 담당자 — 링크 토큰)

- **진입점**: 계정·로그인이 없다. 공연 생성자에게 공유받은 검표 페이지 링크 `/scan/:token`(S-02)이 유일한 진입점이다.
- **네비게이션**: 별도 탭·메뉴 없음. S-02 → S-03(입장 현황)의 단일 목적 흐름만 제공하며, 두 화면 모두 같은 토큰을 라우트에 유지한다.
- **권한 없는 화면**: 토큰이 위조·만료되었거나 다른 공연의 토큰이면 `ENTRY_SCANNER_NOT_AUTHORIZED`(403) → 접근 차단 안내(링크 재요청 안내). 복귀할 목록이 없으므로 홈(A-01) 이동 버튼만 제공한다.

### ADMIN

- **진입점**: 관리자 로그인 후 M-02(이의제기 처리). **MVP 관리자 화면은 M-02·M-03 두 개다.**
- **네비게이션**: 상단에 이의제기(M-02) · **코인 운영(M-03)** 두 항목만 둔다. 대시보드·회원/공연 관리·운영지갑·감사 로그·실패 작업 수동 재처리는 P1로 이관했다(실패한 발행·소각·분배·출금은 시스템이 자동 재시도하고 결정적 실패만 알림).
- **M-03이 하는 일**: 표시 환율 등록·이력 확인과 **준비금 불일치 경고 확인**이다. 불일치가 감지되면 mint·release가 중단되고 이 화면에 중단 상태가 뜬다.
- **권한 없는 화면**: 관리자 권한 없는 계정의 `/admin/*` 접근은 `COMMON_FORBIDDEN`(403) → 홈 또는 로그인으로 리다이렉트.

## 4. 화면 명세 (35개)

> 표기 — 화면명 옆의 **[신설]·[부활]·[재설계]·[변경]·[유지]**는 결정 문서 §10의 처분이다. 관객 화면(A·C)의 문구는 `en 예시 / ko 병기` 형태로 적었다. 실제 구현은 i18n 키로 관리하고, 이 문서의 문구는 en 원문과 ko 대역의 기준값이다.

### C-01 로그인 **[재설계]**

- 사용자 GUEST / 라우트 `/login` / 진입 경로: 앱 최초 진입 시 로그인 버튼, 권한 없는 화면 접근 리다이렉트, 양도 수락(A-10) 로그인 유도 / 목적: **소셜 로그인 3종으로 인증하고, 최초 로그인이면 그 자리에서 가입과 지갑 준비까지 끝낸다.**
- **재설계 요지** — 이메일·비밀번호 폼이 주 액션이던 v3에서 **소셜 버튼 3개(구글·페이스북·카카오)가 주 액션**인 화면으로 바뀌었다. 최초 로그인 = 가입이며, 이때 사용자 소유 지갑이 자동으로 만들어진다(화면에는 지갑이라는 말을 쓰지 않는다). 이메일 로그인은 구분선 아래 "이메일로 계속"으로 내려간다.

**영역 구성**
- 헤더: 서비스 타이틀, **언어 스위치(en/ko)** · 본문: 소셜 로그인 버튼 3개(구글·페이스북·카카오), 구분선, "이메일로 계속" 접기 영역(이메일·비밀번호 폼), 안내 문구 · 하단 고정 액션: 없음(버튼이 본문에 있음)

**상태**
- 상태 매핑(§7 Payment): `REQUESTED` 요청됨 → `CHARGING` 충전 중 → `AWAITING_SIGNATURE` 서명 대기 → `PAYING` 확인 중 → `PAID` 결제 완료 / `FAILED` 결제 실패 / `REFUNDED` 환불됨
- 처리 중: 각 단계 202 폴링(`pollAfterMs` 간격). **화면을 이탈했다 돌아와도 `GET /orders/{orderId}/payment`로 현재 단계를 복원한다**
- **서명 거부·팝업 닫음**: `PAYMENT_SIGNATURE_REJECTED`(§8.2, 잠정 `COMMON_CONFLICT` 409) — 에러 화면이 아니라 결제 방식 선택 상태로 되돌리고 `Payment cancelled. Your balance is unchanged and the order is held for 15 minutes.` / "결제를 취소했어요. 잔액은 그대로이고 주문은 15분간 유지돼요."를 안내한다
- **충전 성공 + 서명 실패**: 충전된 금액은 **잔액으로 남는다**. `Your top-up is safe in your balance.` / "충전한 금액은 잔액에 그대로 있어요."를 명시한다
- 에러: `PAYMENT_AMOUNT_MISMATCH`(409) — 처음부터 다시 시도 안내 / `PAYMENT_INSUFFICIENT_BALANCE`(409) — 카드 결제로 전환 유도 / `PAYMENT_TX_MISMATCH`(§8.2, 잠정 `COMMON_CONFLICT` 409) — "결제 내역을 확인하는 중이에요" 후 재조회 / `CHARGE_CARD_DECLINED`(§8.2, 잠정 `PAYMENT_REQUEST_FAILED` 502) — 다른 카드 안내 / `PAYMENT_TIMEOUT`(504) — 주문내역(A-12) 확인 안내 / `PAYMENT_ALREADY_PAID`(409) — A-06으로 이동 / `TICKET_SOLD_OUT`(409) — 결제 직전 매진 시 잔액 그대로 유지하고 목록 복귀 / `WALLET_NOT_LINKED`(§8.2, 잠정 `COMMON_FORBIDDEN` 403) — C-05 이동
- 주문 만료: 15분 내 미결제 시 주문 `CANCELLED`. 충전분은 잔액으로 남으므로 `Your balance is unchanged.`를 함께 안내한다

**입력 검증**
- 카드 번호·유효기간·CVC 형식. 충전 금액은 자동 계산된 **부족분**이며 사용자가 직접 입력하지 않는다(임의 금액 충전은 A-14)

**모바일·접근성 고려**
- 서명 단계에서는 화면 이탈 방지 안내를 띄우고 뒤로가기를 막는다. 지갑 팝업이 새 창으로 뜨는 경우 팝업 차단 안내를 제공한다. 진행 단계는 색이 아니라 `1/2`·`2/2` 문자열로도 읽히게 한다. 터치 타겟 44px

**상태**
- 상태 매핑(§7 CoinCharge): `REQUESTED` 요청됨 → `FIAT_CONFIRMED` 결제 확인 → `MINTING` 잔액 반영 중 → `COMPLETED` 충전 완료 / `FAILED` 충전 실패 / `EXPIRED` 입금 기한 만료

**입력 검증**

**상태**
- 로딩: 스켈레톤 / 빈: 등록된 환율이 없으면 "환율을 먼저 등록하세요" — 이 경우 관객 화면의 환산 병기는 표시되지 않고 원 값만 나온다
- 에러: `COMMON_FORBIDDEN`(403), `COMMON_VALIDATION_FAILED`(400) — 환율 범위·통화쌍 오류, `COMMON_CONFLICT`(409) — 같은 통화쌍·적용 시각 중복
- 준비금 불일치: 배너를 화면 최상단에 고정하고, 해제 전까지 다른 액션보다 우선 노출한다

**입력 검증**
- 환율은 양수(소수점 6자리까지), 통화쌍은 정해진 목록. 적용 시각은 과거·현재만(미래 예약 없음). 하루 1회 등록을 권장하되 강제하지 않는다

**모바일·접근성 고려**
- 데스크톱 우선. 불일치 경고는 색이 아니라 문구와 배너 위치로 구분한다

### 5.2 202 처리 중 표시

- 트리거: `202 + { jobId, status: "IN_PROGRESS", pollAfterMs }` 응답. **운영자 실행 tx와 사용자 서명 tx 보고(`…/signed-tx`) 모두 같은 형태다.**
- 화면 반응: 액션 버튼을 비활성화하고 "처리 중" 배지 또는 모달을 노출, `pollAfterMs` 간격으로 `GET /api/v1/chain/jobs/{jobId}` 재조회.
- 종료 조건: `CONFIRMED` → 성공 상태로 갱신, `FAILED` → 에러 상태 + 재시도 안내(자동 재시도 대상이면 "확인 중"으로 표기).
- 화면 이탈 후 재진입: 원본 리소스 조회 API로 최신 상태를 다시 가져온다(로컬 상태에 의존하지 않음).
- **관객 화면에서는 `jobId`·tx 개념을 노출하지 않는다** — "확인 중…" / "잔액에 반영 중" 같은 결과 중심 문구만 쓴다.

### 5.3 tx 링크

- 표시: tx 해시를 앞 6자리…뒤 4자리로 축약해 보여주고, 탭하면 새 창으로 **Kaia Kairos(chainId 1001)** 익스플로러를 연다. 주소도 같은 축약 규칙을 쓴다.
- 사용 화면: **P-02·P-06·P-08·P-09·V-01·V-02·M-03.** 관객 화면(A·C)에는 노출하지 않는다.
- 익스플로러 URL은 `GET /api/v1/coin/config` 응답의 값을 쓴다(하드코딩 금지).

### 5.4 금액 표기 **(개정)**

- **원 값이 항상 먼저다**: `₩15,000` — 원 단위 정수, 천 단위 구분 기호, 소수점 없음(decimals=0).
- **환산 병기**: 회원의 `display_currency`가 KRW가 아니면 뒤에 `≈ $11.10`을 붙인다. 환산값에는 **적용 환율과 기준 시각을 툴팁**으로 붙인다(`1 USD = 1,350 KRW · Sep 2, 09:00 KST`).
- **환산은 표시 전용이다**: 결제·환불·충전·정산·분배 요청에 실리는 값은 언제나 원 정수다. 사용자가 입력하는 금액도 언제나 원이다.
- **환율이 없거나 조회에 실패하면 환산값만 감춘다** — 원 값은 어떤 경우에도 그대로 보여준다.
- 부호 표기: 잔액 이력에서 입금은 `+₩15,000`, 출금은 `−₩15,000`. 색이 아니라 부호와 유형 라벨로 구분한다.
- API 응답의 `display: {currency, amount, rate, rateAt}` 객체를 그대로 쓰고, 클라이언트가 환율을 재계산하지 않는다.

### 5.5 토스트

- API 응답의 `msg`를 그대로 노출한다. 성공 시 `msg`가 빈 문자열이면 토스트를 띄우지 않는다. 클라이언트는 `msg` 문자열로 분기하지 않고 `code`로만 분기한다.
- `Accept-Language` 헤더를 보내 서버가 en/ko `msg`를 내려주게 한다. 클라이언트 자체 문구(복사 성공 등)는 §5.5의 예외로 표기한다.

### 5.6 확인 모달

- 비가역 액션(양도 취소, 취소 확정, 집계 확정·잠금·release, 공연 취소, 이의 처리)에는 항상 확인 모달을 거친다. 모달 문구는 결과를 구체적으로 요약한다(예: `Cancel and get ₩15,000 back to your balance?`).
- **서명 팝업은 확인 모달을 대신하지 않는다** — 서명 전 요약(§5.14)이 그 역할을 한다.

### 5.7 빈 상태

- 아이콘·이미지 없이 안내 문구 + 다음 행동 버튼으로 구성한다(예: `No tickets yet.` + 홈으로 이동).

### 5.8 링크 복사·공유

- 사용 화면: A-09 양도 링크, P-04 검표 페이지 링크, P-08 정산 공유 링크.
- 구성: 링크 전문을 읽기 전용으로 노출 + "링크 복사" 버튼(클립보드) + (지원 브라우저에 한해) "공유" 버튼(Web Share API).
- 특정 메신저 SDK에 의존하지 않는다. 미지원·비보안 컨텍스트에서는 복사만 제공하고, 복사 API가 막힌 환경에서는 링크 전문을 그대로 둔다.

### 5.9 소셜 로그인 버튼 **(개정)**

- 사용 화면: C-01 로그인, C-02 가입 유도, A-10 가입 유도.
- **구성: 구글·페이스북·카카오 3개 버튼을 같은 크기로 세로 배치**하고, 이메일 폼과 구분선으로 나눈다. **소셜이 주 액션, 이메일이 보조**다(v3의 위계 반전).
- 복귀 경로: 콜백에서 돌아온 뒤 진입 전 저장한 경로로 이동한다. 양도 링크(`/transfers/:token`)에서 시작했으면 A-10으로 되돌린다. 최초 로그인이면 C-02 보조 폼을 1회 거친다.
- 제공자 브랜드 가이드(색·로고·최소 크기)는 디자인 단계에서 확정한다(§6).

### 5.10 잔액 카드 **[신설]**

- 사용 화면: C-03, A-05, A-13, A-14 완료 화면, P-01, P-02, P-09.
- 구성: **원 값(큰 위계) + 환산 병기(작은 위계) + 갱신 시각 + 액션 버튼**(관객 화면은 `Top up`, P-09는 액션 없음).
- 조회 실패 시: 금액 자리에 `—`와 "다시 시도" 링크를 두고 **다른 정보는 그대로 렌더한다**(카드 전체를 에러로 덮지 않는다).
- 진행 중 항목이 있으면 카드 하단에 "충전 처리 중 ₩30,000" 같은 보류 줄을 한 줄 붙인다.
- 관객 화면에서 카드 제목은 `Balance` / "잔액"이다. 지갑·주소·체인 정보를 넣지 않는다.

### 5.11 언어 스위치 **[신설]**

- 사용 화면: 전 화면 헤더(관객·GUEST 화면은 필수, 공연자·관리자 화면은 선택).
- 구성: `EN` / `한국어` 2값 토글. 비로그인은 브라우저 로케일로 초기값을 잡고 로컬에 저장, 로그인 후에는 `member.locale`을 따르며 변경 시 `PATCH /members/me`로 저장한다.
- 전환은 화면 새로고침 없이 문구만 교체하고 스크롤 위치를 유지한다. 서버 `msg`는 `Accept-Language`로 맞춘다.
- 세부 설정(표시 통화·시간대)은 스위치의 "더 보기"에서 C-04로 보낸다.

### 5.12 환전 고지 문구 **[신설]**

- 사용 화면: A-14(해외 카드 탭), A-05(카드 결제 선택 시).
- 문구: `You'll be charged ₩30,000. Your card issuer converts to your currency.` / "₩30,000이 청구되고, 카드사가 사용 통화로 환산해요."
- **국내 카드·가상계좌 탭에는 이 문구를 쓰지 않는다.**
- 함께 쓰는 보조 문구: `Converted amounts shown here are estimates.` / "여기 보이는 환산 금액은 참고용이에요."
- 플랫폼이 환전을 수행한다는 인상을 주는 표현(`we convert`, "환전해 드립니다")은 쓰지 않는다 — 환전은 카드사가 한다.

### 5.13 KST 병기 **[신설]**

- 사용 화면: 공연 일시·판매 마감·입장 시간·양도 만료·가상계좌 입금 기한·이력 시각 등 **시각이 나오는 모든 곳**.
- 표기: `Sep 20, 7:00 PM (KST 19:00)` / "9월 20일 오후 7:00 (KST 19:00)". 회원 시간대가 KST면 병기를 생략한다.
- 이유: 공연은 한국에서 열리고 마감·입장은 현지 시각 기준이므로, 회원 시간대만 보여주면 착오가 난다.
- 입력(공연자의 공연 일시 등)은 **KST 기준으로만 받는다**.

### 5.14 지갑 서명 단계 컴포넌트 **[신설]**

사용자 서명이 필요한 4개 액션 — **결제(A-05)·보증금(P-03)·규칙 동의(P-06)·팀 출금(P-09)**, 그리고 소유 증명 서명(C-05) — 이 모두 같은 컴포넌트를 쓴다.

| 단계 | 화면 | 문구(en / ko) |
|---|---|---|
| ① 요약 | 무엇에 서명하는지 사람이 읽을 수 있게 표시. 금액·대상·건수, 필요하면 축약 주소 | `Confirm ₩15,000 payment` / "₩15,000 결제를 확인해 주세요" |
| ② 대기 | 지갑 팝업이 뜬 상태. 진행 카운터(`1/2`·`2/2`) 표시 | `Confirm in your wallet` / "지갑에서 확인해 주세요" |
| ③ 확정 대기 | tx 해시 보고 후 서버 검증 | `Confirming…` / "확인 중…" |
| ④ 완료 | 결과 화면 전환 | `Done` / "완료" |
| ④' 거부 | **에러가 아니다.** 직전 화면 상태로 복귀 + 안내 | `Payment cancelled. Your balance is unchanged.` / "취소했어요. 잔액은 그대로예요." |

규칙:
- **팝업 전에 요약을 반드시 보여준다**(§2.3 사람이 읽을 수 있는 tx 표시). 요약 없이 곧바로 팝업을 띄우지 않는다.
- **거부·팝업 닫기는 실패가 아니다** — 진행 중이던 주문·요청은 유지되고, 이미 옮겨진 금액은 잔액으로 남는다. 화면은 에러 토스트 대신 안내 문구를 쓴다.
- **가스는 노출하지 않는다.** 잔액이 모자라면 플랫폼이 조용히 채운 뒤 진행하고, 그 대기 시간에는 `Preparing…` / "준비 중…"만 표시한다. 실패해도 "가스"라는 단어를 쓰지 않는다(`Couldn't start. Please try again.` / "시작하지 못했어요. 다시 시도해 주세요.").
- **관객 화면에서 허용되는 유일한 블록체인 어휘가 `wallet` / "지갑" 한 단어**다(§1.2 원칙 2).
- 승인이 이미 충분하면 카운터는 `1/1`로 줄어든다. 두 서명은 하나의 진행 표시로 묶는다.
- 서명 진행 중에는 뒤로가기·이탈을 막고 안내를 띄운다. 팝업이 새 창으로 뜨는 브라우저에서는 팝업 차단 안내를 제공한다.

### 5.15 provider 배지 **[신설]**

- 사용 화면: C-03, C-05, P-02, P-01(팀 잔액 카드).
- 값: `WEB3AUTH` → `Social account` / "소셜 계정 지갑"(로그인 제공자 아이콘 병기: 구글·페이스북·카카오), `EXTERNAL` → `External wallet` / "외부 지갑"(Kaia Wallet·MetaMask 이름 병기).
- **관객 화면(C-03)에서는 배지 문구를 "소셜 계정으로 연결됨"처럼 부드럽게 쓰고**, 공연자 화면(P-02)에서는 provider 값과 축약 주소를 함께 보여준다.
- 상태가 `SUSPENDED`면 배지 옆에 "이용 정지" 표시를 붙이고 결제·충전 액션을 비활성화한다.

### 8.4 화면이 의존하는 API 중 v4에서 신설된 것

`POST /auth/web3auth` · `GET /wallets/me` · `GET /wallets/me/transactions` · `POST /wallets/challenge` · `POST /wallets/verify` · `POST /wallets/me/gas` · `POST /performances/{id}/deposit/prepare` · `POST /performances/{id}/deposit/signed-tx` · `POST /performances/{id}/rules/agreements/prepare` · `POST /performances/{id}/rules/agreements/signed-tx` · `POST /orders/{id}/payment/signed-tx` · `POST /charges` · `GET /charges/{chargeId}` · `GET /charges/me` · `POST /charges/{chargeId}/simulate-deposit` · `GET /coin/rates` · `PUT /admin/coin/rates` · `GET /coin/config` · `POST /teams/{id}/withdrawals` · `POST /teams/{id}/withdrawals/{withdrawalId}/signed-tx` · `GET /teams/{id}/withdrawals` · `GET /public/reserve-proof`(부활).

삭제된 API에 의존하던 화면 정리: C-01·C-02의 구 OAuth 엔드포인트 2종 → `POST /auth/web3auth` 하나로 통합. P-02의 `GET /teams/{teamId}/wallet`·`…/wallet/transactions` → `GET /wallets/me`·`GET /wallets/me/transactions`로 대체(팀 지갑 = 리더 지갑). P-09의 `GET /teams/{teamId}/redemptions` → `GET /teams/{teamId}/withdrawals`로 개명. C-03의 `PUT /members/me/bank-account` → P1.
