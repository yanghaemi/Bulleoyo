## 2. 문제 정의

> 여러 밴드가 함께 여는 소규모 공동 공연은 예매·입장·정산이 구글폼·계좌이체·수기 명단·구두 합의로 흩어져 있고, **"누구 덕에 팔린 티켓인지"를 아무도 증명하지 못한 채 사후에 바뀌는 정산 규칙** 때문에 팀 사이의 분쟁이 반복된다.

## 3. 서비스 개요

이 서비스는 티켓 100매 이내 규모의 취미·인디 밴드 공동 공연을 대상으로, **티켓 예매·결제·입장·양도·취소부터 공연 수익의 팀별 정산까지**를 하나의 흐름으로 잇는다.

핵심은 정산이다. 공연을 만드는 팀은 티켓 판매를 시작하기 전에 정산 규칙(균등·관객 선택 비율)을 정하고, 참여팀은 각자의 팀 지갑으로 그 규칙에 동의하는 트랜잭션을 남긴다. 전원이 동의해야 판매가 시작되고, 그 순간 규칙은 스마트 컨트랙트에 잠겨 누구도 바꿀 수 없다. 관객은 예매하면서 "어떤 팀을 보러 오는지"를 한 팀 선택하고, 그 선택은 온체인 카운터에 기록된다. 공연이 끝나면 잠긴 규칙과 온체인 카운터로 팀별 분배액이 산출되고, 관객이 결제한 금액만큼 발행된 원화 스테이블코인(KRWS)이 팀 지갑으로 실제 분배된 뒤 소각되어 팀의 정산 계좌로 원화가 입금된다. 참여팀은 정산 검증 페이지에서 같은 값을 재계산할 수 있다.

금융망 API(SSAFY 교육용)는 원화의 입출금 창구(on/off-ramp)를 맡고, 온체인은 정산의 산출·근거·집행을 맡는다. 실제 가상자산은 사용하지 않으며 모든 자산은 테스트넷에서 모의 발행한 KRWS다.

## 5. 공통 운영 원칙

1. **블록체인이 보장하는 것** — 판매 시작 전에 잠긴 정산 규칙의 사후 변조 불가, 기록의 소급 수정 불가, 분배 계산의 결정론적 재현, 참여팀이 플랫폼 화면을 거치지 않고 검증할 수 있는 독립 경로. (기획 §8.3)
2. **블록체인이 보장하지 않는 것** — 입력 데이터(관객 선택·매출)의 진실성은 보장하지 않는다. "위조를 원천 차단한다"가 아니라 "위조하면 발각되는 구조"로 대응한다. **QR 입장 보안은 서버 서명 QR의 몫이며 블록체인의 성과로 서술하지 않는다.** 팀 지갑 키는 플랫폼이 보관하므로 탈중앙을 주장하지 않는다.
3. **관객 화면의 블록체인 용어는 0이다** — 지갑·가스·주소·트랜잭션·민팅 같은 단어를 관객 화면에 노출하지 않는다. 예외는 정산 검증 페이지(`V-01`·`V-02`)뿐이며, 이 화면은 검증을 목적으로 하는 사람을 대상으로 한다. (UX-01)
4. **온체인에는 비식별 데이터만 올린다** — 티켓 ID·팀 ID·지갑 주소·금액·규칙 해시만 기록하고, 개인정보·주문 상세·QR 원본은 서버에 둔다. (PRIV-01)
5. **자금은 한 방향으로만 흐른다** — 금융망 입금 확인 → 동일 금액 KRWS mint → 에스크로 예치 → 컨트랙트가 팀 지갑으로 분배(release) → 금융망 이체 성공 확인 → burn → 팀 정산 계좌 입금. **입금 확인 없는 mint는 금지**하고, **이체 성공 확인 전에 소각하지 않는다.** (CHAIN-08, 정산 지갑 문서)
6. **준비금은 1:1로 유지한다** — 금융망 에스크로 계좌 잔액 ≥ KRWS 총 유통량이 항상 성립해야 한다. 불일치가 확인되면 mint와 release를 중단하고 관리자에게 알린다(`COIN_RESERVE_MISMATCH`). 검증 페이지에 상시 공개한다. (REL-03)
7. **규칙은 잠긴 뒤 불변이다** — 전 참여팀 동의 후 판매를 시작하면(`startSale`) 정산 규칙·참여팀·티켓 옵션·공연 기본 정보의 변경이 서버와 컨트랙트 양쪽에서 모두 거부된다. 관리자도 예외가 아니다. (CHAIN-01)
8. **정산은 정해진 순서로만 진행한다** — 취소 마감(D-3) → 판매 마감(공연 시작 1시간 전) → 공연 종료 → 집계 확정 → 정산 잠금 → 이의제기 48시간 → release → 자동 환급. 순서를 건너뛴 요청은 거부한다. (CHAIN-02)
9. **온체인 처리는 비동기이고, 사용자에게는 서버 상태를 먼저 보여준다** — 트랜잭션이 필요한 요청은 `202`와 작업 식별자(`jobId`)로 접수하고, 화면은 `GET /api/v1/chain/jobs/{jobId}` 폴링으로 진행 중·완료·실패를 표시한다. 예매·결제·티켓 발급은 트랜잭션 확정을 기다리지 않는다. (PERF-04, UX-05)
10. **실패해도 사용자 자산 상태는 서버가 책임진다** — 온체인 기록이 실패하면 큐에 남겨 최대 3회 재시도하고, 그 뒤에는 시스템이 지수 백오프로 연장 재시도하며, 결정적 실패(컨트랙트 revert·준비금 불일치)는 즉시 중단하고 알림을 보낸다. 결제·mint·burn·이체에는 멱등키를 붙여 재시도가 중복 실행으로 이어지지 않게 한다. (REL-04, REL-09)
11. **모든 상태 변경은 지운 흔적 없이 남긴다** — 주문·티켓·정산의 상태 이력은 삭제 대신 전이로 기록하고, 관리자 작업·키 복호화·mint/burn/release는 감사 로그에 append-only로 남긴다. (AUDIT-05, SEC-11)
12. **모의 시연임을 고지한다** — 실제 가상자산을 사용하지 않는다. KRWS는 테스트넷 자체 발행 모의 스테이블코인이고 원화 입출금은 SSAFY 교육용 금융망 API로만 이뤄진다. 화면과 발표 자료에 "가정 기반 시연" 문구를 표시한다. (CON-01·CON-05)
13. **망을 분리한다** — 금융망 API 호출·지갑 키 복호화·KRWS mint/burn 처리는 인터넷에서 직접 도달할 수 없는 **내부 서브넷**에서만 수행하고, **API 서빙은 DMZ**에서 수행한다. 내부 서브넷의 아웃바운드는 NAT 게이트웨이의 허용 목록을 거친다. (SEC-14·SEC-15)

## 5-1. 상태 정의

서비스 전체에서 사용하는 상태 enum을 도메인별로 정리한다. 각 상태의 의미·진입 조건·허용 전이·해당 상태에서 가능/차단되는 행위를 명시한다.

### 회원 상태 (`member.status`)

| 상태 | 의미 | 진입 조건 | 허용 전이 | 비고 |
|------|------|-----------|-----------|------|
| `ACTIVE` | 활성 — 정상 이용 가능 | 회원 가입 완료 | → `SUSPENDED`, → `WITHDRAWN` | 모든 기능 이용 가능 |
| `SUSPENDED` | 정지 — 관리자가 이용을 중지한 상태 | 관리자 조치 | → `ACTIVE` (관리자 해제) | 로그인 차단, 보유 티켓은 유지 |
| `WITHDRAWN` | 탈퇴 — 회원 탈퇴 완료 | 회원 본인 요청 | 종단 상태 (복구 불가) | 개인정보 파기, 공연·정산 이력은 익명화 보존 |

### 팀 상태 (`team.status`)

| 상태 | 의미 | 진입 조건 | 허용 전이 | 비고 |
|------|------|-----------|-----------|------|
| `ACTIVE` | 활성 — 공연 참여·생성 가능 | 팀 생성 완료 | → `DISBANDED` | 정상 운영 |
| `DISBANDED` | 해산 — 소프트 삭제 | 리더 삭제 요청 + 조건 충족(진행 중 공연 없음, 지갑 잔액 0) | 종단 상태 | 과거 공연·정산 기록에서 팀명 유지, 지갑 키 비활성 보존 |

### 팀 초대 상태 (`team_invitation.status`)

| 상태 | 의미 | 진입 조건 | 허용 전이 | 비고 |
|------|------|-----------|-----------|------|
| `PENDING` | 대기 — 초대 발송 후 수락 전 | 리더가 초대 생성 | → `ACCEPTED`, → `EXPIRED` | 초대 링크 유효 |
| `ACCEPTED` | 수락 — 초대 수락 완료 | 대상 회원이 수락 | 종단 상태 | 토큰 무효화 |
| `EXPIRED` | 만료 — 기한 초과 | 만료 시각 도달 | 종단 상태 | 토큰 무효화 |

### 공연 상태 (`performance.status`)

| 상태 | 의미 | 진입 조건 | 허용 전이 | 해당 상태에서 가능한 행위 |
|------|------|-----------|-----------|--------------------------|
| `DRAFT` | 초안 — 생성 직후, 설정 중 | 공연 생성 | → `PENDING_AGREEMENT`, → `CANCELLED` | 공연 정보·티켓 옵션·참여팀 수정 가능 |
| `PENDING_AGREEMENT` | 동의 대기 — 정산 규칙이 설정됨, 팀별 동의 진행 중 | 정산 규칙 저장 | → `ON_SALE`, → `DRAFT`(규칙 재설정), → `CANCELLED` | 규칙 수정(동의 초기화), 팀 동의, 팀 등록·제외 가능 |
| `ON_SALE` | 판매 중 — 티켓 예매 가능 | 전원 동의 + `startSale` 온체인 잠금 확정 | → `SALE_CLOSED`, → `CANCELLED` | 예매·결제·입장 가능. **규칙·참여팀·티켓 옵션 변경 불가** |
| `SALE_CLOSED` | 판매 마감 — 신규 예매 종료 | 판매 마감(공연 시작 1시간 전) 도달 자동 전이 | → `ENDED`, → `CANCELLED` | 신규 예매 불가, 기존 티켓 입장 가능, 양도 가능. **D-3(취소 마감)~판매 마감 구간은 예매 가능·환불 불가** |
| `ENDED` | 종료 — 공연 종료 | 공연 종료 시각 도달 | → (정산 시작) | 입장 처리 종료, 집계 확정 가능 |
| `CANCELLED` | 취소 — 공연 전체 취소 | 생성자 취소 요청(release 전) | 종단 상태 | 전 티켓 수수료 없이 일괄 환불, 정산 `HALTED` |

### 참여팀 상태 (`performance_participant.status`)

| 상태 | 의미 | 진입 조건 | 허용 전이 | 비고 |
|------|------|-----------|-----------|------|
| `REGISTERED` | 등록 — 참여팀으로 등록됨 (v2) | 공연 생성자가 등록 | → `REMOVED` | 동의 대기, 규칙 동의 가능 |

## 회원·인증 `member`

회원 가입·로그인·토큰 관리·프로필과, 관객이 결제에 사용할 금융망 계좌 연결을 다룬다.

### `member`

주요 정보는 다음과 같다.

- 회원 식별자(`member_id`, BIGINT AUTO_INCREMENT)
- 이메일(로그인 아이디, 유니크)
- 비밀번호 해시(자체 가입 시 필수, OAuth 전용 회원은 NULL)
- 이름, 연락처
- 인증 방식 — `LOCAL` / `KAKAO` / `NAVER` (복수 연동 시 최초 가입 방식 기록)
- OAuth 제공자 식별자(provider + provider_user_id, OAuth 가입 시 저장)
- 역할 구분(관객·공연자는 팀 소속으로 결정되고, 관리자 여부만 별도 플래그)
- 회원 상태(활성·정지·탈퇴)
- 가입 일시, 수정 일시(`DATETIME(6)`)

### `refresh_token`

주요 정보는 다음과 같다.

- 토큰 식별자, 회원 식별자
- 리프레시 토큰 값(해시 보관), 발급·만료 일시
- 회전 이력을 위한 이전 토큰 참조, 폐기 여부

### `member_bank_account`

주요 정보는 다음과 같다.

- 계좌 식별자, 회원 식별자(관객 1인 1계좌)
- 금융망 계좌 번호(암호화 보관), 은행 코드, 예금주명
- 연결 확인 일시

### 회원 가입 (자체)

1. 비로그인 방문자는 이메일·비밀번호·이름·연락처를 입력하고 약관에 동의해 가입을 요청한다.
2. 시스템 처리
   - 이메일 형식·비밀번호 규칙·필수 약관 동의 여부를 검증한다.
   - 이메일 중복 여부를 확인한다.
   - 비밀번호를 단방향 해시로 변환해 저장하고 회원을 활성 상태로 생성한다. 인증 방식은 `LOCAL`로 기록한다.
3. 처리 결과
   - **성공**
     - 회원이 생성되고 로그인 화면으로 이동한다.
   - **실패**
     - 회원은 생성되지 않는다.
     - 실패 사유를 제공한다.

### 회원 가입·로그인 (OAuth — 카카오·네이버)

1. 비로그인 방문자는 카카오 또는 네이버 로그인 버튼을 눌러 OAuth 인증을 시작한다.
2. 시스템 처리
   - OAuth 제공자의 인가 코드를 받아 액세스 토큰을 교환하고, 제공자 API로 이메일·이름을 조회한다.
   - 해당 제공자+제공자 사용자 ID로 이미 가입된 회원이 있으면 기존 회원으로 로그인한다.
   - 같은 이메일로 자체 가입된 회원이 있으면 OAuth 정보를 연동하고 로그인한다.
   - 기존 회원이 없으면 약관 동의를 받은 뒤 회원을 생성한다. 비밀번호는 NULL이고 인증 방식은 `KAKAO` 또는 `NAVER`로 기록한다.
   - 서비스 액세스 토큰(30분)과 리프레시 토큰(14일)을 발급한다.
3. 처리 결과
   - **성공**
     - 인증 상태가 되고 이전에 요청한 화면 또는 홈으로 이동한다. 양도 링크에서 진입한 경우 양도 수락 화면으로 돌아간다.
   - **실패**
     - 인증 상태가 되지 않는다.
     - 실패 사유를 제공한다.

### 로그인·로그아웃

1. 비로그인 방문자는 이메일과 비밀번호로 로그인하거나, OAuth(카카오·네이버) 버튼으로 로그인한다.
2. 시스템 처리
   - 자체 로그인: 이메일로 회원을 조회하고 비밀번호 해시를 비교한다. OAuth 전용 회원(`LOCAL`이 아닌 회원)이 비밀번호 로그인을 시도하면 거부하고 해당 OAuth 로그인을 안내한다.
   - OAuth 로그인: 위 "회원 가입·로그인 (OAuth)" 흐름을 따른다.
   - 정지·탈퇴 상태의 회원인지 확인한다.
   - 액세스 토큰(30분)과 리프레시 토큰(14일)을 발급하고, 리프레시 토큰은 서버에 저장한다.
   - 로그아웃 요청 시 저장된 리프레시 토큰을 폐기한다.
3. 처리 결과
   - **성공**
     - 인증 상태가 되고 이전에 요청한 화면 또는 홈으로 이동한다.
   - **실패**
     - 인증 상태가 되지 않는다.
     - 실패 사유를 제공한다. 자체 로그인에서 아이디가 없는 경우와 비밀번호가 틀린 경우를 구분해 알리지 않는다.

### 액세스 토큰 재발급

1. 회원의 클라이언트는 액세스 토큰 만료를 확인하고 리프레시 토큰으로 재발급을 요청한다.
2. 시스템 처리
   - 리프레시 토큰의 서버 저장 여부·만료·폐기 여부를 확인한다.
   - 새 액세스 토큰과 새 리프레시 토큰을 발급하고 기존 리프레시 토큰을 폐기한다(회전).
3. 처리 결과
   - **성공**
     - 새 토큰으로 원래 요청을 이어서 수행한다.
   - **실패**
     - 토큰은 재발급되지 않는다.
     - 실패 사유를 제공하고 로그인 화면으로 보낸다. 위조된 토큰은 재발급을 시도하지 않고 즉시 로그아웃 처리한다.

### 프로필 조회·수정

1. 회원은 마이페이지에서 본인 정보를 조회하고 이름·연락처·비밀번호를 수정한다.
2. 시스템 처리
   - 인증 토큰으로 본인 여부를 확인한다.
   - 입력값을 검증하고, 비밀번호 변경 시 현재 비밀번호를 함께 확인한다.
3. 처리 결과
   - **성공**
     - 변경된 정보가 저장되고 화면에 반영된다.
   - **실패**
     - 정보는 변경되지 않는다.
     - 실패 사유를 제공한다.

### 금융망 계좌 연결

1. 관객은 마이페이지 또는 결제 화면에서 은행·계좌번호를 입력해 결제에 사용할 계좌를 연결한다.
2. 시스템 처리
   - 금융망 API로 계좌 실재 여부와 예금주명을 조회해 회원 이름과 일치하는지 확인한다.
   - 계좌번호를 암호화해 저장하고, 기존 연결 계좌가 있으면 교체한다.
3. 처리 결과
   - **성공**
     - 계좌가 연결되고 결제 화면에서 선택 가능해진다.
   - **실패**
     - 계좌는 연결되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 입력값이 검증 규칙을 위반한 경우 (`COMMON_VALIDATION_FAILED`)
- 이미 가입된 이메일인 경우 (`AUTH_EMAIL_DUPLICATED`)
- 이메일 또는 비밀번호가 일치하지 않는 경우 (`AUTH_INVALID_CREDENTIALS`)
- 액세스 토큰이 만료된 경우 (`AUTH_TOKEN_EXPIRED`)
- 토큰 서명이 일치하지 않거나 폐기된 토큰인 경우 (`AUTH_TOKEN_INVALID`)
- 인증 정보 없이 회원 전용 기능을 요청한 경우 (`COMMON_UNAUTHORIZED`)
- 로그인·계좌 연결 요청이 IP당 허용 횟수를 초과한 경우 (`COMMON_TOO_MANY_REQUESTS`)
- 금융망 API가 계좌 조회 오류를 반환한 경우 (`COMMON_EXTERNAL_SERVICE_ERROR`)
- OAuth 인가 코드 교환이 실패하거나 제공자 API가 오류를 반환한 경우 (`COMMON_EXTERNAL_SERVICE_ERROR`)
- OAuth 전용 회원이 비밀번호 로그인을 시도한 경우 (`AUTH_INVALID_CREDENTIALS` + 해당 OAuth 로그인 안내)
- 계좌 예금주명이 회원 이름과 다른 경우 — 규격 v3에 전용 코드가 없어 `COMMON_VALIDATION_FAILED`로 응답하고, 전용 코드는 §12 신설 제안에 기록했다

## 공연팀 `team`

밴드 단위의 팀 생성, 팀원 초대·수락, 원화를 수령할 정산 계좌 등록을 다룬다. 팀을 만들면 팀 지갑이 함께 만들어진다(`wallet` 장).

### `team`

주요 정보는 다음과 같다.

- 팀 식별자(`team_id`), 팀 이름(유니크), 소개, 장르
- 팀 리더 회원 식별자
- 팀 상태(활성·해산)
- 생성 일시, 수정 일시

### `team_member`

주요 정보는 다음과 같다.

- 팀원 식별자, 팀 식별자, 회원 식별자
- 팀 내 역할(리더·팀원)
- 합류 일시

### `team_invitation`

주요 정보는 다음과 같다.

- 초대 식별자, 팀 식별자, 초대 대상 이메일
- 서명된 초대 토큰, 만료 일시
- 초대 상태(대기·수락·만료)

### `team_settlement_account`

주요 정보는 다음과 같다.

- 계좌 식별자, 팀 식별자(팀당 1개)
- 금융망 계좌 번호(암호화 보관), 은행 코드, 예금주명
- 예금주 검증 결과와 검증 일시

### 팀 생성

1. 회원은 팀 이름·소개·장르를 입력해 팀 생성을 요청한다.
2. 시스템 처리
   - 팀 이름 중복 여부와 입력값을 검증한다.
   - 팀을 생성하고 요청한 회원을 리더로 등록한다.
   - 팀 지갑을 자동 생성해 팀에 연결한다(`wallet` 장 "팀 지갑 자동 생성"). 지갑 생성이 실패하면 팀 생성 전체를 롤백한다.
3. 처리 결과
   - **성공**
     - 팀이 생성되고 팀 관리 화면으로 이동한다. 회원은 공연자 역할을 갖는다.
   - **실패**
     - 팀은 생성되지 않는다.
     - 실패 사유를 제공한다.

### 팀원 초대

1. 팀 리더는 초대할 사람의 이메일을 입력해 초대를 요청한다.
2. 시스템 처리
   - 요청자가 해당 팀의 리더인지 확인한다.
   - 이미 팀원이거나 대기 중인 초대가 있는지 확인한다.
   - 서명된 초대 토큰을 만들고 만료 시각을 부여해 초대를 생성한다.
3. 처리 결과
   - **성공**
     - 초대가 생성되고 공유할 초대 링크가 제공된다.
   - **실패**
     - 초대는 생성되지 않는다.
     - 실패 사유를 제공한다.

### 팀원 초대 수락

1. 초대 링크를 받은 회원은 로그인 후 수락을 요청한다.
2. 시스템 처리
   - 초대 토큰의 서명·만료·사용 여부를 확인한다.
   - 이미 같은 팀에 속해 있는지 확인한다.
   - 회원을 팀원으로 등록하고 초대를 수락 상태로 바꾼다.
3. 처리 결과
   - **성공**
     - 팀에 합류하고 공연자 대시보드에 해당 팀이 나타난다.
   - **실패**
     - 팀에 합류되지 않는다.
     - 실패 사유를 제공한다.

### 정산 계좌 등록

1. 팀 리더는 정산금을 받을 은행·계좌번호·예금주명을 입력해 등록을 요청한다.
2. 시스템 처리
   - 요청자가 해당 팀의 리더인지 확인한다.
   - 금융망 API로 계좌를 조회해 **예금주명이 입력값과 일치하는지 검증한다**(SEC-13).
   - 계좌번호를 암호화해 저장하고 검증 결과·일시를 기록한다.
3. 처리 결과
   - **성공**
     - 정산 계좌가 등록되고 환급 대상 계좌로 사용된다.
   - **실패**
     - 계좌는 등록되지 않으며, 계좌 미등록 상태에서는 정산 환급이 실행되지 않는다.
     - 실패 사유를 제공한다.

### 팀 정보 조회·수정

1. 팀원은 팀 상세를 조회하고, 리더는 팀 이름·소개·장르를 수정한다.
2. 시스템 처리
   - 요청자가 해당 팀의 팀원인지(수정은 리더인지) 확인한다.
   - 팀 정보·팀원 목록·팀 지갑 주소·정산 계좌 등록 여부를 함께 조회한다.
3. 처리 결과
   - **성공**
     - 팀 정보가 조회되거나 수정 내용이 저장된다.
   - **실패**
     - 팀 정보는 변경되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 입력값이 검증 규칙을 위반하거나 팀 이름이 중복인 경우 (`COMMON_VALIDATION_FAILED`)
- 팀을 찾을 수 없는 경우 (`TEAM_NOT_FOUND`)
- 이미 팀에 속해 있는 회원이 초대를 수락한 경우 (`TEAM_ALREADY_JOINED`)
- 초대 링크가 만료된 경우 (`TEAM_INVITE_EXPIRED`)
- 팀 리더가 아닌 회원이 초대·수정·계좌 등록을 시도한 경우 (`COMMON_FORBIDDEN`)
- 팀 지갑 생성에 실패해 팀 생성이 롤백된 경우 (`WALLET_CREATION_FAILED`)
- 금융망 계좌 조회가 실패한 경우 (`COMMON_EXTERNAL_SERVICE_ERROR`)
- 정산 계좌의 예금주명이 일치하지 않는 경우 — 전용 코드가 없어 `COMMON_VALIDATION_FAILED`로 응답하고 §12 신설 제안에 기록했다

## 팀 지갑 `wallet`

팀별 커스터디얼 지갑의 자동 생성·조회·거래 이력·가스 충전을 다룬다. **[권] 팀 키는 정산 규칙 동의(`agreeToRules`) 서명 한 번에만 사용하고, 나머지 트랜잭션은 운영지갑 권한으로 처리한다.**(P-2) 공연자에게는 주소와 익스플로러 링크만 보여주고 개인키·니모닉은 어떤 화면에도 노출하지 않는다.

### `team_wallet`

주요 정보는 다음과 같다.

- 지갑 식별자, 팀 식별자(팀당 1개)
- 지갑 주소(`CHAR(42)`)
- 암호화된 개인키(AES-256-GCM DEK로 암호화, KEK는 환경변수·KMS로 주입), DEK 참조 정보
- 마지막 가스 충전 일시, 마지막 잔액 조회 일시
- 생성 일시

### 팀 지갑 자동 생성

1. 회원이 팀 생성을 요청하면 시스템이 팀 지갑 생성을 함께 수행한다(공연자가 별도로 요청하지 않는다).
2. 시스템 처리
   - 키 쌍을 생성하고 개인키를 envelope encryption으로 암호화해 저장한다. 평문 키는 로그·응답 어디에도 남기지 않는다.
   - 운영지갑이 팀 지갑으로 소량의 테스트넷 가스를 전송한다(온체인 tx). 요청을 `202`로 접수하고 작업(`jobId`)을 만들어 폴링으로 확정을 확인한다.
   - 가스 전송 확정 여부와 무관하게 팀 지갑 주소는 즉시 사용 가능하도록 저장한다.
3. 처리 결과
   - **성공**
     - 팀에 지갑 주소가 연결되고 팀 관리 화면에 주소와 익스플로러 링크가 표시된다.
   - **실패**
     - 지갑은 생성되지 않고 팀 생성 트랜잭션 전체가 롤백된다.
     - 실패 사유를 제공한다. 키 관련 실패의 상세 원인은 노출하지 않는다.

### 팀 지갑 조회

1. 공연자는 팀 관리 화면에서 팀 지갑 주소와 잔액을 조회한다.
2. 시스템 처리
   - 요청자가 해당 팀의 팀원인지 확인한다.
   - 체인 노드에서 KRWS 잔액과 가스 잔액을 조회한다. 노드 응답이 지연되면 마지막 조회값과 조회 시각을 함께 표시한다.
3. 처리 결과
   - **성공**
     - 지갑 주소·KRWS 잔액·익스플로러 링크가 표시된다.
   - **실패**
     - 잔액은 표시되지 않는다.
     - 실패 사유를 제공한다.

### 팀 지갑 거래 이력 조회

1. 공연자는 팀 지갑의 트랜잭션 이력을 조회한다.
2. 시스템 처리
   - 요청자가 해당 팀의 팀원인지 확인한다.
   - 해당 지갑이 관여한 동의·분배·소각 트랜잭션을 페이지 단위로 조회하고, 각 항목에 유형·금액·상태·트랜잭션 해시(`CHAR(66)`)·익스플로러 링크를 붙인다.
3. 처리 결과
   - **성공**
     - 거래 이력이 최신순으로 표시된다.
   - **실패**
     - 이력은 표시되지 않는다.
     - 실패 사유를 제공한다.

### 팀 지갑 가스 자동 충전

1. 시스템은 팀 지갑의 가스 잔액을 주기적으로 점검하거나, 동의 서명 직전에 잔액을 확인한다.
2. 시스템 처리
   - 잔액이 임계치(동의 트랜잭션 1~2회분) 미만이면 운영지갑에서 자동으로 재충전한다. 요청을 `202`로 접수하고 작업(`jobId`) 확정을 확인한다.
   - 운영지갑 가스가 부족하면 충전을 중단하고 관리자에게 알린다.
   - 공연자 화면에는 가스·충전 개념을 노출하지 않는다.
3. 처리 결과
   - **성공**
     - 팀 지갑이 동의 서명을 보낼 수 있는 상태가 된다.
   - **실패**
     - 충전은 이뤄지지 않고 동의 트랜잭션 요청이 거부된다.
     - 실패 사유를 제공한다.

### 실패 사유

- 팀 지갑 생성에 실패한 경우 (`WALLET_CREATION_FAILED`)
- 팀 지갑 정보를 찾을 수 없는 경우 (`WALLET_NOT_FOUND`)
- 서명 직전 개인키 복호화에 실패한 경우 (`WALLET_KEY_DECRYPT_FAILED`)
- 팀 지갑의 가스가 부족해 동의 서명을 보낼 수 없는 경우 (`WALLET_GAS_INSUFFICIENT`)
- 운영지갑의 가스가 부족해 자동 충전을 수행할 수 없는 경우 (`CHAIN_GAS_INSUFFICIENT`)
- 팀원이 아닌 회원이 지갑 정보를 조회한 경우 (`COMMON_FORBIDDEN`)
- 체인 노드 응답이 지연되어 잔액·이력 조회가 완료되지 않은 경우 (`CHAIN_TX_TIMEOUT`)

## 공연 `performance`

공연 생성·수정·탐색, 티켓 옵션 설정, 참여팀 초대·수락, 검표 페이지 링크, 판매·선택 현황 조회, 공연 취소를 다룬다.

### `performance`

주요 정보는 다음과 같다.

- 공연 식별자(`performance_id`), 제목, 소개, 포스터 이미지 경로
- 공연 일시, 입장 시작·종료 시각, 장소명·주소
- 생성자(공연 주최) 팀 식별자와 회원 식별자
- 단독·공동 공연 구분
- 공연 상태 — `DRAFT` / `PENDING_AGREEMENT` / `ON_SALE` / `SALE_CLOSED` / `ENDED` / `CANCELLED`
- 취소 마감 일시(공연일 D-3 00:00), 판매 마감 일시(공연 시작 1시간 전), 판매 시작 일시
- 온체인 공연 식별자와 컨트랙트 주소(`CHAR(42)`)
- 생성 일시, 수정 일시

### `ticket_type`

주요 정보는 다음과 같다.

- 티켓 타입 식별자, 공연 식별자
- 이름(예: 일반·얼리버드), 가격(BIGINT, 원 단위 정수)
- 총 수량, 판매 수량
- 좌석은 지정하지 않는다(스탠딩). 1인 최대 구매 수량은 공연 단위로 4매다.

### `performance_participant`

주요 정보는 다음과 같다.

- 참여 식별자, 공연 식별자, 팀 식별자
- 참여 상태(초대·수락·제외), 초대·수락 일시
- 온체인 참여팀 인덱스(분배 계산의 순서 기준)

### `performance_staff` (v1) {toggle="true"}

	검표 페이지 링크(v2)로 대체되어 더 이상 사용하지 않는다. 이력 보존용으로 남긴다.

	주요 정보는 다음과 같다.

	- 검표 관계자 식별자, 공연 식별자, 회원 식별자
	- 지정 일시, 지정한 회원 식별자

### 공연 생성

1. 팀 리더는 제목·소개·일시·장소·단독/공동 구분을 입력해 공연 생성을 요청한다.
2. 시스템 처리
   - 요청자가 주최 팀의 리더인지 확인한다.
   - 공연 일시가 과거가 아닌지, 입장 시각이 공연 일시와 정합한지 검증한다.
   - 공연 일시에서 취소 마감(D-3 00:00)과 판매 마감(공연 시작 1시간 전)을 계산해 저장한다.
   - 공연을 `DRAFT` 상태로 생성하고 주최 팀을 참여팀으로 자동 등록한다.
3. 처리 결과
   - **성공**
     - 공연이 `DRAFT` 상태로 생성되고 티켓 옵션·참여팀 설정 화면으로 이어진다.
   - **실패**
     - 공연은 생성되지 않는다.
     - 실패 사유를 제공한다.

### 티켓 옵션 설정

1. 공연 생성자는 티켓 타입의 이름·가격·수량을 1개 이상 입력해 설정을 요청한다.
2. 시스템 처리
   - 공연 상태가 `DRAFT` 또는 `PENDING_AGREEMENT`인지 확인한다. 판매가 시작된 뒤에는 거부한다.
   - 가격이 0 이상의 정수인지, 수량이 1 이상인지 검증한다.
   - 티켓 타입 목록을 통째로 교체 저장하고, 이미 판매된 타입은 삭제할 수 없도록 막는다.
3. 처리 결과
   - **성공**
     - 티켓 옵션이 저장되고 공연 상세에 노출될 준비가 된다.
   - **실패**
     - 티켓 옵션은 변경되지 않는다.
     - 실패 사유를 제공한다.

### 참여팀 초대·수락

1. 공연 생성자는 함께 공연할 팀을 초대하고, 초대받은 팀의 리더는 참여를 수락한다.
2. 시스템 처리
   - 공연 상태가 `DRAFT` 또는 `PENDING_AGREEMENT`인지 확인한다.
   - 초대 대상 팀이 존재하는지, 이미 참여 중인지 확인한다.
   - 수락 시 참여 상태를 수락으로 바꾸고 온체인 참여팀 인덱스를 부여한다. 참여팀 목록이 바뀌면 기존 규칙 동의는 모두 무효가 되어 다시 받는다.
   - 참여팀 제외는 판매 시작 전까지만 허용한다.
3. 처리 결과
   - **성공**
     - 참여팀 목록이 갱신되고 정산 규칙 설정 화면에 참여팀이 반영된다.
   - **실패**
     - 참여팀 목록은 변경되지 않는다.
     - 실패 사유를 제공한다.

### 검표 관계자 지정 (v1) {toggle="true"}

	1. 공연 생성자는 공연 당일 검표를 맡을 회원을 지정한다.
	2. 시스템 처리
		- 요청자가 공연 생성자인지 확인한다.
		- 지정 대상이 실재하는 회원인지 확인하고, 참여팀 리더는 자동으로 포함한다.
		- 지정 목록을 저장한다. 검표 권한은 해당 공연에만 적용된다.
	3. 처리 결과
		- **성공**
			- 지정된 회원의 검표 화면에 해당 공연이 나타난다.
		- **실패**
			- 검표 권한은 부여되지 않는다.
			- 실패 사유를 제공한다.

### 검표 페이지 링크 (v2)

1. 공연 생성자는 공연 상세에서 자동 생성된 검표 페이지 링크를 확인하고 검표 담당자에게 공유한다.
2. 시스템 처리
   - 공연 생성 시 공연별 검표 페이지 링크(서명 토큰 포함, 해당 공연에만 유효)를 자동 생성한다.
   - 링크에 접근하면 토큰 서명과 공연 유효성만 검증한다. 검표 담당자의 계정 정보는 서비스에 저장하지 않는다.
   - 링크는 공연 상세 화면과 참여팀 대시보드에서 확인할 수 있다.
3. 처리 결과
   - **성공**
     - 검표 페이지 링크로 접속하면 해당 공연의 QR 스캔 화면이 표시된다.
   - **실패**
     - 토큰이 유효하지 않거나 만료된 경우 접근이 거부된다.
     - 실패 사유를 제공한다.

### 공연 탐색·상세 조회

1. 비로그인 방문자 또는 관객은 판매 중인 공연 목록을 탐색하고 공연 상세를 조회한다.
2. 시스템 처리
   - 공개 대상 상태(`ON_SALE`·`SALE_CLOSED`·`ENDED`)의 공연만 노출하고, 검색어·날짜 조건으로 필터링해 페이지 단위로 반환한다.
   - 상세에서는 출연팀·일시·장소·티켓 옵션·잔여 수량을 제공한다.
   - 관객 화면이므로 지갑 주소·트랜잭션 해시는 노출하지 않는다.
3. 처리 결과
   - **성공**
     - 공연 목록 또는 상세가 표시되고 예매 진입이 가능해진다.
   - **실패**
     - 공연 정보가 표시되지 않는다.
     - 실패 사유를 제공한다.

### 판매·선택 현황 조회

1. 공연자는 판매 현황과 관객의 팀 선택 집계를 조회한다.
2. 시스템 처리
   - 요청자가 참여팀 소속인지 확인한다.
   - 티켓 타입별 판매 수량·매출, 팀별 관객 선택 수를 서버 집계로 계산한다.
   - 온체인 선택 카운터를 함께 조회해 서버 집계와 대조한 결과를 표시한다. 대조 불일치는 화면에 그대로 드러낸다.
3. 처리 결과
   - **성공**
     - 판매·선택 현황과 온체인 카운터 대조 결과가 표시된다.
   - **실패**
     - 현황이 표시되지 않는다.
     - 실패 사유를 제공한다.

### 공연 취소

1. 공연 생성자는 공연 취소를 요청하고 전체 환불에 동의한다.
2. 시스템 처리
   - 요청자가 공연 생성자인지, 정산이 아직 release 실행 전인지(정산 상태가 `RELEASED`·`REDEEMED`가 아닌지) 확인한다.
   - 공연 상태를 `CANCELLED`로 바꾸고 신규 예매를 즉시 차단한다.
   - 컨트랙트에 정산 중단 플래그를 세워 이후 집계·release가 실행되지 않게 한다. 요청을 `202`로 접수하고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 정산 상태를 `HALTED`로 전이하고, 결제 완료된 전 티켓에 대해 수수료 없는 일괄 환불을 시작한다(`refund` 장 "공연 취소 일괄 환불").
3. 처리 결과
   - **성공**
     - 공연이 취소되고 관객에게 환불이 순차 처리된다. 진행 상황은 공연자 화면에서 확인할 수 있다.
   - **실패**
     - 공연은 취소되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 입력값이 검증 규칙을 위반한 경우 (`COMMON_VALIDATION_FAILED`)
- 공연 일시 또는 예매 마감 일시가 올바르지 않은 경우 (`PERFORMANCE_DATE_INVALID`)
- 공연을 찾을 수 없는 경우 (`PERFORMANCE_NOT_FOUND`)
- 공연 주최자가 아닌 회원이 수정·취소·참여팀 관리를 시도한 경우 (`PERFORMANCE_NOT_OWNER`)
- 현재 공연 상태에서 허용되지 않는 요청인 경우 (`PERFORMANCE_INVALID_STATUS`)
- 판매가 시작된 뒤 공연 정보·티켓 옵션·참여팀 변경을 시도한 경우 (`PERFORMANCE_ALREADY_ON_SALE`)
- 초대 대상 팀을 찾을 수 없는 경우 (`TEAM_NOT_FOUND`)
- 이미 참여 중인 팀을 다시 초대한 경우 (`TEAM_ALREADY_JOINED`)
- 참여팀이 아닌 회원이 판매·선택 현황을 조회한 경우 (`COMMON_FORBIDDEN`)
- 취소 트랜잭션이 지연되어 확정되지 않은 경우 (`CHAIN_TX_TIMEOUT`)

## 정산 규칙 `rule`

공연 수익을 어떻게 나눌지 정하고, 참여팀이 각자의 팀 지갑으로 그 규칙에 동의하고, 전원 동의 후 판매를 시작하면서 규칙을 컨트랙트에 잠그는 과정을 다룬다. **이 도메인이 서비스의 핵심 차별 기능이다.**

### `settlement_rule`

주요 정보는 다음과 같다.

- 규칙 식별자, 공연 식별자(공연당 1개)
- 균등 분배 비율·관객 선택 분배 비율(각 bp 단위 정수, 합 10000)
- 규칙 해시(`rulesHash`) — 잠금·동의·검증의 기준값
- 잠금 여부와 잠금 트랜잭션 해시(`CHAR(66)`), 잠금 일시
- 생성 일시, 수정 일시

### `rule_agreement`

주요 정보는 다음과 같다.

- 동의 식별자, 공연 식별자, 팀 식별자
- 동의 상태 — `PENDING` / `AGREED`
- 동의에 사용한 규칙 해시, 동의 트랜잭션 해시(`CHAR(66)`), 동의 확정 일시
- 동의를 요청한 회원 식별자(팀 리더)

### 정산 규칙 설정

1. 공연 생성자는 균등·관객 선택 비율(bp)을 입력하고, 예상 분배액 시뮬레이션을 확인한 뒤 저장을 요청한다.
2. 시스템 처리
   - 공연 상태가 `DRAFT` 또는 `PENDING_AGREEMENT`인지 확인한다.
   - 두 비율의 합이 10000bp인지 확인한다. 각 항목은 0도 허용한다.
   - 규칙을 저장하고 규칙 해시를 새로 계산한다. **규칙이 바뀌면 기존 팀별 동의는 전부 `PENDING`으로 초기화된다.**
   - 공연 상태를 `PENDING_AGREEMENT`로 전이한다.
3. 처리 결과
   - **성공**
     - 규칙이 저장되고 규칙 동의 화면에서 팀별 동의를 받을 수 있게 된다.
   - **실패**
     - 규칙은 저장되지 않는다.
     - 실패 사유를 제공한다.

### 규칙·동의 현황 조회

1. 참여팀 리더와 공연 생성자는 확정될 규칙 내용과 팀별 동의 현황을 조회한다.
2. 시스템 처리
   - 요청자가 참여팀 소속인지 확인한다.
   - 두 비율과 현재 규칙 해시, 팀별 동의 상태(`PENDING`·`AGREED`)와 동의 트랜잭션 해시를 함께 반환한다.
   - 판매 시작 가능 여부(전원 동의 여부, 참여팀 수 조건)를 함께 알린다.
3. 처리 결과
   - **성공**
     - 규칙과 동의 현황이 표시되고, 동의하지 않은 팀은 동의 버튼을 사용할 수 있다.
   - **실패**
     - 규칙·동의 현황이 표시되지 않는다.
     - 실패 사유를 제공한다.

### 정산 규칙 동의

1. 참여팀 리더는 규칙 내용을 확인하고 자기 팀의 동의를 요청한다.
2. 시스템 처리
   - 요청자가 해당 참여팀의 리더인지 확인한다.
   - 화면이 보여준 규칙 해시와 서버의 현재 규칙 해시가 같은지 확인한다. 다르면 규칙이 중간에 바뀐 것이므로 거부한다.
   - 팀 지갑의 가스 잔액을 확인하고 부족하면 자동 충전한다.
   - 팀 지갑 개인키를 복호화해 `agreeToRules(performanceId, rulesHash)` 트랜잭션에 서명·전송한다. **팀 키를 복호화하는 유일한 지점이며, 복호화 사실은 감사 로그에 남긴다.**
   - 요청을 `202`로 접수하고 작업(`jobId`)을 반환한다. 화면은 `GET /api/v1/chain/jobs/{jobId}` 폴링으로 진행 상태를 표시한다.
   - 트랜잭션이 확정되면 동의 상태를 `AGREED`로 바꾸고 트랜잭션 해시를 저장한다.
3. 처리 결과
   - **성공**
     - 팀 동의가 `AGREED`가 되고, 익스플로러 링크가 표시된다. 전원 동의가 되면 공연 생성자의 판매 시작 버튼이 활성화된다.
   - **실패**
     - 동의는 기록되지 않고 상태는 `PENDING`으로 남는다.
     - 실패 사유를 제공한다. 트랜잭션 실패는 최대 3회 재시도한 뒤 시스템이 연장 재시도하고, 결정적 실패 시 알림을 보낸다.

### 판매 시작

1. 공연 생성자는 전 참여팀 동의를 확인하고 티켓 판매 시작을 요청한다.
2. 시스템 처리
   - 요청자가 공연 생성자인지, 공연 상태가 `PENDING_AGREEMENT`인지 확인한다.
   - 공동 공연이면 수락한 참여팀이 2팀 이상인지 확인한다.
   - 모든 참여팀의 동의 상태가 `AGREED`이고 동의에 사용한 해시가 현재 규칙 해시와 같은지 확인한다.
   - 티켓 옵션이 1개 이상 설정되어 있는지 확인한다.
   - 운영지갑으로 `startSale()` 트랜잭션을 전송해 규칙을 잠근다. 요청을 `202`로 접수하고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 확정되면 공연 상태를 `ON_SALE`로 전이하고 규칙을 잠금 상태로 표시한다. **이후 규칙·참여팀·티켓 옵션·공연 기본 정보의 변경은 서버와 컨트랙트 모두에서 거부된다.**
3. 처리 결과
   - **성공**
     - 공연이 `ON_SALE`이 되어 관객에게 노출되고 예매가 가능해진다. 잠금 트랜잭션 해시가 정산 검증 페이지에 표시된다.
   - **실패**
     - 판매는 시작되지 않고 공연은 `PENDING_AGREEMENT`로 남는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 분배 비율의 합이 10000bp가 아닌 경우 (`RULE_RATIO_SUM_INVALID`)
- 모든 참여팀이 동의하기 전에 판매 시작을 시도한 경우 (`RULE_NOT_AGREED_BY_ALL`)
- 판매 시작으로 잠긴 규칙의 수정을 시도한 경우 (`RULE_ALREADY_LOCKED`)
- 동의 요청의 규칙 해시가 현재 서버 규칙의 해시와 다른 경우 (`RULE_HASH_MISMATCH`)
- 공동 공연인데 수락한 참여팀이 2팀 미만인 경우 (`TEAM_MIN_COUNT_NOT_MET`)
- 공연 생성자가 아닌 회원이 규칙 설정·판매 시작을 시도한 경우 (`PERFORMANCE_NOT_OWNER`)
- 참여팀 리더가 아닌 회원이 동의를 시도한 경우 (`COMMON_FORBIDDEN`)
- 판매 시작 이후 규칙·참여팀 변경을 시도한 경우 (`PERFORMANCE_ALREADY_ON_SALE`)
- 현재 공연 상태에서 허용되지 않는 요청인 경우 (`PERFORMANCE_INVALID_STATUS`)
- 팀 지갑 가스가 부족해 동의 트랜잭션을 보낼 수 없는 경우 (`WALLET_GAS_INSUFFICIENT`)
- 팀 지갑 개인키 복호화에 실패한 경우 (`WALLET_KEY_DECRYPT_FAILED`)
- 동의·잠금 트랜잭션이 확정되지 않고 지연되는 경우 (`CHAIN_TX_TIMEOUT`)
- 운영지갑 가스 부족 또는 nonce 충돌로 잠금 트랜잭션이 실패한 경우 (`CHAIN_GAS_INSUFFICIENT`, `CHAIN_NONCE_CONFLICT`)

## 예매·티켓 `ticket`

주문 생성, 관람 목적 팀 선택의 온체인 기록, 티켓 발급, 주문·티켓 조회, 동적 QR 발급을 다룬다.

### `ticket_order`

주요 정보는 다음과 같다.

- 주문 식별자(`ticket_order_id`), 공연 식별자, 주문한 회원 식별자
- 총 결제 금액(BIGINT, 원 단위 정수), 총 수량
- 관람 목적으로 선택한 팀 식별자(공동 공연에서 필수, 한 팀)
- 주문 상태 — `PENDING_PAYMENT` / `PAID` / `CANCELLED` / `REFUNDED`
- 결제 만료 일시(생성 후 15분), 결제 확인 일시
- 생성 일시, 수정 일시

### `order_item`

주요 정보는 다음과 같다.

- 주문 항목 식별자, 주문 식별자, 티켓 타입 식별자
- 수량, 단가(구매 시점 가격, BIGINT), 소계

### `ticket`

주요 정보는 다음과 같다.

- 티켓 식별자(`ticket_id`), 주문 식별자, 티켓 타입 식별자, 공연 식별자
- 현재 소유자 회원 식별자(양도 시 변경), 최초 구매자 회원 식별자
- 티켓 상태 — `ISSUED` / `TRANSFER_PENDING` / `USED` / `CANCELLED`
- 최초 구매 금액(환불액 산정과 양도 시 승계의 기준, BIGINT)
- 온체인 티켓 식별자와 선택 기록 트랜잭션 해시(`CHAR(66)`)
- 발급 일시, 상태 변경 일시

### `ticket_qr_seed`

주요 정보는 다음과 같다.

- 시드 식별자, 티켓 식별자
- QR 서명 시드 값, 시드 발급 일시, 폐기 여부와 폐기 일시(양도 수락 시 폐기·재발급)

### 주문 생성

1. 관객은 공연 상세에서 티켓 타입과 수량을 고르고 주문 생성을 요청한다.
2. 시스템 처리
   - 공연 상태가 `ON_SALE`인지 확인한다.
   - 요청한 티켓 타입이 해당 공연의 것인지 확인한다.
   - 해당 공연에서 이 회원이 이미 보유·주문한 수량과 합쳐 4매를 넘지 않는지 확인한다.
   - 티켓 타입별 재고를 원자적으로 차감한다. 동시 요청 경합에서 밀리면 차감하지 않는다.
   - 서버가 금액을 계산해 주문을 `PENDING_PAYMENT`로 생성하고 결제 만료 시각(15분 후)을 부여한다.
   - 만료 시각까지 결제되지 않은 주문은 자동으로 `CANCELLED`가 되고 재고가 원복된다.
3. 처리 결과
   - **성공**
     - 주문이 생성되고 결제 화면으로 이동한다.
   - **실패**
     - 주문은 생성되지 않고 재고는 차감되지 않는다.
     - 실패 사유를 제공한다.

### 관람 목적 팀 선택 기록

1. 관객은 주문 과정에서 "어떤 팀을 보러 오셨나요?"에 한 팀을 선택한다.
2. 시스템 처리
   - 공동 공연이면 선택이 필수인지 확인하고, 선택한 팀이 해당 공연의 수락된 참여팀인지 확인한다.
   - 선택을 주문에 저장한다. **결제가 확인되기 전에는 온체인에 기록하지 않는다.**
   - 결제 확인 후, 발급된 티켓마다 운영지갑이 `recordChoice(ticketId, teamId)` 트랜잭션을 전송해 온체인 선택 카운터를 올린다. 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다. 예매 응답은 이 확정을 기다리지 않는다.
   - 운영지갑 트랜잭션은 nonce 직렬 큐로 순서를 보장하고, 실패 시 최대 3회 재시도한다.
   - 관객 화면에는 트랜잭션·지갑 용어를 노출하지 않는다.
   - **양도 수락 시 재선택**: 티켓이 양도되면 받는 사람이 팀을 다시 선택하고, 운영지갑이 `cancelChoice` → `recordChoice` 2건을 순서대로 처리해 온체인 카운터를 갱신한다(상세는 `transfer` 장 "양도 링크 수락").
3. 처리 결과
   - **성공**
     - 선택이 저장되고, 온체인 카운터에 반영되어 정산 검증 페이지의 집계에 포함된다.
   - **실패**
     - 주문은 생성되지 않거나(선택 누락·유효하지 않은 팀), 온체인 기록이 보류되어 재시도 큐에 남는다.
     - 실패 사유를 제공한다. 온체인 기록이 최종 실패하면 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다.

### 티켓 발급

1. 결제가 확인되면 시스템이 주문 수량만큼 티켓을 발급한다(관객이 별도로 요청하지 않는다).
2. 시스템 처리
   - 주문 상태를 `PAID`로 전이한다.
   - 주문 항목의 수량만큼 티켓을 `ISSUED` 상태로 생성하고, 소유자를 주문한 회원으로 설정하며 최초 구매 금액을 함께 저장한다.
   - 티켓마다 QR 서명 시드를 발급한다.
   - 관람 목적 팀 선택의 온체인 기록을 비동기로 시작한다.
3. 처리 결과
   - **성공**
     - 예매 완료 화면이 표시되고 내 티켓 목록에서 티켓을 확인할 수 있다.
   - **실패**
     - 티켓은 발급되지 않고 주문은 `PENDING_PAYMENT`로 남아 결제 상태 확인 대상이 된다.
     - 실패 사유를 제공한다.

### 주문·티켓 조회

1. 관객은 주문 내역과 내 티켓 목록·상세를 조회한다.
2. 시스템 처리
   - 요청자가 해당 주문의 주문자 또는 해당 티켓의 현재 소유자인지 확인한다.
   - 주문은 결제·환불 상태와 함께, 티켓은 예정·사용 완료·취소 구분과 함께 페이지 단위로 반환한다.
   - 티켓 상세에는 공연 정보·입장 시각·티켓 상태·양도 및 취소 가능 여부를 함께 담는다.
3. 처리 결과
   - **성공**
     - 주문·티켓 정보가 표시된다.
   - **실패**
     - 정보가 표시되지 않는다.
     - 실패 사유를 제공한다.

### 동적 QR 발급

1. 관객은 티켓 상세 화면을 열어 입장용 QR을 표시하고, 화면은 30초마다 새 QR을 요청한다.
2. 시스템 처리
   - 요청자가 해당 티켓의 현재 소유자인지 확인한다.
   - 티켓 상태가 `ISSUED`인지 확인한다. 사용 완료·취소된 티켓에는 QR을 발급하지 않는다.
   - 티켓의 QR 시드로 서명 토큰을 만들고 유효기간 60초를 부여한다. **고정된 티켓 번호를 QR로 만들지 않는다.**
3. 처리 결과
   - **성공**
     - QR이 표시되고 30초마다 자동으로 갱신된다.
   - **실패**
     - QR은 표시되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 선택한 티켓 종류를 찾을 수 없는 경우 (`TICKET_OPTION_NOT_FOUND`)
- 아직 판매가 시작되지 않은 공연에 예매를 시도한 경우 (`TICKET_SALE_NOT_STARTED`)
- 판매 마감(공연 시작 1시간 전) 이후 예매를 시도한 경우 (`TICKET_SALE_CLOSED`)
- 재고 차감에 실패한 경우 (`TICKET_SOLD_OUT`)
- 1인 최대 구매 수량(4매)을 초과한 경우 (`TICKET_PURCHASE_LIMIT_EXCEEDED`)
- 공동 공연인데 관람 목적 팀을 선택하지 않은 경우 (`TICKET_TEAM_CHOICE_REQUIRED`)
- 선택한 팀이 해당 공연의 참여팀이 아닌 경우 (`TICKET_TEAM_CHOICE_INVALID`)
- 본인 소유가 아닌 티켓의 QR 발급·상세 조회를 시도한 경우 (`TICKET_NOT_OWNED`)
- 이미 입장 처리된 티켓에 QR 발급을 시도한 경우 (`TICKET_ALREADY_USED`)
- 취소된 티켓에 QR 발급을 시도한 경우 (`TICKET_CANCELED`)
- 사용 완료·취소된 티켓에 QR 발급을 시도한 경우 (`TICKET_INVALID_STATUS`)
- 예매 요청이 허용 횟수를 초과한 경우 (`COMMON_TOO_MANY_REQUESTS`)
- 결제 만료(15분)로 자동 취소된 주문에 결제를 시도한 경우 — 전용 코드가 없어 `PERFORMANCE_INVALID_STATUS` 대신 `COMMON_CONFLICT`로 응답하고, 전용 코드는 §12 신설 제안에 기록했다

## 결제 `payment`

관객 계좌에서 플랫폼 에스크로 계좌로의 금융망 이체와 그 상태 확인을 다룬다. 결제 확인은 KRWS 민팅의 유일한 트리거다.

### `payment`

주요 정보는 다음과 같다.

- 결제 식별자, 주문 식별자(주문당 1건)
- 결제 금액(BIGINT, 원 단위 정수), 출금 계좌 식별자
- 결제 상태 — `REQUESTED` / `CONFIRMED` / `FAILED` / `REFUNDED`
- 금융망 거래 식별자, 멱등키(`Idempotency-Key`)
- 요청 일시, 확인 일시, 실패 사유 코드

### 결제 요청

1. 관객은 결제 화면에서 연결된 계좌를 확인하고 결제를 요청한다.
2. 시스템 처리
   - 요청자가 주문자인지, 주문 상태가 `PENDING_PAYMENT`이고 결제 만료 시각을 넘기지 않았는지 확인한다.
   - 클라이언트가 보낸 금액과 서버가 계산한 금액이 같은지 확인한다.
   - 관객의 금융망 계좌가 연결되어 있는지 확인한다.
   - 멱등키를 붙여 금융망 API로 관객 계좌 → 플랫폼 에스크로 계좌 이체를 요청하고, 결제를 `REQUESTED`로 기록한다.
   - 요청을 `202`로 접수하고 작업(`jobId`)을 반환한다. 화면은 폴링으로 진행 상태를 표시한다.
   - 입금이 확인되면 결제를 `CONFIRMED`로 전이하고, **같은 금액만큼 KRWS 민팅**을 시작하며(`coin` 장), 티켓을 발급한다.
3. 처리 결과
   - **성공**
     - 결제가 완료되고 티켓이 발급되어 예매 완료 화면으로 이동한다.
   - **실패**
     - 결제는 진행되지 않으며 차감했던 재고를 원복하고 주문을 취소 처리한다. KRWS 민팅은 실행하지 않는다.
     - 실패 사유를 제공한다.

### 결제 상태 확인

1. 관객은 결제 처리 중 화면 또는 주문 내역에서 결제 상태를 확인한다.
2. 시스템 처리
   - 요청자가 주문자인지 확인한다.
   - 결제 상태와 함께 KRWS 예치 처리 진행 여부, 티켓 발급 여부를 반환한다.
   - 금융망 응답이 아직 오지 않은 경우 "확인 중"으로 표시하고 중복 결제를 유도하지 않는다.
3. 처리 결과
   - **성공**
     - 결제 상태(요청·완료·실패)와 다음 행동 안내가 표시된다.
   - **실패**
     - 상태가 표시되지 않는다.
     - 실패 사유를 제공한다.

### 결제 실패·타임아웃 처리

1. 금융망 API가 오류를 반환하거나 시간 안에 응답하지 않으면 시스템이 보상 처리를 수행한다.
2. 시스템 처리
   - 오류 응답이면 결제를 `FAILED`로 기록하고 재고를 즉시 원복한 뒤 주문을 `CANCELLED`로 전이한다.
   - 응답 없음(타임아웃)이면 결제 성공 여부가 불확실하므로 상태를 확정하지 않고, 멱등키로 결제 결과를 재조회하는 확인 작업을 예약한다. 재고는 결제 만료 시각까지 유지한다.
   - 어느 경우에도 KRWS 민팅은 실행하지 않는다.
   - 관객에게는 중복 결제를 유도하지 않는 문구로 안내한다.
3. 처리 결과
   - **성공**
     - 결제·주문·재고 상태가 일관되게 정리되고, 관객은 주문 내역에서 결과를 확인할 수 있다.
   - **실패**
     - 결제는 확정되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 이미 결제가 완료된 주문에 다시 결제를 요청한 경우 (`PAYMENT_ALREADY_PAID`)
- 클라이언트가 보낸 금액과 서버 계산 금액이 다른 경우 (`PAYMENT_AMOUNT_MISMATCH`)
- 계좌 잔액이 부족한 경우 (`PAYMENT_INSUFFICIENT_BALANCE`)
- 금융망 API가 오류를 반환한 경우 (`PAYMENT_REQUEST_FAILED`)
- 금융망 응답이 시간 안에 오지 않은 경우 (`PAYMENT_TIMEOUT`)
- 주문자가 아닌 회원이 결제를 시도한 경우 (`COMMON_FORBIDDEN`)
- 주문을 찾을 수 없는 경우 (`COMMON_NOT_FOUND`)
- 결제 요청이 동시에 중복 접수된 경우 (`COMMON_CONFLICT`)

## KRWS `coin`

원화 1:1 스테이블코인 KRWS(ERC-20, decimals=0, 1 KRWS = 1원)의 발행·소각 작업과 유통량·준비금 조회를 다룬다.

### `coin_job`

주요 정보는 다음과 같다.

- 작업 식별자(`jobId`로 노출), 작업 유형(mint·burn)
- 대상 금액(BIGINT, 원 단위 정수), 관련 주문·환불·환급 식별자
- 작업 상태 — `PENDING` / `SUBMITTED` / `CONFIRMED` / `FAILED`
- 트랜잭션 해시(`CHAR(66)`), 재시도 횟수, 실패 사유
- 멱등키, 요청 일시, 확정 일시

### `chain_job`

주요 정보는 다음과 같다.

- 작업 식별자(`jobId`로 노출), 트랜잭션 종류(동의·잠금·선택 기록·선택 취소·분배·가스 충전)
- 요청자 회원 식별자, 대상 공연·티켓·팀 식별자
- 작업 상태 — `PENDING` / `SUBMITTED` / `CONFIRMED` / `FAILED`
- 트랜잭션 해시(`CHAR(66)`), 컨펌 수, 재시도 횟수, 실패 사유
- 요청 일시, 확정 일시

### KRWS 발행

1. 결제가 확인되면 시스템이 동일 금액의 KRWS 발행을 시작한다(사용자가 요청하지 않는다).
2. 시스템 처리
   - 금융망 입금 확인 기록이 존재하는지 확인한다. **입금 확인 없는 발행은 어떤 경로로도 허용하지 않는다.**
   - 발행 직전 준비금 상태(에스크로 잔액 ≥ 유통량)를 확인한다. 불일치가 확인되면 발행을 중단하고 관리자에게 알린다.
   - minter 권한 지갑으로 `mint` 트랜잭션을 전송하고 공연별 에스크로에 예치한다. 작업을 `202`로 접수해 `jobId`를 만들고 폴링으로 확정을 확인한다.
   - 최종 실패하면 결제 금액에 대한 자동 환불 보상 처리를 건다.
3. 처리 결과
   - **성공**
     - 발행된 KRWS가 공연 에스크로에 예치되고 정산 재원이 된다. 유통량과 준비금 잔액이 함께 갱신된다.
   - **실패**
     - KRWS는 발행되지 않으며, 결제 금액은 자동 환불된다.
     - 실패 사유를 제공한다.

### KRWS 소각

1. 티켓 환불 또는 팀 환급이 발생하면 시스템이 해당 금액의 KRWS 소각을 시작한다.
2. 시스템 처리
   - 소각 대상 금액과 근거(환불 또는 환급 식별자)를 확인한다.
   - **환급의 경우 금융망 원화 이체 성공을 먼저 확인한 뒤에만 소각한다.** 순서를 뒤집으면 이체 실패 시 토큰만 사라져 준비금 증명이 깨진다.
   - burner 권한 지갑으로 소각 트랜잭션을 전송하고, 작업을 `202`로 접수해 `jobId` 폴링으로 확정을 확인한다.
   - 실패하면 금융망 이체를 진행하지 않거나(환불) 재시도 대기로 남긴다(환급).
3. 처리 결과
   - **성공**
     - 유통량이 줄고 준비금 1:1 관계가 유지된다.
   - **실패**
     - 소각은 이뤄지지 않고 작업이 재시도 대기 상태로 남는다.
     - 실패 사유를 제공한다.

### 유통량·준비금 조회

1. 비로그인 방문자 또는 시스템 내부 검증 작업이 KRWS 총 유통량과 에스크로 잔액을 조회한다.
2. 시스템 처리
   - 체인에서 KRWS 총 유통량을, 금융망 API에서 에스크로 계좌 잔액을 조회한다.
   - 두 값과 차액, 조회 시각을 함께 반환하고 결과를 1분 캐시한다.
   - 에스크로 잔액이 유통량보다 적으면 불일치로 판정해 mint와 release를 중단하고 관리자에게 알린다.
3. 처리 결과
   - **성공**
     - 유통량·에스크로 잔액·차액·갱신 시각이 표시된다.
   - **실패**
     - 값이 표시되지 않고 마지막 성공 조회값과 그 시각을 함께 알린다.
     - 실패 사유를 제공한다.

### 발행·소각 작업 자동 재시도

1. 발행·소각 작업이 실패하면 시스템이 재시도를 자동으로 수행한다(관리자가 트리거하지 않는다).
2. 시스템 처리
   - 작업 상태가 `FAILED`인지 확인하고, 이미 확정된 작업은 재시도하지 않는다.
   - 원래 멱등키를 그대로 사용해 즉시 3회까지 재시도하고, 이후에는 지수 백오프로 연장 재시도한다.
   - 컨트랙트 revert·준비금 불일치 같은 결정적 실패는 재시도하지 않고 즉시 중단한 뒤 알림을 보낸다.
   - 재시도 횟수와 결과를 감사 로그에 남긴다.
3. 처리 결과
   - **성공**
     - 작업이 다시 접수되어 `PENDING`부터 진행되고 결과가 작업 상태에 반영된다.
   - **실패**
     - 작업 상태는 `FAILED`로 유지되고 재시도 횟수가 증가하며 알림이 발송된다.
     - 실패 사유를 기록한다.

### 실패 사유

- 결제 확인 뒤 발행·예치가 아직 확정되지 않은 상태에서 후속 작업을 요청한 경우 (`COIN_MINT_PENDING`)
- 결제는 성공했으나 발행이 최종 실패한 경우 (`COIN_MINT_FAILED`)
- 환불·환급 과정의 소각이 실패한 경우 (`COIN_BURN_FAILED`)
- 공연별 에스크로 잔액이 요청 금액보다 적은 경우 (`COIN_ESCROW_INSUFFICIENT`)
- 에스크로 계좌 잔액이 유통량보다 적어 준비금 1:1이 깨진 경우 (`COIN_RESERVE_MISMATCH`)
- 트랜잭션이 확정되지 않고 지연되는 경우 (`CHAIN_TX_TIMEOUT`)
- 운영지갑 가스가 부족한 경우 (`CHAIN_GAS_INSUFFICIENT`)
- nonce 직렬화에 최종 실패한 경우 (`CHAIN_NONCE_CONFLICT`)
- 금융망 잔액 조회가 실패한 경우 (`COMMON_EXTERNAL_SERVICE_ERROR`)

## 취소·환불 `refund`

관객의 개별 티켓 취소와 공연 취소에 따른 일괄 환불을 다룬다. 환불은 금융망 이체·KRWS 소각·온체인 선택 취소(`cancelChoice`) 세 가지를 함께 처리한다.

### `refund`

주요 정보는 다음과 같다.

- 환불 식별자, 티켓 식별자, 주문 식별자, 결제 식별자
- 환불 사유 구분(관객 취소·공연 취소)
- 원 결제 금액, 취소 수수료(BIGINT), 실제 환불 금액(BIGINT)
- 적용된 수수료 구간(D-7 이전·D-3 이전)
- 금융망 환불 거래 식별자, 소각 작업 식별자, 선택 취소 트랜잭션 해시(`CHAR(66)`)
- 처리 상태와 재시도 횟수, 멱등키
- 요청 일시, 완료 일시

### 환불액 미리보기

1. 관객은 티켓 상세에서 취소를 누르고 환불 예정 금액을 확인한다.
2. 시스템 처리
   - 요청자가 티켓 소유자인지, 티켓 상태가 `ISSUED`인지 확인한다.
   - 현재 시각과 공연일을 비교해 수수료 구간을 판정한다 — 공연일 D-7 이전이면 전액, D-3 이전이면 50%, D-3 00:00 이후면 취소 불가다.
   - 결제 금액·수수료·환불 예정 금액과 취소 마감 시각을 함께 반환한다.
3. 처리 결과
   - **성공**
     - 환불 예정 금액과 수수료 구간이 표시되고 취소 확인 버튼이 활성화된다.
   - **실패**
     - 금액이 표시되지 않고 취소를 진행할 수 없다.
     - 실패 사유를 제공한다.

### 개별 취소·환불

1. 관객은 환불 예정 금액을 확인하고 취소를 확정 요청한다.
2. 시스템 처리
   - 요청자가 티켓 소유자인지, 티켓 상태가 `ISSUED`인지, 취소 마감(D-3 00:00) 이전인지 확인한다. .
   - 해당 공연의 정산이 이미 잠긴 상태면 앱에서의 취소를 거부한다.
   - 티켓 상태를 `CANCELLED`로 전이하고 재고를 원복한다.
   - 멱등키를 붙여 금융망으로 환불 이체를 요청하고, 이체 성공 확인 후 환불 금액만큼 KRWS를 소각한다.
   - 운영지갑으로 `cancelChoice(ticketId)` 트랜잭션을 전송해 온체인 선택 카운터를 되돌린다. 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 주문의 모든 티켓이 취소되면 주문 상태를 `REFUNDED`로 전이한다.
3. 처리 결과
   - **성공**
     - 티켓이 취소되고 환불 금액이 관객 계좌로 입금된다. 온체인 선택 카운터가 감소해 정산 집계에서 제외된다.
   - **실패**
     - 티켓은 취소되지 않는다. 이체가 실패한 경우 소각을 진행하지 않고 재시도 대기 상태로 남긴다.
     - 실패 사유를 제공한다.

### 공연 취소 일괄 환불

1. 공연 생성자 또는 관리자가 공연을 취소하면 시스템이 결제 완료된 전 티켓의 환불을 시작한다.
2. 시스템 처리
   - 공연 상태가 `CANCELLED`이고 정산이 `HALTED`인지 확인한다.
   - 대상 티켓을 조회해 건별 환불 작업을 큐에 넣는다. **수수료는 부과하지 않는다.**
   - 건별로 금융망 환불 이체 → 이체 성공 확인 → KRWS 소각 → `cancelChoice` 순으로 처리하고, 각 단계에 멱등키를 붙인다.
   - 일부가 실패해도 나머지는 계속 처리하고, 실패 건은 시스템이 연장 재시도한다.
   - 처리 진행률(전체·완료·실패 건수)을 공연자 화면에 표시한다.
3. 처리 결과
   - **성공**
     - 전 티켓이 취소되고 관객에게 전액이 환불된다. 정산은 실행되지 않는다.
   - **실패**
     - 실패한 건의 티켓·환불 상태는 그대로 남고, 시스템이 연장 재시도하며 결정적 실패 시 알림을 보낸다.
     - 실패 사유를 제공한다.

### 정산 잠금 이후 취소 차단

1. 관객이 정산이 잠긴 공연의 티켓 취소를 시도한다.
2. 시스템 처리
   - 해당 공연의 정산 상태가 `LOCKED` 이후인지 확인한다.
   - 온체인 분배분의 회수가 불가능하므로 앱에서의 취소를 거부하고, 고객센터 문의 경로를 안내한다.
   - 시도 사실을 로그에 남겨 오프체인 준비금 정책의 처리 대상으로 집계한다.
3. 처리 결과
   - **성공**
     - 취소가 차단되고 관객에게 대안 경로가 안내된다.
   - **실패**
     - 취소는 진행되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 취소 마감(D-3 00:00) 이후 취소를 시도한 경우 (`REFUND_DEADLINE_PASSED`)
- 이미 취소 요청이 접수된 티켓인 경우 (`REFUND_ALREADY_REQUESTED`)
- 정산이 잠긴 이후 취소를 시도한 경우 (`REFUND_AFTER_SETTLEMENT_LOCK`)
- 금융망 환불 이체가 실패한 경우 (`REFUND_TRANSFER_FAILED`)
- 본인 소유가 아닌 티켓의 취소를 시도한 경우 (`TICKET_NOT_OWNED`)
- 이미 입장 처리된 티켓의 취소를 시도한 경우 (`TICKET_ALREADY_USED`)
- 이미 취소된 티켓인 경우 (`TICKET_CANCELED`)
- 사용 완료된 티켓의 취소를 시도한 경우 (`TICKET_INVALID_STATUS`)
- 환불 금액의 KRWS 소각이 실패한 경우 (`COIN_BURN_FAILED`)
- 선택 취소 트랜잭션이 지연되거나 실패한 경우 (`CHAIN_TX_TIMEOUT`, `CHAIN_NONCE_CONFLICT`)

## 양도 `transfer`

일반 티켓의 소유권을 공유 링크로 넘기는 선물 기능을 다룬다. 수락 즉시 소유자가 바뀌고 기존 QR은 폐기된다.

### `transfer`

주요 정보는 다음과 같다.

- 양도 식별자, 티켓 식별자
- 보낸 회원 식별자, 받은 회원 식별자(수락 시 기록)
- 서명된 양도 토큰, 만료 일시(생성 후 24시간)
- 양도 상태 — `PENDING` / `COMPLETED` / `EXPIRED` / `CANCELLED`
- 생성 일시, 수락·취소·만료 일시

### 양도 링크 생성

1. 관객은 티켓 상세에서 선물하기를 눌러 양도 링크 생성을 요청한다.
2. 시스템 처리
   - 요청자가 티켓 소유자인지, 티켓 상태가 `ISSUED`인지 확인한다. 사용 완료·취소·이미 양도 중인 티켓은 거부한다.
   - 공연이 아직 종료되지 않았는지 확인한다.
   - 서명된 일회용 토큰을 만들고 만료 시각(24시간)을 부여해 양도를 `PENDING`으로 생성한다.
   - 티켓 상태를 `TRANSFER_PENDING`으로 전이한다. **이 상태의 티켓은 입장과 취소가 모두 차단된다.**
   - 공유 링크에는 개인정보와 QR 원본을 담지 않는다.
3. 처리 결과
   - **성공**
     - 양도 링크가 생성되고 공유할 수 있다. 만료 시각이 화면에 표시된다.
   - **실패**
     - 양도 링크는 생성되지 않고 티켓 상태도 변하지 않는다.
     - 실패 사유를 제공한다.

### 양도 정보 조회

1. 링크를 받은 사람이 로그인 없이 링크를 열어 티켓 정보를 확인한다.
2. 시스템 처리
   - 토큰의 서명·만료·사용 여부를 확인한다. 만료된 토큰은 양도를 `EXPIRED`로 전이하고 티켓을 `ISSUED`로 되돌린다.
   - 공연 제목·일시·장소·티켓 종류와 보낸 사람의 표시 이름만 반환한다. 개인정보와 QR은 포함하지 않는다.
   - 공동 공연이면 "양도 수락 시 관람 목적 팀을 선택합니다"를 안내한다.
   - 비회원이면 "회원 가입 후 양도를 받을 수 있습니다"를 안내하고 회원 가입·로그인 화면으로 유도한다.
3. 처리 결과
   - **성공**
     - 티켓 정보와 수락 안내가 표시되고, 로그인 후 수락할 수 있다. 비회원은 가입(자체 또는 카카오·네이버 OAuth) 후 양도 수락 화면으로 자동 복귀한다.
   - **실패**
     - 티켓 정보가 표시되지 않는다.
     - 실패 사유를 제공한다.

### 양도 수락

1. 로그인한 관객이 양도 링크에서 수락을 요청한다. 공동 공연이면 관람 목적 팀을 선택한다.
2. 시스템 처리
   - 토큰의 서명·만료·사용 여부를 다시 확인하고, 동시 수락을 막기 위해 원자적으로 처리한다.
   - 보낸 사람과 받는 사람이 동일인이 아닌지 확인한다.
   - 받는 사람이 해당 공연에서 보유하게 될 티켓 수가 4매를 넘지 않는지 확인한다.
   - 티켓의 현재 소유자를 받는 사람으로 변경하고 티켓 상태를 `ISSUED`로 되돌린다.
   - **기존 QR 시드를 즉시 폐기하고 새 시드를 발급한다.** 보낸 사람 화면의 QR은 그 즉시 무효가 된다.
   - 운영지갑이 `cancelChoice(ticketId)` → `recordChoice(ticketId, newTeamId)` 온체인 트랜잭션 2건을 순서대로 전송해 팀 선택을 갱신한다. 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다. 양도 응답은 이 확정을 기다리지 않는다.
   - 두 트랜잭션 중 하나라도 실패하면 최대 3회 재시도하고, 그 뒤에는 시스템이 연장 재시도하며 결정적 실패 시 알림을 보낸다. 온체인 반영이 실패해도 양도(소유권 이전)는 롤백하지 않는다 — 집계 대사에서 불일치로 드러나 정산 잠금이 차단된다.
   - 양도를 `COMPLETED`로 전이하고 토큰을 무효화한다.
3. 처리 결과
   - **성공**
     - 받는 사람의 내 티켓 목록에 티켓이 나타나고 새 QR로 입장할 수 있다.
   - **실패**
     - 소유권은 이전되지 않는다.
     - 실패 사유를 제공한다.

### 양도 취소·만료

1. 보낸 관객이 양도를 취소하거나, 24시간이 지나 링크가 만료된다.
2. 시스템 처리
   - 취소 요청이면 요청자가 보낸 사람인지 확인하고 양도 상태가 `PENDING`인지 확인한다.
   - 양도를 `CANCELLED` 또는 `EXPIRED`로 전이하고 토큰을 무효화한다.
   - 티켓 상태를 `TRANSFER_PENDING`에서 `ISSUED`로 되돌린다.
   - 만료 처리는 배치로 주기 실행하고, 링크 조회 시점에도 즉시 판정한다.
3. 처리 결과
   - **성공**
     - 티켓이 보낸 사람에게 그대로 남고 다시 입장·취소·재양도가 가능해진다.
   - **실패**
     - 양도 상태는 변하지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 양도 링크를 찾을 수 없는 경우 (`TRANSFER_LINK_NOT_FOUND`)
- 양도 링크가 만료된 경우 (`TRANSFER_LINK_EXPIRED`)
- 이미 다른 사용자가 수락한 링크인 경우 (`TRANSFER_LINK_ALREADY_USED`)
- 자기 자신에게 선물을 시도한 경우 (`TRANSFER_SELF_NOT_ALLOWED`)
- 입장 완료·취소·양도 중인 티켓인 경우 (`TICKET_INVALID_STATUS`)
- 로그인하지 않고 수락을 시도한 경우 (`COMMON_UNAUTHORIZED`)
- 본인 소유가 아닌 티켓의 양도·양도 취소를 시도한 경우 (`TICKET_NOT_OWNED`)
- 수락 후 보유 수량이 1인 최대 4매를 초과하는 경우 (`TICKET_PURCHASE_LIMIT_EXCEEDED`)
- 로그인하지 않고 수락을 시도한 경우 (`COMMON_UNAUTHORIZED`)
- 동시에 수락 요청이 몰려 처리 충돌이 난 경우 (`COMMON_CONFLICT`)
- 수락 요청이 허용 횟수를 초과한 경우 (`COMMON_TOO_MANY_REQUESTS`)

## 입장 `entry`

공연별 자동 생성된 검표 페이지에서의 QR 검증·입장 처리와 입장 현황 조회를 다룬다. 입장 판정은 전적으로 서버 서명 QR의 검증으로 이뤄지며 온체인 조회를 하지 않는다.

### `entry_log`

주요 정보는 다음과 같다.

- 입장 이력 식별자, 티켓 식별자, 공연 식별자
- 판정 결과(정상 입장·중복 시도·만료·서명 불일치·시간대 밖·권한 없음)
- 스캔 일시, 최초 입장 일시
- 실패 시 사유 코드

### 검표 공연 목록 조회 (v1) {toggle="true"}

	검표 페이지 접근(v2)으로 대체되어 더 이상 사용하지 않는다.

	1. 검표 관계자는 검표 화면에 들어가 자신이 배정된 공연 목록을 확인한다.
	2. 시스템 처리
		- 요청자가 검표 관계자로 지정된 공연을 조회한다. 참여팀 리더는 자동으로 포함된다.
		- 각 공연의 입장 가능 시간대와 판매·입장 요약을 함께 반환한다.
	3. 처리 결과
		- **성공**
			- 배정된 공연 목록이 표시되고 공연을 선택해 스캔 화면으로 들어갈 수 있다.
		- **실패**
			- 목록이 표시되지 않는다.
			- 실패 사유를 제공한다.

### 검표 페이지 접근 (v2)

1. 검표 담당자는 공유받은 검표 페이지 링크로 접속한다.
2. 시스템 처리
   - 링크의 서명 토큰이 유효한지, 해당 공연의 것인지 검증한다.
   - 유효하면 해당 공연의 QR 스캔 화면을 표시하고, 입장 가능 시간대와 입장 요약(총 티켓 수·입장 완료 수)을 함께 보여준다.
   - 검표 담당자의 계정 정보는 서비스에 저장하지 않는다.
3. 처리 결과
   - **성공**
     - 해당 공연의 검표 화면이 표시되고 QR 스캔을 시작할 수 있다.
   - **실패**
     - 토큰이 유효하지 않거나 만료된 경우 접근이 거부된다.
     - 실패 사유를 제공한다.

### QR 검증·입장 처리

1. 검표 담당자는 검표 페이지에서 카메라로 관객의 QR을 스캔해 입장 처리를 요청한다.
2. 시스템 처리
   - 검표 페이지 링크 토큰이 유효하고 해당 공연의 것인지 확인한다.
   - QR 토큰의 서명을 검증하고 유효기간(60초) 안인지 확인한다.
   - 티켓이 해당 공연의 티켓인지, 상태가 `ISSUED`인지 확인한다. 사용 완료·취소된 티켓은 거부한다.
   - 현재 시각이 입장 허용 시간대 안인지 확인한다.
   - 티켓 식별자 기준으로 원타임 처리를 적용해 동시·중복 스캔을 차단한다.
   - 티켓 상태를 `USED`로 전이하고 입장 이력을 기록한다. 실패한 스캔도 사유와 함께 이력에 남긴다.
   - 판정 결과를 1초 안에 반환해 색·소리로 구분할 수 있게 한다.
3. 처리 결과
   - **성공**
     - 입장이 확정되고 검표 화면에 정상 판정이 표시된다. 바로 다음 스캔을 이어갈 수 있다.
   - **실패**
     - 입장 처리는 되지 않으며 티켓 상태도 변하지 않는다.
     - 실패 사유를 제공한다. 중복 시도는 최초 입장 시각을 함께 보여준다.

### 입장 현황 조회

1. 검표 담당자(검표 페이지 링크 보유자) 또는 참여팀 소속은 입장 현황과 최근 이력을 조회한다.
2. 시스템 처리
   - 검표 페이지 링크 토큰이 해당 공연의 것으로 유효하거나, 요청자가 참여팀 소속인지 확인한다.
   - 총 발급 티켓 수 대비 입장 수, 최근 스캔 이력, 중복·실패 시도 건수를 반환한다.
   - 관객 개인정보는 표시하지 않고 티켓 식별 정보와 시각만 보여준다.
3. 처리 결과
   - **성공**
     - 입장 현황과 최근 이력이 표시되고 주기적으로 갱신된다.
   - **실패**
     - 현황이 표시되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- QR 유효기간이 지난 경우 (`ENTRY_QR_EXPIRED`)
- QR 서명 검증에 실패한 경우 (`ENTRY_QR_SIGNATURE_INVALID`)
- 이미 입장 처리된 티켓을 다시 스캔한 경우 (`ENTRY_ALREADY_ENTERED`)
- 입장 허용 시간대가 아닌 경우 (`ENTRY_NOT_IN_TIME_WINDOW`)
- 유효하지 않은 검표 페이지 링크로 검표를 시도한 경우 (`ENTRY_SCANNER_NOT_AUTHORIZED`)
- 취소된 티켓인 경우 (`TICKET_CANCELED`)
- 다른 공연의 티켓을 스캔한 경우 (`COMMON_NOT_FOUND`)
- 검표 링크 없이 참여팀도 아닌 회원이 입장 현황을 조회한 경우 (`COMMON_FORBIDDEN`)

## 정산 `settlement`

공연 종료 후의 집계 확정, 정산 잠금, 이의제기, KRWS 분배(release), 정산 결과 조회를 다룬다. 순서는 컨트랙트가 강제한다.

### `settlement`

주요 정보는 다음과 같다.

- 정산 식별자, 공연 식별자(공연당 1건)
- 정산 상태 — `NONE` / `AGGREGATED` / `LOCKED` / `DISPUTE_OPEN` / `RELEASED` / `REDEEMED` / `HALTED`
- 총 매출(BIGINT)
- 유효 티켓 수, 팀별 관객 선택 수 합계, 온체인 카운터 대조 결과
- 집계 확정 일시, 잠금 일시, 이의제기 마감 일시(잠금 + 48시간), release 일시
- 집계·잠금·분배 트랜잭션 해시(`CHAR(66)`)

### `settlement_share`

주요 정보는 다음과 같다.

- 분배 식별자, 정산 식별자, 팀 식별자
- 균등 분배액·관객 선택 분배액(각 BIGINT)
- dust 귀속액(BIGINT), 최종 분배액(BIGINT)
- 해당 팀의 관객 선택 수
- 분배 트랜잭션 해시(`CHAR(66)`), 팀 지갑 입금 확인 여부

### `dispute`

주요 정보는 다음과 같다.

- 이의제기 식별자, 정산 식별자, 제기한 팀 식별자와 회원 식별자
- 이의 사유 본문
- 이의 상태 — `OPEN` / `RESOLVED` / `REJECTED`
- 관리자 처리 의견과 처리한 관리자 식별자
- 제기 일시, 처리 일시

### 집계 확정

1. 공연 생성자 또는 관리자는 공연 종료 후 매출·선택 집계를 확정 요청한다.
2. 시스템 처리
   - 공연 상태가 `ENDED`인지, 취소 마감을 지났는지 확인한다. 공연이 취소되어 정산이 `HALTED`이면 거부한다.
   - 처리 중인 결제·민팅 작업이 남아 있지 않은지 확인한다.
   - 유효 티켓(취소되지 않은 티켓)의 매출 합계와 팀별 관객 선택 수를 서버에서 집계한다.
   - **온체인 선택 카운터와 서버 집계를 대조한다.** 불일치하면 확정을 중단하고 관리자 확인 대상으로 넘긴다.
   - 집계 결과를 온체인에 확정하는 트랜잭션을 전송한다. 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 정산 상태를 `AGGREGATED`로 전이한다.
3. 처리 결과
   - **성공**
     - 팀별 분배 예정액이 산출되어 정산 대시보드에 표시되고, 정산 잠금이 가능해진다.
   - **실패**
     - 집계는 확정되지 않고 정산 상태가 유지된다.
     - 실패 사유를 제공한다.

### 정산 잠금

1. 공연 생성자 또는 관리자는 확정된 집계를 확인하고 정산 잠금을 요청한다.
2. 시스템 처리
   - 정산 상태가 `AGGREGATED`인지 확인한다.
   - 잠금 트랜잭션을 전송해 집계·분배액을 고정한다. 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 정산 상태를 `LOCKED`로 전이하고, 이의제기 마감 시각(잠금 + 48시간)을 기록하며 상태를 `DISPUTE_OPEN`으로 이어 전이한다.
   - 이 시점부터 앱에서의 티켓 취소를 차단한다.
   - 참여팀 리더에게 이의제기 기간 시작을 알린다.
3. 처리 결과
   - **성공**
     - 정산이 잠기고 48시간의 이의제기 기간이 시작된다. 팀별 분배액과 마감 시각이 표시된다.
   - **실패**
     - 정산은 잠기지 않는다.
     - 실패 사유를 제공한다.

### 이의제기 제출

1. 참여팀 리더는 이의제기 기간 안에 사유를 작성해 이의를 제출한다.
2. 시스템 처리
   - 요청자가 참여팀 리더인지 확인한다.
   - 정산 상태가 `DISPUTE_OPEN`이고 마감 시각을 넘기지 않았는지 확인한다.
   - 같은 팀이 이미 제기한 이의가 `OPEN` 상태로 남아 있는지 확인한다.
   - 이의를 `OPEN`으로 생성하고 **release 자동 실행을 보류한다.**
   - 관리자에게 알린다.
3. 처리 결과
   - **성공**
     - 이의가 접수되고 정산 대시보드에 표시된다. 48시간이 지나도 release가 자동 실행되지 않는다.
   - **실패**
     - 이의는 접수되지 않는다.
     - 실패 사유를 제공한다.

### 이의제기 처리

1. 관리자는 접수된 이의를 검토하고 인정 또는 반려를 결정한다.
2. 시스템 처리
   - 요청자가 관리자인지, 이의 상태가 `OPEN`인지 확인한다.
   - 처리 의견과 함께 이의를 `RESOLVED` 또는 `REJECTED`로 전이하고 감사 로그에 남긴다.
   - 남은 `OPEN` 이의가 없으면 release 보류를 해제하고 수동 실행이 가능한 상태로 되돌린다.
   - 집계 자체를 되돌려야 하는 경우에는 정산을 `HALTED`로 전이하고 관리자 수동 처리로 넘긴다.
3. 처리 결과
   - **성공**
     - 이의 처리 결과가 기록되고 참여팀에 표시된다. 남은 이의가 없으면 정산을 이어갈 수 있다.
   - **실패**
     - 이의 상태는 바뀌지 않는다.
     - 실패 사유를 제공한다.

### release 실행

1. 이의제기 기간 48시간이 지나면 시스템이 release를 자동 실행한다. 공연 생성자 또는 관리자가 수동으로 실행할 수도 있다.
2. 시스템 처리
   - 정산 상태가 `LOCKED` 또는 `DISPUTE_OPEN`이고 이의제기 마감 시각을 지났는지 확인한다.
   - `OPEN` 상태의 이의가 남아 있으면 실행하지 않는다.
   - 준비금 상태(에스크로 잔액 ≥ 유통량)를 확인한다. 불일치면 실행하지 않는다.
   - 공연 에스크로의 KRWS 잔액이 분배 합계 이상인지 확인한다.
   - 운영지갑이 `release()` 트랜잭션을 전송해 잠긴 규칙과 온체인 카운터로 산출한 금액을 **팀 지갑으로 실제 분배한다.** 요청은 `202`로 접수되고 작업(`jobId`) 폴링으로 확정을 확인한다.
   - 확정되면 정산 상태를 `RELEASED`로 전이하고 팀별 분배 트랜잭션 해시를 저장한 뒤, 팀별 자동 환급을 시작한다(`redeem` 장).
3. 처리 결과
   - **성공**
     - 팀 지갑에 KRWS가 입금되고 트랜잭션 링크가 정산 대시보드와 정산 검증 페이지에 표시된다. 이어서 원화 환급이 자동으로 진행된다.
   - **실패**
     - 분배는 실행되지 않고 정산 상태가 유지된다.
     - 실패 사유를 제공한다.

### 정산 조회

1. 참여팀 소속 공연자는 정산 진행 상태와 팀별 분배 내역을 조회한다.
2. 시스템 처리
   - 요청자가 해당 공연의 참여팀 소속인지 확인한다.
   - 정산 상태·총 매출·팀별 산출 내역(균등·관객 선택·dust)·트랜잭션 해시·환급 진행 상태를 반환한다.
   - 다음 단계와 그 조건(집계 확정 가능·이의제기 마감 시각·release 예정 시각)을 함께 알린다.
3. 처리 결과
   - **성공**
     - 정산 상태 머신과 팀별 분배 내역이 표시되고, 권한이 있는 사용자에게 다음 단계 버튼이 활성화된다.
   - **실패**
     - 정산 내역이 표시되지 않는다.
     - 실패 사유를 제공한다.

### 실패 사유

- 집계 확정·정산 잠금 전에 release를 시도한 경우 (`SETTLEMENT_NOT_LOCKED`)
- 이의제기 기간 중에 release를 시도한 경우 (`SETTLEMENT_DISPUTE_PERIOD`)
- 컨트랙트의 release가 아직 활성화되지 않은 경우 (`SETTLEMENT_RELEASE_NOT_ACTIVE`)
- 이미 정산이 완료된 공연인 경우 (`SETTLEMENT_ALREADY_RELEASED`)
- 온체인 선택 카운터 합과 서버 집계가 불일치한 경우 (`SETTLEMENT_AGGREGATE_MISMATCH`)
- 참여팀이 아닌 회원이 정산 내역 조회·이의제기를 시도한 경우 (`SETTLEMENT_NOT_PARTICIPANT`)
- 결제 확인 뒤 민팅이 아직 확정되지 않은 건이 남아 있는 경우 (`COIN_MINT_PENDING`)
- 공연 에스크로의 KRWS 잔액이 분배 합계보다 적은 경우 (`COIN_ESCROW_INSUFFICIENT`)
- 준비금 1:1이 깨져 분배를 중단한 경우 (`COIN_RESERVE_MISMATCH`)
- 공연 상태가 정산을 진행할 수 없는 상태인 경우 (`PERFORMANCE_INVALID_STATUS`)
- 분배 트랜잭션이 지연되거나 nonce 충돌로 실패한 경우 (`CHAIN_TX_TIMEOUT`, `CHAIN_NONCE_CONFLICT`)
- 이의제기 기간이 지난 뒤 이의를 제출한 경우 / 같은 팀이 중복으로 이의를 제출한 경우 — 전용 코드가 없어 `COMMON_CONFLICT`로 응답하고, 전용 코드는 §12 신설 제안에 기록했다

## 환급 `redeem`

release로 팀 지갑에 들어온 KRWS를 원화로 바꿔 팀 정산 계좌로 보내는 과정을 다룬다. **[권] 팀의 출금 버튼은 두지 않고 release 직후 자동으로 실행한다.**(P-10)

### `redemption`

주요 정보는 다음과 같다.

- 환급 식별자, 정산 식별자, 팀 식별자
- 환급 금액(BIGINT, 원 단위 정수)
- 환급 상태 — `PENDING` / `TRANSFERRED` / `FAILED`
- 금융망 이체 거래 식별자, 소각 작업 식별자, 소각 트랜잭션 해시(`CHAR(66)`)
- 멱등키, 재시도 횟수, 실패 사유
- 요청 일시, 이체 완료 일시

### 자동 환급 실행

1. release가 확정되면 시스템이 팀별 환급을 자동으로 시작한다(팀이 요청하지 않는다).
2. 시스템 처리
   - 팀별 분배액과 팀 지갑의 KRWS 잔액을 확인한다.
   - 팀의 정산 계좌가 등록되어 있고 예금주 검증을 통과했는지 확인한다. 미등록이면 해당 팀만 보류하고 리더에게 알린다.
   - 환급을 `PENDING`으로 생성하고 멱등키를 부여한다.
   - **금융망으로 원화 이체를 먼저 실행하고, 이체 성공을 확인한 뒤에 같은 금액의 KRWS를 소각한다.** 순서를 뒤집지 않는다.
   - 이체가 성공하면 환급을 `TRANSFERRED`로 전이하고, 팀 전원의 환급이 끝나면 정산 상태를 `REDEEMED`로 전이한다.
   - 이체가 실패하면 소각하지 않고 `FAILED`로 남겨 재시도 대상으로 둔다.
3. 처리 결과
   - **성공**
     - 팀 정산 계좌로 원화가 입금되고 환급 이력에 이체 식별자와 함께 기록된다. 유통량이 줄어 준비금 1:1이 유지된다.
   - **실패**
     - 원화는 입금되지 않고 KRWS도 소각되지 않는다. 해당 건은 재시도 대기 상태로 남는다.
     - 실패 사유를 제공한다.

### 환급 이력 조회

1. 팀 리더는 팀의 환급 이력을 조회한다.
2. 시스템 처리
   - 요청자가 해당 팀의 리더인지 확인한다.
   - 공연별 환급 금액·상태·이체 식별자·소각 트랜잭션 해시·실패 사유를 최신순으로 반환한다.
   - 실패 건은 재처리 진행 상황을 함께 표시한다.
3. 처리 결과
   - **성공**
     - 환급 이력이 표시되고 실패 건이 구분되어 보인다.
   - **실패**
     - 이력이 표시되지 않는다.
     - 실패 사유를 제공한다.

### 환급 자동 재시도

1. 환급이 실패하면 시스템이 재시도를 자동으로 수행한다(관리자가 트리거하지 않는다).
2. 시스템 처리
   - 환급 상태가 `FAILED`인지 확인한다.
   - 팀 정산 계좌 등록 여부를 다시 확인한다. **계좌 미등록으로 보류된 건은 팀이 계좌를 등록하는 시점에 자동으로 재개한다.**
   - 원래 멱등키를 그대로 사용해 이체를 재요청하고, 성공 확인 후 소각을 진행한다. 중복 이체가 발생하지 않도록 한다.
   - 즉시 3회까지 재시도한 뒤 지수 백오프로 연장 재시도하고, 결정적 실패는 즉시 중단하고 알림을 보낸다.
   - 재시도 횟수와 결과를 감사 로그에 남긴다.
3. 처리 결과
   - **성공**
     - 환급이 완료되고 상태가 `TRANSFERRED`로 바뀐다.
   - **실패**
     - 환급 상태는 `FAILED`로 유지되고 재시도 횟수가 증가하며 알림이 발송된다.
     - 실패 사유를 기록한다.

### 실패 사유

- 환급할 KRWS 잔액이 없는 경우 (`REDEEM_NOTHING_TO_REDEEM`)
- 팀의 원화 수령 계좌가 등록되지 않은 경우 (`REDEEM_ACCOUNT_NOT_REGISTERED`)
- 이미 접수된 환급 건에 중복 요청이 들어온 경우 (`REDEEM_ALREADY_REQUESTED`)
- 금융망 이체가 실패한 경우 (`REDEEM_BANK_TRANSFER_FAILED`)
- 이체 후 KRWS 소각이 실패한 경우 (`COIN_BURN_FAILED`)
- release가 아직 실행되지 않은 상태에서 환급이 시도된 경우 (`SETTLEMENT_RELEASE_NOT_ACTIVE`)
- 팀 리더가 아닌 회원이 환급 이력을 조회한 경우 (`COMMON_FORBIDDEN`)

## 정산 검증 `verify`

정산의 근거와 결과를 확인하고 직접 재계산할 수 있는 검증 페이지를 다룬다. **참여팀 소속 회원만 조회할 수 있으며 로그인이 필수다.** 이 도메인은 자체 엔티티를 두지 않고 `settlement`·`rule`·`coin`·`chain_job`의 데이터를 읽기 전용으로 조합해 제공한다. **관객 화면의 블록체인 용어 비노출 원칙에서 유일하게 제외되는 영역이다.** 준비금 증명(`V-02`)만 예외로 공개를 유지하며, 별도 엔드포인트로 비로그인 조회를 허용한다.

### 정산 검증 데이터 조회

1. 참여팀 소속 회원은 로그인한 뒤 공연 상세의 링크나 직접 주소로 정산 검증 페이지에 들어간다.
2. 시스템 처리
   - **요청자가 해당 공연의 참여팀 소속인지 확인한다(로그인 필수).** 개인정보는 어떤 항목도 포함하지 않는다.
   - 컨트랙트 주소, 잠긴 정산 규칙(두 비율 bp·규칙 해시), 팀별 동의 트랜잭션 해시, 판매 시작 잠금 트랜잭션 해시를 반환한다.
   - 온체인 팀별 선택 카운터, 유효 티켓 수, 총 매출, 팀별 산출액, release 트랜잭션 해시, 환급 완료 여부를 함께 반환한다.
   - 각 트랜잭션 해시에 익스플로러 링크를 붙인다.
   - 정산이 진행 중이면 현재 단계와 다음 단계 예정 시각을 표시한다.
3. 처리 결과
   - **성공**
     - 검증에 필요한 원본 값과 트랜잭션 링크가 모두 표시된다.
   - **실패**
     - 검증 데이터가 표시되지 않는다.
     - 실패 사유를 제공한다.

### 정산 재계산 검증

1. 참여팀 소속 회원은 검증 페이지의 재계산 위젯을 실행해 팀별 분배액을 직접 계산한다.
2. 시스템 처리
   - **요청자가 해당 공연의 참여팀 소속인지 확인한다(로그인 필수).**
   - 잠긴 규칙과 온체인 카운터를 입력으로 브라우저에서 §7의 공식을 그대로 실행한다. 서버가 계산한 값을 그대로 받아 쓰지 않는다.
   - 브라우저 계산 결과와 서버가 표시한 팀별 산출액을 비교해 일치 여부를 보여준다.
   - 온체인 분배액 합과 금융망 환급액 합의 대사 결과(불일치 건수)를 함께 표시한다.
   - 계산은 2초 안에 끝나야 한다.
3. 처리 결과
   - **성공**
     - 재계산 결과가 서버 표시값과 일치함이 화면에 드러나고, 불일치가 있으면 어느 항목인지 표시된다.
   - **실패**
     - 재계산이 수행되지 않는다.
     - 실패 사유를 제공한다.

### 준비금 증명 조회

1. 방문자는 준비금 증명 페이지에서 예치금과 발행량의 관계를 확인한다.
2. 시스템 처리
   - **이 화면만 예외로 인증을 요구하지 않는다.** 참여팀 확인 없이 조회할 수 있는 별도 엔드포인트로 제공한다.
   - 금융망 에스크로 계좌 잔액과 KRWS 총 유통량, 차액, 마지막 갱신 시각을 반환한다(1분 캐시).
   - 잔액이 유통량 이상이면 정상, 미만이면 불일치로 표시하고 mint·release가 중단되었음을 함께 알린다.
   - 잔액 조회값이 서버를 경유한다는 한계와, 모의 발행(테스트넷)이라는 사실을 화면에 고지한다.
3. 처리 결과
   - **성공**
     - 에스크로 잔액·유통량·차액·갱신 시각이 표시되고 1:1 성립 여부가 드러난다.
   - **실패**
     - 값이 표시되지 않고 마지막 성공 조회 시각이 안내된다.
     - 실패 사유를 제공한다.

### 실패 사유

- 공연을 찾을 수 없거나 아직 검증 대상이 아닌 경우 (`PERFORMANCE_NOT_FOUND`)
- 참여팀 소속이 아닌 회원이 정산 검증 데이터를 조회한 경우 (`COMMON_FORBIDDEN`)
- 로그인하지 않고 정산 검증 데이터를 조회한 경우 (`COMMON_UNAUTHORIZED`)
- 준비금 1:1이 깨진 것으로 확인된 경우 (`COIN_RESERVE_MISMATCH`)
- 금융망 잔액 조회가 실패한 경우 (`COMMON_EXTERNAL_SERVICE_ERROR`)
- 체인 노드 조회가 지연된 경우 (`CHAIN_TX_TIMEOUT`)
- 조회 요청이 허용 횟수를 초과한 경우 (`COMMON_TOO_MANY_REQUESTS`)
- 검증 데이터 조합 중 서버 오류가 발생한 경우 (`COMMON_INTERNAL_ERROR`)

## 관리자 `admin`

**MVP의 관리자 기능은 최소화한다.** 별도의 관리자 운영 화면을 두지 않고, 모든 상태 변경·온체인 작업의 **감사 로그 적재**와 정산 **이의제기 처리**(`settlement` 장 "이의제기 처리")만 남긴다. 실패한 발행·소각·분배·환급 작업은 관리자 수동 재처리 대신 시스템이 자동으로 재시도하고, 결정적 실패만 알림으로 알린다. 관리자 대시보드·회원/공연 관리·실패 작업 수동 재처리·운영지갑 감사 로그 조회 화면은 P1로 미룬다(§10).

### `audit_log`

주요 정보는 다음과 같다.

- 감사 로그 식별자
- 행위자 회원 식별자와 역할, 요청 IP
- 행위 유형(관리자 작업·팀 키 복호화·mint·burn·release·환급·상태 변경)
- 대상 리소스 종류와 식별자
- 요청 요약과 결과(성공·실패), 관련 트랜잭션 해시(`CHAR(66)`)
- 발생 일시. **기록은 append-only이며 수정·삭제하지 않는다.**

### 이의제기 처리

`settlement` 장 "이의제기 처리" 흐름과 같다. MVP에서 관리자가 직접 수행하는 유일한 기능이며, 처리 결과는 감사 로그에 남는다.

### 실패 사유

- 관리자가 아닌 회원이 이의제기 처리를 요청한 경우 (`COMMON_FORBIDDEN`)
- 인증 없이 관리자 기능을 요청한 경우 (`COMMON_UNAUTHORIZED`)
- 대상 이의·정산을 찾을 수 없는 경우 (`COMMON_NOT_FOUND`)
- 이미 처리된 이의를 다시 처리하려 한 경우 (`COMMON_CONFLICT`)
- 요청 처리 중 서버 오류가 발생한 경우 (`COMMON_INTERNAL_ERROR`)

## 7. 정산 공식과 시점 규칙

### 7.1 기호

| 기호 | 의미 |
|------|------|
| `R` | 총 매출 — 취소되지 않은 유효 티켓의 결제 금액 합계 (원 단위 정수) |
| `N` | 수락한 참여팀 수 |
| `bp_e` `bp_s` | 균등·관객 선택 비율 (bp, `bp_e + bp_s = 10000`) |
| `n_i` | 팀 `i`를 관람 목적으로 선택한 유효 티켓 수 (온체인 카운터 기준) |
| `T` | 선택 총합 = `Σ n_i` |

### 7.2 공식

```
전제:  bp_e + bp_s = 10000                (아니면 RULE_RATIO_SUM_INVALID)

1) 풀 산출     E = floor(R × bp_e / 10000)      균등 풀
               S = floor(R × bp_s / 10000)      관객 선택 풀
2) 팀별 산출   e_i = floor(E / N)
               s_i = (T > 0) ? floor(S × n_i / T) : floor(S / N)
3) 팀별 소계   base_i = e_i + s_i
4) 잔액(dust)  dust = R - Σ base_i
5) 최종 정산액 pay_i = base_i + (팀 i가 dust 귀속 대상이면 dust, 아니면 0)

검산:  Σ pay_i = R  (1원의 오차도 허용하지 않는다)
```

- **[권] 기본 비율**(P-5) — 균등 `5000` · 관객 선택 `5000`. 각 항목은 0도 허용한다.
- **[권] dust 귀속 규칙** — 나눗셈 버림에서 생기는 잔액은 **공연을 생성한 팀**에 귀속한다. 이 규칙은 컨트랙트에 명문화하고 검증 페이지에 표시한다. (CHAIN-04)
- **선택이 0건인 경우** — 어떤 팀도 선택되지 않았으면(`T = 0`) 관객 선택 풀을 참여팀에 균등 분배한다. 특정 팀만 0건인 경우는 그 팀의 `s_i`가 0이 될 뿐 예외 처리를 두지 않는다.
- **금액 단위** — 모든 계산은 원 단위 정수로만 수행한다. KRWS는 `decimals = 0`이고 1 KRWS = 1원이므로 온체인 분배액과 금융망 이체액의 단위가 어긋날 여지가 없다. (REL-02)
- **계산 위치** — 분배 산출은 컨트랙트 안에서 수행하고, 서버와 검증 페이지는 같은 공식을 그대로 재현한다. 세 값이 모두 일치해야 정산을 진행한다.

### 7.3 계산 예시

3팀 공동 공연, 티켓 100매 × 20,000원, 비율은 기본값(균등 5000 · 관객 선택 5000), 관객 선택은 A 50건·B 30건·C 20건인 경우다.

| 단계 | 값 |
|------|-----|
| 총 매출 `R` | 2,000,000원 |
| 균등 풀 `E` (5000bp) | 1,000,000원 → 팀당 `e_i` = 333,333원 |
| 관객 선택 풀 `S` (5000bp) | 1,000,000원 → `s_A` = 500,000 · `s_B` = 300,000 · `s_C` = 200,000원 |
| 소계 | A 833,333 · B 633,333 · C 533,333 = 1,999,999원 |
| dust | 1원 → 공연을 생성한 A 팀 귀속 |
| **최종** | **A 833,334 · B 633,333 · C 533,333 = 2,000,000원** |

### 7.4 시점 규칙 (P-9)

```
[판매 기간]                                        [정산 기간]

공연 D-7        D-3 00:00      공연 시작 -1h      공연 종료      종료 +α      잠금 +48h
  │                 │                 │                │              │             │
  ├─ 취소 전액 환불 ─┤                 │                │              │             │
  │                 ├─ 취소 50% 환불 ─┤                │              │             │
  │                 │   (D-3 직전까지) │                │              │             │
  │                 ├─ 환불 불가 · 예매는 판매 마감까지 가능 ─┤        │             │
  │                 │                 │                │              │             │
  │            ★취소 마감        ★판매 마감       ★공연 종료     ★집계 확정    ★release
  │            (ON_SALE 유지)     ON_SALE →         → ENDED       AGGREGATED     RELEASED
  │                             SALE_CLOSED                       → LOCKED      → REDEEMED
  │                                                               → DISPUTE_OPEN
  │                                                                     │
  │                                                                     ├─ 이의제기 48h ─┤
```

| 순서 | 시점 | 일어나는 일 | 상태 전이 |
|------|------|-------------|-----------|
| 1 | 공연일 D-7 00:00까지 | 관객 취소 시 **전액 환불** | Ticket `ISSUED` → `CANCELLED` |
| 2 | 공연일 D-3 00:00 직전까지 | 관객 취소 시 **50% 환불**(수수료 50%) | Ticket `ISSUED` → `CANCELLED` |
| 3 | 공연일 D-3 00:00 | **취소 마감.** 이후 앱에서의 취소·환불 불가. **예매는 계속 가능하다** | 상태 전이 없음(`ON_SALE` 유지) |
| 4 | 공연 시작 1시간 전 | **판매 마감.** 신규 예매 종료. 기존 티켓의 입장·양도는 그대로 가능 | Performance `ON_SALE` → `SALE_CLOSED` |
| 5 | 공연 종료 시각 | 공연 종료. 입장 처리 종료 | Performance `SALE_CLOSED` → `ENDED` |
| 6 | 공연 종료 후 | **집계 확정** — 공연 생성자 또는 관리자가 실행. 온체인 카운터와 서버 집계 대조가 통과해야 한다 | Settlement `NONE` → `AGGREGATED` |
| 7 | 집계 확정 후 | **정산 잠금** — 분배액 고정, 이의제기 48시간 시작 | Settlement `AGGREGATED` → `LOCKED` → `DISPUTE_OPEN` |
| 8 | 잠금 + 48시간 | 이의제기 마감. 미처리 이의가 없으면 **release 자동 실행**(수동 트리거 병행) | Settlement `DISPUTE_OPEN` → `RELEASED` |
| 9 | release 직후 | 팀별 **자동 환급** — 금융망 이체 성공 확인 → KRWS 소각 | Redemption `PENDING` → `TRANSFERRED`, Settlement `RELEASED` → `REDEEMED` |

- 순서를 건너뛴 요청은 서버와 컨트랙트 양쪽에서 거부한다(`SETTLEMENT_NOT_LOCKED`·`SETTLEMENT_DISPUTE_PERIOD`). (CHAIN-02)
- **release 이후의 환불은 온체인 회수가 불가능하다.** 정산이 잠긴 뒤의 취소 요청은 앱에서 차단하고(`REFUND_AFTER_SETTLEMENT_LOCK`) 오프체인 준비금 정책으로 분리한다.
- **공연 취소는 예외 경로다.** 판매 중이든 잠금 이후든 release 전까지는 취소할 수 있고, 이 경우 정산은 `HALTED`로 전이되어 집계·release가 영구히 차단되며 전 티켓이 수수료 없이 환불된다. (P-12)
- **이의제기는 release를 멈춘다.** 참여팀 리더가 48시간 안에 사유를 제출하면 자동 실행이 보류되고, 관리자가 모든 이의를 처리한 뒤에만 수동으로 재개한다. (P-16)

## 8. 비기능 요구사항

전체 항목과 목표값·검증 방법은 [비기능 요구사항 계획 v0 §4](./03_비기능_요구사항_명세서_v0_계획.md)에 있다. 여기서는 MVP 필수(★) 30개를 분류별로 요약한다. 모든 목표값은 현재 **[권]** 이며 8/31 팀 검토에서 확정한다.

**성능** — 판매 오픈 시 동시 100건 예매 요청에서 초과 판매가 0이어야 하고 밀린 요청은 `409 TICKET_SOLD_OUT`으로 정상 응답한다(PERF-02). QR 검표는 스캔에서 판정 표시까지 p95 1초 이내, 스캐너 1대가 분당 30건 이상을 처리해 100명 입장을 5분 안에 끝낸다(PERF-03). 예매 확정 응답은 온체인 트랜잭션 확정을 기다리지 않고, 온체인 반영은 60초 이내에 이뤄진다(PERF-04).

**보안** — 역할 기반 인가를 적용해 공연자는 자기 팀 공연만, 검표 페이지 링크는 서명 토큰으로 해당 공연에만 유효하며 모든 쓰기 API에 소유권 검사를 둔다(SEC-03). 팀 지갑 개인키는 envelope encryption(AES-256-GCM DEK + 외부 주입 KEK)으로 보관하고 DB·코드·로그에 평문 키가 0건이어야 하며, 복호화할 때마다 누가·언제·어떤 트랜잭션인지 감사 로그를 남긴다(SEC-04). minter/burner 키와 operator 키를 분리해 키 하나가 유출돼도 무한 발행이 불가능하게 한다(SEC-05). QR은 유효기간 30~60초의 서명 토큰이고 Redis 원타임 처리로 재사용 시도를 100% 차단하며 고정 티켓번호 QR을 만들지 않는다(SEC-06). 양도 링크는 서명된 일회용 토큰으로 24시간 후 만료되고 수락 즉시 무효화되며 기존 QR 시드를 폐기한다(SEC-07). **망분리를 적용해** API 서버는 DMZ(퍼블릭 서브넷)에, 금융망 연동·팀 키 복호화·mint/burn 처리와 DB는 내부 서브넷에 두고 인터넷에서 내부 서브넷으로의 인바운드를 전부 차단한다(SEC-14). 내부 서브넷의 아웃바운드는 NAT 게이트웨이를 거쳐 금융망 API·체인 RPC 등 허용 목록(whitelist)의 목적지로만 나간다(SEC-15). 팀 키를 감싸는 KEK는 내부 서브넷에서만 주입·사용하고 DMZ 인스턴스에는 어떤 형태로도 두지 않는다(SEC-16).

**개인정보** — 온체인에는 티켓 ID·팀 ID·지갑 주소·금액·규칙 해시만 올리고 개인정보는 0건이다(PRIV-01).

**데이터 정합성·신뢰성** — 재고 차감을 원자적으로 처리해 초과 판매를 0으로 유지한다(REL-01). 온체인 분배액 합과 금융망 이체액 합이 일치해야 하고, `decimals = 0`으로 단위 불일치를 원천 제거하며 대사 불일치는 0건이어야 한다(REL-02). 에스크로 계좌 잔액 ≥ KRWS 유통량이 상시 성립해야 하고 조회 주기는 1분 이내이며 불일치 시 발행을 중단하고 알린다(REL-03). 결제·발행·소각·이체 요청에 멱등키를 붙여 재시도가 중복 실행으로 이어지지 않게 한다(REL-04). 정산은 산출 → 이체 요청 → 완료/실패 → 보상의 상태 머신으로 관리하고 부분 실패는 건별 재시도가 가능해야 한다(REL-05). 온체인 선택 카운터와 DB 집계가 취소 롤백까지 포함해 일치해야 하며 불일치하면 정산 잠금을 차단한다(REL-06). 동일 티켓의 2회 입장은 0건이어야 한다(REL-07).

**가용성·복구** — **Kaia Kairos(chainId 1001)** 를 주 노드로 쓰고, 시연 백업은 **로컬 Hardhat 노드**로 대체한다(AVAIL-01). Kairos는 **1초 즉시 확정**이라 온체인 반영 대기가 짧고, 익스플로러 링크는 `kairos.kaiascan.io`를 사용한다. 가스는 **Kairos faucet(50 KAIA/일, 무요건)** 으로 확보하고, **baseFee 25 gkei** 기준으로 web3j의 `eth_gasPrice` 반환값을 그대로 사용한다. 운영지갑과 팀 지갑의 가스가 임계치(release 10회분) 아래로 떨어지면 알리고 자동 충전하며, 시연 1주 전에 잔액을 확보한다(AVAIL-06).

**스마트 컨트랙트 품질** — 잠금 이후에는 소유자와 operator를 포함해 모든 규칙 setter가 revert된다(CHAIN-01). 취소 마감 ≤ 집계 확정 ≤ 정산 잠금 ≤ 이의제기 48시간 ≤ release의 순서를 컨트랙트가 강제하고 위반 요청은 revert된다(CHAIN-02). 분배는 재진입 방지를 적용한 `release()`로 수행하고 팀 수와 무관한 가스 상한을 지킨다(CHAIN-03). 10000bp 가중치로 계산하고 dust 귀속 규칙을 명문화해 총 분배액과 예치액의 차이가 0원이어야 한다(CHAIN-04). 운영지갑에서 동시 100건을 제출해도 nonce 충돌·드롭이 0건이어야 한다(CHAIN-05). 금융망 입금 확인 없는 발행은 0건이고 minter 권한은 단일하게 유지한다(CHAIN-08).

**투명성·감사가능성** — 정산 검증 페이지는 참여팀 소속 회원만 접근할 수 있고, 브라우저 재계산 값이 서버 표시값과 불일치하는 경우가 0이어야 한다(AUDIT-01). 준비금 증명(`V-02`)은 예외로 로그인 없이 접근할 수 있다. 분배·환급 이벤트와 금융망 이체를 대사해 공연별 불일치 건수를 표시하고 목표는 0건이다(AUDIT-03).

**사용성·호환성** — 관객 화면(검증 페이지 제외)에 지갑·가스·주소·트랜잭션 용어 노출이 0이어야 한다(UX-01). 주요 모바일 브라우저와 인앱 브라우저에서 양도 수락 링크가 정상 동작해야 한다(UX-07).

**유지보수성·배포** — `exec/`에 빌드·배포·환경변수·컨트랙트 배포 절차를 담은 포팅 매뉴얼을 W5에 작성한다(MAINT-08). **망분리 MVP 구현 수준** — EC2 2대(퍼블릭 서브넷 1 · 프라이빗 서브넷 1) + 보안그룹으로 실제 분리를 구성한다. 시간이 부족하면 EC2 1대 안에서 논리 분리(별도 프로세스·방화벽 규칙)로 낮추고 구성도로 대체 설명한다.

**제약사항** — 실가상자산을 사용하지 않는다. 테스트넷 모의 KRWS만 쓰고 실자산 전환 경로를 두지 않는다(CON-01).

## 11. 최종 서비스 방향

이 서비스는 티켓팅 플랫폼을 하나 더 만드는 것이 목적이 아니다. 예매·입장은 이미 여러 서비스가 하고 있고 소규모 공연에서도 구글폼과 수기 명단으로 어떻게든 돌아간다. 해결되지 않은 채 남아 있는 것은 **공연이 끝난 뒤 돈을 어떻게 나눌지에 대한 합의와 그 합의의 증명**이다. 3~4팀이 함께 무대를 채우고도 "누구 덕에 팔린 티켓인지" 아무도 증명하지 못하고, 규칙이 사후에 바뀌어도 반박할 근거가 없다. 우리는 이 한 지점에 블록체인을 쓴다.

그래서 설계의 무게중심은 정산 하나에 있다. 판매를 시작하기 전에 참여팀 전원이 각자의 팀 지갑으로 같은 규칙 해시에 동의하고, 그 순간 규칙은 잠겨 플랫폼조차 바꿀 수 없게 된다. 관객의 "보러 온 팀" 선택은 서버가 집계해서 나중에 제출하는 값이 아니라 예매 시점에 체인에 남는 이벤트다. 공연이 끝나면 잠긴 규칙과 체인 카운터만으로 분배액이 결정되고, 관객이 낸 돈만큼 발행된 원화 스테이블코인이 팀 지갑으로 실제로 이동한 뒤 원화가 되어 팀 통장에 들어간다. 이 전 과정을 참여팀이 직접 재계산할 수 있다.

동시에 우리는 이 구조가 무엇을 보장하지 않는지도 문서와 발표에 같은 비중으로 적는다. 팀 지갑의 키는 플랫폼이 보관하므로 탈중앙을 주장하지 않고, 입력 데이터의 진실성은 기술이 보장할 수 없으므로 "위조를 막는다"가 아니라 "위조하면 발각된다"고 말한다. QR 입장의 안전성은 서버 서명 QR이 만들어내는 것이지 블록체인의 성과가 아니다. KRWS는 테스트넷 모의 발행이고 원화의 이동은 교육용 금융망 API로만 이뤄진다. 대신 준비금 1:1 증명·상환청구권에 해당하는 환급·공시에 해당하는 검증 페이지를 설계에 넣어, 입법이 추진 중인 원화 스테이블코인 규제의 핵심 요건을 미리 반영한 형태로 보인다.

5주라는 기간에서 이 방향을 지키는 방법은 범위를 줄이는 것이다. MVP 12개는 전부 "공동 공연을 만들고 → 규칙을 잠그고 → 관객이 선택하며 예매하고 → 입장하고 → 분배되고 → 검증되는" 하나의 경로 위에 있다. NFT 티켓·유료 재판매·NFC·애플 월렛·AI는 그 경로 밖에 있으므로 확장 범위로 남긴다. 완성도의 기준도 같다. 화면이 몇 개인지가 아니라, 심사위원이 검증 페이지에서 직접 계산한 값이 우리가 화면에 표시한 값과 1원도 다르지 않은지가 이 프로젝트의 성패다.

## 12. 신설 제안

작성 계획 §1.9와 API 공통 응답 규격 v3 §2("문서에 없는 코드는 배포하지 않는다")에 따라, 본문에서는 아래 코드를 사용하지 않고 대체 코드로 응답하도록 썼다. 규격 v3 개정 시 검토 대상이다.

| 제안 코드 | HTTP | 발생 조건 | 현재 대체 | 관련 도메인 |
|-----------|------|-----------|-----------|-------------|
| `PAYMENT_ACCOUNT_HOLDER_MISMATCH` | 400 | 금융망 계좌 예금주명 불일치 — 관객 계좌 연결·팀 정산 계좌 공통 | `COMMON_VALIDATION_FAILED` | `member` `team` |
| `TICKET_ORDER_EXPIRED` | 409 | 결제 만료(15분)로 자동 취소된 주문에 결제를 시도한 경우. 재고가 이미 원복되어 있어 `PAYMENT_*`와 구분이 필요하다 | `COMMON_CONFLICT` | `ticket` `payment` |
| `SETTLEMENT_DISPUTE_CLOSED` | 409 | 이의제기 마감(잠금 + 48시간) 이후 이의를 제출한 경우 | `COMMON_CONFLICT` | `settlement` |
| `SETTLEMENT_DISPUTE_ALREADY_OPEN` | 409 | 같은 팀이 처리되지 않은 이의를 중복 제출한 경우 | `COMMON_CONFLICT` | `settlement` |
| `SETTLEMENT_HALTED` | 409 | 공연 취소로 정산이 `HALTED`인 상태에서 집계 확정·잠금·release를 시도한 경우 | `PERFORMANCE_INVALID_STATUS` | `settlement` |

### 규격 v3 문구 수정 제안

- `TICKET_PURCHASE_LIMIT_EXCEEDED`의 예시 `msg`가 "1인당 최대 **2장**까지 구매할 수 있습니다."로 되어 있다. 정책 전제 P-6은 **1인 1공연 최대 4매**이므로 예시 문구를 "1인당 최대 4장까지"로 맞춰야 한다.
- `REDEEM_ALREADY_REQUESTED`의 설명이 팀의 수동 출금 요청을 전제로 한다. 정책 전제 P-10에서 환급은 release 직후 자동 push로 바뀌었으므로, 발생 조건을 "자동 환급 작업이 이미 접수된 건에 재시도가 중복 요청된 경우"로 고쳐야 한다.
- `WALLET_GAS_INSUFFICIENT`의 설명이 "가스 충전 절차는 미결 안건"이라고 적고 있다. 정책 전제 P-3에서 운영지갑 자동 충전으로 확정했으므로, 이 코드는 자동 충전까지 실패한 경우에만 노출되는 것으로 조건을 좁혀야 한다.

### 그 밖의 확인 필요 사항

- **화면 ID `P-10 공연 취소`가 모달**이라 독립 라우트가 없다. 화면설계에서 `P-03`·`P-08`의 하위 컴포넌트로 기술할지 별도 화면으로 둘지 확인이 필요하다.
- **`verify` 도메인은 자체 엔티티가 없다.** ERD 작성 시 이 도메인은 읽기 전용 조합으로만 존재한다는 점을 명시해야 한다.
- **`chain_job`과 `coin_job`의 분리 기준.** 현재는 발행·소각만 `coin_job`, 나머지 온체인 트랜잭션은 `chain_job`으로 두었다. 하나로 합칠지는 ERD 단계에서 결정한다.
