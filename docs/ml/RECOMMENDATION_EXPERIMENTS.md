# 추천 실험 기록

설계 문서(`docs/superpowers/specs/2026-09-22-recommendation-design.md`) §10 평가 규칙을 따른다. 실험은 번호 E-xx로 누적하고 삭제하지 않는다. 각 실험은 날짜, 목적, 환경(기기·CPU/GPU·라이브러리 버전), 데이터(출처·행 수·분할), 명령(재현 가능한 한 줄), 설정, MLflow run ID(정량 실험만), 결과 표, 해석, 한계, 다음 실험을 적는다. 합성 데이터 실험은 "파이프라인 검증"으로 표시하고 성능 근거로 인용하지 않는다.

## E-01 LightGBM vs XGBoost 클릭 예측기 (2026-09-22, 완료, 합성·파이프라인 검증)

- 목적: 3차 CTR 랭커 라이브러리 선택 — LightGBM과 XGBoost 중 서빙 경로에 맞는 쪽을 고른다.
- 환경: 개발 데스크톱 i5-13600KF 20스레드, GPU 없음, Python 3.13 venv, lightgbm 4.7.0, xgboost 3.4.1, scikit-learn 1.9.1.
- MLflow: 실험 `ctr-ranker`, 2026-09-22 재실행 run — logistic `407f5f5e2bf441daa5137cd66e8ff8d6`, LightGBM `07a0b9a914894f28b3f810be322bab5d`, XGBoost `db5b73c13eae422eaa0ddab9aaea0798`(36k행, 로컬 `ml/ctr/mlruns/`). 모델 파일은 run 아티팩트 `model_LightGBM.txt`·`model_XGBoost.txt`.
- 데이터: `ml/ctr/synth.py` seed 42. 3,000명/36k행(CTR 0.073)과 50,000명/600k행(CTR 0.067). 분할은 회원 단위 80/20(GroupShuffleSplit).
- 명령: `python compare.py 3000` / `python compare.py 50000`
- 설정: 학습률 0.05, 조기 종료 100라운드. LightGBM num_leaves=31·min_child_samples=50. XGBoost max_depth=6·min_child_weight=5·hist·enable_categorical.

결과:

| 행 수 | 모델 | AUC | NDCG@6 | 학습(s) | 트리 | 모델(KB) |
|---|---|---|---|---|---|---|
| 36k | 규칙(겹침·임박) | 0.681 | 0.696 | 0 | 0 | 0 |
| 36k | 로지스틱 | 0.739 | 0.716 | 0.3 | 0 | 1 |
| 36k | LightGBM | 0.736 | 0.724 | 0.15 | 53 | 181 |
| 36k | XGBoost | 0.739 | 0.731 | 0.56 | 56 | 529 |
| 600k | 로지스틱 | 0.728 | 0.719 | 1.1 | 0 | 1 |
| 600k | LightGBM | 0.734 | 0.725 | 1.3 | 166 | 568 |
| 600k | XGBoost | 0.733 | 0.723 | 5.2 | 138 | 1052 |

피처 중요도(36k, gain 비율, LGBM/XGB): genre_overlap 0.40/0.49, days_until 0.12/0.04, position 0.12/0.07, sold_ratio 0.11/0.03, min_price 0.08/0.03, basis 0.01/0.10.

- 해석: 두 GBDT는 품질이 같다(크기별로 순위가 뒤집힘). 둘 다 규칙(NDCG 0.696)과 로지스틱을 이긴다. 학습 속도는 LightGBM이 4배 빠르고 모델 크기는 절반이지만, 결정 요인은 서빙 경로다 — XGBoost는 xgboost4j로 Spring 프로세스에 인프로세스 로드가 가능하다.
- 한계: 생성기(`synth.py`)가 정답 규칙을 알고 있어 AUC·NDCG 수치 자체는 모델 품질 근거가 아니다. 규칙을 되찾는 것이 당연하다.
- 다음: 실데이터(`recommendation_log`) 1만 행 확보 후 E-06으로 재실행.

## E-02 LLM 태깅 품질·속도 (2026-09-22, 완료)

- 목적: Qwen3 4B Q4_K_M vs EXAONE 3.5 2.4B, 노트북(RTX 4050) 기준 태깅 모델 선정.
- 환경: RTX 4050 Laptop 6GB(드라이버 591.74), WSL2 Ubuntu 24.04, Ollama 0.34.2, `ml/server` 커밋 `98203b1`~`febc75c`. 세 모델 상주 상태(VRAM 5.3GB).
- 데이터: `ml/server/samples.py` 공연 소개 10건(기대 장르 수기). 명령 `.venv/bin/python bench_e02.py`.
- 설정: `num_ctx=2048`, `num_predict=200`, `temperature=0`, `think:false`, JSON 스키마 강제(genres enum 10종).
- MLflow run ID(실험 `llm-tagging`, 노트북 `ml/server/mlflow.db`): qwen3:4b `5f282ab0faf24d28971db15da6214a85`, exaone3.5:2.4b `184395d5142040cb8df1870ef3c8e607`. 같은 벤치를 3회 돌려 run 6개가 있으며 수치는 아래 첫 회 기준.

| 모델 | 정답 장르 포함 | 엉뚱한 장르 수(10건 합) | JSON 유효율 | 건당 시간(평균/최대) | VRAM | 콜드 첫 응답 | 웜 |
|---|---|---|---|---|---|---|---|
| Qwen3 4B Q4_K_M | 9/10 | 약 6 | 10/10 | 2.0s / 3.5s (3회 평균 1.6~2.0s) | 5.3GB(3모델) | 2.4~2.6s | 1.9~2.5s |
| EXAONE 3.5 2.4B | 9/10 | 약 19 | 10/10 | 1.0s / 1.2s | 5.3GB(3모델) | 미측정 | 0.9~1.2s |

- 해석: 둘 다 "장르 무관 오픈마이크"를 ETC로 못 잡는다(같은 약점). 차이는 정밀도다. EXAONE은 거의 항상 3개를 채우며 재즈에 CLASSICAL·INDIE, 테크노에 CLASSICAL을 붙였다. 장르 교집합 매칭에서는 잘못 붙은 장르가 곧 잘못된 추천이므로 Qwen3 4B를 택한다(D-R17). Qwen은 2배 느리지만 오프라인 경로라 예산(2~3초) 안이다.
- Qwen 약점: 인디록 공연에 RNB, 하우스 셋에 HIPHOP을 붙인 2건은 프롬프트를 "확실한 것만 1~2개"로 바꿔도 그대로였다(온도 0). 4B 한계로 기록. `RNB, RNB` 중복은 서버에서 제거.
- 한계: 10건·수기 정답. 태그 유용성(mood·keywords)은 수치화하지 않았고 눈으로는 둘 다 쓸 만하다.
- 다음: 실제 공연 등록 데이터로 태그 오류율 재확인(E-05와 함께).

상태: 완료

## E-03 임베딩 지연·품질 (2026-09-22, 완료 — 설계 §7.2 개정 근거)

- 목적: bge-m3 임베딩의 지연과 장르 구분력 확인.
- 환경: E-02와 같음. 호출은 데스크톱에서 Tailscale 경유 `POST /embed`(FastAPI → Ollama). 데이터: `samples.py` 10건, 같은 장르 쌍 3·다른 장르 쌍 42.
- MLflow run ID: 없음(코사인 계산은 일회성 스크립트, 결과는 이 표가 정본).

| 항목 | 결과 |
|---|---|
| 단건 지연(웜) | 115~142ms (5회: 1479, 128, 115, 124, 125) |
| 배치 32건 지연 | 594ms (건당 19ms), 10건 398ms |
| 유휴·재시작 후 첫 호출 | 1.4~3.8s (모델 재적재. 3모델 상주 시 evict가 원인, EXAONE 내린 뒤 1.4s) |
| 같은 장르 평균 코사인 | 0.506 (문서 = 제목+소개+팀+장르+태그) |
| 다른 장르 평균 코사인 | 0.525 |
| 최근접 이웃이 같은 장르 | 0/10 |

문서 구성별 구분력:

| 문서 구성 | 같은 장르 | 다른 장르 | 차이 | NN 적중 |
|---|---|---|---|---|
| 소개만 | 0.494 | 0.514 | -0.020 | 0/10 |
| + 팀 장르 | 0.516 | 0.514 | +0.002 | 0/10 |
| + 장르 + LLM 태그 | 0.506 | 0.525 | -0.019 | 0/10 |
| + 한국어 장르 + 태그 | 0.505 | 0.529 | -0.024 | 0/10 |
| 장르 문장만 | 0.853 | 0.721 | +0.132 | 4/10 |

- 해석: 지연은 예산(30~50ms/건) 대비 단건은 3배 느리지만 배치면 건당 19ms로 충분하다. 품질은 실패다. 제목·장소·시간 같은 내용이 벡터를 지배해 장르 신호가 묻히고, 장르 문장만 넣어야 구분되는데 그건 SQL 장르 매칭을 비싸게 흉내 내는 것이다. 따라서 코사인 상위 K로 홈 추천을 만드는 원안(§7.2)을 폐기하고, 2차는 LLM 태깅으로 1차 매칭을 보강하는 것으로 바꾼다(D-R16). 임베딩은 "비슷한 공연"(분위기·성격 유사) 용도로만 남긴다. 예: 부산 웨이브 페스티벌 ↔ 네온 R&B 나이트 0.590.
- 한계: 표본 10건, 같은 장르 쌍 3개뿐이라 미세 차이는 신뢰할 수 없다. 차이가 0 근처라는 결론만 취한다.
- 다음: "비슷한 공연" 섹션을 만들 때 실제 공연 20건 이상으로 재측정.

상태: 완료
