# 02. 결함과 수정 — 무엇이 잘못됐고 어떻게 고쳤나

이 문서가 가장 중요하다. 발견한 결함을 숨기지 않고, 고친 방법의 근거와 **남은 한계**를 명시한다.
"완성"·"완벽히"·"모두 해결" 같은 표현은 쓰지 않는다 — 실제로 남은 한계가 있으면 그대로 적는다.

구조: **문제 → 원인 → 검토한 대안 → 선택 → 근거 → 남은 한계**. 판단만 필요하고 대안 비교가 없던 경미한
항목은 표로 압축했다.

## 1. 경계면 QA 1·2차에서 나온 `수정` 판정 10건

QA 1차(`_workspace/qa_be-0층_2026-09-08.md`)가 액션 리스트 10건을 냈고, 전부 반영한 뒤 QA 2차
(`_workspace/qa_be-0층-재검증_2026-09-08.md`)가 9건 `해결`·1건(#6)은 "합의 대기"로 유지, 대신 새 불일치
1건(프록시 헤더, §2에서 별도 다룸)을 추가로 잡았다. 아래는 그중 핵심 4건을 상세히, 나머지 6건은 표로 정리한다.

### 1-1. 타인 주문 조회 — 403 → 404

**문제** 남의 주문 상세(`GET /orders/{orderId}`)를 조회하면 `OrderService`가 403 `COMMON_FORBIDDEN`을
던졌다. `payment` 3개 API(`requireOwnedOrder`)는 같은 상황에 404 `COMMON_NOT_FOUND`를 던지고 있어
**같은 자원에 대해 API마다 다른 코드**가 나갔다.

**원인** `OrderService.orderDetail`이 소유자 확인을 "존재 확인" 뒤에 별도 분기로 뒀고, 그 분기가 403을
반환하도록 처음부터 짜여 있었다. `payment` 쪽 코드를 작성할 때는 명세를 다시 확인했지만 `ticket` 쪽은
확인하지 않은 채였다.

**검토한 대안** 없음 — 명세(API-ticket-03 "타인 주문은 `COMMON_NOT_FOUND`로 존재를 숨긴다")와 4xx 표에
404만 있어 선택지가 하나였다.

**선택** 403 `COMMON_FORBIDDEN` → 404 `COMMON_NOT_FOUND`(`ticket/service/OrderService.java:284`).

**근거** 403은 "이 자원은 있지만 권한이 없다"는 뜻이라 존재를 알려주는 부작용이 있다. 명세가 주문 번호의
존재 자체를 숨기라고 명시했다.

**남은 한계** 없음. QA 2차가 `hidesForeignOrder` 테스트로 재확인했다.

### 1-2. 남의 서명 트랜잭션(RLP) 재보고 — 보안 구멍

**문제** 같은 공연에서 다른 관객 B가 관객 A의 `PURCHASE` 서명 RLP를 자기 주문 번호로 재보고하면, 멱등
판정이 `txType`·공연·팀만 비교해 **A의 `jobId`를 재생**해 버렸다. B의 결제는 상태가 안 바뀌어 실질적
피해는 없었지만, 409여야 할 요청이 202로 성공하고 타인의 내부 식별자(`jobId`)가 노출됐다.

**원인** `UserSignedTxService`의 재보고 판정(`sameTarget`)이 "같은 대상(공연·팀·tx종류)에 대한 요청인가"만
봤다. "누가 보고했는가"(요청자·지갑)와 "어느 결제/주문에 대한 것인가"를 비교 키에 넣지 않았다.

**검토한 대안** ① 멱등키 자체에 요청자·주문을 섞어 넣기 — `chain_job.idempotency_key`가 이미
`"usertx:" + keccak256(rlp)` 형태라 키 구조를 바꾸면 기존 job과의 호환이 깨진다. ② 호출부(도메인 서비스)가
"이 재생이 나와 관련 있는가"를 되묻게 하기.

**선택** ②. `Expectation`에 `walletId`·`requester.memberId`를 추가하고, 보증금/동의처럼 대상이 이미
(공연·팀·지갑)으로 완전히 정해지는 곳은 이 5개 키로 충분하다고 보고, 결제처럼 주문 단위 구분이 필요한
곳은 `ReplayGuard`라는 훅을 얹어 `PaymentService`가 "재보고라면 이 결제의 approve/purchase job이어야
한다"를 답하게 했다. 기존 9인자 생성자를 보조 생성자로 남겨 보증금(`PerformanceService`)·동의
(`RuleService`) 호출부는 변경 없이 그대로 컴파일된다.

**근거** `chain_job`에는 `target_order_id`가 없고 링크가 반대 방향(`payment.approve_chain_job_id`)이라,
스키마를 늘리지 않고 재보고 판정에 결제 단위 구분을 넣으려면 호출부가 되묻는 구조가 유일했다.

**남은 한계** 같은 회원이 결제용 APPROVE RLP를 보증금 API의 `kind=APPROVE`로 잘못 보고하는 경로는 5키가
동일해 재생이 통과한다(`qa_be-0층-재검증_2026-09-08.md` §1-1 표 마지막 행). 다만 본인의 RLP이고 상태
전이가 없어(deposit은 APPROVE job을 링크하지 않는다) 실해는 없다 — 기록만 남겼다.

### 1-3. revert 사유가 전부 하나의 코드로 뭉개짐

**문제** `TxReceipt`에 revert 사유를 담을 필드가 없어, 체인 워커가 실패한 트랜잭션의 receipt를
`confirm()`에 넣으면 사유가 무엇이든 `PAYMENT_AMOUNT_MISMATCH`로 고정됐다. 계약 문서 §4.6은
`SaleNotStarted→TICKET_SALE_NOT_STARTED`처럼 revert 사유별 매핑표를 정해 뒀는데 그 정보가 전달될 통로가
없었다.

**원인** `TxReceipt` record가 성공/실패(boolean)만 나르고 실패 이유를 나르는 필드가 처음부터 없었다.

**검토한 대안** ① `TxReceipt`에 필드를 더하지 않고 `markFailed(jobId, ErrorCode)`만으로 워커가 직접
분기하게 한다. ② `TxReceipt`에 `failureCode`를 더해 `confirm()` 경로로도 사유를 넘길 수 있게 한다.

**선택** 둘 다. 계약(Javadoc)으로 "revert 번역은 워커의 책임"이라고 명시하는 것을 본체로 하되, 필드도
함께 추가했다 — `TxReceipt.failureCode`(규격 §3 `ErrorCode` 이름 문자열, revert 원문은 절대 담지 않는다,
SEC-09). 기존 6인자 생성자를 보조 생성자로 남겨 `failureCode=null`이 되게 했다.

**근거** "필드를 안 채워도 이전과 동작이 같아야 한다"는 조건을 지키면서, 이강륜(체인 모듈 담당)과의 합의가
늦어져도 빌드·동작이 막히지 않도록 했다. `GrantRefUsed`(§4.6 "실패 처리 금지, MINT job을 CONFIRMED로
동기화")를 위한 `syncGrantAlreadyUsed(chainJobId, txHash)` 진입점도 함께 열었다.

**남은 한계** develop 병합 이후에도 **워커가 이 자리를 아직 부르지 않는다**(§4, `03_남은_과제.md` 참조).
`TICKET_SOLD_OUT`·`TICKET_SALE_CLOSED`는 대응하는 컨트랙트 custom error가 없어 revert 매핑으로는 애초에
나올 수 없다는 사실이 develop 병합 후 확인됐다(`03_남은_과제.md` 참조).

### 1-4. rate limit 부재

**문제** §0.9가 로그인 IP 60회/분·지갑 챌린지 회원당 10회/분 등 호출 한도를 숫자로 정하고 5개 절의 4xx
표에 429가 실려 있는데, -46(member·wallet·team) 카드는 "§0.12에 해당 Redis 키가 없어 임의로 만들지
않았다"며 미구현으로 남겼다.

**원인** "규격에 없는 저장소 키를 만들지 않는다"는 원칙을 rate limit 카운터에도 그대로 적용했다. 그러나
QA는 이 판단이 -47(재고·주문 멱등키)의 판단과 모순된다고 지적했다 — -47은 "본문이 동작을 명시적으로
요구하면(초과 판매 금지) 키가 없어도 만든다"고 결정했었다.

**검토한 대안** 없음 — QA가 지적한 기준(본문이 숫자로 한도를 정했는가)을 그대로 받아들였다.

**선택** `common/support/RateLimiter`(고정 창, Redis `INCR`)를 신설해 로그인 IP·지갑 챌린지 회원당·예매
매크로·QR 재발급·검표(엔트리 카드가 이미 사용 중)에 적용했다. `Retry-After` 헤더를 429 응답에 붙였다.

**근거** §0.12는 "테이블 없이 Redis에만 두는 상태를 모아 둔" 문서이므로, 본문이 숫자로 한도를 요구하는데
표에 키가 없는 것은 §0.12 쪽의 결손이지 구현을 보류할 사유가 아니다.

**남은 한계** `API-performance-02`(공연 목록 조회) 429는 **의도적으로 구현하지 않았다** — 이 엔드포인트는
비회원이 쓰는 공개 목록이고 §0.9가 숫자·주체(IP인지 회원인지)를 정하지 않았다. IP 60회/분으로 잡으면
공연장 NAT·시연장 공용 와이파이에서 정상 관람객이 통째로 막힐 위험이 있어 숫자·주체가 정해질 때까지
보류했다.

## 2. 저장 시각 타임존 결함 — EC2(UTC)에서 9시간 어긋남

**문제** entry 카드 작업 중 `Ticket.markUsed`가 `LocalDateTime.now()`(JVM 기본 시각대)로 `entered_at`을
찍고 있는 것을 발견했다. 개발 노트북(KST)에서는 문제가 안 보이지만, 배포 대상 EC2가 UTC로 뜨면 저장값이
9시간 어긋나고, 응답 조립(`TimeSupport.toOffset`)이 저장값을 KST로 해석하므로 **응답 시각 자체가
9시간 틀리게 나간다.**

**원인** `TimeSupport.toOffset`은 "저장값은 KST 벽시계"라는 전제로 동작하는데, 그 전제를 지키는 것은
개발자의 습관(`LocalDateTime.now()`를 안 쓰는 것)에만 의존했고 강제하는 장치가 없었다. entry 카드에서
`Ticket.markUsed` 1곳을 고친 뒤 전체를 grep해 보니 **27곳, 19개 파일**에 같은 패턴이 남아 있었다. 성격이
둘로 갈렸다 — 저장(DB에 넣는 값 9시간 이르게 찍힘)과 판정(만료·마감 시각 비교가 9시간 어긋나 결제 15분이
실제로는 9시간 일찍/늦게 만료).

**검토한 대안** ① 각 호출부를 `LocalDateTime.now(TimeSupport.STORAGE_ZONE)`으로 개별 치환만 하고 끝낸다.
② 공용 헬퍼(`TimeSupport.nowStored()`)를 만들어 전수 치환하고, 회귀를 막는 정적 검사 테스트를 추가한다.
③ JVM 기본 시각대 자체를 기동 시점에 `Asia/Seoul`로 고정해 `@CreationTimestamp`·JPA Auditing 경로(19개
테이블의 `created_at`/`updated_at`, Hibernate가 JVM 기본 시각대로 생성)까지 함께 바로잡는다.

**선택** ②+③ 모두. `TimeSupport.nowStored()`를 저장·비교용 "지금"의 단일 출처로 만들어 27곳을 전수
치환했고, `common/config/StorageTimeZoneInitializer`(`EnvironmentPostProcessor`, `Ordered.HIGHEST_PRECEDENCE`)로
컨텍스트가 만들어지기 전에 JVM 기본 시각대를 `Asia/Seoul`로 못 박았다. `noZonelessNowInMainSources`
테스트로 인자 없는 `now()`가 다시 들어오면 빌드가 실패하도록 회귀 방지도 걸었다.

**근거** `@CreationTimestamp`·JPA Auditing은 Hibernate가 세션 생성 시점에 `Clock.systemDefaultZone()`을
붙잡기 때문에 `@PostConstruct`로는 이미 늦다 — `EnvironmentPostProcessor`(빈이 하나도 만들어지기 전에
실행)가 아니면 저장 경로 전체(19개 테이블)를 못 잡는다. 애플리케이션이 배포 설정(컨테이너 `TZ` 환경변수)
없이도 스스로 시각대를 고정하게 만든 것은, 배포 설정 한 줄이 빠지면 조용히 틀리는 값으로 남기지 않기
위해서다.

**남은 한계** QA 2차가 "Hibernate 6.6에서 `hibernate.jdbc.time_zone`이 zoneless `LocalDateTime`에 붙지
않는다"는 be 보고서의 주장을 검토해 **정확하지 않다**고 지적했다 — 실제로는 `Timestamp.valueOf(...)`가
JVM 기본존으로 순간을 확정한 뒤 `jdbc.time_zone`으로 재해석하므로, JVM=UTC·`jdbc.time_zone`=Seoul이면
오히려 어긋난다. 다만 이번 수정으로 JVM 기본존 자체를 Seoul로 고정했기 때문에 (JVM = `jdbc.time_zone`
= MySQL 컨테이너 TZ) 셋이 일치해 결과적으로는 정합하다. **UTC JVM + 실제 MySQL 왕복을 끝까지 돌려
확정한 적은 없다**(정적 분석 + 순수 계산 테스트까지만 했다) — CI에서 `-Duser.timezone=UTC`로 통합 테스트를
1회 도는 것이 남은 확인 항목이다.

## 3. 프록시 헤더 신뢰 경계 — XFF 하나만 고쳐선 안 막힘

**문제** QA 2차가 "로그인 IP 60회/분 한도가 요청마다 다른 `X-Forwarded-For`를 보내면 우회된다"고 지적했다
(nginx가 `$proxy_add_x_forwarded_for`로 클라이언트가 보낸 XFF 값을 그대로 앞에 이어 붙이고, Spring
`ForwardedHeaderFilter`가 그 목록의 첫 요소를 `getRemoteAddr()`로 채택했다).

**원인 재확인** 처음에는 "nginx가 `X-Forwarded-For`를 `$remote_addr`로 덮어쓰기만 하면 끝"이라고
판단했다. 그러나 `spring-web-6.2.11.jar`를 `javap -c`로 직접 확인한 결과, Spring
`ForwardedHeaderUtils#parseForwardedFor`는 **`Forwarded`(RFC 7239) 헤더를 `X-Forwarded-For`보다 먼저
읽고 매치되면 그 자리에서 반환**한다. 즉 XFF만 고치면 클라이언트가 `Forwarded: for=9.9.9.9`를 보내는
것만으로 그대로 우회된다. `ForwardedHeaderFilter`가 신뢰(파싱 후 제거)하는 헤더는 `Forwarded` ·
`X-Forwarded-For` · `X-Forwarded-Host` · `X-Forwarded-Port` · `X-Forwarded-Proto` · `X-Forwarded-Prefix` ·
`X-Forwarded-Ssl` **7종**이고, 기존 nginx 설정은 이 중 2개(XFF·Proto)만 관리하고 있었다.

**검토한 대안** ① 백엔드가 `X-Real-IP`를 IP 주체로 직접 채택한다(Spring 신뢰 목록 밖이라 컨트롤러가
직접 파싱해야 함). ② nginx가 프록시 경계에서 7종 헤더를 전부 서버가 정한 값으로 덮어쓰거나 비운다.

**선택** ②. `exec/nginx/j15b204.p.ssafy.io.conf`의 4개 프록시 지점(`/jenkins/`·`/grafana/`·`/api/`·`/`)
모두에서 `X-Forwarded-For`는 `$remote_addr`로, `Forwarded`·`X-Forwarded-Prefix`·`X-Forwarded-Ssl`은
빈 값(전달 안 함)으로, `X-Forwarded-Host`는 `$host`로, `X-Forwarded-Port`는 `$server_port`로 처리했다.
백엔드 `forward-headers-strategy: framework` 설정은 **그대로 뒀다** — https 판정(`request.isSecure()`)
등에 여전히 필요하고, nginx가 신뢰 헤더를 통제하게 됐으니 `getRemoteAddr()` 채택 방식 자체는 이제 옳다.

**근거** 앞단에 CDN·로드밸런서가 없고(단일 EC2 + 호스트 nginx, `docker-compose.yml`의 업스트림 포트가
전부 `127.0.0.1` 루프백 바인딩) nginx가 유일한 입구임을 확인했다 — 이 조건에서는 클라이언트가 보낸
전달 헤더가 100% 위조 가능한 값이므로 버려도 잃는 정보가 없다. 컨테이너 재현 검증에서 변경 전 설정은
위조 IP(`1.2.3.4`)가 실제로 `getRemoteAddr()`에 반영됐고, 변경 후에는 4개 프록시 전부 실제 피어 IP만
남았다.

**남은 한계** 앞으로 CDN·로드밸런서가 추가되면 이 "덮어쓰기" 방식은 진짜 클라이언트 IP를 지워 버린다 —
그때는 `real_ip` 모듈(`set_real_ip_from`)로 바꿔야 한다는 조건을 설정 파일 주석에 남겨 뒀다. 또한 이
결함은 로컬·테스트 환경(프록시 없음)에서는 재현되지 않아 **자동 테스트로 회귀를 못 잡는다** — 배포
시점에 사람이 위조 헤더로 직접 호출해 확인해야 한다(`infra_xff-hardening.md` §7-2). rate limit 자체가
여전히 단일 IP를 주체로 하므로 NAT 뒤 여러 사용자가 한도를 나눠 쓰는 문제는 이번 수정 범위 밖이다.

## 4. 동시성 결함 3건 — 결제 경로 경합·보상·순서

`backend/` 전용, 대상 문서 §0.8(멱등키)·§0.12(Redis 키)·§0.4(서명 tx 규약). `V1__init.sql` 수정 없음,
아직 **커밋하지 않았다.** `./gradlew clean build -PdockerApiVersion=1.44` — 359 tests, 0 failed(기존
348 + 신규 11). 이 절이 이 문서에서 가장 긴 이유는 세 결함 모두 "정답이 없고 트레이드오프를 골랐다"는
성격이기 때문이다.

### 4-1. 주문 생성 멱등 — check-then-act 경쟁 구간

**문제** 같은 `Idempotency-Key`로 동시에 두 요청이 들어오면 주문이 2건 생기고 재고가 2배 차감됐다.

**원인** `OrderService.createOrder`가 "조회(멱등 저장소 확인) → 재고 차감 → 주문 저장 → 기록"
순서였고, 그 "조회"와 "기록" 사이가 열린 채였다. `remember`가 `SET NX`가 아니라 그냥 `SET`이라 두
요청이 겹치면 **둘 다 조회에서 빈 값**을 받았다. `ticket_order`에는 멱등키 컬럼이 없어(ERD v5) DB
제약도 이 경쟁을 막지 못했다.

**검토한 대안**
- **DB UNIQUE 컬럼**(`ticket_order.idempotency_key`) — 창을 완전히 없애는 가장 확실한 방법이지만 ERD v5
  변경이 필요해 다른 V2 마이그레이션 후보 8건과 함께 묶여야 한다. **기각**(스키마를 늘리지 않는다는
  이번 작업의 전제와 어긋난다).
- **진행 중 요청을 대기시켜 첫 응답을 재생** — §0.9 rate limit·요청 타임아웃과 얽히고 스레드를 오래
  붙잡는다. **기각**.
- **처리 전 `SET NX`로 자리를 먼저 선점** — 조회와 기록 사이의 창을 원자적 선점으로 대체한다. **채택**.

**선택** `common/support/IdempotencyGuard` 신설 — `begin`(SET NX로 선점) → 실패 시 즉시 409, 성공 시
본 처리 → 실패하면 `release`(자리 반납) → **커밋 이후에만** `complete`(완료 값 기록). 값 형식은
`{요청해시}|{orderId}`(완료, TTL 24시간, §0.8 그대로) / `{요청해시}|-{선점토큰}`(진행 중, TTL 60초) 두
가지로 나눴다.

**근거**
- 선점 마커 **TTL 60초**: 정상 처리는 DB 트랜잭션 하나(Hikari `connection-timeout` 3초 포함)라 초 단위로
  끝나므로 60초는 정상 소요보다 충분히 길다. 동시에 결제 만료 15분보다는 짧아서, 서버 크래시로 마커가
  풀리지 않고 남는 최악의 경우에도 그 주문이 자연 만료되는 시점보다 훨씬 먼저 마커가 풀린다 — 사용자가
  같은 키로 하루 종일 갇히지 않는다(24시간 그대로 썼다면 크래시 한 번에 하루가 잠긴다).
- **완료 기록을 커밋 이후로 옮긴 이유**: 커밋 전에 적으면 아직 DB에 보이지 않는 `orderId`를 다른 요청이
  재생해서 받아 404가 난다.
- 진행 중 요청에 대한 응답은 **409 `COMMON_CONFLICT`**로 정했다 — §0.8은 "완료된 요청의 최초 응답 재생"만
  규정하고, 처리 중인 요청은 아직 응답이 없어 재생 자체가 불가능하다. 명세가 규정하지 않은 지점이라
  임의로 채우지 않고 가장 가까운 기존 코드(`COMMON_CONFLICT`)를 재사용했다.

**검증 방식** 고친 코드를 옛 `GET → SET` 방식으로 잠시 되돌려 동시 요청 테스트(`Executors.newFixedThreadPool(2)`로
실제 경합을 발생시킴)를 돌리자 **주문 2건 생성으로 실제로 실패**했고, 원복하니 통과했다. 이 결함이
되살아나면 테스트가 반드시 깨진다는 것을 실증했다(코드는 원복해 반영했다).

**남은 한계** 선점 마커가 60초 만에 풀리므로, 이론상 처리가 60초를 넘게 걸리는 극단적인 경우(DB 부하
폭주 등)에는 세 번째 요청이 통과할 여지가 있다 — 다만 정상 처리 시간(초 단위)과 60초 사이에는 충분한
여유가 있다고 판단했다. 완전한 해소(경쟁 창 자체를 없애는 것)는 V2에서 `ticket_order.idempotency_key
UNIQUE` 컬럼을 추가하는 것이다.

### 4-2. 재고 보상 — Redis가 DB 트랜잭션 밖이라는 사실을 인정

**문제** 주문 생성 중 Redis 재고를 먼저 차감한 뒤 DB 저장이 실패하면 재고가 빠진 채로 영영 남을 수
있었다. 만료 처리(`expireIfNeeded`)도 조회 시점에만 도는 lazy 방식이라, 아무도 그 주문을 다시 열어보지
않으면 재고가 돌아오지 않았다.

**원인** Redis 재고 차감(`ticketStock.reserve()`)과 DB 저장이 하나의 원자적 단위가 아니다. `release()`는
만료·취소 경로에서만 호출됐고, 그 경로 자체가 "누군가 조회할 때"에만 실행되는 구조였다.

**검토한 대안**
- **재고를 DB(`ticket_type.sold_quantity`)로 옮겨 트랜잭션 안에 넣기** — 원자성 문제는 사라지지만 예매
  피크 시점에 같은 행에 대한 잠금 경합이 응답 시간을 지배한다. Redis를 애초에 쓴 이유가 이 문제를 피하기
  위해서였다. **기각**.
- **Redis 트랜잭션 밖이라는 전제를 인정하고 이중으로 방어한다** — 즉시성(롤백 시 바로 되돌림)과
  포괄성(누구도 열지 않아도 결국 되돌아옴)을 각각 다른 장치로 담당시킨다. **채택**.

**선택**
1. **롤백 구독** — `TransactionSynchronizationManager` 기반의 `common/support/TxCallbacks.afterRollback`으로
   트랜잭션이 롤백되면 즉시 재고를 반납한다. 트랜잭션이 아예 없는 경로(동기 호출 실패)는 호출자가
   `catch` 블록에서 직접 보상하도록 했다 — 동기화 등록이 조용히 무시되어 보상이 사라지는 경로를 없앴다.
   두 경로가 겹쳐 재고가 두 번 반납되면 없던 표가 생기므로(초과 판매) `TxCallbacks.once`로 한 번만
   실행되게 감쌌다.
2. **만료 스윕 배치** — `ticket/service/OrderExpiryScheduler`(신규, `@Scheduled(fixedDelayString =
   "PT60S")`, 기존 `SettlementScheduler`의 관례를 그대로 따름)가 60초마다 만료된 `PENDING_PAYMENT` 주문을
   찾아 정리한다. 기존 lazy `expireIfNeeded`는 즉시성을 위해 그대로 남겼다 — 둘은 서로 보완 관계다.
3. **여러 인스턴스 중복 처리 차단** — `TicketOrderRepository.cancelIfPending`이 `UPDATE ... WHERE status =
   'PENDING_PAYMENT'` 조건부 전이로 만들어, 갱신 행 수 1을 받은 인스턴스만 재고를 반납한다. 별도
   분산 락(ShedLock 등)을 들이지 않았다 — 이 프로젝트가 단일 인스턴스 운영이라는 결정(`b204-stack`
   backend 편)과도 맞다. 같은 조건절이 "이미 `PAID`인 주문을 실수로 취소로 덮는 사고"도 함께 막는다.
4. 재고 반납도 **커밋 이후**에 실행한다 — 커밋 전에 반납했다가 그 트랜잭션이 롤백되면 팔 수 없는 표가
   팔린다. 이 변경으로 `PaymentService.startPayment`가 만료를 감지해 예외를 던지는 기존 경로에서
   "DB 취소는 롤백되는데 Redis 재고만 늘어나는" 별개의 초과 판매 구멍도 함께 닫혔다.

**근거** 재고 보상은 "확실하지만 느린 배치"와 "빠르지만 트랜잭션 경계에 의존하는 즉시 반응"을 함께 둬야
어느 한쪽의 빈틈(배치 주기 60초의 지연, 즉시 반응이 놓치는 예외적 실패 경로)을 서로 메운다.

**남은 한계** 커밋 직후 ~ Redis 반납 사이(위 4번 처리 구간)에 프로세스가 죽으면, 그 주문은 이미
`CANCELLED`로 커밋돼 있어 만료 배치가 다시 집어가지 못하고 **재고 몇 장이 영구히 잠긴다.** 반대 순서
(재고를 먼저 반납한 뒤 커밋)는 롤백 시 초과 판매를 만들기 때문에 택하지 않았다 — **"표가 잠긴다"와
"없는 표가 팔린다" 중 전자를 선택**한 것이 이 설계의 답이다. 완전한 해소는 재고 원장을 체인 또는 DB
트랜잭션 안으로 옮기는 별도의 설계 변경이 필요하다.

### 4-3. 늦게 온 receipt — 온체인 사실과 서비스 판정을 분리

**문제** `TicketOrder.markPaid()`에 상태 가드가 없어 무조건 `PAID`로 덮어썼다. 15분 만료로 이미
`CANCELLED`되고 재고까지 회수된 주문에 뒤늦게 결제 receipt가 도착하면(이벤트 인자는 전부 유효해
검증을 통과한다), `CANCELLED`가 `PAID`로 다시 덮이고 티켓이 발급됐다 — **초과 발급**이다.

**원인** 상태 검증이 이벤트 인자 검증에만 있고, "주문이 지금 결제를 받을 수 있는 상태인가"를 확인하는
단계가 없었다.

**검토한 대안**
- **무시(receipt를 버림)** — 사용자 돈은 이미 온체인에서 빠져나갔으므로 이 돈이 장부 어디에도 남지
  않는다. **기각**.
- **그냥 PAID로 처리** — 원래 결함 그대로다. 재고가 이미 회수돼 있어 초과 발급이 된다. **기각**.
- **만료 시간을 늘려서 이 창을 없앤다** — 체인 컨펌 지연에는 상한이 없어(네트워크 혼잡 등) 만료를 아무리
  늘려도 "그보다 더 늦게 오는 receipt"라는 같은 형태의 문제가 다시 생긴다. **기각**.
- **온체인 사실과 서비스 판정을 분리해서 각각 정직하게 기록한다** — **채택**.

**선택**
| 대상 | 처리 | 근거 |
|---|---|---|
| `chain_job` | `CONFIRMED` | 온체인 트랜잭션 자체는 실제로 성공했다 — 이 사실을 왜곡하지 않는다 |
| `payment` | `PAID` 기록 | 사용자 돈이 실제로 나갔으므로 장부에는 남겨야 한다 |
| 티켓 | **발급하지 않음** | 재고가 이미 회수돼 있어 발급하면 초과 판매가 된다 |
| 주문 | `CANCELLED` 유지 + 환불 대상 표시 | 상태를 되돌리지 않고, 대신 사람이 환불 처리를 할 수 있도록 흔적을 남긴다 |
| 잔액 캐시 | `-amount` | 온체인에서 실제로 빠져나간 사실을 캐시에도 반영한다 |

`TicketOrder.markPaid()`는 `PENDING_PAYMENT`에서만 전이하고 그 외에는 예외를 던지게 가드를 추가했다.
`Payment.markPaid()`도 `PAID`·`REFUNDED` 상태에서 재호출하면 예외를 던진다 — `REFUNDED → PAID`는 이미
돌려준 돈이 받은 돈으로 되살아나는 모순이고, `PAID → PAID`는 최초 결제의 tx 해시·`paid_at`을 나중
tx로 덮어써 기록을 잃는다.

**근거** 이벤트 인자 검증을 통과한 **뒤에** 주문 상태를 보도록 순서를 정했다 — 검증 전에 상태부터
가르면 위조된 트랜잭션도 "상태가 맞다"는 이유로 장부에 오를 수 있다.

**환불 대상 표시 방법과 그 한계** `refund` 테이블에 행을 만들 수 없다 — ERD v5에서 `refund.ticket_id`가
NOT NULL인데 이 경우 발급된 티켓이 없다(게다가 `refund` 도메인 자체가 아직 스켈레톤이다).
`payment.failure_code`에 적는 것도 검토했으나, 이 필드는 실패 코드 자리인데 `PAID`인 건에 적으면
의미가 뒤집힌다. 그래서 **`audit_log`에 한 줄**(`action_type=STATUS_CHANGE`, `resource_type='ticket_order'`,
`result=FAILURE`, `tx_hash`, 요약 문자열에 `refundRequired=true`)로 남기는 방법을 택했다 — 스키마를
늘리지 않는 선에서 운영자가 찾을 수 있는 유일한 자리였다.

**남은 한계** **이 목록을 뽑는 관리자 API가 없다.** `AuditLogRepository.findByResourceTypeAndResourceId`가
이미 있어 조회 API 자체는 붙이기만 하면 되지만, 지금은 운영자가 DB를 직접 열거나 에러 로그를 보는
방법으로만 이 상황을 발견할 수 있다.

**공통 검증** `PerformancePaymentFlowTest$Concurrency`의 통합 테스트가 "① 같은 멱등키 동시 요청 → 주문
1건·재고 정상", "② 트랜잭션 롤백 → 재고·멱등 자리 모두 원복", "③ 아무도 조회하지 않아도 만료 배치가
재고를 되돌리고 중복 반납하지 않음", "④ 취소된 주문에 결제 receipt가 늦게 와도 초과 발급하지 않음"
네 시나리오를 각각 실제 경합(스레드 2개, `Executors.newFixedThreadPool(2)` 또는 `CyclicBarrier`)으로
고정한다.

## 5. develop 쪽 결함 2건 (병합 중 발견)

이 두 건은 우리가 만든 결함이 아니라 **develop 브랜치에 이미 있던 결함**이며, 병합 작업 중 우리 테스트·
자산과 부딪혀 드러났다. develop 코드를 최소한으로 수정했다.

### 5-1. `chain_job.tx_type=LOCK`의 의미 충돌

**문제** API v6 §API-rule-04(판매 시작 = `startSale`)와 §API-settlement-03(정산 잠금 = `lock`)이 서로
다른 두 온체인 함수를 가리키면서 **둘 다 `LOCK`**이라는 같은 `tx_type` 값을 쓴다(ERD v5의 `tx_type`
ENUM 12종에 이 둘을 구분하는 별도 값이 없다). develop의 `ContractOperatorTxBuilder`는 `LOCK`을 무조건
`RevenueSplitter.lock(showId)`(정산 잠금)로 변환하고 있었다 — 우리 `RuleService`가 만드는 "판매 시작"
job이 이 빌더를 거치면 **의도와 다른 정산 잠금 트랜잭션이 온체인에 나갈 뻔했다.**

**원인** 하나의 ENUM 값이 두 가지 실제 동작을 가리키는데, 이를 구분할 다른 정보(멱등키 접두 등)를
빌더가 활용하지 않고 있었다.

**검토한 대안** ERD의 `tx_type` ENUM에 값을 추가하는 것(스키마 변경, V2 대상)과, 이미 존재하는 멱등키
접두 문자열로 구분하는 것.

**선택** 멱등키 접두로 갈랐다 — `startSale:`로 시작하면 `FUNC_STARTSALE`, 그 외는 `FUNC_LOCK`으로
분기. 6줄 + 주석 정도의 최소 수정이다.

**근거** 스키마 변경 없이, 이미 각 서비스가 만들어 두던 멱등키 문자열만으로 충분히 구분할 수 있었다.

**남은 한계** 근본적으로는 ERD `tx_type` ENUM에 판매 시작과 정산 잠금을 구분하는 별도 값을 추가하는
것이 맞다 — 지금은 멱등키 문자열이라는, 원래 다른 목적을 가진 값에 의미를 하나 더 얹은 상태다.

### 5-2. 워커의 `LocalDateTime.now()` — 배포 환경 TZ 의존

**문제** develop의 `ChainJobWorker`가 DB에 저장된 `requested_at`(KST 벽시계로 저장된 값)을 JVM 기본
시각대 기준의 "지금"과 비교하고 있었다. UTC로 뜨는 EC2에서는 **모든 job이 실제보다 9시간 늙어 보여
곧바로 `CHAIN_TX_TIMEOUT`으로 처리될 상황**이었다.

**원인** 우리가 이번 작업에서 만든 회귀 방지 테스트(`StorageTimeZoneTest`, §2)를 develop 코드에
적용해보니 이 문제가 그대로 걸렸다 — 우리 쪽에서 이미 정리한 것과 같은 패턴의 결함이 develop
코드(`ChainJobWorker`·`ExchangeRateService`·`SettlementConfirmationService`·`SettlementScheduler`·
`SettlementService`, 총 10곳)에 남아 있었다.

**검토한 대안** 없음 — 우리 쪽에서 이미 정한 해법(`TimeSupport.nowStored()`)을 그대로 적용하는 것 외에
다른 선택지를 검토할 이유가 없었다.

**선택** 10곳을 `TimeSupport.nowStored()`(= `LocalDateTime.now(Asia/Seoul)`)로 치환했다.
`SettlementTime.now()`는 `OffsetDateTime.now(KST)`로 바꿨다.

**근거** KST 머신에서는 치환 전후 동작이 같으므로 develop의 기존 테스트 202건이 그대로 통과한다 —
테스트를 지우거나 `@Disabled`로 덮지 않고 실제로 통과시켰다.

**남은 한계** 없음(이 결함 자체에 한정하면). 다만 근본 원인(JVM 기본 시각대에 의존하는 코드가 애초에
쓰이지 않도록 하는 장치, §2의 `StorageTimeZoneInitializer`)이 develop 쪽에는 아직 없다 — 이번에는
호출부 10곳만 고쳤고, develop 소유 코드 전반에 같은 패턴이 더 있을 가능성을 전수 조사하지는 않았다.
