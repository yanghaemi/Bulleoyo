# 03. 남은 과제 — 미완·팀 결정 대기

이 문서는 "아직 안 끝난 것"만 모았다. 완성된 것처럼 적지 않는다.

---

## 1. 결제 확정 경로가 배선되지 않았다 — 가장 중요한 미완

**"접수·검증은 구현, 확정은 배선 미완"**이 이 프로젝트 백엔드 0층의 정확한 현재 상태다.

- `ChainJobConfirmationService.confirm()`을 부르는 **프로덕션 코드가 없다.** develop의
  `ChainJobWorker`는 `ReceiptVerifier`로 §0.4 ④의 1~3(status·to·from)까지만 확인하고 `chain_job` 상태만
  전이시킨다. 결제 `PAID` 전이·티켓 발급·보증금 확정·규칙 동의 확정은 전부 `ChainJobConfirmationService`
  안에 있는데, **워커가 그 메서드를 아직 부르지 않는다.**
- 이유는 워커가 receipt의 이벤트 로그를 파싱하지 못하기 때문이다 — §0.4 ④⑤의 "기대 이벤트 존재 확인 ·
  인자 대조"에는 이벤트 로그의 topic0(이벤트 시그니처 해시)을 이벤트 이름으로 되짚는 파싱이 필요한데,
  이 파싱이 없어 워커가 `TxReceipt`(이벤트가 포함된 정규화 타입) 자체를 만들지 못한다.
- 테스트가 통과하는 것은 `ChainJobConfirmationService.confirm(chainJobId, TxReceipt)`를 **테스트 코드가
  직접 호출**해서다 — 검증 로직 자체는 실증됐지만, 실제 온체인 트랜잭션이 컨펌된 뒤 이 메서드가 자동으로
  불리는 경로는 없다.
- **실서버에서는 `chain_job`이 `PENDING`에 계속 머문다.** 사용자가 서명해서 트랜잭션을 보내도 결제가
  `PAID`로 넘어가지 않고 티켓도 발급되지 않는다.

**다음 수** ABI가 이미 고정돼 있으므로(`YoYo.Approval` · `RevenueSplitter.Purchased`·`DepositPaid`·
`RulesAgreed`·`SaleStarted`) 각 이벤트의 topic0을 넣고 로그를 `TxReceipt.TxEvent`로 정규화해
`confirm(jobId, receipt)`를 부르는 코드를 워커에 붙이면 된다. 이걸 붙이면 아래 §3의 `GrantRefUsed`
문제도 같은 자리에서 함께 풀린다.

## 2. `createShow`를 아무도 보내지 않는다 — 닭-달걀 문제

`ContractOperatorTxBuilder.SUPPORTED`에 `createShow`가 없고, `performance.on_chain_id`를 채우는 곳은
`confirmStartSale`(판매 시작 확정) 하나뿐이다. 그런데 계약 문서 §4에서 `deposit(showId)`(보증금 납부)는
`createShow` 이후여야 한다 — 지금 구성으로는 보증금 납부 시점에 온체인 컨트랙트가 그 공연을 모르는
상태라 `ShowNotFound`로 revert된다.

`createShow`에 필요한 인자(참여팀 `on_chain_index`·`wallet_address`·`teamShareBp`·`rulesHash`·
`depositAmount`)는 전부 DB에 있어 값을 만드는 것 자체는 문제가 아니다. **막힌 지점은 "이걸 어느
`chain_job.tx_type`으로 보낼 것인가"다** — ERD v5의 `tx_type` ENUM 12종에 자리가 없다. 이건 코드로
풀 수 있는 문제가 아니라 **명세 결정이 필요하다**.

## 3. `GrantRefUsed`가 계속 실패로 기록된다

§4.6은 "GrantRefUsed는 실패 처리 금지, 기존 MINT job을 CONFIRMED로 동기화"라고 정해 뒀고 그 진입점
(`ChainJobConfirmationService.syncGrantAlreadyUsed(jobId, txHash)`)도 이미 만들어 뒀다. 하지만 지금은
이 자리를 부르는 코드가 없어 `GrantRefUsed`가 여전히 `COMMON_CONFLICT#0xce43a105`로 실패 기록된다.
§1의 워커 브리지(topic0 파싱)를 붙이는 작업과 함께 처리하는 것이 맞아 이번에는 따로 하지 않았다.

## 4. `openapi.yaml` 대조를 하지 않았다

프론트 타입은 `docs/design/api/openapi.yaml`(develop `75525b7`에서 갱신됨)에서 생성되는데, 우리 QA 1·2차는
**md 명세(`06_API_명세서_v6.md`)만 보고 대조했다.** `openapi.yaml`을 한 번도 열어 필드 shape를 대조하지
않았다. MR 55(정산 관련)는 `openapi.yaml` 기준으로 맞춰져 있다고 알려져 있어, 우리가 구현한 26개
엔드포인트가 그 기준과 정확히 일치하는지는 **확인되지 않았다.**

## 5. 팀 결정 대기 목록

아래는 코드로 임의로 채우지 않고 (확인 필요)로 남긴 항목이다.

### 5-1. 전역 `non_null` 직렬화 vs 명세의 명시적 `null`
`application.yml`의 `spring.jackson.default-property-inclusion: non_null` 때문에 명세가 `null`을 값으로
보여주는 20여 개 필드가 실제 응답에서는 **필드 자체가 생략**된다(예: API-member-01 `wallet: null`,
API-ticket-02 `expiresAt: null`, API-payment-02의 여러 필드). 프론트 타입이 `T | null`로 정의되면 실제로는
`undefined`가 들어와 strict 모드에서 깨질 수 있다.

선택지는 둘이다 — ① 명세 §0.1에 "값이 null인 필드는 생략될 수 있다"를 추가하고 프론트 타입을 `field?: T`로
쓴다. ② 응답 DTO를 `@JsonInclude(ALWAYS)`로 바꿔 명세 예시대로 null을 실제로 내려보낸다(이 경우 `display`·
`rate` 생략 규칙은 필드 단위로 따로 유지해야 한다). **(확인 필요)**

### 5-2. V2 마이그레이션 후보 8건+
스키마 변경 없이 "받되 저장하지 않음" 또는 "코드로 파생"으로 우회해 둔 항목들이다. 결정되면 ERD v5의
다음 버전과 `V2__*.sql`이 필요하다.

| # | 항목 | 우회 방법(현재 동작) |
|---|---|---|
| 1 | `performance.endAt` | 요청으로 받아 검증에만 쓰고 저장하지 않음. 상세 조회 응답에서 필드 생략 — **가장 먼저 결정이 필요**(프론트 계약 구멍) |
| 2 | `team.contactEmail` | 받되 저장 안 함, 조회 시 항상 생략 |
| 3 | `wallet.walletLabel` | 요청 값을 비영속으로 그대로 되돌려 줌 |
| 4 | `entry_log`(검표 이력 테이블) | Redis(최근 500건·TTL 7일)로 대체 — 사후 분석용 영구 보관이 아니다 |
| 5 | `audit_log.action_type` ENUM 확장 | 로그인·로그아웃·프로필 변경·검표 링크 발급 등을 기존 `STATUS_CHANGE` 값으로 뭉뚱그려 기록 |
| 6 | `performance_participant.status` ENUM 3값(`INVITED`/`ACCEPTED`) | 현재 ENUM은 2값(`REGISTERED`/`REMOVED`) — `wallet_address` 유무로 파생 |
| 7 | `ticket_order.idempotency_key` UNIQUE | Redis 선점(`SET NX`)으로 대체(`02_결함과_수정.md` §4-1) — 완전한 창 제거는 아니다 |
| 8 | 늦은 receipt의 환불 대상 표시 | `ticket_order.refund_required` 같은 조회 가능한 필드 대신 `audit_log` 문자열로 남김(`02_결함과_수정.md` §4-3) |

### 5-3. §0.12 Redis 키 규약 보강
구현 과정에서 §0.12 표에 없는 Redis 키를 여러 개 신설했다(재고 `stock:performance:*`, 주문 멱등
`idem:order:*`, rate limit `rate:{scope}:{subject}:{분}`, 검표 링크 버전·이력·요약 `entry:*` 등). 서버
내부 값이라 프론트 계약은 아니지만, §0.12가 "테이블 없이 Redis에만 두는 상태를 모아 둔" 문서를 자처하는
이상 여기에 반영이 필요하다.

### 5-4. 비회원 `rate`(표시 환율) 기본 통화
비회원이 공연 목록·상세를 조회할 때 표시 통화 기본값(USD 등)을 명세가 정하지 않아, 지금은 비회원에게는
`rate` 필드 자체를 생략한다. **(확인 필요)**

### 5-5. revert 번역 책임 위치 — 이강륜과 합의 필요
`TxReceipt.failureCode` 필드는 만들어 뒀지만, 이 필드를 채우는 주체가 워커인지 확정 서비스인지는 아직
합의되지 않았다(`02_결함과_수정.md` §1-3). 필드를 아무도 채우지 않아도 기존 동작(전부
`PAYMENT_AMOUNT_MISMATCH`)과 같다는 것은 확인했으므로 합의가 늦어져도 빌드·배포는 막히지 않는다.

## 6. `TICKET_SOLD_OUT`·`TICKET_SALE_CLOSED`는 revert로 나올 수 없음이 확인됐다

develop 병합 시점에 계약 문서 §4.6의 revert 매핑표(44개)를 실제 컨트랙트 custom error 목록과 대조한 결과,
이 두 코드에 대응하는 온체인 custom error가 없다는 것이 확인됐다. 재고는 서버 Redis가, 판매 마감은 서버
`saleCloseAt`이 판정하기 때문에 애초에 컨트랙트가 이 두 상황을 별도 에러로 구분하지 않는다. 이 두 코드는
지금처럼 **서버 사전 검증 경로**(API-ticket-01·API-payment-01)에서만 나오고, 온체인에서 가장 가까운
것은 `SaleNotStarted → TICKET_SALE_NOT_STARTED`다. 없는 매핑을 지어내지 않고 사실만 기록해 뒀다 — 명세
§4.6에 이 사실을 한 줄 적을지는 문서 담당 판단으로 남긴다.

## 7. 사람이 해야 할 조치

### Jenkins Secret file `B204_ENV`
브라우저에서 Jenkins → Manage Jenkins → Credentials → `B204_ENV` → Update로 파일을 열어 아래 두 줄이
없으면 추가해야 한다(기존 줄은 그대로 둔다).

```
APP_BASE_URL=https://j15b204.p.ssafy.io
OPERATOR_ADDRESS=0xfbB324CC674dD2FF21Dff670404391e78F4a199f
```

- `OPERATOR_ADDRESS`는 **`B204_ENV`의 `OPERATOR_PRIVATE_KEY`에 대응하는 주소여야 한다.** 위 값은
  `origin/develop`의 `kairos.json roles.operator`다. 실제 운영 키가 다르면 그 키의 주소를 넣어야 하고,
  이 경우 컨트랙트 role도 재점검이 필요하다(주소가 `OPERATOR_ROLE`을 갖지 않으면 트랜잭션이 revert된다).
- `APP_BASE_URL`은 compose에 같은 기본값이 이미 들어 있어 없어도 동작은 하지만, 명시하는 편이 안전하다.
- 서버 `~/app/.env`는 손으로 고치지 않는다 — `develop`에 반영된 뒤 Jenkins `Deploy dev` 스테이지가
  `B204_ENV`로 다시 만든다.

### nginx 설정 반영
`exec/nginx/j15b204.p.ssafy.io.conf`의 프록시 헤더 하드닝은 저장소에만 반영돼 있고 **서버에는 아직
반영되지 않았다.** Jenkins가 컨테이너 안에서 돌아 호스트 nginx를 건드리지 못하므로 사람이 직접
`cp` → `nginx -t` → `systemctl reload nginx` 절차를 밟아야 한다(`infra_xff-hardening.md` §7-1).
반영 후 위조 헤더로 직접 호출해 확인하는 절차(§7-2)도 함께 필요하다 — 이 결함은 로컬 테스트로는
재현되지 않는다.

### 동시성 결함 수정 커밋
`02_결함과_수정.md` §4의 세 결함 수정은 아직 커밋되지 않은 상태로 워킹트리에 남아 있다. 리뷰 후 커밋이
필요하다.
