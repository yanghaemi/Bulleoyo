# 04. 멱등과 부분 실패 — 지금 무엇이 이중 지급을 막고 있나

이 문서는 결함 기록이 아니다. **이 시스템이 멱등과 부분 실패를 어떻게 다루는지 지도로 그린 것**이다.
`02_결함과_수정.md` §4(동시성 결함 3건, 2026-09-09)는 "무엇이 깨졌고 어떻게 고쳤나"를 다뤘고, 여기는
"지금 어떤 장치가 무엇을 막고 있나"를 다룬다. 겹치는 대목은 §4를 가리키기만 하고 다시 쓰지 않는다.

작성 기준일 2026-09-16, HEAD 기준(브랜치 `feat/fe/api-integration-2`).

---

## 가장 먼저 말할 것

**이중 지급을 실제로 막는 것은 서버의 멱등키가 아니라 컨트랙트의 `stage` 상태기계다.**

`RevenueSplitter.sol:830`이 `s.stage != Stage.SETTLEMENT_LOCKED`면 `InvalidStage`로 revert하고, 첫
release가 성공하면 `s.stage = RELEASED`(`:845`)·`s.escrow -= total`(`:846`)이 된다. 서버의
`chain_job.idempotency_key` UNIQUE와 `SettlementGates`는 **불필요한 tx가 나가지 않게 하는 1차 방어**이고,
둘 다 뚫리는 좁은 창이 있지만(§5) 그 창에서도 컨트랙트가 최종적으로 막는다.

## 1. 멱등 장치가 하나가 아니라 넷이다

"멱등키"를 하나의 개념으로 뭉뚱그리기 쉬운데, 이 코드베이스에는 성격이 다른 네 가지가 있다.

### 1-A. Redis `SET NX` 선점 — `common/support/IdempotencyGuard.java`

- 값 2종: 완료 `{요청본문 keccak256}|{결과id}` TTL **24h**(`:64`) / 진행 중 `{해시}|-{선점토큰}` TTL
  **60초**(`:67`)
- 키: `{prefix}{memberId}:{Idempotency-Key}`(`:182-185`) — **회원 범위**
- `begin()` 분기(`:112-154`): SETNX 성공 = 최초 / 해시 불일치 = **409**(`:139-142`) / 진행 중 마커 = 409
  (**명세 밖 자체 결정**, `:34-37`) / 완료 = 결과id 반환
- `complete()`는 **커밋 이후에만**(`:162-168`), `release()`는 Lua로 자기 토큰일 때만 삭제(`:75-77`)
- **남는 창(주석에 명시, `:54-56`)**: 커밋됐는데 `complete` 전에 프로세스가 죽으면 60초 뒤 같은 키가
  새 주문을 만든다
- 사용처 2곳: 주문 생성(`ticket/service/OrderService.java:122`, 본문 전체 해시), 결제 시작
  (`payment/service/PaymentService.java:112`, `"orderId=..."` 해시)

이 장치의 60초 TTL·경합 검증 방식은 `02_결함과_수정.md` §4-1과 같은 결정이다 — 거기서 다시 다루지 않는다.

### 1-B. `chain_job.idempotency_key` UNIQUE — `V1__init.sql:90`

온체인 작업 4경로가 이 방식이다: refund-02 · performance-12 · settlement-05 · coin-07.

- **settlement-05와 coin-07은 컨트롤러 파라미터가 없고 `RequestContextHolder`로 헤더를 직독한다**
  (`SettlementService.java:660-673`, `CoinGrantService.java:100-111`). 주석에 D-14·D-1로 기록돼 있다
- **check-then-act가 남아 있다** — `findByIdempotencyKey` → 없으면 `save`가 원자적이지 않아 동시 요청
  시 UNIQUE 위반 500: `SettlementJobEnqueuer.java:63-88` · `CoinGrantService.java:130-152` ·
  `UserSignedTxService.java:150-181`. 주문·결제는 §1-A의 SETNX로 이 구멍을 메웠지만 chain_job 경로는
  그대로다

### 1-C. 서명 RLP 자연 멱등 — `chain/service/UserSignedTxService.java`

- **헤더를 쓰지 않는다.** 키는 `"usertx:" + keccak256(rlp.trim().toLowerCase())`(`:296-300`) — tx hash가
  아니라 **RLP 문자열 해시**
- 재보고 시 디코드·대조를 통째로 건너뛰고 기존 job 반환(`:150-161`), 호출부는 `replayed`면 도메인 전이를
  하지 않는다(`RuleService.java:458-460`, `PaymentService.java:317-324`)
- 남의 RLP 차단: `sameTarget()`(`:244-254`)이 `txType`·`targetPerformanceId`·`targetTeamId`·`walletId`·
  `requester.memberId` 5키 비교, 다르면 409
- **남은 한계(코드로 확인됨)**: 결제용 APPROVE RLP를 보증금 `kind=APPROVE`로 보고하면 5키가 같아 구분
  불가. `02_결함과_수정.md` §1-2가 기록한 한계가 지금도 그대로다

## 2. 명세와 코드가 갈라진 곳

| 명세 §0.8 주장 | 코드 실태 |
|---|---|
| 필수 6개 | **일치** |
| 누락 → 400 | **일치**(6경로 모두 `COMMON_VALIDATION_FAILED`) |
| 키+요청해시 24h 저장 | order·payment만. chain_job 4경로는 **해시 미저장** |
| 최초 응답 그대로 재생 | 응답 본문 저장 없음. **id만 재생하고 응답은 재조립** |
| 같은 키 다른 본문 → 409 | order/payment는 완전 충족. 나머지 4경로는 **대상 필드만** 비교 |

"대상 필드만"이 구체적으로 무엇을 놓치는가:

- coin-07은 `(walletId, amount)`만 보고 **`memo`를 무시**한다(`CoinGrantService.java:244-248`)
- refund-02는 `ticketId`만 본다 — `reason`·`expectedRefundAmount` 무시
- performance-12는 **`reason` 무시**
- settlement-05는 **`note` 무시**
- chain_job 키는 회원 범위가 아니라 **전역**이다(§1-A의 order·payment 키와 대비된다)

## 3. 부분 실패 — 명세가 말하는 것이 코드에 없다

**이 절이 이 문서에서 두 번째로 중요하다.**

- **`results[]`는 미구현이다.** DTO 자리는 있지만(`chain/dto/ChainDtos.java:95-96`) 채우는 코드가 없고
  `chain/service/ChainJobService.java:110-111`이 `null`을 하드코딩하며 주석으로 "지어내지 않는다"라고
  적어 뒀다. `chain_job` DDL에 컬럼도 없다. 2026-09-16 실물 응답 확인에서도 `settlement_05`에 `results`
  키가 없었다.
- **release는 부분 실패할 수 없다.** `RevenueSplitter.sol:827-855`의 `release(showId)`는 팀 전원
  transfer를 도는 **단일 원자 tx**다. 한 건이 revert하면 전체가 revert되어 stage도 escrow도 그대로다
  (`:842-854`). 컨트랙트 주석 `:820-823`이 push 방식의 위험을 "감수한다"고 명시한다. 따라서 명세
  §11-05의 "팀별 부분 성공 + `retryable` 표시 + 자동 재시도"는 **개념 자체가 코드에 없다**.
- 서버도 전부-아니면-전무다: `SettlementConfirmationService.java:256-295`가 CONFIRMED면 전 share를
  `markReleased()`, FAILED면 `applyRelease`가 아예 호출되지 않는다. 테스트가 고정한다
  (`SettlementApiIntegrationTest.java:678-690`).
- job status는 `PENDING/SUBMITTED/CONFIRMED/FAILED` 4값뿐. `PARTIAL` 같은 값은 enum에도 DDL에도 없다.

### 진짜로 부분 실패하는 것은 공연 취소 일괄 환불이다

HALT 1건 + 주문별 REFUND **N건**의 독립 job(`RefundService.java:242-267`). 각 job이 따로 성공·실패한다.
결제 행이 없는 주문은 건너뛰고 나머지를 접수한다(`:254-260`).

**그런데 응답에는 HALT job의 jobId 하나만 나간다**(`PerformanceService.java:1056-1060`). refund job N건은
실리지 않아 **진행률을 볼 수단이 없다.**

### `retryable`은 아무 동작과도 연결돼 있지 않다

`ChainJobService.java:147-151`이 `signerType==OPERATOR && status==FAILED && retryCount<maxRetry` 셋으로
파생 계산할 뿐 저장 컬럼도 revert 사유 구분도 없다. 그리고 **재시도 API가 존재하지 않는다** —
`ChainController`는 조회 하나뿐(`:38-42`)이고 워커는 `PENDING`+`OPERATOR`만 집는다
(`ChainJobWorker.java:157-158`). 현재는 **표시값**이다.

### 워커 내부 재시도

`ChainJobStateWriter.java:69-85`. `>` 비교가 의도적(`:76-77`)이라 "최대 3회"는 최초 전송 + 재시도 3회 =
**총 4회 시도**. 상태 전이는 전부 `REQUIRES_NEW` 짧은 트랜잭션이고 이유가 `:19-21`에 있다("전송은
성공했는데 바깥 트랜잭션이 롤백돼 PENDING으로 남으면 같은 tx를 두 번 보낸다"). `GrantRefUsed` revert는
실패가 아니라 **CONFIRMED로 동기화**한다(`ChainJobWorker.java:357-389`).

## 4. FAILED 이후 재시도 — 경로마다 다르고, 하나는 교착이다

- **기본은 재실행 안 됨.** `findByIdempotencyKey`가 status를 보지 않아 FAILED job의 jobId를 그대로
  재생한다.
- **예외 2곳**만 `ChainJob.retireIdempotencyKey()`로 정본 키를 `{key}#failed:{id}`로 밀어내 재시도를
  허용한다(`ChainJob.java:209-216`): CREATE_SHOW(`ShowCreationService.java:147-149`), UPDATE_RULES
  계열(`RuleService.java:553-555`).
- **MINT에는 금지**된다 — `grantRef = keccak256(멱등키)`라 키를 바꾸면 이중 발행이 된다
  (`ChainJob.java:210-212`에서 예외를 던진다).

### ⚠ 자동 release 교착 — 운영 문제

자동 release의 키는 `release:auto:{settlementId}` **고정**이다(`SettlementService.java:449`). RELEASE에는
`retire`가 없으므로 **한 번 FAILED되면 스케줄러가 매 60초 같은 FAILED job을 재생하고 새 job을 영영 만들지
못한다**(`SettlementScheduler.java:82-113` + `SettlementService.java:458-468`). 수동 API로 새 UUID를 주면
새 job이 만들어져 빠져나올 수 있다. **사람이 개입해야 풀린다.**

## 5. 좁은 창 하나 — release 게이트가 공연 취소보다 약하다

`SettlementGates.release()`의 in-flight 검사는 **`PENDING`·`SUBMITTED`만** 본다
(`SettlementGates.java:341-343`).

→ RELEASE job이 **CONFIRMED인데 `applyConfirmedJobs()`가 아직 안 돌아 `settlement.status`가 여전히
LOCKED/DISPUTE_OPEN인 구간**(스케줄러 주기 2초, `SettlementScheduler.java:49`)에 **새 멱등키**로 release를
다시 요청하면 게이트를 통과해 두 번째 RELEASE job이 만들어진다.

- **돈은 나가지 않는다** — 두 번째 tx는 컨트랙트 `InvalidStage`로 revert(§0 참조). 남는 것은 FAILED job
  한 건이다.
- **공연 취소 쪽은 이 창을 이미 막았다** — 같은 창을 설명하는 주석이 `PerformanceService.java:1159-1165`
  에 있고 거기서는 **CONFIRMED까지 검사**한다(`:1173-1177`). release 게이트에는 그 보강이 없다. 대칭이
  깨져 있다는 것이 요점이다.

## 7. 프론트엔드 — 키를 누가 만들고 얼마나 들고 있나

- `newIdempotencyKey()`는 `frontend/src/shared/api/client.ts:177`(UUIDv4, 비보안 컨텍스트 폴백 포함).
  **클라이언트가 자동 생성하지 않는다** — 생성·보관 책임이 호출하는 feature에 있다.
- `IDEMPOTENCY_REQUIRED` 레지스트리(`client.ts:205-220`)가 6개를 못 박고, DEV에서 헤더가 빠지면 콘솔
  경고를 낸다.
- **키 수명이 세 갈래로 갈려 있다**
  - 마운트당 한 개: `PaymentPage.tsx:152`, `SettlementPage.tsx:116`
  - 본문 내용으로 키: `TeamChoicePage.tsx:174`(본문 JSON 서명 비교), `features/admin/CoinGrantForm.tsx:177`
    (`isSameGrant`)
  - 없음: `useCancelTicket`·`useCancelPerformance`는 **훅만 있고 호출부가 0건**이다. 티켓 취소·공연 취소
    화면이 아직 안 붙었다.
- **셋의 공통 약점**: 키가 컴포넌트 ref에 있어 **언마운트되면 사라진다.** 실패 후 페이지를 떠났다 돌아와
  같은 값을 다시 넣으면 새 키가 나간다. 코인 지급은 서버에 "같은 지갑 진행 중" 게이트가 없어 첫 job이
  PENDING인 중에 이러면 2회 발행이 가능하다(유일한 신호는 `coin_08`의 PENDING 행). release는 서버가
  진행 중 RELEASE를 `COMMON_CONFLICT`로 막아 해당 없다.

## 8. 두 메커니즘이 충돌한 실제 사례 (2026-09-16, 커밋 `5500b56`)

**서버의 멱등이 프론트의 가정을 깬 사례다.**

`useChainJob`은 리렌더·포커스 refetch로 같은 데이터가 다시 와도 콜백을 두 번 부르지 않으려고
`jobId:status` 표식을 뒀는데, 그 표식이 훅 수명 내내 남아 있었다.

그런데 서버는 멱등키를 지킨 재시도에 **같은 jobId를 재생한다** — FAILED job도 마찬가지다(§4). 즉
"release 실패 → 다시 시도"라는 **정상 경로**에서 훅이 이미 알린 것과 똑같은 `(jobId, status)`를 받고
표식에 걸려 `onFailed`를 부르지 않았다.

결과: 호출부의 약속이 매달리다 120초 뒤 상한 타이머가 `CHAIN_TX_TIMEOUT`으로 떨어뜨려 **실패가 "확정이
늦어지고 있습니다"로 둔갑**했다. 재시도할수록 진짜 이유를 늦게 알게 되는 화면이다.

새 감시가 시작될 때 표식을 버리는 것으로 고쳤다. 리렌더·포커스 refetch는 `jobId`·`enabled`를 바꾸지
않아 중복 방지는 그대로다. 화면 테스트는 이걸 못 잡아(재시도 jobId를 다른 값으로 목한다) 훅 테스트로
고정했다(`shared/queries/chainRetry.test.tsx`).

**교훈**: 서버가 멱등을 "같은 응답 재생"으로 구현하면, 클라이언트의 "같은 응답은 한 번만 처리" 최적화와
정면으로 부딪친다.

## 9. 남은 과제 — `03_남은_과제.md`에 이어지는 항목

1. `results[]` 미구현 — 명세가 약속한 것을 서버가 주지 않는다. **명세를 현실에 맞추거나(release는
   원자적이라 애초에 부분 성공이 없다) 공연 취소 일괄 환불의 진행률 표현을 따로 설계하거나** 둘 중
   하나여야 한다.
2. `retryable`이 표시값뿐 — 재시도 API가 없다. 화면이 "다시 시도"를 안내하는데 같은 키로는 같은 FAILED가
   돌아온다(M-03이 지금 이 상태다). **`chain_01`의 `retryable`이 클라이언트에게 무슨 뜻인지 명세가
