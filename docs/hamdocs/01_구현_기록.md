## 1. S15P21B204-46 — member · wallet · team

로그인(Web3Auth idToken 검증)부터 지갑 등록·팀 생성까지. 완료 기준은 "로그인 → 지갑 등록 → 팀 생성"
세로축 1편이 통합 테스트로 관통하는 것.

### 달성 여부
달성. `MemberWalletTeamFlowTest`가 세로축 1편 + 27개 경계 케이스로 고정한다. 73 tests, 0 failures.
JWKS 검증을 mock으로 우회하지 않고 `Web3AuthStubServer`(JDK `HttpServer`)가 실제 JWKS를 서빙해
`NimbusJwtDecoder.withJwkSetUri(...)` 경로를 실제로 태웠다. 외부 지갑 서명도 `TestWallet`이 secp256k1
개인키로 실제 서명한다.

### 구현한 엔드포인트 (도메인별)
- **인증** — `POST /auth/web3auth`(로그인) · `POST /auth/refresh`(회전 + 재사용 탈취 감지) · `POST /auth/logout`
- **회원** — `GET/PATCH /members/me`
- **지갑** — `GET /wallets/me` · `GET /wallets/me/transactions` · `POST /wallets/challenge` · `POST /wallets`(202,
  기본 지급 `MINT` job 생성)
- **팀** — `POST /teams` · `GET /teams/me` · `GET/PATCH /teams/{teamId}`

`API-member-02`(`/auth/login`)·`API-member-08`(`/auth/signup`)은 P1이라 스켈레톤(`COMMON_INTERNAL_ERROR`)
그대로 남겼다. 상세는 `_workspace/be_member-wallet-team_endpoints.md` §1·§3.

## 2. S15P21B204-47 — performance · rule · ticket · payment

### 범위·완료 기준
공연 생성부터 규칙 동의·판매 시작·주문·결제까지. 카드 지시 범위는 performance 01·05·02·03·07·08이었으나
**13·14(보증금)를 함께 구현**했다 — rule-01의 선행 조건이 보증금 `PAID`라 세로축이 그 앞에서 막히기 때문이다.

### 달성 여부
달성. `PerformancePaymentFlowTest`가 "공연 생성 → 초대·수락 → 티켓 옵션 → 보증금 → 규칙 설정 → 참여팀 동의
→ 판매 시작 → 주문 → 결제 → 티켓 발급"을 한 편으로 관통한다. 102 tests(73 → +29), 이후 `ContractCallsTest`
11건이 계약 문서 §8의 selector 4개·RLP 왕복 디코드·`rulesHash` 정규화를 고정했다.

체인 대납 서명(§0.4)의 핵심 3단계(멱등 → 디코드 → 대조)는 실증됐다 — 서명 RLP를 문자열로 지어내지 않고
`KaiaTxBuilder`가 Kaia `0x31` tx를 실제로 인코딩하고 서버가 디코드해 대조한다. 다만 **실제 대납 전송·receipt
폴링은 이 카드 범위 밖**이며, 체인 포트(`chain/port/*`)는 스텁이었다(develop 병합에서 실물로 교체 — §4).

### 구현한 엔드포인트 (도메인별)
- **performance** — 생성(01) · 목록(02, 비회원) · 상세(03, 비회원) · 티켓 옵션 전체 교체(05) · 참여팀 초대(07) ·
  수락(08) · 보증금 prepare(13)·signed-tx(14)
- **rule** — 설정(01) · 조회(02) · 동의 prepare(03)·signed-tx(05) · 판매 시작(04, OPERATOR 서명)
- **ticket** — 주문 생성(01, `Idempotency-Key` 필수) · 내 주문 목록(02)·상세(03) · 내 티켓 목록(04)·상세(05) ·
  동적 QR 발급(06, HMAC-SHA256 30초 윈도우)
- **payment** — 결제 시작(01) · 상태 조회(02) · signed-tx(03, `abandoned` 취소 경로 포함)

체인 포트 인터페이스(`FeeDelegatedTxPort`·`OperatorTxPort`·`TxReceipt`)를 정의하고 확정 진입점
`ChainJobConfirmationService.confirm()`을 만들어 체인 모듈 담당자(이강륜)와의 경계면으로 남겼다. 이 인터페이스는
develop 병합 이후 실물로 교체됐다(§4). 상세는 `_workspace/be_performance-rule-ticket-payment_endpoints.md`.

## 3. S15P21B204-48 — entry

### 범위·완료 기준
QR 검표(입장 처리)와 입장 현황 조회. 완료 기준은 같은 QR을 2회 스캔하면 거부되는 것 — 실제 Redis
컨테이너로 `SETNX` 원자성을 검증해야 유효하다(H2·임베디드 Redis면 거짓 통과한다).

### 달성 여부
달성. `PerformancePaymentFlowTest`의 세로축이 결제 완료 → 티켓 발급 → QR 생성 → 입장(200) → **재입장
거부(409)**까지 이어져 관통한다. 124 tests(102 → +22), 연속 2회 실행 모두 통과(시간 의존 테스트 흔들림 없음).

경로는 카드 지시(`POST /api/v1/entries`)와 명세(`POST /api/v1/entries/verify`)가 갈렸는데 **명세를 따랐다**
— `EndpointInventoryTest`의 엔드포인트 64개 인벤토리도 이미 그 경로로 고정돼 있었다.

QR 발급(-47)과 검증(-48)은 같은 클래스 `ticket/support/QrTokens`의 같은 `issue(...)`를 써서 서명 규약이
바뀌면 두 경로가 함께 바뀌도록 했다. 검사 순서는 **서명 먼저, 윈도우 나중**이다 — 그렇지 않으면 위조 토큰이
전부 "만료"로 읽힌다.

### 구현한 엔드포인트 (도메인별)
- **entry** — 검표(`POST /entries/verify`, 검표 토큰 또는 참여팀 회원) · 입장 현황(`GET
  /performances/{id}/entries`)
- **performance** — 검표 링크 발급(10, PERFORMER, `rotate`로 버전 회전) — 범위 밖처럼 보이지만 API-entry-01·02
  검증의 유일한 발급처라 함께 구현했다

상세는 `_workspace/be_entry_endpoints.md`.

## 4. develop 병합 (2026-09-09)

대상: `feat/be/init` ← `origin/develop`(`bb1f76b`). 커밋 `ae929fa`·`13583da`.

### 실물 체인 모듈 도입 — 우리 스텁 포트를 걷어냈다
`chain/port/*`와 `chain/port/stub/*`는 실물이 오기 전의 임시 경계였다. develop에 실물 체인 모듈
(`web3j-ext`)이 들어와 그 자리를 대신할 수 있게 되자, 같은 일을 하는 이름이 둘 남는 것을 피하려고
**삭제하고 호출부를 실물에 직접 붙였다.**

| 지운 것 | 대체 |
|---|---|
| `FeeDelegatedTxPort` + 스텁 | `chain/service/FeeDelegationService` |
| `SenderSignedTx` | `FeeDelegationService.DecodedUserTx`(`recoveredFrom`·서명 검증 포함 — 스텁의 한계였던 ecrecover 부재가 해소됨) |
| `OperatorTxPort` + 스텁 | `chain_job` + `ChainJobWorker`/`ContractOperatorTxBuilder`(지갑 큐) |
| `chain/support/Rlp`(손으로 쓴 디코더) | web3j-ext `TxTypeFeeDelegatedSmartContractExecution.decodeFromRawTransaction` |
| `KrwsBalanceReader`(항상 empty) | `YoYoBalanceReader` → `CoinChainReader`(실물 `eth_call`) |

남긴 seam은 `TxReceipt` 하나(패키지만 `chain/port`→`chain/service`로 이동). `ChainJobConfirmationService`의
입력 타입이고, develop의 워커가 아직 이 자리를 부르지 않기 때문에 남겨 뒀다(§03 참조).

테스트 쪽에서는 `KaiaTxBuilder`가 손으로 `[v,r,s]`에 임의값을 넣던 것을 **web3j-ext
`KaiaTransactionEncoder.signMessage`로 진짜 서명**하도록 바꿨다.

### 코인 개명 KRWS → YoYo
develop 관례(`831927a`)를 그대로 따랐다. 클래스 `YoYo`, 프로퍼티 `yoyo-address`(env
`CONTRACT_YOYO_ADDRESS`), 티커 문자열 `"YoYo"`. **사용자에게 보이는 통화 표기 `₩`/`KRW`는 그대로다**
— 통화는 KRW이고 KRWS가 아니었으므로 개명 대상이 아니다. 클래스 rename(`KrwsBalanceReader` →
`YoYoBalanceReader`) + main 9파일·test 3파일·문서 갱신.

의도적으로 개명하지 않은 곳 — `V1__init.sql`(Flyway 체크섬), `FlywayMigrationTest`의
`cached_krws_balance`(ERD v4에서 삭제된 컬럼 이름, 역사적 사실), `Jenkinsfile`의 `contracts.KRWS.address`
폴백과 `VITE_CONTRACT_KRWS_ADDRESS`(infra가 개명 과도기용으로 일부러 둘 다 둠).

### 병합 중 발견한 develop 쪽 결함 2건
merge 자체가 아니라 develop 코드에 원래 있던 결함이며, 병합 중 우리 테스트/자산과 부딪혀 발견했다.
상세 원인·수정은 `02_결함과_수정.md` §4에 정리했다 — 여기서는 존재만 기록한다.

1. `chain_job.tx_type=LOCK`이 "판매 시작"과 "정산 잠금" 두 가지 뜻으로 함께 쓰여 잘못된 트랜잭션이
   나갈 뻔했다.
2. `ChainJobWorker` 등 develop 코드의 `LocalDateTime.now()` 10곳이 UTC 서버에서 job을 9시간 늙어 보이게
   만들어 즉시 타임아웃 처리됐다.
